# Aiao Pool 未来功能需求与目录规划

整理日期：2026-11-05。依据[立项方案](plans/p2p-product-proposal.md)的形态路线（§7）、商业化假设（§8）与版本规划（§4）整理；技术底座维持根 requirements 的 epic-011 / epic-012 不动。本页描述方向，不是排期承诺；进入实施前各自以新 story 立项（编号段见 [CONVENTIONS](CONVENTIONS.md#文档类型与编号段)）。

## 产品目标

在浏览器版（M1 MVP）之上，逐步补齐桌面常驻形态、跨网兜底与企业分发渠道，并在 M3 验证免费/Team 商业化。保持产品本质不变：**云盘式资产视图 × P2P 零存储传输**——直传的速度与隐私 + 云盘的账号与持久性。

| 方向                | 用户价值                                 | 后续交付范围                                                                               |
| ------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------------ |
| 桌面端（v2）        | 托盘常驻、真后台，大文件与断外网体验完整 | Electron 先行、Tauri 补位；1 GiB、断外网传输、离线 TTL、局域网发现增强                     |
| 跨网中继（预留）    | 办公网组播屏蔽或跨网团队也能连           | TURN/STUN 中继（D-07：出现真实跨网需求再立项）                                             |
| Chrome 扩展（增量） | 不开页面也能对已共享文件持续做种与接收   | Offscreen Document 嵌自己域名 iframe；企业策略强制安装（D-08：v2 后定）                    |
| 商业化（M3）        | 团队治理、配额与保障可付费               | 免费/Team 双档、支付、邀请扩容；付费点挂在管理与配额上，不押首年收入                       |
| 协作纵深（立项池）  | 团队在同一数据资产上协作                 | epic-012：整库克隆、实时信号、远程 DevTools、局域网枢纽（价值待证，以 rxdb:US-708 为前置） |

## 形态路线（可行性已查证）

| 形态            | 常驻能力         | 覆盖          | 角色                                               |
| --------------- | ---------------- | ------------- | -------------------------------------------------- |
| 浏览器页面      | 开页面才在线     | 全平台免安装  | MVP 形态                                           |
| Electron 桌面端 | 托盘常驻、真后台 | Win/mac       | v2 先行：与浏览器同内核，阶段 B 验收口径已定义     |
| Tauri 桌面端    | 托盘常驻、真后台 | Win/mac/Linux | 长期常驻形态；轻量常驻成本低，1 GiB 目标的正确归宿 |
| Chrome 扩展     | 浏览器开着才在线 | Chrome/Edge   | 轻量伴侣 / B2B 分发渠道                            |

Tauri 侧只需把 TCP 服务放进 Rust 进程（plugin/command），协议层不用改（US-708 双进程 TLS 夹具已验收）；代价是 Rust 工具链、双 WebView 差异与独立 CI lane。Chrome 扩展经 Offscreen Document（Chrome 109+）嵌自己域名的 iframe 跑现有前端核心，文件与页面同源 OPFS、零迁移；保活靠 SW 信令心跳 + `chrome.alarms` 自愈重建，偶现秒级~30 秒级离线窗口由断点续传接续。

## 商业化假设（M3 前再议）

- **模式假设**：免费个人档（设备数上限、回退单次 ≤100MB）+ Team 席位订阅（管理后台、回退配额与更大单文件、保留期、优先支持）。
- **定价锚点**（第三方口径已标注）：文叔叔 VIP ~¥450/年、Send Anywhere ~$6–10/月、Tailscale $8/用户/月、WeTransfer Starter €8/月、奶牛快传 Pro ¥99–799/年 → 建议 Team 档 ¥30/席位/月（约 $5）起步，beta 期间验证转化率后再定。
- **收入假设**：该品类无 P2P 订阅先例，首年不设收入硬指标，目标是把「团队愿意为回退 + 治理付费」验证掉（M3 复盘，定 D-03/D-04）。
- **前车之鉴**：Send Anywhere 订阅变现不顺、Snapdrop 社区无法货币化——付费点必须挂在「管理、配额、保障」上，而不是「传输」本身。
- **成本结构（护城河）**：P2P 直传边际成本≈0（信令 DO + Supabase 免费档）；成本只发生在回退（R2 存储，Cloudflare egress 免费）。云中转竞品的成本随用量线性涨，我们的不涨。

## 风险与对策（立项方案 §10 摘录）

1. **滥用（Firefox Send 死因）**：恶意软件/钓鱼分发可以直接杀死产品 → M1 管理后台必选（rxdb:US-713）、速率限制与举报（POOL-US-102）；账号体系本身就是门槛。
2. **LAN 连不上**（组播屏蔽的办公网）：A 定位下是可接受边界 → 桌面端局域网发现 + rxdb:US-712 枢纽兜底；团队出现跨网需求再议 TURN（D-07）。
3. **变现无先例**：低成本渐进（直传零成本撑免费档）、付费点挂在管理与配额上、不押首年收入。
4. **国内不可达**：workers.dev / supabase.co 大陆直连不通 → D-06 已定：首期只做海外与有代理能力的团队。
5. **可持续性**：边际成本结构 + 邀请制控量，先算清单次回退成本再放量。
