# 用户故事：多级审批与可配置合并规则

## 作为/我想要/以便

**作为** 需要严格变更治理的团队管理员
**我想要** 配置多级、按角色或按规则触发的审批流程
**以便** 高风险数据变更在合并前得到足够的独立确认。

## 范围边界

### In Scope

- 支持多个审批阶段、并行或顺序审批，以及每阶段所需角色和人数。
- 审批策略可以按团队、目标分支或业务规则配置，并在 PR 中显示当前进度。
- 新提交、目标分支变化或规则变化使受影响的批准重新校验。
- 合并服务端根据当前策略原子判断，不接受前端拼出的“已批准”结果。

### Out of Scope

- 首版单级批准/免审批规则之外的自动风险评分、外部签名和跨团队审批。
- 复杂工作流编排器和任意脚本化审批条件。

## 验收标准

| # | 前置条件 | 操作 | 预期结果 | 状态 |
| --- | --- | --- | --- | --- |
| 1 | 团队配置两个顺序审批阶段 | PR 通过第一阶段后查看状态 | 显示第一阶段已完成、第二阶段待处理；未完成第二阶段不能合并 | ⬜ |
| 2 | 团队配置并行审批和人数阈值 | 多名审核者提交结果 | 按当前角色和人数计算进度；达到阈值后才通过对应阶段 | ⬜ |
| 3 | PR 追加新提交或目标分支变化 | 查看审批状态 | 只使受影响版本的批准失效；保留历史并明确需要重审的阶段 | ⬜ |
| 4 | 管理员修改审批策略 | 查看已有和新建 PR | 服务端记录策略版本；合并时按当前适用规则重新验证，不允许客户端沿用过期策略 | ⬜ |
| 5 | 用户只有部分阶段审核权 | 查看或操作 PR | 只能操作授权阶段，不能伪造其他阶段完成；跨端显示同一审批进度 | ⬜ |
| 6 | 任何阶段未满足或检查失败 | 尝试合并 | 服务端拒绝并返回具体阶段或检查原因，业务数据和 PR 状态不变 | ⬜ |

验收证据：后续实现时补充顺序/并行审批、策略版本、版本失效和服务端合并负例用例。

## 技术笔记

审批策略应版本化并绑定团队/目标分支。审批记录需要保存阶段、角色、版本、操作者和结果；合并事务重新读取策略和当前 PR 版本。该故事是首版基础审批故事的后续，不改变 [ADMIN-US-209](ADMIN-US-209-review-approval.md) 的单级规则承诺。
