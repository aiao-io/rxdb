# VS Code 插件兼容与 CodeMirror 接入分析

> 分析日期：2026-11-07。
> 范围：aiao-vscode 兼容 VS Code 插件的可选路线，重点分析保留 CodeMirror 的可行性。
> 状态：研究建议，待目标插件清单与原型验证；不代表新增故事已立项、确定排期或兼容性已验收。

## 结论

**✅ 值得验证。可以保留 CodeMirror，但需要插件宿主、`vscode` API 兼容层和工作台适配。**

Monaco 不是插件兼容的硬性前提。插件通过 `vscode` API 访问文档、编辑器与工作区，理论上可以把这些调用转换为 CodeMirror 和现有工作台的操作。
实际成本在于实现 API 的行为语义、插件生命周期与工作台服务，而不是解析或安装一个 VSIX 文件。

建议先选少量目标插件做完整功能验证，再决定是否扩展兼容范围。
如果需求主要是补全、跳转、诊断、重命名，则优先评估语言服务或 LSP；语言能力接入与运行原有 VS Code 插件是两个不同目标。

本轮整理了方案与本地接入点，没有完成插件宿主选型、CodeMirror 兼容原型或真实插件运行验收。
不能据此承诺任意 VSIX、全部 Web 插件或桌面插件可用。

## 第一阶段：双编辑器接入

本阶段按用户确认的范围接入 Monaco，同时保留 CodeMirror，在设置中切换；插件兼容分析继续作为后续研究。
默认选择 CodeMirror，旧配置自动补齐该默认值，明确无效的编辑器配置仍报错。

- 选择在当前浏览器内持久化，刷新和重开项目继续沿用。
- 两种编辑器使用统一的挂载接口，共用工作台的编辑缓冲、保存、格式化、诊断与快捷命令。
- 切换迁移文本、选区与滚动位置，释放旧实例；撤销历史在切换后重新开始。
- Monaco 的脚本、样式、字体与 Worker 由现有资产构建流程生成并自托管，所需资源就绪后再挂载。
- 异步加载期间的文本更新继续进入最新缓冲；切换或关闭后忽略已过期的加载结果。
- Vue 文件暂使用 HTML 语法展示，完整 Vue 语言服务和插件宿主仍需后续评估。

实现入口为 [编辑器接口](../src/workbench/editor.ts)、[切换生命周期](../src/workbench/editor-switcher.ts)、
[Monaco 资源加载](../src/workbench/monaco-loader.ts)、[Monaco 适配](../src/workbench/monaco-editor.ts) 与
[设置及持久化](../src/workbench/workbench-state.ts)。使用方式见[应用说明](../README.md#编辑器选择)。
验收覆盖设置恢复、切换时保留草稿、加载取消，以及真实浏览器输入、格式化撤销、保存、刷新与 Worker 资源。

## 保留 CodeMirror 的适配设计

以下是拟议职责划分，尚未实现：

```text
VS Code 插件
     ↕
插件宿主 + vscode API 兼容层
     ↕
aiao 工作台适配层
     ├─ CodeMirror：文本、选区、编辑、补全、诊断
     ├─ 项目会话 / OPFS：文件、保存、变更事件
     └─ Angular / Dockview：命令、通知、面板
```

### 文档与编辑器

| VS Code 契约                           | 拟议接入点                               | 必须验证的语义                                                   |
| -------------------------------------- | ---------------------------------------- | ---------------------------------------------------------------- |
| `TextDocument`、文档打开/修改/关闭事件 | 项目会话与 CodeMirror 文档状态           | 项目级稳定 URI、语言标识、文档版本、增量变更与事件顺序           |
| `TextEditor`、选区与编辑操作           | CodeMirror state、selection、transaction | 行列与 UTF-16 偏移转换、多选区、编辑来源、撤销与重做             |
| `WorkspaceEdit`                        | 项目会话与编辑器事务                     | 跨文件操作、未打开文件、并发编辑、失败处理，以及编辑与保存的边界 |
| 补全、悬浮提示、定义跳转等 provider    | CodeMirror 对应扩展或界面                | 请求取消、异步结果过期、跨文件定位与结果释放                     |
| `DiagnosticCollection`                 | CodeMirror 诊断与问题面板                | 文件与范围映射、严重性、来源、替换与清除                         |

插件修改文档后，应进入现有编辑缓冲并触发正常的变更通知；保存仍通过项目会话完成。
`workspace.fs` 面向工作区文件系统，打开文档则可能存在未保存内容，适配时必须保留二者的区别。
双向事件需要识别操作来源，避免插件与编辑器互相回传同一次修改。

### 工作区与界面

按目标插件实际调用的能力逐项实现：

- `workspace.fs` 与文件变更事件：映射项目文件操作，覆盖读写、重命名、删除、切换项目和关闭时的订阅释放。
- `commands`：命令注册、调用、注销与错误传播接入现有命令系统。
- 配置与插件状态：明确全局、工作区、项目之间的作用域和持久化位置。
- 通知、Quick Pick、输出与状态栏：接入现有界面，并验证取消与释放行为。
- Tree View、Webview 等复杂界面：在有明确目标插件需求后单独评估，不能默认视为兼容。

不支持的调用应明确报错或在已验证的能力清单中标为不支持，避免用空实现伪装兼容。

## 运行环境与分发边界

**浏览器插件宿主。** Web 插件通常提供 `browser` 入口，在 Web Worker 环境运行；只有 `main` 入口的插件不能直接放入浏览器宿主。
声明式主题、语法和代码片段无需同等的可执行插件宿主能力，但仍需适配各自的贡献点；VS Code 的主题或 TextMate 语法不能默认直接用于 CodeMirror。

**Node 插件宿主。** 依赖 Node API、本地可执行程序或原生模块的插件，需要额外运行环境与相应能力。
当前 WebContainer 的终端能力不能替代插件加载、激活、API、通信、文档与界面桥接。
是否利用它运行部分 Node 插件，必须另做验证；不能外推为支持全部桌面插件或原生二进制。

**插件来源。** 微软 Marketplace 对第三方产品的访问有限制，插件本身也可能限制运行宿主或分发方式。
候选来源为 Open VSX、作者允许分发的 VSIX，以及允许自行构建的源码；仍需逐个核对来源与授权。

**安装管理。** 原型先预装已核对的插件，再评估 VSIX 安装、版本约束、启停、卸载、离线资源与状态持久化。
解析 VSIX 和成功激活只是验证环节，不能替代功能验收。

## LSP 与插件兼容的区别

CodeMirror 有官方 `@codemirror/lsp-client`，可评估用于接入语言服务器。
语言服务器还需要选择浏览器 Worker、本地或远端等运行方式，并与工作区及编辑缓冲保持同步。

| 目标                      | 建议优先验证                                    | 不应推导的结论                                      |
| ------------------------- | ----------------------------------------------- | --------------------------------------------------- |
| 补全、跳转、诊断、重命名  | 项目级语言服务或 LSP + CodeMirror               | 支持某语言服务，不等于运行该语言的整个 VS Code 插件 |
| 运行指定 VS Code Web 插件 | 浏览器插件宿主 + 该插件所需 API 和贡献点        | 一个插件通过，不等于所有 Web 插件通过               |
| 运行依赖 Node 的插件      | 真实 Node 宿主或另行验证的运行后端 + 工作台桥接 | 浏览器里能执行 Node 命令，不等于具备完整桌面兼容性  |

## 建议的原型与验收

先确定目标插件的名称、版本、来源、运行入口和必需功能，列出其 API 与运行环境依赖。
原型同时固定宿主与兼容 API 版本，结果记录为逐插件的功能矩阵。

建议依次验证：

1. 一个可审查的最小 Web 插件，完成「激活 → 注册命令 → 读取当前文档 → 修改文本 → 撤销/重做 → 保存 → 关闭释放」。
2. 一个真实目标插件，验证其核心功能、所需 API 和工作台贡献点。
3. 通过后再评估主题、语言插件、面板等新增范围，以及安装与持久化管理。

关键验收场景：

- 中文、emoji、CRLF、多选区及多次连续编辑的位置与事件保持一致。
- 异步请求返回前用户继续输入、切换文件或关闭项目时，过期结果不会错误写入。
- 插件编辑未保存文档后，草稿恢复、显式保存和 Git 暂存继续遵守现有边界。
- 跨文件编辑、重命名与删除遇到冲突或失败时，按确定的 API 契约处理，不误报成功。
- 禁用插件、切换项目、关闭工作台后，命令、订阅、Worker 与界面资源正确释放。
- 不支持的 API 或运行环境依赖给出可定位的失败信息；安装成功不计为功能通过。

实施阶段按红—绿—重构推进，并运行变更对应的工作台与浏览器验证。
在原型完成前，不给通用兼容率、交付周期或任意插件支持作承诺。
