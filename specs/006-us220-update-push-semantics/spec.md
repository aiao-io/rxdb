## User Scenarios & Testing _(mandatory)_

### User Story 1 — 只改部分列的修改能推上去 (Priority: P1)

用 Supabase 作远端的应用开发者，让最终用户在本地只改一条记录的某几列（典型是勾选 Todo 的「已完成」）。这次修改推送到远端时，
远端只改这几列，其余列保持原值；推送成功，水位线推进，另一台设备拉取后看到同样的结果。不会因为没带上的必填列让整批推送失败、
进而卡住整个仓库的同步。

**Why this priority**: 参考 schema 与参考 demo 上「勾选一条 todo」就能触发推送失败（故事症状 1），是最常见的修改形态；不修这条，
同步在最基本的场景下不可用。

**Independent Test**: 在不开 RLS 的参考 schema 上，远端先有一条 todo；推送一条只含「已完成」的修改，检查远端该列已变、标题未变，
日志多出一条修改记录；再用两个客户端经推送路径重复一遍，第二个客户端拉取后看到同样的结果。

**Acceptance Scenarios**:

1. **Given** 参考 schema，远端已有一条 todo，**When** 推送只含「已完成」（及更新时间、更新人）的修改，**Then** 推送成功；
   「已完成」已更新，标题等未下发的列不变；日志写入一条修改记录（AC#1）。
2. **Given** 两个客户端连同一个真实远端，**When** 客户端 A 只改一条 todo 的「已完成」并经常规推送路径推送、客户端 B 拉取，
   **Then** A 推送成功、水位线推进；B 看到「已完成」已变、标题不变（AC#6）。
3. **Given** 参考 demo 连本地远端，**When** 新建一条 Todo 并推送、再勾选完成并推送、另一浏览器上下文拉取，**Then** 两次推送都成功，
   另一上下文看到该 Todo 已完成（AC#7）。

### User Story 2 — 启用行级权限的表上，有权修改的行都能改 (Priority: P1)

远端业务表启用了行级权限（RLS）。只要调用方按「修改」与「读取」的权限规则有权改这一行，推送就成功：改自己拥有的行时，不因载荷里
没带归属列而被误拒；在「谁都能改、只有自己能建」的共享编辑表上改别人的行时，不因「新建」规则更窄而被误拒。归属列保持原值。

**Why this priority**: 按归属判定权限是 RLS 最常见的写法，共享编辑也是常见形态；今天这两类表上的正常修改一律被误报为权限拒绝
（故事症状 2、3），而且误报会被 US-218 阶段 B 当成真实拒绝暴露给最终用户。

**Independent Test**: 分别建两张表：一张「全部操作都限本人」，一张「读与改不设限、新建限本人」；以普通登录用户的身份推送不含归属列
的修改，前者改自己的行、后者改他人的行，两者都成功且归属列不变。

**Acceptance Scenarios**:

1. **Given** 业务表策略「全部操作仅本人可见可写」，目标行属于调用方，**When** 推送不含归属列的修改，**Then** 成功，归属列不变（AC#2）。
2. **Given** 业务表策略「读不设限、新建仅本人、改不设限」，目标行属于他人，**When** 推送不含归属列的修改，**Then** 成功，归属列不变；
   「新建」规则不参与修改的判定（AC#3）。

### User Story 3 — 改不了的修改被明确报错，并说清是「被拒」还是「行已不存在」 (Priority: P2)

一条修改在远端没能生效时，推送必须失败并给出可区分的原因：目标行存在但调用方无权修改或无权读取，报权限拒绝；目标行在远端已经
不存在，报另一种错误，且远端不会凭空插入一条只有部分列的残缺行。两种情况都不写日志，都不静默当成功。

**Why this priority**: 普通修改语句被权限过滤或找不到行时都是「静默零行」，若不加判定，修改会悄悄丢失、日志与数据对不上；
「行已不存在」今天还会复活残缺行（故事症状 4）。两种原因分开，是 US-218 阶段 B 区分「被拒」与「已删」并做本地对齐的前提。
它排在 P2，是因为 P1 修好后正常修改不再失败，本故事只覆盖少数真正改不了的修改。

**Independent Test**: 在一张表上让目标行存在但对调用方不可改（或不可读），推送修改，断言报权限拒绝、行未变、无新日志；
再对一条远端不存在的 id 推送修改，断言报另一种错误码、表里没有新行、无新日志。

**Acceptance Scenarios**:

1. **Given** 目标行存在，但「修改」或「读取」的权限规则不放行，**When** 推送修改，**Then** 报权限拒绝（42501）；行未变；无新日志；
   不得因普通修改语句的静默零行退化为成功（AC#4）。
2. **Given** 目标行在远端已不存在（对任何角色都不存在），**When** 推送修改，**Then** 报错，错误码与权限拒绝不同；不插入任何行；
   无新日志（AC#5）。

### User Story 4 — 既有安全回归持续通过 (Priority: P3)

维护者手工对运行中的远端容器执行 SQL 安全回归，既有用例与本故事新增用例全部通过，PR 描述贴实跑输出。

**Why this priority**: 回归是本故事所有 SQL 行为的落地证据，但它不单独给最终用户带来价值，依赖 US1～3 的行为先就位。

**Independent Test**: 对运行中的本地远端容器执行 SQL 安全回归脚本，逐条看结果。

**Acceptance Scenarios**:

1. **Given** 既有 SQL 回归 9 条加本故事新增用例，**When** 执行 SQL 安全回归脚本，**Then** 全部 PASS；属于 US-218 的
   `rls-filtered-delete` 用例状态不因本故事变化（AC#8）。

### Edge Cases

- 同一批推送里既有新建又有修改：新建仍走现有「整行插入、冲突则更新」的语义，修改走普通修改语义；两者在同一事务里，任一条失败整批回滚。
- 同一实体的多条本地修改在推送前被合并为一条：合并后的列集合仍是部分列，按 US1 的规则落库。
- 本地「新建后又修改」被合并为一条新建：载荷是整行，走新建语义，不受本故事影响。
- 修改的载荷除主键与审计列外不含任何业务列（例如只有更新时间、更新人）：照常按修改落库，目标行存在且有权时成功。
- 一条修改把可空列显式改成空值：空值属于载荷里出现的列，必须写进去，不能与「没下发的列」混淆。
- 目标行对调用方不可读但实际存在：属于「被拒」（AC#4），不得报成「行已不存在」。
- 同一批里一条修改「行已不存在」、另一条正常：整批回滚，报「行已不存在」的错误码；客户端下一轮原样重发（US-218 阶段 B 之前，**推断**）。
- 新客户端连旧版远端 SQL，或旧客户端连新版远端 SQL：行为由 plan 选定的兼容策略决定（见 FR-011），不得出现「推送成功但修改丢失」。

## Requirements _(mandatory)_

### Functional Requirements

**修改的落库语义**

- **FR-001**: 推送路径上的本地修改 MUST 在远端按普通修改语义落库：只改载荷里出现的列，未出现的列保持原值。
- **FR-002**: 修改 MUST 只受目标表「修改」与「读取」的权限规则约束；「新建」的权限规则与非空约束对未下发的列 MUST NOT 参与判定。
- **FR-003**: 推送路径上的本地新建 MUST 保持现有语义（整行插入、主键冲突则更新），不因本故事改变。
- **FR-004**: 修改成功时，远端日志 MUST 为该实体写入一条修改记录，与现状一致。
- **FR-005**: 修改的下发 MUST 与新建分开，使远端能按 FR-001 与 FR-003 分别落库；下发形状由 plan 决定。

**零行生效的判定**

- **FR-006**: 修改在调用方权限下零行生效、且目标行实际存在时，推送 MUST 以权限拒绝（42501）失败；行不变，不写日志。
- **FR-007**: 修改的目标行在远端已不存在时，推送 MUST 以一个与 42501 不同的错误码失败；不插入任何行，不写日志。
  该错误码的取值由 plan 决定，并与 US-218 阶段 B 的错误分类一致。
- **FR-008**: 「行是否存在」的判定 MUST 不受调用方权限规则的影响（否则「被拒」与「已不存在」无法区分），且 MUST NOT 向调用方泄露
  除「存在 / 不存在」以外的行内容。
- **FR-009**: 「行是否存在」的判定原语 MUST 与 US-218 阶段 A 共用同一个，机制、签名与错误码在两份 plan 里一次冻结，不得各写一份。
- **FR-010**: 任何情况下，修改 MUST NOT 静默零行成功，也 MUST NOT 跳过而不报错。

**版本配合**

- **FR-011**: 若修改的下发形状改变了远端 SQL 的入参，plan MUST 二选一并写明：新版远端 SQL 兼容旧客户端的载荷；或在迁移文档写明
  「先升级远端 SQL，再升级客户端」。无论选哪种，新旧组合 MUST NOT 出现「推送成功但修改丢失」。

**测试与文档**

- **FR-012**: 每条 AC MUST 有对应的自动化或脚本化验证：AC#1～5 为 SQL 回归用例，AC#6 为连真实远端、经常规推送路径的 spec，
  AC#7 为 demo e2e 用例，AC#8 为回归脚本整体通过。
- **FR-013**: 既有单元测试中对推送载荷形状的断言 MUST 随下发形状同步更新，不得删除断言。
- **FR-014**: 适配器 README 与站点上的 Supabase 适配器文档 MUST 同步远端 SQL 入参与修改语义的说明。
- **FR-015**: 本故事 MUST NOT 改动任何公共 TypeScript API；三框架绑定无需改动。

### Key Entities

- **本地修改（UPDATE 变更）**: 一条本地变更，携带实体 id 与「变更过的列的新值」，不含未变更的列，也不含归属列；同一实体的多条
  修改在推送前合并，结果仍是部分列。
- **推送批次**: 一次推送的新建、修改、删除与对应的日志条目，在远端一个事务里落库，任一条失败整批回滚。
- **远端日志（main 分支变更记录）**: 远端为每次成功的业务写入记录的一条变更，按（schema、表、实体 id）与业务写入配对；
  其完整性规则由 US-218 AC#6 定义。
- **存在性判定原语**: 绕开调用方权限、只回答「这一行在远端是否存在」的判定；US-220 与 US-218 阶段 A 共用。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 在参考 schema 与参考 demo 上，「勾选一条 todo」的推送成功率从 0% 变为 100%；勾选后未下发的列与推送前逐列一致（差异 0 列）。
- **SC-002**: 故事症状 2、3 的两种权限形态上，调用方有权修改的行，推送误报权限拒绝的次数为 0。
- **SC-003**: 无权修改或无权读取的行，100% 以权限拒绝失败；目标行已不存在的修改，100% 以另一种错误码失败；两种情况下新增日志 0 条、
  新增行 0 条。
- **SC-004**: 「静默零行成功」与「复活残缺行」在全部新增用例里出现 0 次。
- **SC-005**: SQL 安全回归脚本的既有 9 条与新增用例全部 PASS；AC#6 的两客户端 spec 与 AC#7 的 demo e2e 用例通过。
- **SC-006**: 在本地远端上，单条修改的推送落库耗时 < 100 ms（宪法默认的数据库操作预算）；存在性判定只在零行生效时执行，
  成功路径不多一次查询（**推断**为可达，plan 阶段核实）。
- **SC-007**: 公共 TypeScript API 变化为 0；三框架绑定代码变化为 0。

## Assumptions

- 本地修改的变更只含变更过的列、不含归属列，这一契约（变更接口注释、两种本地存储的更新触发器、推送前的合并逻辑）不变；本故事
  只改远端落库与载荷下发方式。
- 「用远端当前行补齐载荷再走新建语义」已实验否定（修不了共享编辑表），不再作为候选。
- 存在性判定原语的候选机制为「绕开调用方权限的存在性探针」或「按该实体在 main 分支的最新日志判定」，由本故事与 US-218 的 plan 共同冻结；
  本 spec 只约束其外部行为（FR-008、FR-009）。
- 「行已不存在」在 US-218 阶段 B 之前仍会让该仓库的推送卡住（**推断**）；它的自动处理（回执、本地对齐移除）属于 US-218 阶段 B，
  不在本故事范围。今天同一场景在非空约束表上是 23502、在可空表上是静默复活残缺行，本故事把后者变成显式错误。
- 远端行已删、本地仍在修改这类并发冲突的解决策略、`SupabaseRepository.update` 的直写路径、新建路径的语义，均不在范围内（故事 Out of Scope）。
- 仓库没有参考 SQL 的版本校验（服务端版本函数返回的是数据库版本），所以 FR-011 的兼容策略只能靠载荷兼容或迁移文档保证。
- SQL 安全回归不在 CI 里，需手工对运行中的容器执行，PR 描述贴实跑输出；连真实远端的 spec 与 demo e2e 依赖本地远端容器。
- 开工条件：本故事与 US-218（阶段 A～C）的 plan 全部完成后才进入开发；合入时本故事先于 US-218 阶段 B（roadmap 约束 16）。
