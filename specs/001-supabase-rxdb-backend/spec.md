# Feature Specification: Supabase-first 后台与 RxDB 同步架构

**Feature Branch**: `013-supabase-rxdb-backend`

**Created**: 2026-11-15

**Status**: Draft

**Input**: User description: "开始实施 Supabase-first 后台架构：普通业务表和 RPC 直连 Supabase；Auth Admin API、封禁用户和 service role 操作经过 Edge Function；后台服务使用 RxDB 同步；后台配置使用 rxdb-model 显示和编辑；配置通过 RxDB 分支与提交逻辑同步；研究并验证 Supabase PGMQ 队列。"

## User Scenarios & Testing

### User Story 1 - Admin 统一登录并安全管理平台用户 (Priority: P1)

管理员使用平台账号进入后台，普通业务数据直接读取和修改；涉及 Auth 用户列表、封禁、解禁或平台级权限的动作由受保护的后台操作完成。

**Why this priority**: 这是减少 Cloudflare 代理层并保护平台特权的基础。没有清晰的身份和权限边界，后续直连 Supabase、后台同步和配置编辑都不能安全实施。

**Independent Test**: 使用管理员、普通用户和匿名会话分别执行普通业务查询、管理员 RPC、用户列表、封禁和解禁操作，确认普通路径可用，特权路径拒绝越权，浏览器始终没有平台特权密钥。

**Acceptance Scenarios**:

1. **Given** Admin 使用有效平台账号，**When** 登录、刷新和退出，**Then** 会话可以恢复和失效，且账号密码不经过 Cloudflare 业务代理。
2. **Given** 管理员已登录，**When** 查询或修改授权范围内的模板、策略、任务、用量或积分业务数据，**Then** 操作成功并遵守用户和工作区权限。
3. **Given** 普通用户、匿名用户或已撤权管理员，**When** 请求 Auth 用户列表、封禁或解禁，**Then** 请求被拒绝且没有发生特权写入。
4. **Given** 有效管理员重复提交同一管理操作，**When** 使用相同操作标识重试，**Then** 业务结果和审计记录只生效一次。

### User Story 2 - 后台服务同步共享业务数据 (Priority: P1)

后台服务在本地保存共享业务实体，并通过同步保持与 Supabase、Admin 和其他客户端的数据一致；服务重启或网络暂时中断后可以继续工作。

**Why this priority**: 后台服务必须和前端使用同一套数据模型和同步语义，否则配置和任务会形成第二套状态系统，无法可靠处理离线、重启和冲突。

**Independent Test**: 启动两个独立 RxDB 节点，分别从前端和后台修改同一组业务实体，制造断网、重启和并发冲突，确认已确认的变更不丢失、不重复应用，权限错误可以被观察和恢复。

**Acceptance Scenarios**:

1. **Given** 后台服务使用有效的普通平台身份，**When** 启动并连接远端，**Then** 可以加载授权范围内的数据并恢复同步游标。
2. **Given** 前端提交一项业务变更，**When** 后台服务同步，**Then** 后台本地数据收到相同内容、版本和删除状态。
3. **Given** 后台修改允许写入的业务实体，**When** 网络恢复并同步，**Then** 其他客户端可以收到变更，重复重试不会重复应用。
4. **Given** 后台服务在同步中退出，**When** 服务重新启动，**Then** 未确认变更继续同步，已确认变更不会重复执行。
5. **Given** 后台需要平台级权限，**When** 执行 Auth Admin 或封禁操作，**Then** 通过受保护的后台操作完成，普通同步身份不会获得平台特权。

### User Story 3 - 管理员用模型驱动界面编辑配置 (Priority: P2)

管理员在后台使用统一的列表、详情、表单和查询组件查看、编辑和校验模板、策略、平台模型及工作区配置。

**Why this priority**: 统一模型可以消除 Admin 手写状态机，减少显示、编辑、校验、撤销和同步之间的行为差异。

**Independent Test**: 在后台完成一次配置查询、编辑、校验、保存、撤销和刷新恢复，确认页面状态来自本地实体模型，并能显示同步和冲突结果。

**Acceptance Scenarios**:

1. **Given** 配置实体已经注册，**When** 管理员打开列表、详情或编辑页，**Then** 页面显示本地已同步数据并支持筛选和分页。
2. **Given** 管理员修改合法字段，**When** 保存，**Then** 本地变更立即可见并进入待同步或待提交状态。
3. **Given** 浏览器暂时断网，**When** 管理员查看或编辑已有配置，**Then** 已有数据仍可用，网络恢复后变更继续同步。
4. **Given** 字段无效或 revision 已过期，**When** 管理员提交，**Then** 页面显示明确错误或冲突，不能静默覆盖其他人的变更。

### User Story 4 - 配置分支和提交可被后台应用 (Priority: P2)

管理员可以在配置分支上编辑和提交变更，后台服务收到完整提交后校验父提交、内容指纹和版本，再原子应用、发布或拒绝。

**Why this priority**: 配置变更需要可追踪、可审计、可回滚；仅同步当前配置值无法解释谁改了什么，也无法安全发布一组相关改动。

**Independent Test**: 在一个分支上修改多个配置实体并提交，模拟投影延迟、重复推送、后台重启、父提交缺失和版本冲突，确认后台只应用完整且可验证的提交。

**Acceptance Scenarios**:

1. **Given** 管理员在配置分支上修改实体，**When** 创建提交，**Then** 系统生成提交身份、父提交、操作者、内容指纹和有序变更记录。
2. **Given** 提交投影部分写入或处理进程崩溃，**When** 系统重启，**Then** 能发现并补齐缺失投影，不把未完成提交标记为已应用。
3. **Given** 后台收到完整且可验证的提交，**When** 执行应用，**Then** 配置、审计和提交状态在同一业务操作中一致更新。
4. **Given** 同一提交或操作被重复推送，**When** 后台再次应用，**Then** 不重复修改配置、不重复写审计、不重复发布。

### User Story 5 - 评估 PGMQ 作为任务调度层 (Priority: P3)

平台任务运营者可以运行一个可回退的 PGMQ PoC，验证任务入队、消费、重复投递、长任务、结果取回和消费者故障恢复，再决定是否迁移生产任务链路。

**Why this priority**: PGMQ 可能降低多消费者、积压和重试场景的调度成本，但当前 Durable Object 已经承担任务状态和刷新续接，必须用故障数据而不是直觉决定是否切换。

**Independent Test**: 在隔离环境中运行 PGMQ consumer，覆盖数据库事务入队、provider 成功后 ack 前崩溃、visibility timeout、消费者重启、结果清理和双区域部署，并输出与 Durable Object 的对比结论。

**Acceptance Scenarios**:

1. **Given** 用户有有效账号和积分，**When** 创建生成任务，**Then** 任务、积分预留和队列消息一致写入或全部回滚。
2. **Given** 消费者在 provider 成功后删除消息前崩溃，**When** 消息重新可见，**Then** 结果和积分不会重复结算。
3. **Given** provider 超时或返回永久错误，**When** 消费者执行重试，**Then** 任务按策略重试或归档，并保留可观察失败原因。
4. **Given** PoC 全部故障场景完成，**When** 评审结果，**Then** 明确记录迁移或保留 Durable Object 的决定，生产链路不会因 PoC 失败而中断。

### Edge Cases

- Admin 会话过期、账号被封禁或管理员 membership 被撤销时，普通查询、普通写入和特权操作分别返回可区分的授权错误。
- 同步节点使用错误工作区或过期远端身份时，必须暂停危险写入并保留本地数据。
- 同一配置同时被两个分支修改时，必须保留冲突双方；未经解决的提交不能发布。
- commit projection 先于业务实体或业务实体先于 projection 到达时，后台必须等待完整 envelope，不得部分应用。
- PGMQ 消息重复可见、消费者被杀、provider 无幂等键、结果 Storage 写入成功但任务状态更新失败时，必须通过任务状态和 CAS 收敛。
- 网络恢复后重复 Realtime 通知或重复同步批次不能造成重复实体、不一致 revision 或重复审计。

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 允许 Web 和 Admin 使用同一平台账号完成登录、刷新、退出和会话恢复。
- **FR-002**: 系统 MUST 允许管理员直接查询和修改授权范围内的普通业务数据，并执行工作区和用户权限检查。
- **FR-003**: 系统 MUST 从已验证的当前会话确定操作者身份，不得把浏览器提交的用户 ID、actor 或角色字段当作可信身份。
- **FR-004**: 系统 MUST 将 Auth 用户列表、封禁、解禁、Auth Admin API 和绕过普通权限的操作限制在受保护的后台操作中。
- **FR-005**: 系统 MUST 确保浏览器和普通同步节点不能读取或使用平台级 secret/service role 凭据。
- **FR-006**: 系统 MUST 记录管理员和后台服务的可审计写操作，并使用操作标识防止重复执行。
- **FR-007**: 系统 MUST 允许后台服务以普通平台身份同步授权范围内的业务实体、删除状态、版本和分支元数据。
- **FR-008**: 系统 MUST 在网络中断、进程重启、远端重复通知和同步重试后保留未确认变更，并避免重复应用已确认变更。
- **FR-009**: 系统 MUST 对并发修改提供可观察的版本冲突结果，不得静默覆盖另一方的已确认修改。
- **FR-010**: 系统 MUST 使用统一的领域实体元数据支持后台配置列表、详情、表单、筛选、校验和编辑。
- **FR-011**: 系统 MUST 让配置编辑进入本地工作树，并允许管理员查看未提交、已提交、同步、冲突、应用和发布状态。
- **FR-012**: 系统 MUST 为配置提交保存分支、父提交、操作者、操作标识、内容指纹和有序变更记录。
- **FR-013**: 系统 MUST 在后台应用配置提交前验证提交完整性、父提交、内容指纹、权限和当前版本。
- **FR-014**: 系统 MUST 以幂等方式应用同一配置提交，配置、审计和提交状态不能因为重试产生重复副作用。
- **FR-015**: 系统 MUST 提供 PGMQ PoC，验证事务入队、重复投递、可见性窗口、重试、长任务、结果保留、消费者重启和双区域运行。
- **FR-016**: 系统 MUST 在 PGMQ PoC 未通过时保留当前 Durable Object 任务实现和回退路径。
- **FR-017**: 系统 MUST 不把完整 RxDB 内部系统表直接当作普通业务同步契约；需要完整提交图时，必须单独定义兼容协议。

### Key Entities

- **Admin Session**: 当前管理员的会话、账号状态和授权范围。
- **Business Entity**: 模板、provider policy、平台模型、工作区配置、任务和用量等可同步业务对象。
- **Sync Checkpoint**: 每个同步节点的远端身份、游标、分支和最后确认状态。
- **Config Branch**: 配置编辑的分支、父分支和当前工作树上下文。
- **Config Commit**: 一组配置变更的不可变身份、父提交、操作者、指纹和生命周期状态。
- **Config Commit Change**: 提交内按顺序排列的实体操作、patch、inverse patch 和版本信息。
- **Generation Task**: 生成请求、积分预留、执行状态、结果引用、重试信息和幂等身份。
- **Queue Message**: 指向 Generation Task 的最小调度消息，不包含凭据、session、原图或大结果。
- **Audit Event**: 管理员、后台服务和配置应用产生的不可变审计记录。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 100% 的 Auth 用户列表、封禁、解禁和平台级特权操作无法通过浏览器直接执行，且生产浏览器构建物中不存在 secret/service role 凭据。
- **SC-002**: 管理员在有效权限下完成普通配置查询和保存的成功率达到 99%，授权失败能够在 1 秒内显示明确错误。
- **SC-003**: 在至少 100 次断网、进程重启和重复同步演练中，已确认业务变更零丢失、零重复应用，冲突全部可观察。
- **SC-004**: 在至少 50 次提交投影延迟、重复推送和后台重启演练中，未完成提交零次被标记为已应用，同一提交零次重复写入配置或审计。
- **SC-005**: 后台配置管理员能够在单次工作流中完成查询、编辑、校验、提交和查看应用结果，关键状态无需刷新页面才能显示。
- **SC-006**: PGMQ PoC 覆盖事务回滚、重复投递、provider 成功后崩溃、超时重试、结果清理、消费者重启和双区域共 100% 的预定故障场景，并输出明确的迁移决策。
- **SC-007**: PGMQ PoC 失败或中止时，当前 Durable Object 任务服务仍能继续处理已有任务，用户可继续刷新、取回和确认结果。

## Assumptions

- 现有 Supabase Auth、业务表、RLS、Storage、RxDB Supabase adapter、sync plugin 和 working-tree 能力继续作为迁移基础。
- Web 图片 Storage 直连已经完成，不在本次实施中重新设计上传协议。
- Admin 当前 Angular 产品优先接入 `rxdb-model-angular`；公共实体模型仍需保持 React/Vue 可复用。
- 后台服务使用专用普通平台身份或普通 JWT；平台级特权统一调用受保护的后台操作。
- 配置提交的第一版本采用领域级 projection，不直接同步 RxDB 内部 `Commit` 和 `CommitChangeSet` 系统实体。
- PGMQ 只先做隔离 PoC；在 PoC 通过并完成迁移评审前，Durable Object 仍是生产任务实现。
- 用户要求继续沿用现有积分、任务状态、结果 Storage、审计和双区域数据隔离约束。
- 本次实施优先完成 P1 基础能力，再按依赖进入 P2 配置工作流和 P3 PGMQ 评估。
