**Feature Branch**: `003-us031-sortable-tree-entities`

**Created**: 2026-10-08

**Status**: Draft

## User Scenarios & Testing _(mandatory)_

### User Story 1 — demo 有了可排序的树实体，旧树实体原样不动 (Priority: P1)

使用 `@aiao/rxdb-test` 的开发者能拿到四个可排序的树实体：菜单两种（全量加载、库算「是否有子节点」）、文件两种（同上），
列、索引与计算属性和对应的旧实体一致，只多了「按父节点分组的手动排序」与「排序键必填」。旧的 `MenuSimple` / `MenuLarge` /
`FileNode` / `FileLarge` 一个字节都不变，依赖它们的适配器测试、远端测试表与桌面宿主照常工作。

**Why this priority**: 其余故事都建立在新实体之上；旧实体被六个 SQLite runner 的共享套件、PGlite / supabase 测试与远端表共用，
改它们会让测试整批失败（故事「新建可排序树实体，不改现有四个」）。

**Independent Test**: 只交付实体本身即可验证：元数据初始化通过，新库里四张新表的排序键列必填；不给排序方式查询时按「父节点、
排序键、主键」升序返回，根节点在前；旧实体的全部现有测试不改即通过。

**Acceptance Scenarios**:

1. **Given** 四个可排序树实体，**When** 元数据初始化并在新库建表，**Then** 校验通过，排序键列建成必填（AC#1）。
2. **Given** 新实体在多个父节点下各有若干节点、根节点若干，**When** 不给排序方式查询，**Then** 按父节点、排序键、主键升序返回，
   根节点（无父节点）一组排在最前（AC#1）。
3. **Given** 旧的四个树实体，**When** 运行它们的现有测试（含六个 SQLite runner 共用的菜单套件、PGlite 与 supabase 树测试），
   **Then** 不改即通过；旧实体的表结构、默认查询顺序与写入行为不变（AC#1）。

### User Story 2 — 新建节点永远追加到同父末尾 (Priority: P1)

在三端 demo 的树菜单与文件管理器（全量、虚拟滚动、懒加载各一页）里新建根节点或子节点，新节点出现在同一父节点下所有兄弟之后，
刷新页面后仍在原处。文件管理器的根级文件与文件夹属于同一组：先建文件夹、再建文件、再建文件夹，第二个文件夹排在文件之后，
不会与文件抢同一个位置。在一个尚未展开、子节点还没加载的父节点下新建子节点，同样追加到它既有子节点的末尾。

**Why this priority**: 「新建根文件夹与根级文件撞键」已复现（故事缺陷一）；新建是树页面最基本的写入，三端都要能放心用。

**Independent Test**: 在任一端的文件管理器根级依次新建文件夹 A、文件 X、文件夹 B，刷新页面，顺序为 A、X、B；在菜单懒加载页
折叠一个已有子节点的节点，在它下面新建子节点，展开后新节点在最后。

**Acceptance Scenarios**:

1. **Given** 三端菜单与文件管理器六页改用新实体，**When** 新建根节点与子节点并刷新页面，**Then** 新节点在同父末尾，刷新后顺序不变（AC#2）。
2. **Given** 文件管理器根级为空，**When** 依次新建文件夹 A、文件 X、文件夹 B 并刷新，**Then** 顺序为 A、X、B，三者的排序键互不相同（AC#2）。
3. **Given** 懒加载页某节点已有子节点且处于折叠、子节点未加载，**When** 在它下面新建子节点后展开，**Then** 新节点在既有子节点之后（AC#2）。
4. **Given** 同一操作，**When** 分别在 Angular、React、Vue 上执行，**Then** 三端结果一致（AC#2）。

---

### User Story 3 — 删除并提升子节点后，顺序确定且一次完成 (Priority: P1)

删除一个有子节点的菜单项并选择「提升子节点」时，它的子节点改挂到它的父节点下，按原来的先后排在该父节点原有子节点之后；
「子节点改挂」与「删除该节点」要么一起成功、要么一起不发生。三端行为相同。

**Why this priority**: 「删除提升后撞键」已复现（故事缺陷二）；React / Vue 现在逐条保存子节点再删父节点，中途失败会留下部分子节点
已搬走的状态，与 Angular 的一次提交不一致。

**Independent Test**: 祖父 G 下有 P、Q，P 下有 c1、c2；删除 P 并提升子节点，刷新后 G 下顺序为 Q、c1、c2。

**Acceptance Scenarios**:

1. **Given** G 下有 P、Q，P 下有 c1、c2，**When** 删除 P 并提升子节点、刷新页面，**Then** G 下依次是 Q、c1、c2，P 已删除（AC#4）。
2. **Given** 被删节点是根节点，**When** 删除并提升子节点，**Then** 子节点成为根节点，排在原有根节点之后（AC#4）。
3. **Given** 提交过程中失败（例如被删节点已被别处删掉），**When** 执行删除提升，**Then** 子节点与被删节点都保持原状，界面展示错误（AC#4）。
4. **Given** 同一操作，**When** 分别在三端执行，**Then** 三端结果一致，且都是一次提交（AC#4）。

### User Story 4 — 批量添加从同父真实末尾之后追加 (Priority: P2)

在树菜单与文件管理器里批量添加（100～10,000 条）时，新节点按生成顺序排在各自父节点原有子节点之后，与原有节点不交错、互不同键。
文件管理器根级已有排在最后一个文件之后的文件夹时，新批次的根节点排在那个文件夹之后。

**Why this priority**: React 懒加载文件管理器以「文件夹优先」排序后的末位作锚点，会与排在后面的文件夹撞键（故事源码实证、未运行）；
批量添加是 demo 造数据的主要入口，但不是最终用户的日常操作，所以排在 P2。

**Independent Test**: 在文件管理器根级依次建文件 X、文件夹 F，批量添加 100 条，刷新后根级前两项仍是 X、F，新节点全部在 F 之后。

**Acceptance Scenarios**:

1. **Given** 同父下已有节点，**When** 批量添加并刷新，**Then** 新节点按批内顺序排在原有节点之后（AC#3）。
2. **Given** 文件管理器根级有排在最后一个文件之后的文件夹，**When** 批量添加，**Then** 新根节点排在该文件夹之后（AC#3）。
3. **Given** 批量添加同时生成父节点与它们的子节点，**When** 提交，**Then** 每个新父节点下的子节点按生成顺序排列，整批一次提交（AC#3）。

---

### Edge Cases

- **空组**：父节点下还没有子节点时，新建的第一个子节点正常落库，之后的子节点排在它后面。
- **同批的新父节点**：批量添加里父节点和它的子节点同在一批，子节点按生成顺序排在新父节点下，不读也不受其他父节点影响。
- **批量生成的临时空串键**：批量生成逻辑现在会先给节点写空串排序键；不再自己算键后，空串会被当作非法的显式键整批拒绝，必须不写。
- **既有 demo 库**：换成新实体后，库里旧实体的树数据不再显示，新实体的表在既有库上补建；旧数据不迁移（故事 Out of Scope）。
- **备份与失败现场归档**：demo 的实体清单变了，本阶段合入前导出的归档按「不兼容」拒绝恢复，属预期。
- **拖放仍走旧路径**：本阶段 demo 的拖放还是自己算键再保存；合法的显式键原样保留，拖放照常可用。拖进未展开懒加载节点的撞键
  （故事缺陷三）在阶段 B 关闭，本阶段不处理。
- **撤销**：新建、批量添加、删除提升各是一次提交，撤销一次恢复一次操作。
- **懒加载页删除折叠节点**：节点折叠、子节点未加载时，删除仍要弹出「级联删除 / 提升子节点」的选择；选提升时未加载的子节点同样改挂、不被级联删掉
  （Angular 懒加载页现在按已加载节点判断，直接删除会连带删掉整棵子树）。
- **在未加载子节点的文件夹里新建**：Angular 懒加载文件管理器选中文件夹不加载其子节点，新建的键由引擎按库里的尾键给出，不受页面加载状态影响。
- **桌面宿主**：Electron / Tauri 不渲染树页面，不注册新实体，行为不变。
- **实体模型页**：新实体出现在 demo 的通用实体浏览页，默认按父节点、排序键排序；其 `children` 关联表会出现拖拽手柄（US-028 阶段 B 的谓词自动开启），本阶段不另加验收。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: `@aiao/rxdb-test` MUST 提供四个可排序树实体，分别对应 `MenuSimple`、`MenuLarge`、`FileNode`、`FileLarge`：
  列、索引（同级唯一、父节点 + 排序键）、计算属性、「是否有子节点」的计算方式与对应旧实体一致；以父节点为分组字段声明手动排序，排序键必填。
- **FR-002**: 四个新实体 MUST 注册进 `rxdb-test` 的实体清单（三端 demo 由此带上），带公开类型说明，并纳入 `rxdb-test` 的公开契约与实体数断言；
  命名 MUST NOT 与 `rxdb-test` 现有的排序契约夹具重名，注册顺序 MUST NOT 破坏三端实体模型页「首个实体是 `Account`」的断言。
- **FR-003**: 旧的 `MenuSimple` / `MenuLarge` / `FileNode` / `FileLarge` MUST 保持表结构、默认查询顺序与写入行为不变；远端 `menu_large`
  参考表与 Electron / Tauri 的实体注册 MUST 不变。
- **FR-004**: 三端（Angular / React / Vue）的树菜单与文件管理器六页（全量、虚拟滚动、懒加载）MUST 改用对应的新实体，三端页面与实体的对应关系一致。
- **FR-005**: 新建节点（根级与子级、文件与文件夹）时页面 MUST NOT 给出排序键，由引擎追加到同父末尾；新建路径上的自算键与失败后落成首键的兜底 MUST 删除。
- **FR-006**: 批量添加 MUST NOT 给出排序键（含临时空串），由引擎按父节点分组、按批内顺序追加；整批 MUST 一次提交。
- **FR-007**: 删除并提升子节点时，子节点改挂与删除被删节点 MUST 在一次提交内完成；子节点 MUST NOT 携带原组的排序键，
  由引擎按原先后追加到新父节点组末尾。三端 MUST 采用同一提交方式。
- **FR-008**: 树页面上除拖放外的写入（新建、重命名、批量添加、删除、级联删除、删除提升）失败时，页面 MUST 在页内展示错误、保持库里已提交的状态，
  下一次操作可用；MUST NOT 留下未处理的失败或用阻塞式弹窗代替页内提示；三端 MUST 使用同一组提示文案与状态。拖放的失败提示属阶段 B。
- **FR-012**: 删除提升与「是否弹出删除对话框」的判断 MUST 以库里的子节点为准，不得只看页面已加载的节点；懒加载页里折叠节点的子节点同样被提升，不被级联删除。
- **FR-009**: 本阶段 MUST NOT 改动拖放的写入方式与显示排序（属阶段 B）；在新实体上，现有拖放 MUST 继续可用。
- **FR-010**: 三端 MUST 以 Playwright 端到端用例覆盖 User Story 2～4 的验收场景：操作后刷新页面读回顺序；需要直接读排序键的断言
  （如根级文件夹 / 文件交替新建的键互不相同）经 demo 可读库的途径完成。
- **FR-011**: 三端的单元测试 MUST 断言 demo 交给引擎的写入不含排序键（新建、批量、删除提升），每条缺陷 MUST 有一条不修即红的回归用例。

### Accessibility

本阶段不新增交互控件：新建、批量添加、删除对话框沿用现有控件。页内错误提示 MUST 以 `role="alert"` 宣告、可关闭、关闭按钮可用键盘操作，
三端同一结构；不破坏现有树页面的键盘操作，三端 a11y 现状不得退化。

### Key Entities

- **可排序菜单（全量）**：对应 `MenuSimple`；标题、父节点、排序键；同父标题唯一（忽略大小写，根节点同样生效）；「是否有子节点」在内存里算。
- **可排序菜单（大规模）**：对应 `MenuLarge`；同上，另有父节点 + 排序键索引；「是否有子节点」由库计算，供懒加载与虚拟滚动使用。
- **可排序文件节点（全量）**：对应 `FileNode`；名称、类型（文件 / 文件夹）、扩展名、大小、父节点、排序键；同父「名称 + 扩展名」唯一；
  完整文件名、是否文件夹、可读大小三个计算属性。
- **可排序文件节点（大规模）**：对应 `FileLarge`；同上，「是否有子节点」由库计算。
- **排序域**：同一父节点下的全部子节点构成一条序列，根节点（无父节点）是一组；不同组的排序键互不相干、可以重复。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 三条已复现缺陷中，阶段 A 负责的两条（新建根文件夹撞键、删除提升后撞键）的回归用例在三端全部通过，且回滚修复后会失败。
- **SC-002**: 三端各页面的新建、批量添加、删除提升场景，刷新前后顺序 100% 一致，三端对同一操作序列给出相同顺序。
- **SC-003**: 旧四个树实体的现有测试零修改通过（六个 SQLite runner 共用的菜单套件、PGlite 与 supabase 树测试）。
- **SC-004**: 批量添加 10,000 条（demo 最大档位）时，不写排序键、由引擎追加的耗时不超过**同一次运行里**同一批行带显式键耗时的 1.2 倍；
  新建单个节点的落库在 100 ms 内完成。旧实体加页面预算键的耗时与「显式键」一档在实测中相当（见 research R3），以同次运行自比作为判据，不依赖跨机器基线。
- **SC-005**: demo 的新建、批量添加、删除提升路径上不再出现自算排序键的代码（故事 AC#9 检索的这部分为空）；拖放路径留给阶段 B。

## Assumptions

- US-028 阶段 A + D 已交付的按组创建追加、改分组字段追加与事务写边界可直接使用；它们的语义正确性由 US-028 的跨适配器契约套件保证，
  本阶段只验收 demo 是否把键交给了引擎。
- 父节点经关系对象设置时会同步写入父节点字段（故事技术笔记），引擎按组追加读到的就是新父节点。
- demo 已有的旧树数据不迁移，换实体后不再显示是可接受的代价（owner 2026-10-08 定案，同 US-028 阶段 E 的 `Task` 先例）。
- 新实体复刻还是继承旧实体由 plan 定，前提是旧实体表结构不变。
- 批量添加的性能风险由 plan 先测基线再定方案：引擎追加每个目标组读一次尾键，随机造树会产生大量组（同批新建的父节点各成一组），
  若超出 SC-004，优化引擎追加（例如按组索引、跳过同批新建父节点的尾键读取）属于本阶段范围。
