## User Scenarios & Testing _(mandatory)_

### User Story 1 — 被权限拦下的删除不留幽灵日志，而是明确拒绝（阶段 A，Priority: P1）

远端业务表启用了行级权限（RLS）。最终用户在本地删除一条自己无权删除的记录，推送时远端不删这一行、也不记一条删除日志，
而是以权限拒绝失败；推送方本地不会被告知「已删除」，其它设备也拉不到这条从未生效的删除。目标行连「读取」规则都不放行时同样如此，
不会被当成「远端已删」放过。目标行确实已经被别人删掉时，删除按既有幂等语义成功。

**Why this priority**: 幽灵 DELETE 今天就能复现（故事症状 1），远端与所有客户端静默分叉且没有任何一端报错，是本故事最严重的问题。

**Independent Test**: 在一张「读不设限、删除仅本人」的表上，以普通用户身份推送删除他人的行，断言权限拒绝、行仍在、无新日志；
把「读取」也改成仅本人后重复，结果相同；再对一条远端已不存在的 id 推送删除，断言成功。

**Acceptance Scenarios**:

1. **Given** 业务表开 RLS，目标行对调用方可见，删除规则不放行，**When** 推送删除该行并附删除日志，**Then** 以 42501 失败；行仍在；
   该客户端没有新日志（AC#1）。
2. **Given** 业务表开 RLS，目标行存在，但读取与删除规则都不放行，**When** 推送删除该行，**Then** 以 42501 失败，**不**按「已不存在」放过；
   行仍在；无新日志（AC#2）。
3. **Given** 目标行已被他人删除（对任何角色都不存在），**When** 推送删除该行，**Then** 按既有幂等语义成功，不因「零行生效」被误判为拒绝（AC#4）。
4. **Given** 同批含一条被拒操作和若干可放行操作，**When** 推送，**Then** 整批回滚，无任何日志写入（AC#5；阶段 B 再放开部分成功）。

### User Story 2 — 远端日志与业务写一一配对（阶段 A，Priority: P1）

远端的变更日志是其它设备拉取的唯一来源。任何一次推送，main 分支上每条日志都必须对应一次真实的业务写，每次业务写也都必须有日志；
伪造的「只写日志不删行」或残缺的「只写行不写日志」调用一律被拒绝，业务表与日志都不变。正常推送里「多条本地变更压缩成一次远端操作」
仍视为配对。

**Why this priority**: 推送入口对所有登录用户开放，不配对的调用今天被接受（故事症状 4）；只回收日志表直写（阶段 C）关不掉这个口子。

**Independent Test**: 直接调用推送入口，分别构造「有删除日志、无对应删除」与「有业务写、无对应日志」两种调用，断言均被拒、两张表都不变；
再构造「同一实体三条日志、一次业务写」的调用，断言成功。

**Acceptance Scenarios**:

1. **Given** main 分支一条删除日志，没有对应的删除操作，**When** 调用推送入口，**Then** 拒绝，业务表与日志表都不变（AC#6）。
2. **Given** 一次业务写，没有对应的日志，且关闭了触发器自动记日志，**When** 调用推送入口，**Then** 拒绝，业务表与日志表都不变（AC#6）。
3. **Given** 同一实体的 N 条源变更压缩为 1 次业务写，**When** 调用推送入口，**Then** 视为配对，成功（AC#6）。

### User Story 3 — 一条被拒不再拖垮整批（阶段 B，Priority: P1）

同一批推送里有一条变更被远端权限拒绝时，其余可放行的变更照常生效并拿到远端 ID；被拒的那条标为「被拒绝」并附原因（含 SQLSTATE），
之后不再被重推，水位线越过它，同步不再卡住。多条本地变更压缩成一次远端操作时，被拒结果扇出到它的全部源变更。网络错误、服务端 5xx
与非权限类数据库错误不算被拒，仍按原有语义重试。远端漏回某条变更的结果时整批按失败处理，不再静默放过。

**Why this priority**: 阶段 A 把幽灵删除改成拒绝后，没有逐实体回执的客户端会被这条拒绝永久卡住（故事症状 2、「阶段 A 单独发布的代价」）；
阶段 B 是阶段 A 可用的前提。

**Independent Test**: 在开 RLS 的表上准备一条会被拒的变更和若干正常变更，经常规推送路径推送一次，断言正常变更都拿到远端 ID、被拒变更
标为被拒并带 SQLSTATE；再推送一次，断言被拒变更未被重发、水位线已越过。

**Acceptance Scenarios**:

1. **Given** 同批含一条被权限拒绝的变更和若干可放行变更，**When** 推送，**Then** 可放行的变更生效并拿到远端 ID；被拒的那条标为被拒绝，
   附拒绝原因（含 SQLSTATE）（AC#8）。
2. **Given** 场景 1 之后，**When** 再次推送，**Then** 被拒变更不再被重推，水位线越过它；其余待推变更正常推送（AC#9）。
3. **Given** 同一实体的多条本地变更被压缩成一次远端操作，该操作被拒，**When** 推送，**Then** 这些源变更都标为被拒绝，都不拿远端 ID（AC#10）。
4. **Given** 推送因网络错误、5xx 或非权限 / 约束类数据库错误失败，**When** 推送，**Then** 不标被拒绝，按既有重试语义处理，水位线不推进；
   只有 plan 列明的 SQLSTATE（至少 42501）计为被拒（AC#13）。
5. **Given** 远端适配器返回的回执缺少某条本地变更，**When** 推送，**Then** 整批按失败处理，水位线不推进（AC#14）。
6. **Given** 相同批次重试，**When** 推送，**Then** 已生效的变更不重复执行副作用，返回首次提交的同一远端 ID（AC#15）。

### User Story 4 — 被拒实体在本地回到远端状态，依赖它的子实体一并处理（阶段 B，Priority: P2）

推送方本地已经写下了被拒的值。推送完成后，被拒实体在本地被覆盖为远端当前值（被拒的新建在本地移除），这次对齐不产生新的待推变更、
不进撤销栈。同批里引用被拒父实体的子实体新建也标为被拒，原因指向父实体，同批其它变更照常生效。

**Why this priority**: 只阻止重推，推送方会一直显示一份远端没有的数据；不处理依赖，子实体的外键失败又会把整批卡住。它依赖 US3 的回执先就位。

**Independent Test**: 推送一条会被拒的修改，推送完成后检查本地该实体等于远端当前值、待推变更数不变；在带外键的参考表上推送「被拒的父
新建 + 引用它的子新建 + 一条无关新建」，断言父子都被拒、无关新建生效。

**Acceptance Scenarios**:

1. **Given** 一条变更被拒，推送方本地仍是被拒前写入的值，**When** 推送完成，**Then** 该实体在本地回到远端当前状态（被拒的新建在本地移除），
   且不产生新的待推变更（AC#11）。
2. **Given** 同批含被拒的父实体新建和引用它的子实体新建，**When** 推送，**Then** 子实体也标为被拒，原因指向父实体；同批其它变更照常生效，
   整批不因外键失败卡住（AC#12）。

### User Story 5 — 三框架都能看到被拒变更及原因（阶段 B，Priority: P2）

应用开发者在 Angular、React、Vue 任一框架里都能用对称的 API 拿到被拒变更的列表与原因，并在 demo 里看到它们。

**Why this priority**: 被拒不再阻塞同步后，若开发者看不到它，用户的修改就会「无声消失」；三框架对称是项目铁律。

**Independent Test**: 在三个 demo 里各触发一次 AC#8，检查界面上都出现被拒变更及原因，三端调用的 API 名称与形状一致。

**Acceptance Scenarios**:

1. **Given** 三框架 demo，**When** 触发 AC#8，**Then** Angular / React / Vue 都能看到被拒变更及原因，API 对称（AC#16）。

---

### User Story 6 — 生产部署下客户端不能直写日志表，分支同步不受影响（阶段 C，Priority: P2）

部署方按生产指引部署参考 SQL 后，登录用户不能绕过推送入口直接往日志表写记录；非 main 分支的推送仍正常写日志，分支同步不回退。
站点文档写明生产环境的日志表权限、业务表 RLS 的推荐策略与已知限制。

**Why this priority**: 日志表今天对所有客户端角色完全开放（故事症状 3），伪造删除与症状 1 等效；但它需要部署方主动按指引操作，且 AC#6
已经关掉了推送入口这一半，所以排在 P2。

**Independent Test**: 按生产指引部署后，以登录用户身份直接向日志表插入一条记录，断言被拒；再推送一条非 main 分支变更，断言日志照常写入。

**Acceptance Scenarios**:

1. **Given** 按生产指引部署的参考 SQL，**When** 以 `authenticated` 直接向日志表插入，**Then** 被拒（AC#17）。
2. **Given** 同上，**When** 推送非 main 分支的变更，**Then** 日志照常写入，分支同步回归不回退（AC#18）。
3. **Given** 站点的 Supabase 适配器文档，**When** 阅读，**Then** 写明生产环境的日志表权限、业务表 RLS 的推荐策略与已知限制（AC#19）。

### User Story 7 — 回归护栏（阶段 A，Priority: P3）

维护者手工对运行中的远端容器执行 SQL 安全回归：改不了的修改继续以权限拒绝失败，既有用例全部通过，PR 描述贴实跑输出。

**Why this priority**: 回归是阶段 A 所有 SQL 行为的落地证据，但不单独给最终用户带来价值。

**Independent Test**: 对运行中的本地远端容器执行 SQL 安全回归脚本，逐条看结果。

**Acceptance Scenarios**:

1. **Given** 目标行对调用方可见，修改规则不放行，**When** 推送对该行的修改，**Then** 以 42501 失败；行未变；无新日志（AC#3；US-220 合入后由其
   AC#4 继续保证）。
2. **Given** 既有 SQL 回归 9 条，**When** 执行 SQL 安全回归脚本，**Then** 全部 PASS（AC#7）。

### Edge Cases

- 被拒的删除目标行在推送方本地存在、但按读取规则对调用方不可见（拉取不经业务表读取规则过滤）：属于「被拒」（AC#2），不得按「已不存在」放过。
- 一批删除里部分被拒、部分已不存在、部分成功：阶段 A 整批以 42501 回滚；已不存在的那部分本身不构成失败。
- 本地「新建后又删除」在推送前被抵消：该实体不进日志也不进业务写，不参与配对校验。
- 非 main 分支的推送只写日志、不碰业务表：不参与配对校验（AC#6），也不参与阶段 A 的零行判定。
- 推送入口以「不关闭触发器自动记日志」的方式被调用：业务写由触发器记日志，配对规则只要求「每条显式日志都有业务写」（AC#6）。
- 同一实体在一批里同时有被拒的修改和随后的删除：推送前已按实体合并为一次远端操作，回执按实体给出。
- 被拒实体在远端已不存在（例如被拒的新建，或修改时行已被他人删除）：本地对齐即移除该实体（AC#11），不产生新的待推变更。
- 父实体被拒导致子实体外键失败，同时子实体本身也会被权限拒绝：子实体标为被拒即可，原因取其一，plan 定优先级。
- 「行已不存在」的修改（US-220 的 `RX001`）在阶段 B 中的归类：由 plan 列明是否计为被拒（AC#13）；不得退化为无限重试。
- 新客户端连旧版远端 SQL、旧客户端连新版远端 SQL：行为由 plan 选定的兼容策略决定（FR-022），不得出现「推送成功但修改丢失」或
  「被拒变更被当成已生效」。
- 阶段 A 先于阶段 B 发布：被拒那条会卡住该仓库的推送，直到用户手工处理（故事「阶段 A 单独发布的代价」）；plan 定发布方式（FR-008）。

## Requirements _(mandatory)_

### Functional Requirements

**阶段 A：不写幽灵日志，统一拒绝**

- **FR-001**: 推送里的删除在调用方权限下零行生效、且目标行实际存在时，推送 MUST 以权限拒绝（42501）失败；行不变，不写日志。
- **FR-002**: 推送里的删除目标行在远端已不存在时，MUST 按既有幂等语义成功，不得报为拒绝。
- **FR-003**: 「行是否存在」的判定 MUST 不受调用方权限规则影响，MUST NOT 向调用方泄露「存在 / 不存在」以外的行内容；
  判定原语 MUST 与 US-220 共用同一个，机制、签名与错误码在两份 plan 里一次冻结。
- **FR-004**: 推送里的新建 / 修改被权限规则拒绝时 MUST 以 42501 失败、不写日志（今天已成立，作为回归护栏）。
- **FR-005**: 阶段 A 下，一批里任一条被拒 MUST 让整批回滚，不写任何日志、不改任何业务行。
- **FR-006**: main 分支的显式日志 MUST 与业务写按（schema、表、实体 id）配对：每条日志都须有业务写；关闭触发器自动记日志时，每次业务写都须
  有日志；N 条源变更对应 1 次业务写视为配对。不配对 MUST 拒绝，业务表与日志表都不变，错误码由 plan 登记。
- **FR-007**: 非 main 分支的日志 MUST NOT 参与配对校验与零行判定。
- **FR-008**: plan MUST 二选一并写明阶段 A 的发布方式：与阶段 B 同一版本发布；或单独发布并在迁移文档写明手工恢复步骤。

**阶段 B：逐实体回执**

- **FR-009**: 远端适配器的推送结果 MUST 为本批每个实体给出明确结果（已生效 / 被拒绝）；被拒结果 MUST 带拒绝原因（含 SQLSTATE）。
- **FR-010**: 推送 MUST 允许部分成功：被拒实体不影响同批其它实体生效与拿到远端 ID。
- **FR-011**: 实体结果 MUST 扇出到该实体的全部源变更；被拒实体的源变更 MUST NOT 拿到远端 ID。
- **FR-012**: 被拒变更 MUST 在本地持久标记，MUST NOT 再被重推；水位线 MUST 越过它。
- **FR-013**: 推送完成后，被拒实体 MUST 在本地被覆盖为远端当前值（远端不存在则移除）；这次对齐 MUST NOT 生成新的待推变更、MUST NOT 进撤销栈。
- **FR-014**: 同批中依赖被拒父实体的子实体 MUST 标为被拒，原因指向父实体；MUST NOT 因外键失败让整批失败。
- **FR-015**: 只有 plan 列明的 SQLSTATE（至少 42501）计为被拒；网络错误、5xx 与其它数据库错误 MUST 按既有重试语义处理，水位线不推进。
- **FR-016**: 远端适配器 MUST 保留数据库返回的 SQLSTATE 与错误详情，供分类与原因展示使用。
- **FR-017**: 推送结果缺少本批任一实体（或任一源变更）的结果时，MUST 整批按失败处理，水位线不推进。
- **FR-018**: 相同批次重试 MUST 不重复执行副作用，并返回首次提交的同一远端 ID；首次被拒的实体在重试时 MUST 得到同样的被拒结果或被正确重新判定，
  由 plan 写明。
- **FR-019**: Angular / React / Vue 三框架 MUST 以对称的 API 暴露被拒变更及原因，三个 demo 都能展示。
- **FR-020**: 推送结果契约是破坏性变更：MUST 过 API 基线，MUST 附迁移说明并在站点迁移目录登记；所有远端适配器实现与测试夹具 MUST 按新契约返回。
- **FR-021**: 被拒状态若需本地系统表结构变化，MUST 随附迁移；是否需要由 plan 决定。
- **FR-022**: 若阶段 A / B 改变了远端 SQL 的入参或返回形状，plan MUST 写明新旧版本组合的行为与升级顺序；任何组合 MUST NOT 出现
  「推送成功但修改丢失」或「被拒变更被当成已生效」。

**阶段 C：日志表收口与部署指引**

- **FR-023**: 按生产指引部署时，客户端角色（`anon` / `authenticated`）MUST NOT 能直接写日志表。
- **FR-024**: 非 main 分支的推送 MUST 保留写日志的路径，分支同步回归不回退。
- **FR-025**: 站点的 Supabase 适配器文档 MUST 写明生产环境的日志表权限、业务表 RLS 的推荐策略与已知限制（含存在性判定原语的剩余探测面）。

**测试与文档**

- **FR-026**: 每条 AC MUST 有对应的自动化或脚本化验证：AC#1～7 为 SQL 回归用例；AC#8～15 为单元测试与连真实远端的 spec；AC#16 为三框架
  demo e2e；AC#17、18 为 SQL 回归或连真实远端的 spec；AC#19 为文档评审。
- **FR-027**: 既有 SQL 回归 9 条与 `rls-filtered-delete` MUST 在阶段 A 交付时全部 PASS；PR 描述贴实跑输出。

### Key Entities

- **推送批次**: 一次推送的新建、修改、删除与对应的日志条目。阶段 A 下在远端一个事务里落库，任一条失败整批回滚；阶段 B 起允许按实体部分成功。
- **实体操作**: 推送前按实体合并后的一次远端写（新建 / 修改 / 删除），由（schema、表、实体 id）标识；对应 1～N 条源变更。
- **远端日志（main 分支变更记录）**: 其它设备拉取的唯一来源；每条须与一次真实业务写配对。
- **存在性判定原语**: 绕开调用方权限、只回答「这些 id 在远端是否存在」的判定；与 US-220 共用。
- **实体回执**: 远端对一个实体操作的结果：已生效（附远端 ID）或被拒绝（附 SQLSTATE 与原因）。
- **被拒变更**: 本地变更的一种终态：不再重推、不拿远端 ID，可被应用查询并展示原因。

## Success Criteria _(mandatory)_

- **SC-001**: 全部阶段 A 新增用例里，「远端行仍在、日志却记了删除」出现 0 次；被拒删除与修改 100% 以 42501 失败，新增日志 0 条。
- **SC-002**: 目标行已不存在的删除 100% 成功，误报为拒绝 0 次；目标行存在但不可读的删除误报为「已不存在」0 次。
- **SC-003**: 不配对的推送调用 100% 被拒，业务表与日志表变化 0 行；正常推送路径因配对校验被拒 0 次。
- **SC-004**: 含 1 条被拒变更的批次，其余变更 100% 生效；被拒变更第二轮推送被重发 0 次，同步卡住 0 次。
- **SC-005**: 被拒实体在推送完成后与远端当前值逐列一致（差异 0 列），对齐产生的新待推变更 0 条。
- **SC-006**: 网络错误、5xx 与非登记 SQLSTATE 被误标为被拒 0 次。
- **SC-007**: 三框架 demo 都能展示被拒变更及原因；三端 API 名称与形状差异 0 处。
- **SC-008**: 按生产指引部署后，客户端角色直写日志表成功 0 次；分支同步回归失败 0 条。
- **SC-009**: 在本地远端上，单批推送（含存在性判定）落库耗时 < 100 ms（宪法默认的数据库操作预算）；存在性判定只在零行生效时执行，
  成功路径不多一次查询（**推断**为可达，plan 阶段核实）。

## Assumptions

- 「行是否存在」的判定原语、「已不存在」的 SQLSTATE 与推送入口的签名，以 US-220 plan 的冻结候选 F1～F3 为起点，在本故事 plan 中交叉核对后一并冻结；
  若须调整，两份 plan 与契约同步修改。
- 阶段 B 以 US-220 为前置：在 US-220 之前，修改按新建语义落库产生的误报会被阶段 B 当成真实拒绝暴露（故事「前置」）。
- 阶段 C 单靠回收日志表直写关不掉不配对调用，那一半由 AC#6（阶段 A）关。
- 拉取侧过滤（「用户能拉到自己按读取规则读不到的行」）、角色与所有权声明、Supabase 之外适配器的 RLS 等价物、被拒变更与撤销 / 重做的交互，
  均不在范围内（故事 Out of Scope）。
- 唯一真正实现推送的远端适配器是 Supabase；HTTP 适配器的推送直接抛「不支持」，不受契约变更影响；跨框架测试夹具需按新契约改。
- 仓库没有参考 SQL 的版本校验，新旧组合只能靠入参兼容或迁移文档保证。
- SQL 安全回归不在 CI 里，需手工对运行中的容器执行，PR 描述贴实跑输出；连真实远端的 spec 与 demo e2e 依赖本地远端容器。
- 开工条件：本故事三个阶段与 US-220 的 plan 全部完成后才进入开发；合入时 US-220 先于本故事阶段 B（roadmap 约束 16）。一个 PR 只交付一个阶段。
