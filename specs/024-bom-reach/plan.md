## 现有证据与先测量顺序

- `resolve/expansion.ts` 的 `whereUsed` 在同一读事务中逐层取父发生项，按发生项完整路径返回，逐节点结算预算。
- `resolve/bom-sql.ts` 的 `buildParentsOfItemsSql` 负责组织、类型、发布、日期、ECN 等过滤，其结果还经过既有配置/序列/批次过滤。备选裁决与候选保留由`resolveBom`及完整消费入口负责；`expandBom/whereUsed`保留原有首轮多头路径合同，不因加入Reach改变公开行为。
- `backend/bom-trigger-ddl.ts` 当前使用有界递归判并集环；远端 DDL 在 `resolve/cycle-constraint-ddl.ts` 另含作用域 advisory lock 和隔离级别检查。
- 原 `benchmarks/bom.bench.ts` 只有 `whereUsedInstance`；本轮已用独立 `benchmarks/bom-reach.bench.ts` 补真实主数据测量，避免与正在修改的视图基准互相占用文件。

独立基准覆盖100/1000/10000物料的有界组件背景图，每组件含共享装配、重边和8层反查路径；另测20串菱形。避免把单条1万层链或稠密全连图当普通工作负载。

每个后端独立连接与预热至少 5 次，串行采样至少 20 次，固定数据和输入；同时留无使用方、少量使用方、较深祖先链和预算截断场景。保留 p50/p95/max、原始样本、节点/边/可达对/结果路径数、截断原因、查询计划、SQL 次数及环境信息。先比较现状与必要索引，再比较物化方案；同一个测试会话外不能复用旧结果冒充新查询。

原始报告分别写 `benchmarks/reports/bom-reach-baseline.json` 和 `bom-reach-comparison.json`，实际命令与结论写本目录后续 `quickstart.md`。现有 `benchmarks:benchmark-bom` 是可复用 Nx 入口；扩双后端前由主会话核对其依赖和配置，不猜 CLI flag。

**收益门禁与已确认决定**：真实1万物料反查已达到SC-004：236.24→7.60ms，收益96.78%。因此生产仅补`BomLineOccurrence.childItemId`索引，不默认增加可达JOIN；作用域索引和10000路径场景的负收益均保留。`benchmark-bom-reach-prototype`已对非空反查、无使用方和10000路径三类场景完成隔离交错采样：p95分别9.376→10.327ms、1.798→1.235ms、17.943→18.852ms；报告不覆盖旧基线，原型不进入默认生产读取。可达性一致性和判环验收独立于读取剪枝。

## Technical Context 与范围

TS strict、既有 RxDB 实体元数据、SQLite 与 PGlite 的 SQL 触发器、Vitest 双后端测试、现有 Nx benchmark 入口。主要改 `rxdb-plugin-bom`；不预设修改 `rxdb` 引擎，不增加后台作业或三端绑定 API。

生产文件拟分为 `src/reach/entities.ts`、`src/reach/reach-ddl.ts`、`src/reach/reach-sql.ts`；`entities.ts`/插件入口只接线。判环与维护各一个职责，避免继续把算法堆进巨大 `bom-trigger-ddl.ts`。`resolve/expansion.ts`/`bom-sql.ts` 只接经过基准证明的候选读取优化。

## 数据结构

派生实体 `BomReach`，namespace `bom`、tableName `bom_reach`。沿用 `EntityBase` 的标识和审计字段，显式 `log: false`，公开 create/update/delete 权限均为 `system`；触发器内部使用底层执行器写入，不生成第二套领域变更日志。

优先通过现有插件系统实体贡献和迁移通道在建表前登记，不要求旧调用方为内部优化修改其 `entities` 数组，也不把派生实体塞进 ERP 主数据清单；现有 `BOM_ENTITIES` 的消费行为保持兼容。R004 要复核现有系统贡献 API 的新库/旧库调用顺序，确认后再接线，不预设新增引擎接口。

| 字段               | 类型                    | 约束/用途            |
| ------------------ | ----------------------- | -------------------- |
| `bomType`          | `ebom \| mbom \| sales` | 非空，作用域组成部分 |
| `orgId`            | string                  | 非空，作用域组成部分 |
| `ancestorItemId`   | UUID                    | 非空，引用物料       |
| `descendantItemId` | UUID                    | 非空，引用物料       |

- 唯一索引 `(bomType, orgId, ancestorItemId, descendantItemId)`；反向索引 `(bomType, orgId, descendantItemId, ancestorItemId)`。
- CHECK `ancestorItemId <> descendantItemId`；仅存正长度可达对，自反节点只在维护 SQL 的临时集合中补入。
- 不增加 depth、path、pathCount、revisionId、effectiveFrom/To、qty 或乘积列。
- 新对的 UUID/时间戳由各后端现有 SQL 能力生成；唯一物料对才是逻辑身份，随机 ID 不参与图算法。原有行在非拓扑更新中连审计列也不得改。
- 派生表不参与 BOM ERP 导入/导出、实例图或离线同步。公开权限避免误用，不宣称可防止有数据库管理权限的调用方手工篡改派生表。

## 图和存储不变量

`G(t,o)` 的边来自仍存在的 `BomLineOccurrence`，经 line→header→parentRevision 确定父物料与作用域，仅 `flowDirection='consume'`；不按头/修订发布态、日期、ECN 可见性或候选选择过滤。

`R(t,o)` 必须恰好等于 `G(t,o)` 的正长度传递闭包。每个成功语句结束后成立，事务回滚恢复原状态；同一事务后续语句立即能看到最新闭包。无关作用域和未受影响的物料对零 DML。

“并集不带生效期”不等于永久保留已删除边；ECN 取消/撤回删除最后支持发生项后，图和闭包必须一起移除该路径。

## 双后端一致的增量算法

### 插入 consume 边 P→C

1. BEFORE 阶段执行既有写入协议、作用域约束及判环。自环直接拒绝；在正确的旧闭包中检查 `(C,P)` 是否存在。
2. AFTER 阶段，从旧闭包读 `A={P}∪ancestors(P)`、`D={C}∪descendants(C)`，只对 `A×D` 去重插入不存在的正长度对。使用冲突忽略的唯一插入，不 UPDATE 已存在对；不先 DELETE 后重建。
3. 重复物料边已由另一条发生项支持时，所有可达对通常已存在，本次闭包实际写入为零。

### 删除 consume 边 P→C

AFTER DELETE 时闭包仍包含这条旧边的贡献，因此可以从旧闭包取同一个 `A×D` 候选集合。对每个受影响祖先，在**删除后的真实发生项图**上有界求可达物料；仅 DELETE 候选中已不可达的对。多重边和替代菱形路径仍连通的对保留。

重检递归使用集合去重，不把路径字符串放入递归状态；可用 `(source,item,depth)` 有界状态，避免不同路径在 20 菱形中指数枚举。触及硬限制却不能完成否定证明时，整条源删除必须失败并回滚，不能把“不知道”当“不再可达”。

ECN 级联删除逐条进入同一维护逻辑；现有归属外键不允许绕过发生项删除直接丢失父作用域。测试须证明级联执行时 OLD 的作用域仍可解析；不得用 NULL 作用域跳过维护。

### 修改端点或流方向

BEFORE阶段先拒绝成环，见证从排除OLD发生项的真实图取得。DAG里C→P的路径不可能依赖从P出发的OLD边，否则已经到达P或形成旧环，因此旧闭包的反向点查与排除OLD后的判断等价，不必在BEFORE阶段改写派生表。

AFTER UPDATE由一个触发器体先按删除规则撤掉旧consume贡献，再按插入规则补齐NEW；删除重检排除同一发生项ID，避免把NEW提前当作旧支持。任何一步失败整体回滚。

删除与插入的顺序由同一个AFTER触发器体拥有；不得依赖多个同阶段触发器的创建先后或命名排序。归属列仍由原有存储协议拒绝，非法写入的任何副作用随语句回滚。

方向未变且子件未变时维护触发器不执行；`qty`、损耗、位号、日期、工序、ECN 发布/改期、修订/头发布均不触发维护。不要把触发器 `UPDATE` 入口做成每次都重算再发现无差异。

## 判环、深度与远端并发

- `(C,P)` 是一次复合唯一索引点查；US-509 所称 O(1) 命中是“不遍历图”的意图，B-tree 实际查找复杂度为 O(log R)，不夸称无条件常数时间。
- 命中已确定拒绝，之后只为保持错误合同求一个见证路径；这不是重新用全路径枚举决定是否成环。自环见证只有一个物料。
- 不存深度并不允许放宽现有 `BOM_CYCLE_DEPTH_LIMIT=128`。保留独立有界检查/见证规则；无法完成的判定明确拒绝，不能以闭包没有深度列为由静默通过旧硬限。
- 有闭包加速的物理方案与旧递归方案在同一套 accepted/rejected oracle 上对拍。闭包缺失或迁移未完成必须显式失败，不偷偷回退而掩盖部署错误。
- SQLite/PGlite 的维护与源写入同事务；远端 PostgreSQL 新维护/更新/删除入口必须复用 `(bomType,orgId)` 锁及 Read Committed 检查，不能只给插入判环加锁。已关闭的真实 PostgreSQL 多连接验收必须回归，PGlite 不能替代它。

## 读取、预算与兼容

`bom_reach` 只提供可能祖先/后代候选，精确路径仍按现有 ResolutionContext 获取真实发生项，并保留排序、备选/配置/序列/批次候选、数量与导出守卫。禁止直接把闭包行转成 ExpansionNode，禁止只取 closure 中一个物料对代替多条发生项路径。

现有 BFS 每层/每节点的 depth/expansions/paths/AbortSignal 结算保留；不能为了候选预取在预算触顶前全量枚举所有路径或读取所有发生项。是否预取、剪枝哪些 SQL 只由 US0 测量决定；收益未证实时不扩大查询改动。

20 串联菱形的正长度对为 `C(61,2)-20=1810`（每个菱形中两个并列分支互不可达）；同时保留原查询恰好返回 10000 个节点、原因 `paths` 的实测断言。深度 40 不能替代路径数硬停。

## 显式迁移与恢复

新库贡献空派生表；旧库经现有系统迁移`0001-bom-reach`在同一事务回填、对拍并安装依赖闭包的触发器。回填的递归状态仅有作用域和物料对，使用UNION去重，有限图上最多产生N²对；不遍历路径，也不把查询的128路径深度当成物料对闭包的列。旧环产生自反对即明确失败。路径见证、负向判定和读取预算继续保留128硬停。

重连只验证完整性，不删除重建；迁移水位属于现有机制。缺对、伪对和缺失表不能作为空缓存继续使用；失败不留下已完成迁移水位。恢复旧备份后也必须经同一迁移/校验再启用新触发器。
