# Threat Model: 提交能力的防线边界

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Adapter Contract**: [contracts/adapter-contract.md](./contracts/adapter-contract.md)

启用提交能力后，仓库里多出一批「门禁」：raw 写判定、bulk-write 门禁、捕获挂载点、受信写登记表、`'*active*'` 哨兵、active branch token。它们看起来像一条安全防线，于是每次评审都会有人问同一个问题的不同变体——第三方适配器能不能仿冒受信键？用户能不能建一个叫 `*active*` 的分支？另开一个 `sqlite3` 连接直接写表怎么办？

这些问题没有统一答案，因为**这些门禁守的不是同一样东西**。本文件把边界一次性写死：每道门禁挡谁、不挡谁，以及「不挡」是缺陷还是设计。评审里再出现这类条目时，判据在这儿，不在报告里。

## 1. 一句话结论

> **提交能力的门禁防的是「漂移」，不是「对抗」。**

漂移 = 一个本该记录工作树单元的写路径，因为有人新写了代码、换了调用方式、忘了登记，而悄悄绕过了捕获。这类事故的特征是**当事人不知道自己绕过了**，后果是工作树与业务表不一致、冷重放缺项——这正是 SC-009「任何业务表净变化都能由 HEAD + `WorkingTreeEntry` 重放」要挡的。

对抗 = 一方**知道**门禁存在并主动构造输入去躲开它。v1 不承诺挡住任何一种对抗，原因见 §2。

两者的区别直接决定修法：防漂移的门禁要**fail-closed 且噪声可接受**（宁可误伤，见 SC-009 判据）；防对抗的门禁要能**验证身份**，而本地库里没有可验证的身份。

## 2. 三个圈：模型内 / 模型外 / 根本不是边界

| 圈               | 谁                                                                                                     | 门禁的作用                                                |
| ---------------- | ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------- |
| **模型内**       | 本仓库与下游应用**经 adapter 写业务表**的代码                                                          | 挡住绕过捕获的写入，fail-closed 抛错                      |
| **模型外**       | 绕过 adapter 的外部数据库句柄（另开 `sqlite3`、直接打开 OPFS 文件、psql 连 PGlite、DevTools 手写 SQL） | **拦不住，v1 也不承诺拦得住**（spec.md「能力边界」）      |
| **根本不是边界** | 第三方适配器实现                                                                                       | 见 §2.1——它不在门禁的**里面**，它**就是**门禁所在的那一层 |

### 2.1 第三方适配器：不是威胁，是实现者

**第三方适配器不在威胁模型内。** 这不是「暂时不管」，是结构性的：

raw 判定、bulk-write 门禁、捕获钩子**全部由适配器自己调用**——`rawQuery()` 在 [rxdb-adapter.ts](../../packages/rxdb/src/rxdb-adapter.ts) 上是可选方法，共享判定由核心导出、由各适配器在自己的实现入口调起（adapter-contract.md §2 实现约束）。一个不调用它们的适配器不是「突破了门禁」，而是**那里压根没有门禁**：适配器就是写路径本身，要求它防着自己，等于要求锁防着锁匠。

因此这些门禁的性质是**一致性契约**，不是防御边界。它的执行手段也相应地是契约手段，而不是运行时校验：

- 义务写在 [contracts/adapter-contract.md](./contracts/adapter-contract.md)；
- 履行与否由 [contracts/conformance-suites.md](./contracts/conformance-suites.md) 的两套具名套件判定，**不靠自述**（SC-006 要求 6 个 v1 后端双双全绿）；
- 套件不过 = 这个适配器不支持提交能力，而不是「这个适配器被攻破了」。

一个恶意的第三方适配器能做的事，远比仿冒受信键多——它能直接写表、能吞掉错误、能返回假数据。讨论它绕过 raw 判定，是在一个已经完全失守的位置上讨论某一扇窗户。

### 2.2 这个结论解掉的评审条目

| 曾被挡住的条目                         | 现在的判据                           |
| -------------------------------------- | ------------------------------------ |
| 受信写标记是自报字符串键，可被仿冒     | §4：它防漂移，不防仿冒               |
| `'*active*'` 哨兵与用户数据同命名空间  | §5：它防碰撞，不防攻击               |
| raw 判定的受信 intent 豁免没有生产通道 | §3：豁免已删除，未来要接先补身份通道 |

## 3. raw 写通道与「受信 intent」

### 3.1 判定里没有「受信 intent 豁免」这一步，是刻意的

[raw-write-judgment.ts](../../packages/rxdb-plugin-working-tree/src/working-tree/raw-write-judgment.ts) 的判定曾有 5 步，第 2 步是「携带内部受信 `intent` → 放行」。**2026-09-23 连同上下文槽位一并删除，判定变为 4 步。**

删而不是留空位，理由是这一步在生产里**永远取不到真值**：`TRUSTED_CALLSITE_REGISTRY` 的 9 个条目全部走 `switchBranch` / `mergeChanges` 这两个**带类型的**写原语（adapter-contract.md §3 登记表），一个 raw 调用点都没有（2026-09-25 补登的 #10 走 `transaction()` 事务体末尾的自报，同样是带类型的调用路径，结论不变）。它是一条死分支——却是整条防线上**唯一无条件放行**的一步。留着它的成本不是死代码，是**误导**：读判定的人会以为这条通道存在并且被用着，写新代码的人会以为「加个 intent 就能绕过去」是被支持的用法。

### 3.2 未来真要内部受信 raw 写路径，要补的是什么

不是把槽位加回来。raw 通道上**没有任何东西能证明发起方身份**——SQL 字符串里带一个 `intent` 字段，和调用方自己说「我是可信的」是同一件事，而 §1 已经说明：验证不了身份的门禁只能防漂移，而一个**无条件放行**的分支连漂移都防不了，它是漂移的入口。

要接，先得有一条**能证明身份的传递通道**：intent 不能作为 SQL 的一部分或公开参数传入，必须由写原语在**带类型的调用路径**上携带（`switchBranch` / `mergeChanges` 今天就是这么做的——所以它们根本不需要 raw 豁免）。在那条通道存在之前，正确的做法是让内部受信路径继续走带类型的写原语。

### 3.3 `TrustedWriteIntent` 仍然存在，但管的是另一件事

删掉的是**raw 判定里的豁免**，不是 [`TrustedWriteIntent`](../../packages/rxdb/src/trusted-write/trusted-write-intent.ts) 本身。它现在只承担一个职责：**写入口语义矩阵取哪一行**——同一个 `switchBranch`，分支物化必须**不**产生工作树单元，undo/redo 必须产生（spec.md 写入口语义矩阵 / adapter-contract.md §3 最后一列）。这是语义分派，不是豁免。

它不做成公开参数，也是这个原因：能选矩阵行 = 能让自己的写入不产生工作树单元。

## 4. 受信写登记键是自报的——它防漂移

[`declareTrustedWrite()`](../../packages/rxdb/src/trusted-write/trusted-write-scope.ts) 收的是「文件 · 符号 · 意图」三段字符串键，运行时只查 `TRUSTED_CALLSITE_REGISTRY` 这张表，**不校验调用方真的在那个文件那个符号里**。词法审计（`pnpm audit:callsite-drift`）也只扫 `packages/`。

这是**按 §1 设计的**，不是遗漏：

- **它挡住的**：新写一处批量重写却忘了登记 → `declareTrustedWrite()` 查不到键，当场抛错（fail-closed，未携带标记的批量重写一律按未知入口拒绝）；登记表与真实调用点漂移 → 静态扫描报警。这两件事都是「当事人不知道自己绕过了」，正是漂移。
- **它挡不住的**：一个知道键长什么样、并且主动去仿冒它的调用方。而能仿冒它的代码必须已经能 `import` 核心包并拿到 adapter 实例——到了这一步，它直接调 `adapter.mergeChanges()` 比仿冒键更省事。

把 intent 做成写入原语选项上的结构化字段是更强的形状，但**强的方向不是防仿冒**，而是让漂移在类型层就暴露（编译期而不是运行期）。那是重构收益，不是安全收益，因此不按安全项排期。

## 5. `'*active*'` 哨兵防的是碰撞

[active-branch-guard.ts](../../packages/rxdb/src/system/active-branch-guard.ts) 用 `'*active*'` 作为 `activeKey` 的哨兵值，与用户分支 ID 同命名空间。它的安全性**不**来自「别人猜不到」，而来自创建期校验：`assertUsableBranchId()` 在分支 ID 进库前拒绝含保留字符的值，所以库里不可能出现第二个 `*active*` 行去和哨兵抢唯一约束。

即：它防的是**用户无意间起了个撞车的名字**（碰撞），不是**用户存心去撞**（攻击）。后者的前提同样是攻击方已经能写系统表——到那一步唯一约束是谁都无所谓了。

> 与之相关但**不在**本文件解决范围的：`activeKey` 是 `activated` 的第二份拷贝，靠约 10 处写点手工共写维持不变量。那是**数据建模**问题（该由生成列或部分唯一索引表达），不是威胁模型问题，仍按顺延项排期。

## 6. 跨连接与跨进程

同一个库被多个连接 / 多个进程同时写，**在模型内**——它是漂移的一种，而且是最典型的一种：两个连接都是自己人，都经 adapter，只是其中一个的能力位是旧的。

危害的形状是**沉默**。连接 B 在连接期读到「能力未启用」，于是一个捕获钩子都不装（FR-046 要的正是这个形状：未启用的库与上线本功能之前逐字节一致）；随后 A 调了 `enable()`，而 B 手里那份判断再也不会被重新问一次。B 之后的每一次写都照常成功、照常落业务表，只是不产生工作树单元——直到有人在任一端调 `status()` / `commit()`，才发现那一批编辑根本不在待提交集里。没有异常，没有告警。

### 6.1 v1 landed 的是「通知 + 接通」，不是 fail-closed

评审给过两条路：**在 B 的下一次写之前装上钩子**，或**拒绝旧连接继续写**。后者要求每次写都同步复核能力位，与 FR-046 的零行为差异直接冲突（未启用的库会因此多出一条每写一次都要走的检查）。v1 取前者：

1. `WorkingTreeManager.enable()` / `enableIfEmpty()`（真的翻了能力位的那一支）在事务提交后调 `RxDB.broadcastCapabilityEnabled('workingTree')`；
2. 核心经网关发一条 `capability_enabled` 消息（`GatewayCapabilityEnabledMessage`）；
3. 收到的连接派发 `CAPABILITY_ENABLED` 事件，`capability` 不是字符串时整条丢弃；
4. 工作树插件在 `install(scope)` 里登记的监听器比对能力名后，**同步**经 `RxDB.localAdapterIfConnected` 取本纪元适配器并装上捕获。

三处形状是被威胁逼出来的，改动时不要各自「简化」：

- **这条消息只出不进**，收端一条都不再发。它不带 `entities`，`isCrossTabEvent()` 对它恒为 `false`，而实体事件那条链的防回声靠 `#processingRemoteEvent` 这个**瞬时**标志——事务队列缓到 COMMIT 才重放时它早已复位。每次回声换一个 `messageId`，256 条的去重窗口拦不住。
- **接收端同步装**，不走 `await firstValueFrom(localAdapter$)`。那一个 `await` 让出一个微任务，而这条通道存在的全部意义就是「在下一次写之前装上」；那条缝隙里的写照样不留痕迹。
- **监听器登记在 `install(scope)`，不在 `bootstrapExisting()`**。后者按契约「只在既有库上调，新库一次都不调」，挂在那里等于建库的那个客户端一次都收不到——而「A 建库、B 连上、B 启用」正是这条通道最该救的排列。

### 6.2 自愈补广播够不着的 realm

`WorkingTreeManager.runEnabled()` 在事务提交后补一次 `#healCapture()`：门禁刚在同一笔事务里读到 `enabled === true`，而生产代码里没有任何一处卸载钩子，所以「过了门禁却没有钩子」不存在良性解释。于是任何一次工作树 API 调用（`status()` 这样的只读调用也算）都会把这条连接接回来。

它**是自愈，不是修复**：只让今后的写留下痕迹，此前绕开捕获的那些写不会被追认，也无从追认。

### 6.3 关掉了什么、没关掉什么

| 情形                                                                   | v1             | 靠什么                                           |
| ---------------------------------------------------------------------- | -------------- | ------------------------------------------------ |
| 同源的浏览器 tab / worker / 同 realm 的多实例                          | 关             | §6.1 的广播                                      |
| 跨进程（Electron 主/渲染、Tauri、Node 多进程）、`multiInstance: false` | **收窄，未关** | §6.2 的自愈——但只在该连接调过一次工作树 API 之后 |
| 通知在途的那一小段（`enable()` 返回 → 对端装上钩子）                   | **未关**       | 无。落在这段里的对端写入仍然不留痕迹             |
| 从不调用工作树 API、只顾写业务表的跨进程连接                           | **未关**       | 无                                               |
| 跨进程的实时一致性（commit 的 CAS 之外再加一层分布式协调）             | 不在 v1 范围   | —                                                |

**commit 的 revision CAS（FR-031）不是这一条的兜底。** 它防的是「调用方读到 status 之后又有工作树写入」，判据是 revision 变了；而这里丢的单元**根本没写进工作树**，revision 一动不动，CAS 照常命中。把它算成这条的最后一道防线会高估现状。

回归用例：`packages/rxdb/src/__tests__/gateway/capability-propagation.spec.ts`（发、收、不回声、坏载荷）、`packages/rxdb-plugin-working-tree/src/__tests__/system/capability-enabled-listener.spec.ts`（同步装、认能力名、幂等、随纪元退场）、`packages/rxdb-adapter-wa-sqlite/src/__tests__/working-tree-cross-connection.spec.ts`（**两个真实适配器实例共享同一个持久库**的端到端，含 §6.2 的自愈）。最后一条选 wa-sqlite 不是偏好：六个 v1 后端里只有它的 `IDBBatchAtomicVFS` 支持多个真实连接同时打开同一个持久库。

接线状态另见 [tasks.md](./tasks.md) 与 [contracts/adapter-contract.md](./contracts/adapter-contract.md)。

## 7. 门禁一览

| 门禁                                          | 防                       | 不防                                                              | 判据                        |
| --------------------------------------------- | ------------------------ | ----------------------------------------------------------------- | --------------------------- |
| raw 写 4 步判定                               | 未登记的 raw 写路径漂移  | 绕过 adapter 的外部句柄                                           | adapter-contract.md §2      |
| `upsertMany` / `deleteByIds` bulk 门禁        | 不经 `rawQuery` 的批量写 | 同上                                                              | adapter-contract.md §1      |
| 捕获挂载点清单                                | 新增写原语忘了挂捕获     | 不调用捕获的适配器                                                | §2.1                        |
| `declareTrustedWrite()` 登记表                | 新调用点忘了登记         | 仿冒登记键                                                        | §4                          |
| `'*active*'` 哨兵 + `assertUsableBranchId`    | 用户分支 ID 与哨兵碰撞   | 直写系统表                                                        | §5                          |
| active branch token + revision CAS            | 并发提交丢更新           | 跨进程实时一致性；**漏捕获的写**（根本没进工作树，revision 不动） | FR-031 / §6                 |
| `capability_enabled` 广播 + `runEnabled` 自愈 | 同源连接漏掉能力启用     | 通知在途的那一小段；从不调工作树 API 的跨进程连接                 | §6                          |
| 物化 staging 页指纹                           | 来源方传坏、落库之后被改 | payload 形态：加密列交成明文照样落库，失败残留一直留到调用方丢弃  | FR-044 / data-model.md §2.9 |

## 8. 写进公开文档的那一句

SC-015 的六项公开文档说明里必须有这一句，它是本文件对用户可见的全部：

> **启用提交能力的数据库，业务表只能经 RxDB 写入。**

它不是免责声明的注脚，是使用前提。
