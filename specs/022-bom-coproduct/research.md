# 联合成本精度与实施记录

## 逐输出34位与精确尾差的冲突

初始文字使用“每个输出各自34位half-even，再由最后一项接精确尾差”。这两个条件不能总是同时成立。

取 `C = 9999999999999999999999999999999999`、份额 `0.1 / 0.2 / 0.7`。第一项独立34位为 `10^33 − 0.1`，第二项独立34位舍入为 `2×10^33`；精确尾差为 `7×10^33 − 0.9`，需要35位有效数字。若再截到34位，合计就不再严格等于 C。

主会话决定采用**整批共同量子**：若规范十进制 `C = coefficient × 10^exponent`，非零 coefficient 绝对值有 d 位，则共同量子为 `10^(exponent + d − 34)`。现有 kernel 交来的 C 已≤34位，故它是该量子的整数倍。对每项精确乘积在共同量子上half-even，最后正份额项用整数余量承接，分配总额与 C 严格一致。

这会使较小份额的相对精度比“逐项各自34位”更粗；它换取整批守恒与每项34位上限，两者都在本切片验收。币种小数位没有另外强制截到分/厘，不自行引入现有成本合同不存在的货币取整规则。

## 零份额不是尾差容器

若份额 `0.5 / 0.5 / 0`，最后输出的份额为0。前两项在奇数量子金额下可能各向偶数舍入，不能把残差强塞给零份额输出。主会话确认：所有零份额输出恒分配0，结果顺序保留；尾差由稳定排序最后一个正份额输出承接。

份额域为9位定点，最小正份额 `0.000000001`。这也给共同34位量子下的最后正份额留下足够余量，不需要用负分配或超精度金额兜底。

## 首轮真实回归的前置

`bom-coproduct.spec.ts` 使用现有真实 SQLite/PGlite 装配、显式 EntityManager、正常保存/发布/ECN，以及原 `rollupCost` 与 `explodeBom`。新 reader 直接接调用方事务 query，避免为来源另开快照。

红阶段由主会话先给头与发生项添加可空 `jointCostShare`、并扩展produce枚举，再跑套件。缺失schema导致的建库或首个保存错误没有当作业务红。初轮38项业务红，C13库名长度错误修正后实际进入同库快照验证。

随后接入真实实体、双后端保存/发布/ECN、原成本入口和同快照来源选择。补完持久守卫升级、保存期间编辑/撤回、修订边界与必填字典后，主会话已确认联产核心49/49、v2集成16/16、共享种子6/6通过；保存共同层另有SQLite仓储13/13、EntityStatus69/69通过，完整core和最终门禁待收口。成本错误类独立于按需引擎，原路径重导同一class；BOM公开仅新增既定类型/错误，不增加另一个生产成本入口。

## 已发布输出依赖与草稿导入

保持produce保存期必须引用已发布修订，与importBomDraft不自动发布主数据，两者都不放宽。v2把输出主数据拆到显式dependencies，目标库先准备发布事实，再导入草稿；空库直接导入必须明确失败且零残留。回归同时覆盖未发布依赖、单位不符、v1混入produce、未知版本和JSON number份额。

已有库迁移需要新增两处可空份额列并更新原enum CHECK；SQLite需要保留全量约束的表重建流程，不能只加列。新增的持久库测试先按当前schema前置建库，再植入同名旧守卫并重连，证明守卫替换；它不声称自动完成了旧schema迁移。
