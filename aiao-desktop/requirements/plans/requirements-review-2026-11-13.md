# Aiao Desktop 需求文案与功能完整性评审

- 评审日期：2026-11-13（Asia/Shanghai）。
- 评审范围：`aiao-desktop/requirements/` 下原有的 40 份 Markdown，包含 22 个用户故事、3 个 Epic、需求视图、决策、模板与设计记录。
- 对照快照：分支 `012-web-desktop-product`，提交 `dedffa7fc0e472478bc26b13f21bf189f71a33a9`；评审开始时工作区干净。
- 方法：全文审阅与跨文档核对，抽查产品约定、任务配置和相关实现入口；浏览器文件选择与存储隔离边界另经 Context7 / MDN / HTML 标准核对。
- 性质：产品需求评审与排期建议。下文的“高 / 中 / 低”表示建议处理顺序，不是已复现代码故障的严重等级；建议项不自动成为已立项承诺。
- 验证边界：本次运行了需求结构门禁与门禁测试，没有重跑产品浏览器冒烟、真实账号登录、域名绑定或线上发布。

## 一、总体判断

**🟡 凑合：工程治理比较成熟，产品定义与真实使用闭环还不够。✅ 值得继续做，但下一步应先补数据保障、范围一致性和可验收规则。**

目前文档能回答“代码怎么组织、应用怎么接入、怎样跑验收”，对“主要服务谁、用户完成什么任务、失败以后怎样保住工作成果”的回答偏弱。继续增加应用数量，不能直接弥补这些缺口。

值得保留的部分：

- 故事、Epic、决策、能力矩阵、验收台账分工清楚；22 个故事的状态统计与索引一致，当前为 10 个 Done、12 个 Backlog。
- 已明确前端产品、本地存储、批准应用清单、Orbit 接入和同源游戏的边界，没有把浏览器桌面直接承诺成完整操作系统。
- US-101～103、US-201～204 把验收标准映射到了具体检查项；文档也明确区分源码可见、替身验收和真实线上验收。
- 路线图把旧库升级验收放在 Applications 数据改写之前，这个顺序合理。
- 多浏览器、真实键盘、读屏、数据升级等未证明项已公开登记，没有全部写成“已支持”。

需要纠正的判断：**“能打开所有应用”和“能可靠地完成一项工作”是两种交付口径，当前文案有时把它们混在一起。**

### R01：先明确产品要让用户完成什么

**依据**：[需求首页](../README.md)“在浏览器里还原一套 macOS 风格的桌面”；[US-101](../stories/desktop/ADESK-US-101-desktop-shell-baseline.md)“完整的桌面和内置应用”；[US-203](../stories/application/ADESK-US-203-aiao-code.md)“不离开桌面就能开发”。

这几句话分别指向桌面体验、日常工具和开发工作台，优先级会完全不同。文档没有说明主要用户是哪一类，也没有选出下一版必须完成的端到端任务。

建议补一页简短的产品定义，至少包含：主要用户、前三个核心任务、使用设备与输入方式、版本退出条件、明确不支持的任务。可先围绕以下流程评审，不必全部承诺：

1. 创建一个文件，在 TextEdit 与终端之间处理，保存、关闭、再次打开后内容正确。
2. 从启动入口找到应用，完成一次操作，关闭后再次进入仍能继续工作。
3. 在 Aiao Code 新建项目、修改文件并运行；清楚区分项目数据与桌面虚拟磁盘的数据。

“像真正的系统”“完整桌面”“原生 Mac 应用”适合表达设计方向，不适合作为完成条件。应换成具体任务和明确边界。

### R02：把当前能力与已接受的目标彻底分开

**依据**：

- [README](../README.md)正文说 US-206 尚未交付，术语表却把“代码在打开时懒加载”“经宿主 facade 使用本地库”写成内置应用现状；同一表对内置应用的定义也没有覆盖已经交付的 bundled HTML 游戏。
- 首页“其余应用展示写在代码里的演示内容”没有说明 [US-102](../stories/desktop/ADESK-US-102-local-data-and-real-disk.md) 已交付可修改、可持久化的多个应用数据域，读者容易理解成全部只读。
- [应用管理设计](application-management-design.md)实施切片 5 要求 bundled HTML 通过受信 bridge 接入；[US-206](../stories/application/ADESK-US-206-lazy-app-runtime-and-host-capabilities.md) 和 [D-18](../decisions.md#d-18应用懒加载与宿主系统能力统一) 明确规定本阶段不提供这个 bridge。
- [EPIC-003](../epics/ADESK-EPIC-003.md)“也拖不垮桌面”是绝对保证，故事实际承诺主要是加载与协议失败影响当前窗口，没有资源耗尽或运行卡死的产品级验收。

建议首页分成“已验收能力 / 已立项未交付 / 已知限制”三段。术语只定义概念，不夹带加载策略和实现进度。设计记录跟随 D-18 删除过期 bridge 承诺；“拖不垮”改为能够验收的故障范围。

### R03：文件选择器的技术前提写得过宽

**依据**：[D-12](../decisions.md#d-12集成应用的接入契约)、[US-202](../stories/application/ADESK-US-202-integrated-app-runtime.md) 的范围外、[US-203](../stories/application/ADESK-US-203-aiao-code.md) 的导入文件夹限制，以及 [US-206](../stories/application/ADESK-US-206-lazy-app-runtime-and-host-capabilities.md) 的 filesystem 描述，都使用了“跨源 iframe 弹不出文件选择器”一类说法。

需要区分三件事：

| 能力 | 正确的需求表述 |
| --- | --- |
| `showDirectoryPicker()` / `showOpenFilePicker()` 等句柄 API | 写明具体 API、同源和用户手势限制，以及当前浏览器实测结果；不能概括为所有上传入口不可用。[S1] |
| 普通 `<input type="file">` 文件选择 | HTML 标准及 MDN 的 `showPicker()` 说明明确对 file / color 类型保留跨源例外；实际 Orbit sandbox、用户手势和产品 UI 仍需实测。[S2] |
| 桌面虚拟磁盘的打开 / 保存面板 | 是产品提供的文件授权与交互能力，不等于用户机器上的文件选择器。 |

这不意味着现有 Aiao Code 的“导入文件夹”已经可用，也不意味着本次要换实现。应修正文案，避免后续错误排除普通文件导入方案，或把宿主虚拟文件面板当成所有浏览器文件能力的替代品。

### R04：换域名不能只验收 Aiao Code 的存储分区

**依据**：[US-004](../stories/platform/ADESK-US-004-custom-domain.md) 只验收域名、发布和 Aiao Code 项目 / 登录状态；[US-102](../stories/desktop/ADESK-US-102-local-data-and-real-disk.md) 已把桌面用户数据保存在本站本地存储。

从 `aiao-desktop.pages.dev` 切到 `desktop.aiao.io` 会改变桌面自身的 Origin。OPFS 属于来源私有存储，因此不能假定新域名会自动看到旧域名的桌面文件、备忘录和设置；这是依据浏览器存储规则作出的判断，不是本次实跑结论。[S3]

US-004 应补充：

- 旧站有数据、新站为空时的提示，以及旧站入口保留期限。
- 用户主动导出 / 导入的迁移路径，或明确告知本次只开通新地址、数据暂不迁移。
- 已有新站数据时的冲突策略；迁移失败不破坏任一端数据。
- 分别验收桌面本站数据迁移、Aiao Code 项目可见性、Aiao Code 已有登录状态，不能用“同一存储分区”代替三个结论。

还有一处直接矛盾：US-004 AC#2、技术笔记要求自定义域名“逐文件”核对；[US-003](../stories/platform/ADESK-US-003-cloudflare-pages-deploy.md) 和 D-16 规定该地址只核对入口页，部署独有地址才逐文件核对。抽查 `scripts/deploy/deploy.spec.mjs` 的 `liveTargets` 断言也采用后一口径。应统一为 US-003 的现有承诺，或正式扩大范围。

### R05：持久化需要覆盖失败、退出与恢复

**依据**：US-102 AC 主要覆盖创建、修改、刷新和抹掉；备份 / 导出明确排除；[US-106](../stories/desktop/ADESK-US-106-database-upgrade-path.md) 同样排除备份。当前 [后续方向](../future-requirements.md) 也没有独立的数据备份候选项。

用户已经可以把真实工作成果写进本地库，需求却没有完整回答：

- 保存中、已保存、保存失败分别怎样显示；是否允许失败后继续编辑、重试或导出当前内容。
- Notes 自动保存防抖期间关窗、刷新；TextEdit 未保存时关窗、退出应用或重新打开同一文件，分别怎样处理。
- SQLite 元数据与 OPFS 文件体写入中断时的恢复结果；不是要求跨存储神奇地“同一事务”，而是定义中断前后至少保住哪一份内容。
- 配额不足、存储不可用或 Worker 初始化失败时，怎样说明原因并保留已有数据。D-07 的数据库 IndexedDB 路径不等于整个文件系统已有无 OPFS 的可用方案。
- “抹掉磁盘”到底清除哪些数据：用户文件、各应用记录、系统偏好、游戏 localStorage、终端镜像、远程应用数据应分别说清；确认、取消和执行中断也要有结果。

OPFS 受浏览器配额限制，清除站点数据会删除 OPFS；普通存储与获得持久化授权的存储也有不同的清理条件。[S3][S4] 因此“刷新后还在”应保留为具体测试结论，不能扩写成数据永久安全。

建议新增“本地数据保障”需求，并把保存失败、未保存保护、最小备份恢复放在扩大使用范围之前。

### R06：最终一致不等于用户改动得到保护

**依据**：[US-105](../stories/desktop/ADESK-US-105-multi-tab-sync.md) AC#1 允许两个页面保存同一文件后任意一次写入胜出，胜出规则交给实现定义；正文又承诺“磁盘、系统设置与应用数据”都实时互通。

这能证明副本收敛，却不能回答用户为什么丢掉另一份修改。应用数据也只有设置与文件等少量例子，没有覆盖备忘录、提醒事项等独立数据域。

需要补齐以下规则：

1. 明确选择最后写入生效、冲突提示或另存副本，并定义保存成功与冲突的可见反馈；如果允许覆盖，写进用户可见边界。
2. 覆盖“改名与旧路径保存”“删除与保存”“抹掉与写入”“两个终端扫描回写同一文件”等组合，不能只测试两个按钮同时保存。
3. 规定共享范围：文件和应用记录可共享；窗口布局、焦点、恢复快照是否按标签页分开；Dock 固定顺序是否全局共享。否则 US-104 的布局记录和 US-205 的偏好可能出现相互覆盖。
4. 在不支持实时互通前，明确第二个标签页的用户提示；是否需要临时限制写入，应根据并发实测结果评审，不能直接认定当前已发生库损坏。

### R07：宿主能力需要逐项契约，不能靠能力名称完成验收

**依据**：US-206 AC#8～12 已覆盖拒绝、协议版本、关闭和取消，但 `filesystem` 的“保存位置”、`clipboard` 的手势要求和 `app` 的启动授权还没有可供接入方实现的具体规则。

建议给每个能力补一行契约表：请求名、输入 / 输出、授权主体、影响范围、是否要求用户确认、超时、取消、关闭后行为、稳定错误码。

其中优先定清楚：

- **文件**：打开返回一次性内容还是可复用文件凭证；保存如何提交内容、确认覆盖、检查版本与限制大小；凭证是否绑定实例、何时失效。只返回一个路径不足以同时说明“怎样保存”和“只能访问选定文件”。
- **权限**：区分浏览器 iframe `allow` 权限与桌面 `capabilities`；US-203 已授予直接剪贴板读写，升级时必须核对两层配置，不能把宿主接口的默认拒绝写成对浏览器所有访问路径的保证。
- **菜单与应用启动**：多窗口菜单归属、命令 ID 冲突、单窗口应用重复打开时的聚焦行为；应用 A 是否能让 B 自动执行带文件参数的动作。
- **实例退出**：加载中关闭、重试后旧实例迟到的 ready / RPC、文件面板尚未完成时关窗，均不能让已关闭实例继续写入或重新出现。
- **用户可见反馈**：拒绝、用户取消、超时不能全部变成同一句“失败”；用户取消通常应返回调用方并安静结束。

这些内容应进入 US-206 的契约与 AC，接入方无需阅读宿主内部类也能正确实现。

### R08：应用目录投影要覆盖整个清单生命周期

**依据**：[US-205](../stories/application/ADESK-US-205-application-management.md) AC#3 已很好地覆盖旧包补齐与同名非包条目保留；AC#12 处理应用下线后的 Dock 清理，但没有对应的 Applications 包清理规则。

还需要定义：清单应用改名、图标 / bundle 元数据更新、应用下线、运行类型变更、包被复制到其他目录、旧包缺标识时如何识别所有权。只写“幂等生成”不能决定旧条目应保留、迁移还是删除。

另一个范围冲突是“Applications 显示所有可启动应用”与“同名非包条目保留，对应应用从其他入口打开”。后者是合理的冲突保护，但需要正式声明为前者的例外，并在 Finder 给出可理解的反馈。

保护规则应同时覆盖包内子项和对祖先目录的递归操作；清单下线时只能处理系统拥有的投影，不能据显示名删除用户文件。终端保护若采用回写时撤销，用户短时间看见包消失后的提示与恢复时点也要写清楚。

### R09：旧版构建的降级保护有历史边界

**依据**：US-106 要求“旧构建遇到更高 schema 必须拒绝写库”；D-16 则允许在托管面板回滚到上一部署。

这项要求不能自动约束一个已经发布、当时没有实现版本检查的旧构建。需要定义“允许回滚到哪些版本”，以及从哪个发布版本开始具备降级保护；之前的部署是否禁止作为数据升级后的回滚目标。

建议把以下内容写进升级故事：

- 构建版本、数据 schema 版本、种子版本、应用清单版本各自的用途和兼容关系。
- 支持的升级起点与保留的旧产物 / 夹具标识，不能长期使用无法定位的“上一版”。
- 新表自动补建、旧表字段变化、缺表损坏三种输入分别怎样处理；目前“模拟缺表即不兼容”和“新增实体自动补建”容易混淆。
- 升级中途关闭、失败后重试、两个版本标签页并存的结果。
- 回滚顺序与可接受目标：应用静态产物能回滚，不代表数据 schema 自动可回滚。

该问题应在 US-205 改写已有包之前明确。

### R10：浏览器支持矩阵需要先定义最低门槛

**依据**：[US-005](../stories/platform/ADESK-US-005-cross-browser-smoke.md) 允许“全部通过，或降级项写明原因”；窄屏实现也可以改为提示页，并在以后重写 AC。

这给成本控制留下空间，但缺少最低支持集合，容易变成任何失败都能通过写说明关闭。建议在开发前确定三档：

| 档位 | 最低要求 |
| --- | --- |
| 完整支持 | 指定的桌面、文件、持久化、应用启动与核心编辑流程全部通过，另列终端和游戏能力 |
| 有限支持 | 核心文件流程仍可用；不可用的高依赖能力在入口明确禁用并说明原因，禁止点击后静默失败 |
| 不支持 | 进入产品前给出明确提示，不创建一套看似能保存却无法可靠保存的数据 |

390×844 是否支持窗口拖动与缩放，应现在选定，不能一边保留“可用”承诺，一边允许实现时改成提示页。真 Safari 与 Playwright WebKit 的区分已经写得正确，继续保留。

无障碍已由 US-108 认领，不算完全缺失；建议为文件面板、Dock 拖放等新增 UI 同步补键盘等效操作，避免把全部可达性留到最后一次性修。

### R11：把“更快、即时、稳定”改成能重复测量

**依据**：US-206 比较 initial 体积但没有冻结基线；US-105 使用“数秒”“即时”；[US-008](../stories/platform/ADESK-US-008-smoke-suite.md) 以拆分前耗时的 1.1 倍为上限；US-005 两轮通过后写“没有时序性 flake”。

建议补齐测量环境、基线提交、冷 / 热启动、是否清空用户数据、网络与缓存条件、采样次数、统计值、超时阈值和允许误差。

几个具体改法：

- “无回退的 initial 体积”只能证明打包边界；首屏可交互时间、首次打开应用时间、最小化后资源使用应分别度量，阈值经基线测试后确定。
- US-206 的“首次读取才种子”要在新库与已有库各测一次；不能因为首屏小组件读取数据而又把其他应用实现静态带回来。
- “数秒同步”需设正常可见标签页的时限，并单列后台标签页恢复后的收敛要求。
- US-008 的耗时比较应在同一机器、同一组行为、相同运行条件下采样；新增夹具自检的耗时是否计入也要说明。
- 两轮冒烟通过写成“两轮未出现 flake”，不能推导为不存在时序缺陷。
- 外网被测试路由拦截，不等于用户断网后可以重新加载整个站点；若要承诺离线启动，应另设验收。

## 四、文案怎样改

### 1. 首页可以采用的写法

以下为替换草案；其中产品定位仍需维护者确认，事实范围按当前故事书写：

> Aiao Desktop 是一个在浏览器中运行的 macOS 风格桌面，提供统一的应用入口、窗口交互和浏览器内的本地文件空间。当前主要验收环境是桌面尺寸的 Chromium。
>
> 已交付桌面外壳、可持久化的虚拟磁盘与部分应用数据、终端，以及经 Orbit 接入的 Aiao Code。内置应用包含交互演示；各应用的完整业务能力以对应故事的验收范围为准。Aiao Code 的项目保存在它自己的来源中。
>
> Applications 统一投影、Dock 管理、应用懒加载、统一宿主能力和窗口恢复已立项，尚未交付。当前没有账号与跨设备同步；本地数据的保留边界、备份能力与浏览器支持范围应在数据保障和兼容性故事交付时继续补齐。

### 2. 验收标准改写示例

以下阈值和错误码属于提议，需要立项时确认：

| 场景 | 前置条件与操作 | 建议的可验收结果 |
| --- | --- | --- |
| 保存失败 | 文件已有已保存版本；编辑后人为使文件体写入失败，再点击保存 | 显示“保存失败”；编辑缓冲区保留；磁盘旧内容不变；恢复存储后可重试；成功后才显示“已保存” |
| 跨标签页同步 | 同一上下文、两个可见页面；A 在 Desktop 新建文件，B 不刷新 | 正常测试负载下 B 在约定时限内出现文件；后台恢复和终端扫描另设阈值；超时即失败，不写“数秒内大概出现” |
| 文件授权 | 应用获得用户选定文件 A 的实例凭证，随后请求文件 B，或关闭窗口后再次使用凭证 | A 按授权读写；B 被拒绝；关闭后的凭证失效；取消选择不写磁盘；每种结果有稳定错误码 |
| 域名迁移 | 旧域名有用户文件和备忘录，新域名已有另一份内容 | 明确选择导入策略；迁移后内容按策略保留；失败时两端原内容完整；不假定 Origin 改变后自动共享 |
| 应用下线 | 新版清单移除预装应用，用户复制过其包并自建同名文件 | 系统投影按既定规则清理；用户文件不被误删；Dock 与窗口恢复给出一致结果 |

### 3. 每类文档只承担一种职责

- README：用户、核心任务、当前范围、已知限制和导航。
- Story：用户可见结果、边界、AC 与证据入口；实现类名保留在技术笔记。
- Decisions：已接受的约束、原因、状态与被替代关系；避免混入大段临时排障日志。
- Plans：有日期的设计与实施记录；与 Story 冲突时明确更新或标为历史，不让过期方案继续指导实现。
- Verification：具体版本、环境、命令、结果与产物。检查项数量、运行耗时、部署 ID 放这里。
- Future：可讨论候选，每项写场景和解锁条件，不能直接变成下一版的工作承诺。
