# 用户故事：旧库升级路径

## 作为/我想要/以便

**作为** 长期使用 Aiao Desktop 的人
**我想要** 桌面升级后原来的文件、设置与应用数据都还在，新功能的数据自动补齐
**以便** 发新版不丢数据，也不用担心升级把库「抹掉」。

## 范围边界

### In Scope

- 浏览器级升级验收：用上一版正式构建首次打开并写入数据，再换成当前版本打开，断言数据保留、新数据域按 `seed:<domain>` 标记补写、不覆盖用户改动。冒烟目前每次从空 OPFS 开始，这个盲区在验收台账里已列。
- 升级清单制度化：新增实体或数据域时，必须补建表、补种子、**同时升 schema 版本**（不升版本，下面的「自动补建」和「损坏」就区分不开），并通过升级验收，写进故事的技术笔记与验收台账。
- **版本与兼容基线**：四种版本各管一件事，是否兼容只由第二种判定：
  1. 构建版本：发布出去的产物（短 SHA、Pages 部署编号），用来定位「上一版」与回滚目标；
  2. 库的 schema 版本：库里记录的结构版本，决定库能不能打开、要不要升级、能不能降级；
  3. 种子版本：`seed:<domain>` 标记，只表示某个数据域的初始内容写过没有，不阻止库打开；
  4. 应用清单版本（[ADESK-US-205](../application/ADESK-US-205-application-management.md) 引入）：只管 `/Applications` 的 `.app` 投影是否补齐，不阻止库打开。
- **支持的升级起点**：升级验收的「上一版」必须是可定位的固定标识（提交 SHA 或保存下来的产物），登记在技术笔记的「升级起点」表；每次 schema 或实体变化都追加一行，不写「上一版」这种会漂移的说法。
- **三种输入，三种处理**：①库的 schema 版本低于当前构建，只是缺少新增的实体或数据域 → 自动补建并补种子，不覆盖旧内容（AC#2）；②库的 schema 版本低于当前构建，既有实体的字段变了 → 按迁移步骤升级，没有对应的迁移步骤就按不兼容处理（目前没有发生过，第一次出现时补迁移步骤与 AC）；③库里有 schema 版本记录且与当前构建一致，但结构与实体不符（缺表、缺列），或版本记录存在却无法解析 → 视为损坏，不静默修补、不静默清库（AC#3）。「新增实体自动补建」和「缺表即不兼容」靠 schema 版本区分，不靠有没有缺表。**没有版本记录的库**——此前发布的所有构建建的库都没有这条记录——视为最旧的版本，走 ① 的升级路径（补建、补种子、写入版本记录），不按损坏处理；版本记录从本故事交付的构建起写入，写在哪里（系统偏好表或引擎元数据）实现时定。
- 不兼容时用户可见：库结构损坏或无法升级时给出明确错误与恢复建议，不静默清库；抹掉磁盘仍是显式入口。
- 连续升级可重复：每个版本按同一清单升级，同一库连升两级也成立。
- **升级的原子性**：升级中途被关闭（关标签页、进程被杀）或失败后重试，库要么还是升级前的完整状态，要么是升级后的完整状态，不出现半升级的库（AC#6）。
- **两个版本的标签页并存**：新版本升级了库之后，仍开着的旧版本标签页在下一次写库前必须发现 schema 更高，拒绝写入并提示刷新，不把库写坏——和降级保护是同一套机制（AC#7）。
- **降级保护**：旧构建（例如按 [D-16](../../decisions.md#d-16发布到-cloudflare-pages一键发布命令) 在 Pages 面板回滚到旧部署后）遇到 schema 比自己高的库，必须拒绝打开并给出提示，不写库、不损坏；换回新构建后数据完整。这条只约束本故事交付之后的构建：此前已经发布的构建没有版本检查，要求不到它们，所以要明确回滚目标的边界（技术笔记「回滚目标」）。

### Out of Scope

- 备份、导出与跨设备迁移（原未来方向的既有边界，候选见 [future-requirements](../../future-requirements.md) 的「本地数据保障」）。
- 从第一版 Web Desktop 或其他产品迁移数据。
- 跨大版本的自动数据改写工具。

## 验收标准

| #   | 前置条件                                                                                                           | 操作                                               | 预期结果                                                                     | 状态 |
| --- | ------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------- | ---------------------------------------------------------------------------- | ---- |
| 1   | 用上一版正式构建首次打开，写文件、设置与备忘录                                                                     | 换成当前版本打开                                   | 文件、设置、应用数据原样保留，没有页面错误                                   | ✅   |
| 2   | 旧库的 schema 版本低于当前构建（或没有版本记录，如此前发布的构建建的库），缺少当前版本新增的数据域（模拟新增实体） | 当前版本首次打开                                   | 新数据域按 `seed:<domain>` 标记补写一次，旧域内容不被覆盖，刷新后不重写      | ✅   |
| 3   | 库的 schema 版本与当前构建一致，但结构不符（模拟缺表）                                                             | 打开桌面                                           | 给出明确错误与恢复建议，不静默补建、不静默清库；恢复入口可见                 | ✅   |
| 4   | 升级流程固定                                                                                                       | 连续升级两个版本（v1→v2→v3 各打开一次）            | 每步数据完整，步骤可重复执行                                                 | ✅   |
| 5   | 库的 schema 版本高于当前构建（模拟回滚到具备降级保护的旧构建）                                                     | 用旧构建打开桌面，再换回新构建                     | 旧构建给出明确提示并拒绝写库；换回新构建后数据完整                           | ✅   |
| 6   | 旧库正在升级                                                                                                       | 升级中途关闭标签页（或结束浏览器进程），再重新打开 | 库是升级前或升级后的完整状态之一，数据不丢；再次打开能完成升级，种子不重复写 | ✅   |
| 7   | 新版本已升级库，同一浏览器上下文里的旧版本标签页仍开着                                                             | 在旧版本标签页里保存一个文件                       | 旧版本标签页拒绝写入并提示刷新，库没有被写坏；刷新到新版本后数据完整         | ✅   |

验收证据：第 1、2、3、5 条由 `aiao-desktop-e2e:e2e` 的升级检查组覆盖；验收入口有两条——发布前保留上一版产物、冒烟用旧版建库再换新版打开，以及单测夹具用旧 schema 建库文件再经当前实体打开。第 4 条由同一入口的连升两步覆盖，第 5 条由同一入口先用新构建升级库、再换旧构建打开覆盖。第 6 条在升级过程中注入中断（夹具关闭标签页）后重新打开；第 7 条用同一上下文里新旧产物各一个页面（[ADESK-US-008](../platform/ADESK-US-008-smoke-suite.md) 的多页夹具与新旧产物服务器）。

## 技术笔记

- [D-07](../../decisions.md#d-07系统数据存在本地-sqlite) 的按域种子标记已经支持「新域补写」，缺的是浏览器级验收与升级清单；sqlite-wasm 的建表由 RxDB 处理，但已有库上的变化（新表、新种子）必须在浏览器里实跑过才算数。
- 冒烟当前每次从空 OPFS 开始，升级检查组要单独管理浏览器配置：先旧版建库，再新版打开，中途不抹掉（持久 profile 与新旧产物服务器的夹具见 [ADESK-US-008](../platform/ADESK-US-008-smoke-suite.md)）。
- 「上一版产物」的取得方式（发布流水线保留产物，或 CI 用旧 commit 构建）在实现时定，但新旧两版必须由同一个 origin 提供：OPFS 按 origin 隔离，Pages 的历史部署地址（`<编号>.aiao-desktop.pages.dev`）与生产地址不同源，不能直接拿来当「上一版」。做法是本地静态服务器先托管旧产物建库，再在同一端口切到新产物。
- **升级起点**：登记升级验收用的固定「上一版」，每次 schema 或实体变化追加一行（标识用提交 SHA，或保存产物的位置与摘要）。现在没有登记，实现本故事时写入第一行：当时线上生产部署对应的提交 SHA 与 schema 版本。
- **回滚目标**：静态产物能回滚，不代表库的 schema 会跟着回滚。降级保护从本故事交付的构建（记为 B0）起才存在：

  | 部署                                | 具备降级保护 | 数据被更高 schema 升级过之后，能否作为回滚目标               |
  | ----------------------------------- | ------------ | ------------------------------------------------------------ |
  | B0 之前的所有部署（含交付前的线上） | 否           | 否：旧构建会直接打开新结构的库，行为没有保护                 |
  | B0 及之后                           | 是           | 是：遇到更高的 schema 会拒绝写库并提示，换回新构建后数据完整 |

  在库的 schema 还没有被升级过之前，回滚到 B0 之前的部署是安全的；一旦某个部署把库升到更高的 schema，B0 之前的部署就不能再用作回滚目标。回滚前先对照这张表，再在 Pages 面板操作（[D-16](../../decisions.md#d-16发布到-cloudflare-pages一键发布命令)）。
