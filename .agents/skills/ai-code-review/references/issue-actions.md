# 单问题修复、复核与异议

下文 `ai-review` 指 `node scripts/ai-review/ai-review.mjs`。

## 加载记录

- `ai-review find-issue <完整 ID 或前缀>` 会查当前检出位的根 `requirements/reviews/` 和各应用的旧记录目录。退出码为 0 表示唯一匹配；否则列出全部候选，不任选一个。
- 读完整记录及全部事件，核对 `found_*` 字段和最近一次复核的快照。
- 记录描述它所在那棵树的代码。处理别的分支上的问题，就到检出了该分支的检出位里找。那棵树里没有记录、问题却存在时，按评审流程在那里新建，并用 `related_findings` 写明与哪条记录同根因。
- 证据无法复现或代码已经不同时，先记一次复核结果，不套用陈旧补丁。

每个动作都写真实的 AI 或人工身份与角色。评审、修复、复核可以由不同会话或模型完成，也可以由同一个完成，按步骤如实记录；不以多数意见代替证据。

## fix：修复单个问题

1. 按证据复现，先写能暴露问题的回归测试并确认红灯。确实无法自动复现的环境边界如实记录，不编造结果。
2. 只改这个根因必要的代码、三框架绑定与测试。为满足同一契约需要跨项目改的，列清关联项目，不顺手处理别的问题。
3. 用相关的 Nx targets 验证，记录命令、结果和没跑的部分。并发假失败按仓库规范串行复跑，不靠调高并行掩盖。
4. 回归转绿且检查通过，才改为 `Fixed`；事件写修复前后的快照、改动路径、行为变化和验证结果。检查没过就保持原状态，只追加一个 fix 事件，写明失败与剩余工作。
5. 用户同时要求复核并关闭时，可以接着 verify。同一模型可以做，但两步的证据和角色分开记。

授权只覆盖这个问题及必要的关联改动，不自动逐条修其他记录。修复改了代码，下一次增量评审会重审这些文件；fix 本身不登记覆盖。发现原结论有误时转为 dispute，不为了「完成修复」写无意义的代码。

## verify：单独复核

对照原证据、修复或异议记录与当前代码，核对触发路径、回归测试以及相关框架与消费者，再按 [CONVENTIONS](../../../../requirements/CONVENTIONS.md)「状态定义」一节的转移表改状态：

- `Fixed` 的修复有效且必要验证通过 → `Resolved`；修复无效或回归失败 → `Open`。
- `Open` 的问题因其他改动消失（代码被删、别人修了）→ `Resolved`，写明是哪次改动。
- 原发现不成立且有反证 → `Dismissed`，保留反证。
- 维护者明确决定接受风险或延期 → `Accepted`，写下维护者决定的出处、风险和再评估条件。AI 不能以「影响小」自行接受。
- 证据相互矛盾或不足 → 维持原状态，列出待裁决点或缺口。

复核事件写明复核时的快照。状态只对这个快照成立，不表示已经合入 main，也不表示别的分支修好了。

## dispute：提出不修异议

先复核原断言，再追加反证、对应的代码与测试、不修的理由和建议结论，状态改为 `Disputed`。

要区分「问题不存在」「触发前提不成立」「已被上游保证」和「缺陷成立但希望延期或接受风险」，后两种不能写成修复。原发现和之前的处理证据都保留；只有复核结论或维护者决定满足转移表，才能结束异议。

## 事件与并发

- 事件 ID 用 `ai-review new-id --prefix EV` 生成。每个事件至少写时间、操作、执行者、输入与输出快照、状态转移、结论、验证与剩余事项；取不到的身份字段写 `unknown`。
- 当前状态写在 frontmatter，依据写在正文事件里，两者保持一致。正文对问题和根因的描述可以修正，已有事件不改写、不删除。
- 写前用 `git hash-object <记录>` 记下摘要，写入前再核对；变了就重读，合并双方事件后再写。出现语义冲突时保留双方结论，暂停这个问题的关闭，继续做其他不依赖它的已授权工作。
