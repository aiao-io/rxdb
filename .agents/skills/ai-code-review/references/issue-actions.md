# 单问题修复、复核与异议

## 加载同一份问题记录

在根及现有应用需求的 `reviews/` 中按完整 ID 或唯一前缀定位，读取整个记录及全部处理事件。
核对 project、branch、range、base 和证据快照。显式选择其他分支时先核对该分支是否也存在问题，查找并续用其既有同根因记录；确有问题且尚无记录才独立建档并关联，没有问题不建文件。没有明确要求时沿用问题所在分支。
使用匹配分支的 checkout 或隔离工作区做修复，保留当前工作区无关改动。证据无法复现或目标版本不一致时先记录复核结果，不套用陈旧补丁。

所有动作都记录真实 AI/人工身份。记录允许评审、修复、复核分别由不同会话或模型完成；不要求回到原评审模型，也不以多数模型意见替代证据。

## fix：修复单个问题

1. 根据证据复现，先写能暴露问题的回归，按仓库 TDD 要求确认红灯；确实无法自动复现的环境边界如实记录，不编造测试结果。
2. 只改此根因必要的代码、框架绑定与测试。需要跨项目修复以满足同一契约时列清关联项目，不扩大为其他问题清理。
3. 通过发现到的 Nx targets 执行相应检查，记录命令、结果与未运行的部分。并发假失败按仓库规范复验，不调高并行掩盖。
4. 记录修复前后 SHA 或工作区快照、文件与行为变化、回归证据；补丁就绪后状态为 `Fixed`。若检查未过，保留失败与剩余工作，不能写成 Resolved。
5. 若本次指令同时要求验证并关闭，可继续 verify；同一模型可执行，但各步骤的证据与角色分别保留。

授权只覆盖本问题及必要关联改动。不要自动逐条修复其他报告，也不要更新项目的完整评审检查点。
发现原结论有误时转入有证据的 dispute，不能为了“完成修复”引入无意义代码。

## verify：单独复核

比较问题原证据、修复或异议记录与当前分支实际代码，核对触发路径、回归和相关框架/消费者。
修复有效且必要验证完成时改为 `Resolved`，追加验证者、快照与结果；仍成立则保持 Open 或重开；缺证据维持未关闭并列明缺口。
异议有充分反证、问题确实不成立时可改为 `Dismissed`，保留反证与适用指纹；相互矛盾的证据保留 `Disputed` 并呈现待裁决点。
已确认缺陷但主动不修属于 `Accepted`，必须记录维护者既有明确决定、风险与再评估条件；AI 不能以自认为影响小代替该决定。
关闭只对该记录的分支与证据成立，不表示代码已合入 main 或其他分支已修复。

## dispute：提出不修复异议

先复核原断言，追加反证、对应代码/测试、选择不修的理由及建议结论。
区分“问题不存在”“触发前提不成立”“已被上游保证”与“缺陷成立但希望延期/接受风险”；后两者不能伪装成修复。
提出异议时设为 `Disputed`。保留原发现和之前处理证据；只有复核或维护者决定满足状态规则后才能终结。

## 事件与并发

按模板追加事件，至少包含 eventId、action、actor、时间、输入/输出快照、状态转移、修改/异议、验证及未解决项。未知身份字段写 unknown。
当前状态在 frontmatter，证据在正文事件；更新必须保持两者一致。记录事件为追加式，正文的问题与根因可修正，但不能抹掉不同模型已经提供的证据。
写前重新核对原文件摘要；别人已经追加事件就重读并归并，不能覆盖。发生语义冲突则保留双方结果，暂停该问题的关闭动作，继续其他不依赖它的已授权工作。
