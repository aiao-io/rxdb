# 协作首版共享契约

本页定义 ADMIN-US-201～213 共用的状态与并发规则，具体交付范围和验收标准仍在各故事中；调整本页时必须同步对应 AC。这些规则是验收依据；实现与证据见 [协作记录](plans/collaboration-implementation.md)，不能由契约文本本身推定功能完成。

## C01：身份、初始化与邀请

归属：[201 会话](stories/collaboration/ADMIN-US-201-supabase-email-otp-session.md)、[202 团队](stories/collaboration/ADMIN-US-202-team-membership-workspace.md)、[204 本地上下文](stories/collaboration/ADMIN-US-204-local-context-explicit-import.md)。

本地团队上下文键包含真实用户、团队、应用和任务/分支。匿名本机模式与团队模式分开；既有匿名数据、连接前备份恢复入口和数据标识继续保留。登录不自动上传匿名库，也不把匿名内容改归登录用户。

### 会话与离线访问

“热续作”指当前进程已经在线验证身份、成员关系并打开该任务；“冷启动”包括刷新、新标签页和重新打开应用。缓存权限只用于限定本机可恢复范围，不作为服务端授权。

| 场景                                        | 本机读取与保存                                                          | 云端操作与恢复                                                          |
| ------------------------------------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 在线且会话有效                              | 验证成员关系后打开授权上下文                                            | 每个请求重新授权                                                        |
| 热续作中断网，会话有效或自然过期            | 可继续当前已解锁任务的本地读取、保存和排队；不能扩大到未验证的团队/任务 | 暂停上传；联网后先刷新/认证并重新验证权限，再查询待发送请求的结果及重试 |
| 冷启动离线，缓存会话仍未过期                | 仅恢复该用户上次在线验证、已缓存且未被显式锁定的上下文                  | 不发云端请求；会话自然到期后可按热续作规则继续当前任务                  |
| 冷启动且会话已过期、缺失或无已验证上下文    | 保留但锁定团队草稿，不展示其内容；显示登录入口                          | 在线刷新会话或重新认证、确认同一用户仍有权限后解锁                      |
| 主动退出、切换账号或已收到成员/任务权限撤销 | 立即锁定原团队上下文，保留其草稿；其他账号不能读取、接管或发送原队列    | 停止原订阅和未发出的请求；同用户重新认证且有权后才可恢复                |

离线设备无法即时获知云端撤权，不承诺远程抹除已缓存数据。已发出的请求可能已被服务端提交；退出后的迟到回执不得写入新账号视图，原用户恢复后按幂等键查询结果，不能假定取消网络请求等于撤销事务。

### 首次初始化

部署/验收前由可信服务端命令或种子迁移显式指定团队键、应用键及已验证的初始管理员用户 ID，一次事务建立团队、管理员成员与六类操作权限、空的默认共享分支和版本化审批策略。默认策略要求至少一名非 PR 作者的审核者批准；初始管理员先邀请审核者，或通过有审计的策略变更启用免审批模式。

初始化使用稳定幂等键；重复执行返回已有标识，参数与已有归属不一致则失败，不重置权限或策略。任一步失败整笔回滚。普通登录者不能抢占管理员，浏览器不持有初始化凭据。初始化只建空共享分支及治理元数据，不导入样例业务数据；之后业务数据只能走 PR 合并入口。首版不提供自助创建组织或团队的管理界面。

### 邀请消费

邀请保存团队、服务端按认证提供方规则规范化的目标邮箱、拟授予权限、邀请人、有效期、令牌摘要、版本和状态。不得自行去掉邮箱的点号或 `+` 后缀来扩张接受者集合。只有服务端确认的、当前已验证邮箱与邀请目标匹配的登录用户可接受；URL、表单邮箱和客户端缓存都不能作为身份凭据。

接受邀请在单个服务端事务中验证身份、待接受状态、有效期、邀请人当前成员管理权及可授予权限范围，并建立唯一的团队/用户成员关系、消费邀请、记录审计。错误账号或未验证邮箱不消耗邀请，不泄露团队业务内容，提供切换账号后重试入口。已有成员接受邀请不隐式提升权限；权限变更另走成员管理。

同用户重复接受已成功的邀请返回原结果，不重复建成员；如果成员后来被移除，旧邀请不能恢复关系。重发原子撤销旧版本并签发新版本，旧链接立即失效。接受、撤销、重发按服务端事务提交顺序裁决：只有一个待接受版本可被消费；若接受先完成，之后的撤销不能反向删除成员，须另行执行移除成员并审计。

## C02：保存、提交与同步覆盖范围

归属：[205 任务草稿](stories/collaboration/ADMIN-US-205-task-draft-continuous-editing.md)、[206 同步](stories/collaboration/ADMIN-US-206-draft-sync-offline-recovery.md)、[207 PR](stories/collaboration/ADMIN-US-207-data-pr-lifecycle.md)。

| 状态             | 持久化对象                          | 可以声称完成的动作                               |
| ---------------- | ----------------------------------- | ------------------------------------------------ |
| 编辑器未保存输入 | 当前表单/单元格缓冲区               | 尚未本地保存，不能计入同步内容                   |
| 已保存、未提交   | 当前任务 working tree，含跨实体变更 | 已保存到本机，刷新可恢复                         |
| 已提交、待上传   | 不可变提交及父提交关系              | 已形成同步快照，远端尚未确认                     |
| 已上传           | 服务端已接受的具体提交及回执        | 该版本已同步至任务分支；不代表较新本地修改已同步 |
| 已合并           | 原子合并产生的共享版本              | 对应候选结果已进入共享数据                       |

首版的“同步”命令先检查编辑器缓冲区；有未保存输入时要求保存全部或取消同步，不静默忽略输入。随后在本地事务中把当前任务全部已保存变更形成一个不可变提交，保存父提交和待发送记录，再上传；离线且本机上下文已解锁时可以完成前半段并排队。普通“保存”不生成提交、不上传。

空工作树不制造空提交；已有待上传提交时重试原提交，没有待上传提交时显示无需同步。上传期间的新保存留在下一份工作树中；确认 S 已上传时仍显示 S 之后的修改待同步。失败和超时重试复用提交 ID、内容和操作幂等键，不能重新生成同内容提交。请求审核明确显示服务端已接收的来源版本，并提示本机尚未纳入的修改。

平台 `commit()` 的整单提交能力可以复用；通用实体 push/pull 不等于提交图复制。任务同步还需产品协议保存提交 ID、父子关系、原作者与内容摘要，不能将拉取到的实体变化重新记成拉取者的原始提交。

## C03：同一任务的双设备分叉

归属：[206 同步](stories/collaboration/ADMIN-US-206-draft-sync-offline-recovery.md)。这与 [211](stories/collaboration/ADMIN-US-211-three-way-conflict-preview.md) 的“任务分支对共享分支”合并是两种并发问题。

上传包含团队/应用/任务、`expectedRemoteHead`、提交链、稳定操作 ID。首次上传用明确的空头标记；提交的父链必须从预期头延续。服务端在同一事务中验证权限、提交身份与内容、父链和远端头，持久化提交并比较更新任务头；不允许强制推送覆盖。首次接收的新提交作者必须匹配真实会话；引用已有祖先时使用服务端原记录，不能由客户端改写作者。

- 远端头与预期一致且父链合法：接受并返回已接收头。
- 相同操作和相同提交已接受：返回原回执及当前远端头，不重复建提交；即使远端后来推进，也能确认该提交已到达。相同 ID 搭配不同内容或父链必须拒绝。
- 另一设备已推进同一任务：拒绝陈旧上传并返回可见的当前头；保留远端已接受提交、本地分叉提交、工作树和未保存输入，不自动覆盖或重设父节点。当前设备不得显示“全部已同步”。

首版恢复路径为显式“另存为新任务”：先保留并提交本地已保存变化，以原提交链创建新的任务分支，记录原任务来源并保留提交 ID、祖先和原作者；服务端原子创建分支并幂等返回新任务。新任务使用新的上传操作 ID；网络失败可重试。原任务及其 PR 继续指向已接受的远端头，新任务需要新 PR。用户随后可切回原任务拉取远端版本。首版不提供同任务分叉自动合并或强制覆盖。

远端通知只提示变化；只有不存在未保存输入、未提交变更或待上传提交时才允许直接快进本机任务。否则先走上述保留/另存流程；通知到达不能替用户丢弃内容。

## C04：最终合并候选版本

归属：[210 检查](stories/collaboration/ADMIN-US-210-diff-checks.md)、[211 冲突预览](stories/collaboration/ADMIN-US-211-three-way-conflict-preview.md)、[209 审核](stories/collaboration/ADMIN-US-209-review-approval.md)。

最终预览由服务端产生不可变的 `candidateId`，关联团队/应用/PR、共同起点 B、来源任务头 S、目标共享头 T、显式冲突选择、最终新增/修改/删除结果摘要、schema 版本和检查/审批策略版本。可读预览、检查结果、批准和最终写入都指向同一候选；客户端提交的候选内容或摘要不具有权威性。

PR 可以在检查未完成时请求审核和讨论，但仅对已解决全部冲突、检查通过且仍为当前版本的候选接受“批准”。冲突选择只有任务编辑者或目标分支合并者可提交；仅有审核权的人不能修改候选内容。候选创建/替换使用预期 PR 修订号，拒绝并发覆盖，记录操作者与选择；离线选择只是本机草稿，恢复后必须经服务端验证。

B、S、T、冲突选择、最终结果或相关规则版本任一变化都使候选、检查及批准过期；重新生成候选、检查并审核。即使来源提交没有变化，也不能沿用旧批准。新版本不自动解除必须处理的线程和“要求修改”；历史候选仍只读可追溯。无法找到可信共同起点时阻塞预览和合并，不猜测或降级为整表覆盖。

回归例：B 的价格为 100，S 为 120，T 为 110。审核者批准选择 120 的候选 C1 后，合并者把冲突结果改成 999，必须得到 C2；C1 的批准和检查不能授权 C2。目标头、规则在预览后变化同样处理。

## C05：审核结果聚合

归属：[209 审核](stories/collaboration/ADMIN-US-209-review-approval.md)、[208 讨论](stories/collaboration/ADMIN-US-208-data-pr-discussion-comments.md)。

每名审核者在一个 PR 中有服务端排序的审核历史和当前有效结论；操作带幂等键及该审核者的预期结论修订号。并发旧请求被拒绝，重复请求返回同一记录，不靠客户端时间或最后到达的覆盖决定结论。

| 条件                                                                       | 当前聚合结果                                                             |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 任一未解除的“要求修改”存在                                                 | 需要修改并阻塞合并，其他人的批准不能抵消                                 |
| 没有阻塞意见，至少一名非 PR 作者、当前仍具目标分支审核权的成员批准当前候选 | “至少一人批准”条件满足                                                   |
| 没有阻塞意见，但只有过期批准或批准人已失去审核权                           | 缺少有效批准                                                             |
| 团队启用免审批模式                                                         | 只跳过批准人数门槛；仍检查要求修改、必须处理线程、候选、检查、权限和版本 |

同一审核者可以在当前候选检查通过后用新的批准解除自己的“要求修改”。新候选不会自动清除该阻塞；原审核者已离开或意见需撤销时，仅具成员管理及审核权限的成员可执行单独的“撤销阻塞意见”，必须填写理由并保留审计，不能伪造原审核者批准。只有作者、评论或合并权限不足以执行该操作。已撤销的意见不自动产生批准。

成员撤销或审核权限收回立即使其已有批准失效；之后恢复成员关系或审核权也必须重新批准，不能复活旧记录。遗留的“要求修改”仍待显式解除。批准自己的 PR 不计入首版批准门槛。关闭/重开保留审核历史；重开时对当前候选和权限重新验证，不能直接恢复绿色状态。

## C06：共享数据唯一写入入口

归属：[203 权限](stories/collaboration/ADMIN-US-203-permission-server-isolation.md)、[212 合并](stories/collaboration/ADMIN-US-212-authorized-atomic-merge.md)、[213 审计](stories/collaboration/ADMIN-US-213-history-audit-restore.md)。

业务客户端对共享业务表、共享头和合并审计的直接插入、更新、删除一律拒绝，管理员或有合并权的普通会话也不例外。任务同步、导入、恢复不能写共享分支；没有暴露给前端的“有权限直写”替代通道。

最终合并以 PR、`candidateId`、预期来源/目标头和幂等键请求服务端。事务重新确认真实身份、权限、PR 可合并状态、候选及规则仍当前、最终结果检查通过、有效批准聚合和必须处理线程；服务端重算/核对候选结果并仅写入该结果。重新计算得到不同内容时拒绝，不能在事务中偷偷换用新的冲突值。

来源头、目标头、PR 当前候选、策略、权限、审核及线程状态的校验与写入必须具备同一原子裁决顺序；并发撤权、新增阻塞意见、任务追加提交或另一 PR 合并要么先发生并阻塞本次，要么在本次提交后生效，不能在校验与提交之间被遗漏。业务数据及级联变更日志、目标头、合并提交、PR 状态、候选关联、审批规则快照和审计一起提交或回滚。

重复已成功请求先验证调用者当前有权读取结果，再返回原回执，不因目标头已推进而重新合并；同一幂等键配不同候选/参数必须拒绝。超时后可查询最终结果；未知结果不能显示成功。审计必须能从共享版本还原到实际合并候选、批准/阻塞处理历史、原提交作者及真实合并人。
