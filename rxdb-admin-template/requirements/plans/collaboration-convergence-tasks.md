# 协作后端收敛实施计划

> 日期：2026-11-17。状态：方向已定、尚未实施。决策见 [D-09](../decisions.md#d-09协作后端收敛方向)；实施故事为 [ADMIN-US-218](../stories/collaboration/ADMIN-US-218-delta-commits-bounded-cost.md)～[ADMIN-US-221](../stories/collaboration/ADMIN-US-221-task-drafts-on-working-tree.md)，上线验收仍由 [ADMIN-US-217](../stories/collaboration/ADMIN-US-217-production-deployment-operations.md) 承接。

目标不变：一套服务端权威、像 Git 一样「任务分支 → 提交 → 数据 PR → 绑定候选的审批 → 原子合并」的协作后端，并以最小成本接入 Supabase。本计划只改变存储、传输与部署形态；ADMIN-US-201～216 的用户可见行为、[共享契约](../collaboration-contract.md) 与领域引擎的裁决规则保持不变。

## 1. 现状问题

量级示例：2000 条记录、每条约 300 字节，一个提交约 600 KB；到第 100 个提交，工作区行约 60 MB。此后每条评论都要克隆并整值重写约 60 MB（JSONB 无法局部更新，WAL 也按整值产生），每个在线成员每次刷新都要下载 60 MB 以上。现有的 2 MiB 上限只约束上传，不约束快照下发。整行状态也使命令入口无法放进 Edge Function（每个请求 2 秒 CPU、256 MB 内存）。

## 2. 目标结构

```text
三端应用
  ├─ 团队库（RxDB + working-tree，ADMIN-US-221 之前为现有 IndexedDB 任务存储）
  ├─ Supabase JS：会话 · RLS 分页读取 · Realtime Broadcast 失效通知 · Realtime Presence
  └─ 命令入口（唯一写路径）：Edge Function，或等价的 Node 服务
        └─ 纯 TypeScript 领域引擎（裁决规则与测试不变）
              └─ Supabase Postgres
                    ├─ admin_private：成员、策略、提交与 ChangeSet、引用、候选、回执
                    └─ public：RLS 只读投影（共享记录、PR、提交元数据、审计、通知）
```

原则：

1. 服务端权威不变：所有写入只经命令入口与领域引擎，客户端不直写任何业务表，包括评论。
2. 提交改为字段级 ChangeSet，形状对齐平台 working-tree 的 `CommitChangeSet`，命令成本只与本次改动有关。
3. Supabase 擅长的交给 Supabase：读取用 PostgREST + RLS，通知用 Broadcast，在线状态用 Presence，身份用本地 JWT 校验。
4. 不把引擎改写成 PL/pgSQL；三方字段级合并继续由产品的纯函数 `mergeRecords` 完成。
5. 客户端在平台补齐「导入远端提交」等能力之后再切到 working-tree，此前先切换协议、不切换本地存储。

## 3. 存储与命令模型（ADMIN-US-218）

**提交协议。** 提交为 ChangeSet 列表，每项含 `namespace`、`entity`、`entityId`、`operation`（insert / update / delete）、`patch`、`inversePatch`：insert 的 patch 为整行，update 只含变更字段，delete 的 inversePatch 为整行。提交 ID 使用 UUIDv7，与平台一致；服务端按规范化 ChangeSet 重算 SHA-256 内容指纹并与客户端声明比对，ID 不再承担内容寻址。

**表结构（示意）。**

| 表                               | 内容                                                                       | 写入方式               |
| -------------------------------- | -------------------------------------------------------------------------- | ---------------------- |
| `workspaces`                     | 名称、修订号、schema 版本、策略版本、成员代际                              | 治理行，裁决顺序的起点 |
| `members` / `invitations`        | 权限、启用状态、已验证邮箱；邀请摘要、版本、有效期                         | 成员命令               |
| `policies`                       | 版本化的审批阶段                                                           | 只追加                 |
| `commits` / `commit_changes`     | 提交元数据（父 ID 数组、作者、消息、指纹）与 ChangeSet                     | 只追加                 |
| `refs`                           | 共享分支与任务分支的头及修订号                                             | CAS 更新               |
| `shared_records`（public）       | 共享头按记录物化的行                                                       | 仅合并事务             |
| `prs` / `candidates` / `reviews` | PR 状态与修订号；不可变候选（B/S/T、冲突选择、结果、检查、规则版本）；审核 | PR 命令                |
| `threads` / `comments`           | 讨论与字段定位                                                             | 讨论命令               |
| `notifications`                  | 按用户分页、已读状态                                                       | 只追加 + 已读标记      |
| `operations`                     | 幂等键、操作者、请求指纹、结果                                             | 按保留期清理           |
| `audit`（public 投影）           | 审计事件，只追加；后续按月分区                                             | 只追加，不删除         |

引用推进统一使用比较交换：

```sql
UPDATE admin_private.refs
SET head = $new_head, revision = revision + 1
WHERE team_id = $1 AND app_id = $2 AND ref = $3 AND head IS NOT DISTINCT FROM $expected_head
RETURNING revision;
```

**锁顺序。** 整行锁换成固定顺序的细粒度锁，保留 D-06「授权与数据变更同一裁决顺序」：

1. 治理行：普通命令 `FOR SHARE`，成员、邀请、策略变更 `FOR UPDATE`。撤权与批准、合并因此互斥。
2. PR 行：PR 相关命令 `FOR UPDATE`。
3. 引用行：上传锁任务引用，合并先锁共享引用再锁任务引用。
4. 读路径一律不加锁、不写库；过期数据在写事务或定时任务中清理。

**合并输入只取改动过的记录。** 目标 T 取自物化的 `shared_records`；合并基 B 的值由 T 反向应用共享分支上 B 之后各合并提交的 `inversePatch` 得到，只针对改动过的记录；来源 S 的值由 B 加上任务分支在 B 之后的 ChangeSet 得到。合并成本因此与「合并基以来双方改动的记录数」成正比。候选、冲突与字段级合并语义沿用现有 `records.ts` / `governance.ts` 及其用例。

**保留与分页。** 回执保留 30 天：期内用原操作 ID 重试返回原结果；提交按 ID 去重，过期后重试也不会重复建提交；客户端超过保留期的待确认请求停止自动重试、交给用户确认。通知与审计分页读取；审计只追加、不删除，归档另行设计。

**元数据清单。** 由应用的 RxDB 实体定义（`ENTITIES` 的实体元数据）生成版本化的 schema 清单：实体、字段类型、必填、唯一、关系与数值约束。清单随初始化登记，工作区记录 `schemaVersion`。服务端按清单校验 ChangeSet，取代 `records.ts` 中写死的资产规则；特殊业务检查保留扩展钩子。

**读接口过渡。** 在 ADMIN-US-219 接入 RLS 读取之前，快照接口拆为：工作区摘要（成员、策略、引用、PR 列表元数据、当前用户的未读通知）、PR 详情（当前候选、冲突、检查、审核、线程）、提交元数据分页（不含 ChangeSet）、PR 变更记录、审计分页。版本通知后只刷新摘要和当前打开的 PR。

**预算。** 以 `admin-collaboration:benchmark-growth` 度量（1000 条共享记录、每个提交改 5 条），对照第 3.1 节的基线：

- 普通命令：200 个提交时耗时不超过 50 ms，且与 10 个提交时相差不超过 20%（基线 2.7～4.4 s，随提交数线性增长）。
- 单次普通命令产生的 WAL 不超过 50 KB（基线 6.8 MB）。
- 摘要响应不超过 50 KB，且不随提交数增长（基线快照 26.8 MB）。
- 改动 100 条记录的上传或合并，服务端耗时在 300 ms 以内。
- 10000 条共享记录、1000 个提交的规模在阶段 3 复测，确认 Edge Function 的 CPU 与内存余量。

## 4. Supabase 原生化（ADMIN-US-219、ADMIN-US-220）

- **读取**：public 下的 RLS 只读投影直接经 PostgREST 分页查询；跨团队、跨应用返回空。自定义 API 只保留命令写入。
- **通知**：命令事务内调用 `realtime.send()`（或 `realtime.broadcast_changes()`），发往私有频道 `collab:<team>:<app>`；`realtime.messages` 上的 RLS 只允许该团队/应用的可读成员订阅。载荷只含修订号、类别与 ID，客户端据此拉取变化部分。替换现有对 `admin_workspace_versions` 和 `admin_presence` 的 Postgres Changes 订阅：后者对每次变更、每个订阅者都要执行一次 RLS 查询。
- **在线状态**：改用同一私有频道的 Realtime Presence，删除 `admin_presence` 表与每 15 秒一次的 presence 命令。撤权时服务端广播撤权事件，各端移除该成员；被撤成员的客户端锁定团队上下文，频道在其令牌刷新时重新鉴权。
- **身份**：启用非对称 JWT 签名密钥，命令入口用 `getClaims()` / JWKS 本地校验，稳态下不再逐请求访问 Auth。邮箱验证只在接受邀请时向 Auth 确认一次，结果写入成员行。缩短 access token 有效期，以收窄账号删除后旧令牌仍可用的窗口；团队级撤权仍由每条命令的成员校验即时生效。
- **部署形态（ADMIN-US-220）**：命令入口打包为 Supabase Edge Function，与 Node 入口共用同一引擎模块和同一套契约测试。经 Supavisor transaction 模式连库（事务内 `FOR UPDATE` 可用，关闭预编译语句），使用只授予协作表权限的专用数据库角色，密钥只来自函数环境。资源预算按 2 秒 CPU / 256 MB 留出余量。

**实施状态（2026-11-18）：** 读取、通知、在线状态与身份四项已由 [ADMIN-US-219](../stories/collaboration/ADMIN-US-219-supabase-native-read-realtime.md) 在本地隔离 Supabase 栈落地并验收（证据见故事）。与上文的偏差：

- 读取用 `security_barrier` 只读视图加只读函数，而不是把私有表直接移到 public；提交图推导放在函数里，不受 PostgREST `db-max-rows` 截断，部署需设 `db-max-rows ≥ 500`。
- 版本行保留，作为修订号序列与跳号补齐的依据；广播与递增版本行在同一条语句里，是提交前的最后一步。
- 网络中断（无 FIN）时，在线成员由 Realtime 空闲超时移除，本机实测约 59 秒，原实现是 45 秒心跳过期。
- 本地验签用 `node:crypto`，ADMIN-US-220 做 Edge Function 时需确认 Deno 兼容或改用 WebCrypto。

**部署形态实施状态（2026-11-18）：** [ADMIN-US-220](../stories/collaboration/ADMIN-US-220-supabase-only-deployment.md) 已在本地落地：fetch 风格的处理函数由 Node 与 Edge 两个入口共用；Edge 产物以 esbuild 打成自包含 ESM，驱动用打进产物的 `pg`；所有事务以 `SET LOCAL` 设时限，不依赖会话级状态；专用角色 `admin_collaboration` 只授协作所需权限，广播经 SECURITY DEFINER 函数。Edge 侧的身份变量改名为 `ADMIN_JWKS_URL` / `ADMIN_JWT_SECRET` / `ADMIN_JWT_ISSUER`，因为 Supabase 不接受 `SUPABASE_` 前缀的函数密钥。最坏情形（一个 PR 改动全部 10000 条记录后合并）CPU 为限额的 71%，超限时改用 Node 入口，或把批改拆成多个 PR。

## 5. 与 rxdb-plugin-working-tree 结合（ADMIN-US-221）

平台的 [working-tree](../../../packages/rxdb-plugin-working-tree/README.md)（[epic-006](../../../requirements/epics/epic-006-working-tree-commits.md)）把「未提交改动」和「提交历史」做成了数据库内的一等概念，三端绑定对称（`useWorkingTree` / `useWorktrees`）。2026-11-17 核对源码的结论：**客户端可以结合，服务端不能直接复用**。

**可直接复用：**

| 能力                                                       | 用于产品的位置                             |
| ---------------------------------------------------------- | ------------------------------------------ |
| 写捕获、`status()` / `diff()`                              | 未保存 / 已保存 / 已提交状态与本地差异     |
| `commit()`：整单提交、修订号 CAS、操作 ID 重放、空提交拒绝 | 「同步」前半段（C02）                      |
| `commits$` / `commitChanges()`                             | 待上传提交与其 ChangeSet，作为上传 outbox  |
| `createBranchFromCommit()`                                 | 「另存为新任务」（C03）                    |
| `restore()`：历史内容作为新的未提交变更                    | 版本恢复草稿（D-06 第 6 条、ADMIN-US-213） |
| UUIDv7 提交 ID、SHA-256 `contentFingerprint`               | 与第 3 节协议一致                          |

**平台缺口**（远端 push/pull 与冲突裁决目前是 epic-006 的非目标，需要在根 requirements 另行立项）：

| 能力                                                              | 现状                                                | 规模     | 不补的后果                                       |
| ----------------------------------------------------------------- | --------------------------------------------------- | -------- | ------------------------------------------------ |
| 导入远端提交：保留 ID、父链、作者、指纹，并把分支头快进到外部提交 | 提交 ID 在本地生成，父提交只取当前 HEAD，不伪造作者 | 新能力   | 换设备续作丢失原提交身份，违反 ADMIN-US-206 AC#2 |
| 从导入的共享提交建任务分支                                        | 只能从本地 change 或当前 HEAD 可达的提交分叉        | 随上一项 | 需维护本地/服务端提交 ID 映射，作者记成系统账号  |
| 合并类提交（多父）                                                | `parentIds` 已是数组，但没有 merge 种类，写路径单父 | 小改     | 共享分支的合并历史无法原样导入                   |
| `discard()` / `restore()` 回写业务表                              | 只回滚逻辑工作树，查询仍读到已放弃的编辑            | 中改     | 「放弃草稿」后列表与表单仍显示旧编辑             |
| 三方字段级合并与冲突裁决                                          | 平台只有单向覆盖合并和内部的合并预览                | 新能力   | 不影响：合并继续在产品服务端执行                 |

**结合方式（平台缺口补齐后）：**

- 每个「用户 × 团队 × 应用」一个团队库（sqlite-wasm `vfs: 'idb'` + history + working-tree），`enable()` 为库级且不可逆，因此不与匿名工作台共库；关闭通用同步，提交只经产品协议上传。
- 本地 `shared` 分支经「导入远端提交」镜像服务端共享引用；任务 = 从导入的共享提交建出的分支。
- 编辑复用各应用已有的模型驱动 `EntityList`：团队模式把实体页的 RxDB 实例切换为当前任务库；协作包保留团队、PR、审核、历史等共享面板，删除 `editor.ts`、`form-drafts.ts`、`local.ts`。
- 保存 = RxDB 写入；同步 = `commit()` 后读取 `commitChanges()` 上传；另存 = `createBranchFromCommit()`；恢复 = `restore()`。
- 第 3 节的 ChangeSet 协议使切换只影响客户端，服务端与已存数据不变。

**为什么不现在就切：** 没有「导入远端提交」，第二台设备拿不到原提交 ID、父链和作者，ADMIN-US-206 AC#2 与 C02「不能将拉取到的实体变化重新记成拉取者的原始提交」都会被破坏；没有回写业务表的 `discard()`，ADMIN-US-205 的放弃语义也不成立。因此 ADMIN-US-221 以平台立项为前置，不阻塞上线。

## 8. 风险

- 锁拆分后，撤权与批准、并发上传、合并与状态变更交错等不变量依赖锁顺序；现有并发与事务回滚集成用例必须原样通过，并补「治理行 `FOR SHARE` 与 `FOR UPDATE` 交错」用例。
- Realtime Presence 的撤权移除不再是数据库事务的一部分，需要以撤权广播加重新鉴权兜住 ADMIN-US-215 的时限。
- Edge Function 冷启动与 CPU 上限：阶段 3 以最重的候选生成用例验收；超限时保留 Node 入口作为部署选项。
- 平台能力可能晚于产品上线：ADMIN-US-221 保持 Backlog，团队任务继续使用现有 IndexedDB 存储，但已切换为 ChangeSet 协议。
