## 性能与体积优化

### T04 · P1 · 最近活动的大日志量查询成本

原实现：[dashboard-activity-source.ts](../../apps/react/src/app/pages/dashboard-activity-source.ts) 通过 `findAll` 全量读取，再由 [dashboard-model.ts](../../apps/react/src/app/pages/dashboard-model.ts) 聚合后取五项。现已使用覆盖索引与 SQLite 操作单元聚合，只向 JS 返回五行；数据库内部仍扫描匹配索引，不代表只扫描五条日志。

- [x] 先测量千条、万条、十万条日志下的读取行数、查询与聚合耗时、页面可交互时间和内存，建立三端可比较的基线，再确定预算及优化方案。
- [x] 评估按操作单元读取或分批读取的方案；必须保留事务边界、同毫秒排序、当前分支隔离、撤销及重做失效状态。
- [x] 针对跨批次事务、一个事务超过五条、分支切换和刷新持久化先写测试，再实现并比较性能结果。

验收条件：五个操作单元结果与现有语义一致，读取成本满足事先约定的预算，三端共享用例通过。禁止直接对原始日志 `limit 5`，以免截断事务或不足五个操作单元。

验收结果：[性能记录](dashboard-performance-verification.md) 已包含 1k / 10k / 100k 基线与预算、九组真实 sqlite-wasm 结果和生产 UI 刷新核对。十万条时三端活动流约 0.47–0.49 秒、生产 UI 约 0.83–0.86 秒，向 JS 返回五行。旧归档首次补索引的连接成本另列，未隐藏。公共历史插件纯本地计数优化与应用一起验证。
