# 用户故事：差量提交与有界命令成本

## 作为/我想要/以便

**作为** 团队成员与协作服务的部署者
**我想要** 团队长期使用、积累大量提交、评论和审计之后，各项操作依然流畅，同步与刷新只传输变化的部分
**以便** 协作服务可以长期运行，并能放进 Edge Function 的资源限制里，只部署 Supabase。

## 范围边界

### In Scope

- 提交改为字段级 ChangeSet，形状对齐平台 working-tree 的 `CommitChangeSet`；提交 ID 使用 UUIDv7，服务端重算内容指纹。
- 工作区整行 JSONB 拆为成员、策略、提交、引用、共享记录、PR、候选、审核、讨论、通知、回执、审计等表；引用以比较交换推进，按固定顺序加细粒度锁。
- 合并候选只加载合并基以来双方改动过的记录；字段级三方合并语义不变。
- 回执保留期，通知与审计分页；读路径不加锁、不写库。
- 由 RxDB 实体元数据生成的 schema 清单驱动 ChangeSet 校验，取代写死的资产规则。
- 快照接口拆为摘要、PR 详情、提交元数据、PR 变更记录与审计分页。

### Out of Scope

- RLS 直读、Realtime Broadcast / Presence 与本地 JWT 校验，由 [ADMIN-US-219](ADMIN-US-219-supabase-native-read-realtime.md) 承接。
- Edge Function 部署形态，由 [ADMIN-US-220](ADMIN-US-220-supabase-only-deployment.md) 承接。
- 客户端改用 RxDB 工作树，由 [ADMIN-US-221](ADMIN-US-221-task-drafts-on-working-tree.md) 承接；本故事中客户端仍用现有 IndexedDB 任务存储，只把提交协议切换为 ChangeSet。
- 审计的合规导出与归档，另行立项。

验收证据：阶段 0 基线见 [收敛实施计划 3.1 节](../../plans/collaboration-convergence-tasks.md#31-阶段-0-基线与切片进度)，#1、#6 的预算以同一脚本 `admin-collaboration:benchmark-growth` 前后对照关闭。#6 已完成「读取不加排他锁、不在读路径写库」（切片 A）：`repository.integration.spec.ts` 的「写锁期间读取立即返回」与「心跳不能越过并发撤权」两例，分别用改动前实现（`111f7a6ce`）与 Presence 无锁变异验证会红；切片 B 已让版本通知后只拉摘要，提交与候选内容、共享数据和更早审计按需读取（`engine.spec`、`http.spec`、`controller.spec`、`pr-view.spec`、`history-view.spec` 与集成用例，30 个协作 E2E 同轮通过）；200 个提交时摘要 66 KB（基线快照 26.8 MB），但仍按约 0.3 KB/提交线性增长、超出 50 KB 预算，提交元数据分页在切片 D 完成，故保持 ⚠️。

切片 C（2026-11-17，[结果](../../plans/evidence/collaboration-slice-c-2026-11-17.json)）：

- #2 ✅：提交只含字段级 ChangeSet，上传体积与改动记录数成正比；服务端重算指纹，不一致整批 `invalid`；首个新提交的父必须是任务头；同 ID 同指纹幂等、同 ID 不同内容或不属于该任务即拒绝（`commit.spec`、`commits.spec`、`engine.spec`、`http.spec` 与集成用例；去掉指纹核验的变异使 3 个拒绝用例变红）。
- #3 ⚠️：B、S 只由合并基以来的变更推导，候选、冲突、检查与字段级合并结果与旧实现一致（与旧引擎对拍 60 个随机历史、`golden.spec` 40 个内存种子与 3 个 PostgreSQL 种子）；但生成候选时仍加载完整的 T 并做全量检查，「只加载改动过的记录」留在切片 E。
- #1、#4 ⚠️：命令路径不再读取提交历史，200 个提交时一条评论 9 ms、WAL 39.6 KB；现有并发、交错与回滚集成用例在新实现上全部通过。但工作区行仍随已执行命令数增长、每条命令仍锁整行，切片 D 拆表与拆锁之后，再以 1000 个提交、10000 条共享记录复测并复验并发用例。

切片 D（2026-11-17，[默认参数](../../plans/evidence/collaboration-slice-d-2026-11-17.json)、[AC#1 规模](../../plans/evidence/collaboration-slice-d-ac1-2026-11-17.json)）：

- #4 ✅：锁顺序为治理行 → PR 行 → 共享引用 → 任务引用 → 版本行；普通命令对治理行 `FOR SHARE` 且从不更新它，成员、邀请、策略变更 `FOR UPDATE`。新增集成用例覆盖撤权等待在途批准、撤权后批准被拒、不同任务并发上传与不同 PR 并发评论不再串行、同一任务并发上传一胜一负；成员命令改共享锁、普通命令不锁治理行、修订号写回治理行等 17 个变异全部变红。原有并发、交错与回滚用例全部通过。
- #5 ✅：回执保留 30 天，期内重试返回原结果，过期后提交按 ID 去重；写事务每次最多清理 20 条过期回执（`SKIP LOCKED`）；客户端超过 29 天未确认的请求停止自动重试，交给用户重发或放弃。
- #1 ⚠️：10000 条共享记录、1000 个提交时评论、回复、审核、已读、成员变更为 8.5～14.6 ms（≤ 50 ms），WAL 2.0～3.7 KB，与 10 个提交时相同；耗时差异有两项超过 20%，但曲线不单调（500 个提交时更快），该轮与另一项构建并行，需在空闲机器上加大样本复测后关闭。
- #6 仍为 ⚠️：摘要已不含提交元数据，与提交数无关（默认参数 200 个提交时 25.5 KB），但仍带全部讨论、审核与通知，随协作活动增长（AC#1 规模下 54 KB），由 ADMIN-US-219 改为 RLS 分页直读后关闭。

切片 E（2026-11-17，[结果](../../plans/evidence/collaboration-slice-e-2026-11-17.json)）：

- #3 ✅：生成候选与合并只读取合并基以来双方改动过的记录，唯一与引用检查经 `admin_private.record_keys` 索引按需查询；300 条与 3000 条共享记录时语句与参数规模完全相同，「加载完整 T」的变异只让读取量用例变红；与旧实现对拍 60 个随机历史，候选、冲突、检查与合并结果逐条一致。10000 条共享记录时改动 100 条记录的候选加合并 52～108 ms。
- #7 ✅：`schema-flow.spec.ts` 用项目 / 里程碑 / 标签三种非资产实体的清单，在引擎与 PostgreSQL 上走完任务提交、候选、审批与合并，必填、唯一、关系与数值约束均由清单检出；`domain-free.spec.ts` 断言协作包非测试源码不含资产实体名与字段名。
- 上传时核对 ChangeSet 能应用到父内容，不吻合整批 `invalid` 且零写入（读取量只与任务分叉以来的改动有关）。
- #1 ✅（2026-11-18，机器空闲、每项 15 个样本）：先在同一库上测 10 → 1000 个提交的增长曲线（[结果](../../plans/evidence/collaboration-ac1-rerun-2026-11-18.json)），回复、审核在 1000 个提交时比 10 个提交时慢 31%、25%，其余三种命令在 ±7% 以内，WAL 不变。为分清原因做了两组对照，每组都在全新库上只测一个点，讨论量相同、只有提交数不同：不做 `VACUUM ANALYZE` 时五种命令一起慢 16%～36%，连完全不碰提交表的成员变更与已读也慢（[10](../../plans/evidence/collaboration-ac1-controlled-10-2026-11-18.json)、[1000](../../plans/evidence/collaboration-ac1-controlled-1000-2026-11-18.json)）；测量前先 `VACUUM ANALYZE`（基准新增 `BENCH_VACUUM=1`）后，1000 个提交时五种命令为 10 个提交时的 −15%～−3%，WAL 逐字节相同，改动 100 条记录的候选加合并 41.6 → 41.8 ms（[10](../../plans/evidence/collaboration-ac1-controlled-vacuum-10-2026-11-18.json)、[1000](../../plans/evidence/collaboration-ac1-controlled-vacuum-1000-2026-11-18.json)）。差距来自批量写入刚结束时统计信息过期与后台 autovacuum，不来自命令路径；所有命令均在 4.6～14.6 ms，远低于 50 ms。
- #8 ✅（2026-11-18 最终回归，主检出同一轮代码）：协作包单测 581 例、集成 79 例；协作 e2e 在 Node 与 Edge 两种模式下各 54 例（三端 × 18 个场景，覆盖 ADMIN-US-201～216 与 221）全部通过；三端单测 React 141、Vue 155、Angular 156 例，三端匿名工作台 e2e 各 104 例通过。后端收敛本身没有改变用户可见行为，只有切片 E 改了几条校验文案（见上）；编辑界面改为模型驱动、在线状态改用 Realtime 空闲超时，分别是 ADMIN-US-221 与 ADMIN-US-219 的有意改动，在各自故事里验收。
- #6 ✅（ADMIN-US-219，2026-11-18）：团队页改为经 PostgREST 读取 RLS 只读投影，只含工作区、成员、邀请与有上限的 PR / 任务 / 通知窗口，讨论、审核与审计按需加载；读取不加锁、不写库，体积不再随提交数或讨论增长。
- 用户可见变化：「金额必须为非负数」改为「必须为非负数」（不是数字时为「必须为数字」）；其余边界情况的文案变化见协作包 README。

## 技术笔记

方案、表结构、锁顺序、合并输入的推导方式与预算见 [协作后端收敛实施计划](../../plans/collaboration-convergence-tasks.md) 第 3 节。要点：

- 合并基的值由物化的共享头反向应用共享分支上的 `inversePatch` 得到，不需要另存每条记录的历史版本。
- 治理行对普通命令加 `FOR SHARE`、对成员与策略变更加 `FOR UPDATE`，保留 [D-06](../../decisions.md#d-06数据协作的产品模型) 的统一裁决顺序。
- 产品尚未部署，迁移文件可按新结构重写，没有线上数据迁移。
- ChangeSet 协议是 [ADMIN-US-221](ADMIN-US-221-task-drafts-on-working-tree.md) 切换客户端存储的前提：切换时服务端与已存数据不变。
