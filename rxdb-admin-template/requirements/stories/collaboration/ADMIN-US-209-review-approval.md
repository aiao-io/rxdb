# 用户故事：数据 PR 审核、批准与要求修改

## 作为/我想要/以便

**作为** 被授权的审核者
**我想要** 针对当前数据提交批准或要求修改
**以便** 在合并前留下明确的审核结论，并让作者知道需要补什么。

## 范围边界

### In Scope

- 审核动作绑定 PR 当前来源提交版本，而不是只绑定 PR 编号。
- 支持批准、要求修改和查看审核历史。
- 要求修改保持 PR 打开，作者可以继续追加提交并重新请求审核。
- 新提交使旧版本的批准失效，但保留旧批准和审核历史。
- 审核权与合并权分离；团队可配置至少一人批准，或允许有合并权的人直接合并。

### Out of Scope

- 多级审批、顺序审批和按金额/实体类型配置审批流；见 [ADMIN-US-216](ADMIN-US-216-multi-level-approval.md)。
- 首版自动选择审核人、审批代理和外部电子签名。

## 验收标准

| #   | 前置条件                      | 操作                            | 预期结果                                                              | 状态 |
| --- | ----------------------------- | ------------------------------- | --------------------------------------------------------------------- | ---- |
| 1   | PR 已请求审核且用户拥有审核权 | 打开当前版本并提交批准          | 记录审核人、时间、来源提交版本和结果；当前版本的批准状态更新          | ⬜   |
| 2   | PR 已请求审核且用户拥有审核权 | 提交“要求修改”                  | PR 保持打开并标记为需要修改；作者可以继续追加提交，不能误显示为已批准 | ⬜   |
| 3   | 已批准的 PR 追加了新提交      | 查看审核摘要                    | 旧批准显示为针对旧版本并失效；当前版本需要重新审核，旧历史仍可查看    | ⬜   |
| 4   | 审核者没有合并权              | 完成批准后尝试合并              | 可以完成审核，但合并入口和服务端合并请求都被拒绝                      | ⬜   |
| 5   | 团队规则要求至少一人批准      | 当前版本没有有效批准            | 合并条件明确显示缺少批准；即使用户有其他非审核权限也不能绕过          | ⬜   |
| 6   | 团队规则允许合并者无需审批    | 有合并权的成员查看通过检查的 PR | 页面显示免审批规则，服务端按该规则允许后续合并；普通审核结论仍保留    | ⬜   |
| 7   | 多名审核者在不同客户端操作    | 查看审核历史                    | 结果按版本和时间保留，重复提交同一结论不会产生互相覆盖的假状态        | ⬜   |

验收证据：待实现后补充批准失效、要求修改、权限分离和两种团队策略的三端测试。

## 技术笔记

审核记录至少需要 PR、来源提交版本、审核人、结果、时间和可选说明。检查、讨论和审核都必须指向当前版本；服务端合并前还要再次确认批准仍覆盖当前来源头，不能信任客户端缓存的绿色状态。
