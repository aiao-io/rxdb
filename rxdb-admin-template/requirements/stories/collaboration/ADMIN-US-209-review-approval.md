# 用户故事：数据 PR 审核、批准与要求修改

## 作为/我想要/以便

**作为** 被授权的审核者
**我想要** 针对当前最终合并候选批准或要求修改
**以便** 在合并前留下明确的审核结论，并让作者知道需要补什么。

## 范围边界

### In Scope

- 批准绑定服务端当前 candidateId，覆盖来源/目标头、冲突选择、最终结果和规则版本。
- 支持批准、要求修改和查看审核历史。
- 要求修改保持 PR 打开，作者可以继续追加提交并重新请求审核。
- 候选任一输入变化或批准人失去审核权使旧批准失效；新版本不自动解除要求修改。
- 审核权与合并权分离；默认至少一名非作者审核者批准，可配置免审批模式。
- 按每人最新有效结论聚合；任一未解除的要求修改阻塞，撤销阻塞须授权、理由与审计。

### Out of Scope

- 多级审批、顺序审批和按金额/实体类型配置审批流；见 [ADMIN-US-216](ADMIN-US-216-multi-level-approval.md)。
- 首版自动选择审核人、审批代理和外部电子签名。

## 验收标准

| #   | 前置条件                                              | 操作                                          | 预期结果                                                                                 | 状态 |
| --- | ----------------------------------------------------- | --------------------------------------------- | ---------------------------------------------------------------------------------------- | ---- |
| 1   | PR 已请求审核，当前候选无冲突且检查通过，用户有审核权 | 提交批准                                      | 记录 candidateId、来源/目标版本、审核人及服务端顺序；仅当前有效候选的批准可计数          | ✅   |
| 2   | PR 待审核且用户有审核权                               | 提交要求修改                                  | PR 保持打开并阻塞；即使尚无完整候选也可记录当前来源版本的问题，作者可继续追加            | ✅   |
| 3   | 已批准后来源、目标、冲突选择或规则变化                | 重新生成候选并查看摘要                        | 旧批准和检查过期，历史可读；新候选须重审，旧要求修改不会被自动清除                       | ✅   |
| 4   | 审核者没有合并权                                      | 批准后尝试合并                                | 审核可以完成，UI 和服务端拒绝合并                                                        | ✅   |
| 5   | 团队要求至少一人批准                                  | 仅有作者本人批准、过期批准或失去审核权者批准  | 均不足以满足门槛，仍需要非作者且当前有权者批准当前候选                                   | ✅   |
| 6   | 团队启用免审批模式                                    | 查看并尝试合并存在要求修改或必须处理线程的 PR | 仅免除批准人数，阻塞意见、线程、检查、冲突和权限仍必须通过                               | ✅   |
| 7   | 同一审核者重复或并发提交相反结论                      | 带幂等键及预期结论修订号提交                  | 重复请求返回原记录，陈旧修订拒绝；按服务端已接受顺序决定当前结论                         | ✅   |
| 8   | A 要求修改而 B 批准同一 PR                            | 查看聚合并尝试合并                            | 结果仍为需要修改，B 的批准不能抵消 A 的阻塞                                              | ✅   |
| 9   | A 曾要求修改且当前候选检查通过                        | A 在当前候选上改为批准                        | 解除 A 的阻塞并记录新批准；其他人的阻塞和必须处理线程不受影响                            | ✅   |
| 10  | 阻塞者离开团队或意见需被撤销                          | 执行撤销阻塞意见                              | 仅同时有成员管理及审核权限者可带理由撤销并审计；作者身份或合并权本身不足，撤销不生成批准 | ✅   |
| 11  | 已有批准人被移除或收回审核权                          | 刷新或直接调用合并                            | 批准立即失效，恢复权限后也须重新批准；遗留要求修改仍待显式解除                           | ✅   |
| 12  | 三端面对相同候选及多人意见                            | 对照摘要、失效历史和合并条件                  | 按 C05 得出相同结果；未解决冲突、检查未通过或过期候选不能接受批准                        | ✅   |

验收证据：engine 覆盖候选绑定、无候选时按来源要求修改、相反审核意见独立聚合、审核者仅解除自己的阻塞、幂等修订号、撤权后批准失效、免审批与显式撤销；三端浏览器覆盖无候选禁止批准、要求修改阻塞、恢复草稿重新审批、顺序/并行人数门槛和审核/合并权限分离。 详见 [协作实现与验收记录](../../plans/collaboration-implementation.md)。✅ 表示已有本地验收证据；⚠️ 表示仍缺外部环境证据，均不等同于故事已合入或已部署。

## 技术笔记

共享契约 C04/C05 定义候选身份和聚合规则。每名审核者的当前结论通过服务端修订号并发更新，历史只追加。批准覆盖最终结果，要求修改作为 PR 阻塞持续到本人以新批准解除或授权管理操作撤销。最终合并重新读取权限与聚合，不信任客户端绿色摘要。
