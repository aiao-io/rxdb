# 用户故事：数据 PR 讨论、评论与变更定位

## 作为/我想要/以便

**作为** PR 作者、评论者或审核者
**我想要** 在变更上下文中讨论并把评论定位到具体记录、字段和提交版本
**以便** 团队能围绕数据事实沟通，知道哪些问题必须处理后才能合并。

## 范围边界

### In Scope

- PR 详情提供“讨论、提交、数据变更、检查”四个页签。
- 评论可以定位到实体记录、字段和提交版本，并支持回复、标记处理和重新打开。
- 普通评论用于记录意见，不阻塞合并；标记为“必须处理”的问题阻塞合并。
- 新提交后保留旧版本的评论和线程引用，不把历史评论静默移动到新值。
- 讨论权限与 PR 可见范围、团队和当前版本一致。

### Out of Scope

- @mention、站内通知、邮件通知、富文本附件和讨论搜索；后续增强见 [ADMIN-US-214](ADMIN-US-214-comment-notifications.md)。
- 实时在线成员和当前查看记录；见 [ADMIN-US-215](ADMIN-US-215-presence.md)。

## 验收标准

| #   | 前置条件                         | 操作                                     | 预期结果                                                                       | 状态 |
| --- | -------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------ | ---- |
| 1   | 用户有权查看 PR                  | 打开 PR 详情并切换四个页签               | 讨论、提交、数据变更和检查分别呈现；切换页签不会丢失当前 PR 和版本上下文       | ⬜   |
| 2   | 用户有评论权限                   | 在某条记录的某个字段和提交版本上发表评论 | 评论显示记录、字段、版本和作者定位；打开评论可以回到对应变更                   | ⬜   |
| 3   | 评论线程已有参与者               | 回复、标记处理或重新打开线程             | 回复按时间保留；处理状态可见并可在有权限时重新打开，历史不被覆盖               | ⬜   |
| 4   | PR 存在普通评论和必须处理的问题  | 查看合并条件                             | 普通评论不阻塞；未处理的必须处理问题明确阻塞合并并显示阻塞来源                 | ⬜   |
| 5   | 作者追加了新提交                 | 查看旧版本评论和当前版本                 | 旧评论仍指向原提交版本；当前版本显示需要重新确认的状态，不把旧讨论伪装成已解决 | ⬜   |
| 6   | 用户没有当前团队或 PR 的评论权限 | 尝试新增、回复或改变处理状态             | UI 和服务端都拒绝越权操作，已有讨论不被修改                                    | ⬜   |
| 7   | 三端打开同一个 PR                | 查看讨论、定位和处理线程                 | 评论内容、定位字段、阻塞状态和历史顺序一致                                     | ⬜   |

验收证据：待实现后补充四页签、字段级评论、版本保留、必须处理阻塞和权限负例用例。

## 技术笔记

评论定位应保存实体类型、记录主键、字段名、来源提交版本和必要的变更快照；不能只保存一段当前行号。线程状态改变需要服务端记录操作者和时间。PR 版本更新时旧线程仍然可读，是否重新打开由当前版本检查和审核规则决定。
