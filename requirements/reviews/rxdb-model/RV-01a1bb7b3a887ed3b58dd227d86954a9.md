# RV-01a1bb7b3a887ed3b58dd227d86954a9：宿主表单数据校验放行非有限数字与不安全整数，绕过同模块严格输入约束

## 问题与影响

同一数值通过 setField 输入会被拒绝，但经初始 data 或 setData 进入共享表单后，会被标成 valid 并允许 submit：number 的 ±Infinity、integer 的 2^53 均如此。调用方依赖 valid/submit 作为持久化前门禁时会把明确不合法的数字送给保存动作，界面也无法提示错误。仅涉及异常数值的宿主输入，定为 P2。

## 证据与根因

证据快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

- `packages/rxdb-model/src/entity-value.utils.ts:381` 的数字校验只用 isNaN；Infinity 不是 NaN。第 383 行对 integer 只用 Number.isInteger，放过超出安全整数范围的值。
- 同文件第 195 行严格解析要求有限数字，第 208 行要求安全整数，所以同值在用户输入与宿主输入之间出现确定性矛盾。
- `packages/rxdb-model/src/entity-form/form-validation.ts:34` 调用该宽松校验；EntityFormController.setData 重建的快照及 submit().validate 均依赖它，未重新走严格解析。
- 有界真实控制器复现依次将宿主 amount 设为 Infinity、-Infinity、9007199254740992：三者 strictInputAccepted=false，但 fieldError=null、snapshotValid=true、submitValid=true。已有数字与安全整数用例只锁住严格解析入口，没有覆盖宿主数据门禁。

## 修复方向

在 model 共享数字校验中统一有限数和安全整数边界，保持已承诺的字符串转换语义；补构造 data、setData、validateForm、submit 与 setField 同值对照。三框架共用同一修复，核对字段范围语义在两条入口一致。
