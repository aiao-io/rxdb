# RV-01a1bb7340ab78b793a5f7fb7afdca71：共享结构化克隆将 JSON 的 **proto** 键变成原型，表单快照与提交静默丢数据

## 问题与影响

合法 JSON 对象可含自有 **proto** 键。JSON/json 字段经 headless 表单初始化或 setField 克隆后，该键被删除式丢失，提交仍被判合法但输出数据已改变；副本还短暂获得输入控制的原型。问题限于这一特殊键，按罕见输入的数据保真缺陷定为 P2，不声称污染全局 Object.prototype。

## 证据与根因

证据快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

- `packages/rxdb-model/src/structural-equal.ts:29` 创建普通 `{}`，第 32 行用 `copy[key] = ...` 复制任意键。**proto** 会调用继承的 setter，未被定义为自有数据属性。
- `packages/rxdb-model/src/entity-form/headless.ts:140` 与第 141 行经 cloneData 保存输入和初值；快照、setField 与 submit 继续复用 cloneStructured，所以错误进入三端共用的公开表单数据路径。
- JSON.parse 构造的输入 `{"__proto__":{"label":"kept"},"normal":1}` 经直接克隆后仅有 normal，自有键丢失，structuralEqual(source,copy) 为 false。
- 使用真实 createEntityFormController（json 字段 payload）后，snapshot.data.payload 与合法 submit().data.payload 均变为 `{"normal":1}`；原输入仍保留 **proto**。已有 core-headless-regression 的 Date/字节/循环隔离测试与 structural-equal 用例未覆盖这种 JSON 键。

## 修复方向

复制任意对象键时使用不会触发继承 setter 的数据属性定义，保留正常对象消费契约；覆盖 JSON 自有 **proto**、constructor/prototype 和嵌套键的输入、快照、编辑、submit 往返。三端绑定共用核心修复即可，但应核对表单消费者不会再次用普通赋值丢键。
