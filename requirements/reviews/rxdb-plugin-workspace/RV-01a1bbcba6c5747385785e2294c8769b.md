# RV-01a1bbcba6c5747385785e2294c8769b：workspace flush 在安装等待跨连接纪元后会误把新纪元写入当成旧调用已完成

## 问题与影响

`flush()` 在等待旧连接纪元的 `ready` 期间发生断连并重新连接时，续体只检查当前实例是否存在任意 `#indexedDBStore`，没有核对它是否仍是调用开始时的同一纪元。于是旧调用可能在新纪元安装后继续进入新纪元的 `#settleQueue()`：它会等待或消费新纪元的草稿，然后以“旧 flush 已完成”的结果返回。旧纪元原本未落盘的草稿已经在释放时被丢弃，调用方却得到成功，持久化屏障的结果与调用所属纪元不一致。

这是连接生命周期下的 P2 持久化状态错误：调用方可能据此清除本地待保存状态，或把旧纪元的草稿丢失误判成已落盘。

## 证据与根因

冻结源码 SHA：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

- `packages/rxdb-plugin-workspace/src/RxDBPluginWorkspace.ts:324`–`:334` 的 `flush()` 先 `await this.ready`，随后只以 `this.#indexedDBStore === undefined` 判断是否仍可用，再调用 `#settleQueue()`。
- `packages/rxdb-plugin-workspace/src/RxDBPluginWorkspace.ts:349`–`:352` 的 `install()` 在新连接纪元会重置/替换安装 Promise；`#loadView()` 的安装 Promise 可跨越异步 IndexedDB 读取。
- `packages/rxdb-plugin-workspace/src/RxDBPluginWorkspace.ts:597`–`:629` 的释放会清空旧队列并重置 `#installPromise`，然后新纪元重新填充 `#indexedDBStore`。因此旧 `flush()` 的 await 续体若在新 install 后恢复，只看到一个非空的新 store。
- 现有 `packages/rxdb-plugin-workspace/src/__tests__/RxDBPluginWorkspace.spec.ts:507`–`:552` 覆盖的是旧纪元写盘任务迟到时不结算新纪元的 flush waiter；没有覆盖 `flush()` 自身在旧 `ready` 尚未结算时跨释放/重连后继续使用新纪元的情况。

静态时序即可得到该结果：调用先挂在旧 `ready` 上，释放清空旧状态并创建新 store，旧 Promise 续体再执行时当前 store 已属于新纪元。未执行动态复现、测试、浏览器、注入或网络探测。

## 修复方向

让 `flush()` 在入口捕获当前连接纪元的身份（例如 store 引用或递增 generation），并在 `await ready` 后以及登记/等待队列前复核仍为同一纪元；若已释放或切换，拒绝旧调用。配套补一个“旧 ready 尚未完成 → disconnect → reconnect → 旧 flush”生命周期断言。
