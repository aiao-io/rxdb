# RV-01a1bbd292287d4a9e03bc485a0b42c5：Docker 首次安装路径未安装 curl 却无条件调用 curl

## 问题与影响

在干净的 Debian/Ubuntu 或 RHEL 主机上按文档执行 `setup.sh`，基础依赖安装完成后脚本会进入 Docker 仓库安装或 sparse clone 路径；这些路径都无条件调用 `curl`。`install_base_packages` 的安装清单没有 curl，导致新机 bootstrap 在安装 Docker GPG key、下载 Compose/AWS 或 sparse clone 前直接失败。文档把脚本定位为从零 bootstrap，属于常见初始环境下主流程不可用，定为 P1。

## 证据与根因

冻结 SHA `0ffa3c419fcc59dc3e13d695ca4658116134bfa0`：`docker/setup.sh:82` 的 `install_base_packages` 仅安装 `git openssl jq ca-certificates` 及 apt/rpm 辅助包；`docker/setup.sh:124` 的 Debian `install_docker` 直接执行 `curl -fsSL https://download.docker.com/...`，`docker/setup.sh:149` 的 Amazon Linux 分支也直接执行 curl，`:192` 的 `sparse_clone` 依赖 git 而 AWS 分支下载同样使用 curl。没有 `command -v curl` 检查或安装步骤。

静态调用链复核：除非主机原本自带 curl，否则 `setup.sh` 不能到达 clone/安装完成；`--skip-deps` 更明确要求用户预装依赖，但默认从零路径没有该前提。未在真实主机安装 Docker，未改源码。

## 修复方向

把 curl 纳入各发行版基础包安装，或在首次使用前做明确的依赖检查并给出可执行修复；为无 curl 的最小 Debian/RHEL fixture 增加 bootstrap 检查。
