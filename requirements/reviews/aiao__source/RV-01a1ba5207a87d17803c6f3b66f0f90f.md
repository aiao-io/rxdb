# RV-01a1ba5207a87d17803c6f3b66f0f90f：全量时间过滤错误排除开始后同一秒内登记的覆盖

## 问题与影响

按 Skill 的 `date -u +%Y-%m-%dT%H:%M:%SZ` 取得全量开始时间后，若某批覆盖在这一秒剩余时间内登记，后续 `status --since` 永远不认该批覆盖。工具把已完成的批次重新列为必审；停止后恢复也无法继承该批结果，用户可能重复评审或误以为登记失败。触发限于开始秒内的快速批次，定为 P2。

## 证据与根因

证据快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`scripts/ai-review/ai-review.mjs:578` 的 `accepts()` 用字符串顺序比较 `entry.at >= since`。覆盖时间由 `Date.toISOString()` 生成，带毫秒；Skill 推荐的开始时间不带毫秒。同一秒时，`.500Z` 在字符串排序中反而小于 `Z`，尽管实际晚 500 毫秒。

独立临时 Git 仓库中，用 `recordCoverage(..., { now: new Date('2026-11-08T08:10:30.500Z') })` 登记两个必审单元；然后分别查询：

- `since: '2026-11-08T08:10:30Z'` → `covered: 0`；
- `since: '2026-11-08T08:10:30.000Z'` → `covered: 2`。

两种 since 表示同一个开始时刻，结果应相同。该复现没有修改实际仓库的覆盖日志。

## 修复方向

将时间解析为时间戳后比较，或在入口校验并统一 ISO 精度。补同秒毫秒边界、秒边界与非法时间输入回归，并保留旧日志可读性。
