# RV-01a1bb2b329e79698e6cbbe5fa9a33e8：覆盖率合并按局部计数 ID 相加会把命中归到错误源码位置

## 问题与影响

同一源码文件的 Node/browser Istanbul 报告拥有不同的计数 ID → 源位置映射时，合并器直接把相同 ID 相加，并只保留左侧映射。两次测试实际覆盖了不同语句，结果却被合成同一语句重复命中。覆盖率门禁与展示会得到错误的覆盖比例，可能误拒也可能误放。问题要求两份映射不同，属于 P2 边界条件。

## 证据与根因

证据快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`scripts/merge-vitest-reports.mjs:33` 至 `scripts/merge-vitest-reports.mjs:42` 只保留左侧 statementMap/fnMap/branchMap，同时通过 `mergeCounters` 按数字 ID 合并 s/f/b。Istanbul ID 是各报告自己的键，位置才是可跨报告匹配的语义；代码没有核对两份映射相等，也没有按位置重建键。

隔离输入是同一文件 `/workspace/src/shared.ts` 的两份有效报告：左侧 ID 0=第 1 行、ID 1=第 2 行，s={0:1,1:0}；右侧 ID 0=第 2 行、ID 1=第 1 行，s={0:1,1:0}。两行分别在两次运行中被执行，合并应当 covered=2/2。实际 lines 和 statements 均为 covered=1/2、pct=50。`writeValidatedCoveragePair` 随后仍接受这一份自洽但语义错误的产物。

消费者为 `packages/rxdb-plugin-search/project.json:28`、`packages/rxdb-plugin-storage/project.json:43` 的 test-browser，合并后的数据由 CI coverage job 读取。既有 `scripts/merge-vitest-reports.spec.mjs` 两个 coverage 用例左右映射完全相同，不能检出该根因。

## 修复方向

按源位置合并并重新编号计数，或先明确拒绝映射不一致的输入；不能继续按碰巧相同的数字 ID 归并。补语句/函数/分支映射不一致的回归。
