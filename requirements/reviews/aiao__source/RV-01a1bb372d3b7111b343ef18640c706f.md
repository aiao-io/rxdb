# RV-01a1bb372d3b7111b343ef18640c706f：文档门禁把独立代码块中的同名变量当作同一个历史槽位别名

## 问题与影响

同一篇指南先展示历史操作、再展示独立的同步示例，两个代码块都使用 manager 这类自然变量名时，只要前一个块把它绑定到 versionManager，后一个正确绑定到 syncManager 的 push 调用也被判为历史侧旧 API。合法文档会被 CI setup 硬阻断，必须无意义地全篇改变量名才能通过。属于多代码块作用域边界，定为 P2。

## 证据与根因

证据快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`scripts/audit/docs-plugin-surface.mjs:184` 至 `scripts/audit/docs-plugin-surface.mjs:192` 把整篇所有 versionManager 别名收进一个 Set。`scripts/audit/docs-plugin-surface.mjs:130` 再拿该全集检查每一行，不保留代码围栏和重绑定的作用域信息。

隔离文档同时列全 history/sync 包名；第一个 ts 围栏是 const manager = db.versionManager 后 createBranch，第二个独立 ts 围栏是 const manager = db.syncManager 后 await manager.push()。对它调用真实 auditDoc，实际返回“第 9 行 manager.push() 走的是 versionManager，已移到 syncManager”。第二个示例明确绑定同步槽位，结果应为空。

既有 docs-plugin-surface.spec.mjs 只分别验证历史别名、同步别名以及 diff 删除行，未把这两种合法示例放到同一篇文档。

## 修复方向

以代码块/局部绑定为边界解析别名；保留先展示调用再给完整示例的需求时，也不能跨独立示例传播绑定。补同名变量分别绑定两个槽位的多围栏回归。
