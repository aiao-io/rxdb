# RV-01a1bb8de8a17981adf0148d01cf8c73：套件调用门禁把无花括号的条件调用当作无条件覆盖

## 问题与影响

把 conformance 套件调用包进 if (process.env.RUN_CONFORMANCE) 且不加花括号后，条件未设置时该套件不注册任何用例，门禁却仍认为这一格合格。声明的 6×3 矩阵因此可能缩水而 CI 静态检查全绿。属于合法条件语法的漏检，定为 P2；当前冻结的18个真实入口仍是无条件顶层调用，不宣称它们已经停跑。

## 证据与根因

证据快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`scripts/audit/working-tree-suite-callsites.mjs:346` 只用花括号深度和当前圆括号栈判断 topLevel。无花括号 if 的条件圆括号在套件函数名前已经闭合，两个深度都为0，因此会被误记为 unconditional 顶层调用。

先用最小合法条件语句验证：inspectSource 返回 called=true、disabledBy=null，describeRejection 返回 null；RUN_CONFORMANCE 未设置时执行该语句，实际调用次数0。再取冻结的真实 PGlite capture 入口，只在第54行原有完整套件调用前插入相同 if 前缀，保持实际导入、工厂参数及其他代码不变，门禁仍返回相同的合格结果。

既有 working-tree-suite-callsites.spec.mjs 覆盖函数体、describe.skip/skipIf/runIf 等，却没有普通无花括号 if。已核对6个后端全部18处公共具名导入与实际顶层调用，问题是判据缺口而非现有矩阵缺项。

## 修复方向

按语句层级识别无条件的模块调用，或明确拒绝条件控制下的调用；不能把括号/花括号深度等同于执行保证。补有/无花括号条件、条件表达式及正常直接调用的边界回归。
