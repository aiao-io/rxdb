# RV-01a1ba456a7c7323b258c99b701fc1c0：覆盖日志截断后续写会使断点状态永久不可读

## 问题与影响

评审进程异常中断，覆盖 JSONL 最后一行只写了一部分时，`status` 能暂时忽略该尾行；但下一批 `cover` 直接追加 JSON，不处理半行。旧半行与新 JSON 粘连后成为有换行的损坏行，此后所有 `status` / `cover` 都报错，连此前完整登记的覆盖也读不出来。需要异常中断恰好留下半行，定为 P2；普通批次间停止与恢复不受此问题影响。

## 证据与根因

证据快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`scripts/ai-review/ai-review.mjs:474` 至 `scripts/ai-review/ai-review.mjs:477` 无条件忽略最后一个无换行片段，注释明确将其视为写到一半的行。`scripts/ai-review/ai-review.mjs:557` 随后直接 `appendFileSync()`，既没有隔离损坏尾部，也没有防止并发写者与恢复操作交错。

在独立临时 Git 仓库中，先以 `recordCoverage()` 登记全部单元，再向该临时仓库的覆盖日志模拟写入不带换行的 `{"v":1,"key":`。此时 `coverageStatus().complete` 为 `true`。然后正常登记一个单元，再读取状态，实际得到 `coverage.jsonl 第 3 行损坏`。复现没有改动本仓库真实覆盖日志。

现有 `ai-review.spec.mjs` 没有「半行尾部 → 重启 → 继续登记」用例。

## 修复方向

为日志追加设计可恢复的批次提交边界，或在具备并发互斥的恢复流程中隔离未完成尾部，保留之前完整条目。不要直接丢弃整份覆盖文件；补异常尾行和并发登记的续审回归。
