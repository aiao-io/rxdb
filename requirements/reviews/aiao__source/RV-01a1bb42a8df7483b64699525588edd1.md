# RV-01a1bb42a8df7483b64699525588edd1：本地启动和重置把初始化发给了另一个 Compose 项目

## 问题与影响

按 docker/README.md 快速开始，在没有额外 SUPABASE_CI_PROJECT_NAME 的常规环境运行 ./start.sh：容器已在 supabase 项目启动且就绪，初始化却去 supabase-ci 项目执行，报 db 未运行后退出。./reset.sh 也会先清掉默认栈测试对象，再在同一初始化步骤失败，无法重建测试数据。这是文档主入口的常见必现路径，定为 P1。

## 证据与根因

证据快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`docker/docker-compose.yml:11` 声明 name: supabase。`docker/start.sh:35`、`docker/start.sh:38`、`docker/start.sh:46` 的拉取、启动、就绪探测都使用默认 docker compose，因此归属这个项目；第 76 行调用 init-db.sh，没有传递项目身份。

`docker/init-db.sh:10` 默认 PROJECT_NAME=supabase-ci，第 20 行又固定 -f docker-compose.ci.yml。它只适配隔离 CI 调用者，不再适配 start.sh 的默认栈。`docker/reset.sh:73` 复用同一错误入口。

复制冻结 start/init 脚本到本组目录，用不会启动容器的 Docker/Curl 替身完成有界调用链复现。实际命令顺序先 compose pull、compose up -d、默认项目 pg_isready，最后转成 compose -p supabase-ci -f .../docker-compose.ci.yml exec db psql，复现退出 1。配置 name 与调用参数的冲突不依赖数据库时序。

README 的启动、重置、单独初始化命令均走该链；supabase-ci-up.sh 则显式传隔离项目，仍符合新 init-db 的假设。修复要同时保留两类调用者。

## 修复方向

由调用者明确传递 Compose 项目和配置，或让本地启动与初始化统一使用同一份栈入口；不要靠固定回退项目名推断实际已启动的容器。补 start→init、reset→init 与隔离 CI→init 三条身份一致性回归。
