# RV-01a1bb46f57973faaab89271e9582018：React 无限滚动切换查询时首个提交仍把旧列表标成已加载完成

## 问题与影响

无限列表 A 已加载后，父组件将筛选条件改为 B，而 B 的第一页仍在等待。useInfiniteScroll 在 B 的首个提交继续返回 A 的 value、isLoading=false 以及旧 hasMore/error，直到被动 effect 执行才复位。界面和消费者 layout effect 已处于 B 的查询上下文，却读到“B 已加载”的 A 数据；会显示错误分组/工作区的结果，也会让按已加载状态执行的选择或滚动逻辑使用旧列表。问题是提交边界错误，之后能够正常收敛，定为 P2。

## 证据与根因

证据快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

- `packages/rxdb-react/src/useInfiniteScroll.ts:90` 的 state 不携带产生它的数据库/实体/optionsKey 身份；第 261 行无条件将旧 pages 展平返回。
- 第 249–258 行只在 useEffect 中更新 optionsRef、resetState、loadMore；新查询首次 render 与消费者 layout effect 均早于这个复位点，因此必然有一次旧结果被提交。
- 对应的基础查询 `packages/rxdb-react/src/hooks.ts:87` 使用 previous 查询身份在 render 期复位元数据，并在 layout effect 失效旧请求。无限滚动未采用对应保护。
- `packages/rxdb-react/src/__tests__/useInfiniteScroll.spec.ts:183` 的 options-change 用例在 rerender 后 waitFor 新请求发出，断言已经越过错误首个提交；真实 browser 测试的 layout 时序探针针对 useFind，未覆盖 useInfiniteScroll。

本组 `repro-react-infinite-scroll-first-commit.mjs` 在 Happy DOM 中挂载真实 React createRoot，使用现有构建公共入口和 RxJS Subject；消费者每次 layout effect 记录 key、ids、loading。A 返回一条记录后切到尚未发值的 B，实际记录：

```json
[
  { "key": "b", "ids": ["a-private"], "loading": false },
  { "key": "b", "ids": [], "loading": true }
]
```

第一条即 B 的首个提交；第二条才是 effect 触发的正确加载态。复现不依赖真实数据库或浏览器绘制，因此证实的是已提交快照和 layout 可见状态，不声称测量了真实浏览器闪烁时长。

## 修复方向

让返回快照与当前 rxdb/EntityType/optionsKey 身份对齐，查询身份变更时在提交前使旧列表失效并给出正确 loading 状态；同时失效旧回调，防止被动清理之前的 emission 复活旧结果。保留原有 refresh、活页重锚和 StrictMode 行为。补以消费者 layout effect 观察首个提交的筛选变化与数据库切换测试，不能只在 waitFor 后检查最终结果。
