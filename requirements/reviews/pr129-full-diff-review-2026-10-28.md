## 确认的问题

### B-01 · P1：高级索引没有按 SQLite 检出位重命名，创建工作树失败

**位置：** [`advancedIndexStatements`](../../packages/rxdb/src/entity/storage-ddl.ts) 第 28 行；[`create_table_sql`](../../packages/rxdb-adapter-sqlite-core/src/table/create_table_sql.ts) 第 306 行。

```ts
`CREATE ${index.unique ? 'UNIQUE ' : ''}INDEX ${quoteSqlIdentifier(index.name)} ON ${tableRef}`;
```

**触发：** 实体声明 `indexes: [{ name: 'title_lookup', properties: ['title'], method: 'btree' }]`，先为主表集执行 `create_table_sql(..., WorktreeTableSet.MAIN)`，再为同库的 `WorktreeTableSet.of('wt_review', [Entity])` 执行建表。第二次真实 SQLite 执行报 `index sx_ReviewAdvancedIndex_title_lookup_d26b8f08 already exists`。

**根因与影响：** 新增路径只把物理表名传给高级索引构造器，索引仍用同一个逻辑名。SQLite 索引名在库内共享；同文件中普通索引将物理表名计入索引名，条件唯一索引通过 `get_storage_object_name(..., tableSet)` 隔离。用户一旦把这次新增的高级/生成列索引和已有工作树能力组合，第二个检出位建表即失败。此条不推断 PostgreSQL 有相同的跨 schema 冲突。

**验证：** Nx 驱动的 SQLite 原生集成复现，失败发生在第二次 DDL 执行，不是字符串快照推测。源文件 `/tmp/rxdb-bom-review-shadow-index.spec.ts`，日志 `/tmp/rxdb-bom-review-shadow-index.log`。复验命令：

```sh
NX_DAEMON=false NX_NO_CLOUD=true pnpm nx run rxdb-adapter-sqlite-core:test src/__tests__/review-shadow-index.spec.ts --browser.enabled=false --coverage.enabled=false --maxWorkers=1 --output-style=static
```

复验需先将临时源码放回命令指定位置，结束后移除。

**修复：** 由适配器提供包含表集身份的索引物理名解析，同时对齐漂移检查的 expected/actual 名称。补“主表 + 两个 shadow 表集 + 重连漂移检查”的组合回归；直接加 `IF NOT EXISTS` 会让影子表缺索引，不能解决隔离问题。

### B-02 · P1：草稿 ECN 引入的逻辑行会泄漏进正式结构

**位置：** [`buildResolvedOccurrencesSql`](../../packages/rxdb-plugin-bom/src/resolve/bom-sql.ts) 第 140–150 行；同文件 `buildHeaderOccurrencesSql`、`buildChildrenOfRevisionsSql`、`buildParentsOfItemsSql` 使用同一过滤模式。

```ts
`JOIN ${line} l ON l."id" = occ."lineId"`,
// WHERE 只验证发生项侧：
`  AND ${ecnVisibleExpr(dialect, 'occ')}`,
```

**触发：** 在草稿头内创建 `ecnInId` 指向 draft ECN 的逻辑行；在该行创建 `ecnInId = null` 的普通发生项；随后发布头。以上写入均经正常实体 API，两个后端都接受。评估日在 ECN 生效日之前调用 `resolveBom`，返回了这条本应尚不可见的行。

**根因与影响：** 读取检查发生项自己的 ECN，却没有检查逻辑行的引入 ECN。写入期的 line/occurrence 归属矩阵只在已发布头的成员写入路径约束，草稿阶段接受的组合在头发布时没有补验。结果是未发布变更进入正式 BOM；数量、成本、导出读取也共享缺失的逻辑行过滤，不能只修界面。

**验证：** Chromium 中运行真实 wa-sqlite 与 PGlite；两例均为 `expected length 0, received 1`。完整临时复现在 `/tmp/rxdb-pr129-bom-audit.spec.ts`，日志 `/tmp/rxdb-pr129-bom-audit.log`。

**修复：** 把逻辑行和发生项的可见性作为共享 SQL 规则，在四条读取路径一致应用；在头发布时校验当前成员的 ECN 归属，阻止草稿数据绕过已发布矩阵。补草稿头发布、未来生效、取消/撤回及四类读取的双后端回归。

### B-03 · P1：无投入的成本层级通过明细缓存绕过拒绝，返回负成本

**位置：** [`rollupCostInSnapshot` 内的 `buildLayerDetail`、`buildDetail`](../../packages/rxdb-plugin-bom/src/quantity/cost.ts) 第 1025–1029、1198–1202 行；对照 `computeBatchCostOf` 第 912–916 行。

```ts
const detail = await buildLayerDetail(headerMeta, L, path);
batchCostCache.set(batchKey(headerMeta, L, true), allocated.batch);
const unitCost = await unitCostOf(headerMeta);
```

**触发：** 合法已发布头设置 `costLotQty = '1'`，只有一条 `by_product` 行，产量 2、抵减价 5，没有任何 `consume` 行；使用默认批量卷算。

**实测：** wa-sqlite 与 PGlite 均成功返回 `root.batchCost = '-10'`、`root.unitCost = '-10'`，没有 `BomCostError`。相同领域的 `explodeNode` 明确拒绝“头没有 consume 行（无投入）”；`computeBatchCostOf` 也有该拒绝，但当前调用没有经过它。

**根因与影响：** 明细路径复制了批成本逻辑，却漏了投入校验。`buildDetail` 先把未校验结果放入缓存，默认批量恰等于标准批量时 `unitCostOf → batchCostOf` 命中缓存，绕过唯一的拒绝点。显式换批量可能改变是否命中，错误因此取决于优化路径。此处问题是把“无投入结构”当成功，不是笼统禁止合法生产的负净成本。

**验证：** 同 B-02 的真实双后端复现，两例均为 `promise resolved instead of rejecting`，返回对象包含上述负值。

**修复：** 在两条成本路径共用的层级准备阶段执行同一投入校验，保证校验先于缓存发布。回归同时覆盖默认标准批量、其他显式批量、仅副产/仅废料，以及正常有投入但净成本为负的区别。

### B-04 · P2：数据库变更后，整机展开仍把旧结果当作当前结果

**位置：** [`ExplosionPage.stale` 与构造器 effect](../../apps/dev-rxdb-bom/src/app/pages/explosion/explosion.page.ts) 第 101、114–117 行；[`BomExplosionView`](../../apps/dev-rxdb-bom/src/app/bom-workspace-state.ts) 只保存 `key`、`epoch`。

```ts
readonly stale = computed(() => this.view() !== null && this.view()!.key !== this.workspace.contextKey());
if (this.ready() && (!view || view.epoch === epoch)) return;
```

**触发：** 完成一次整机展开，在保持日期、计划量等条件不变时发布/取消影响该结构的 ECN，再返回展开页面。服务通过 `dataRevision` 通知实际数据改变，`dataEpoch` 只在重置时改变；旧结果保存在全局 workspace 中。

**根因与影响：** 请求在途时检查了 revision，已经缓存的结果却没有保存/比较它。旧需求不显示“待更新”，`exportable()` 仍为 true。`IntegrationPanel` 下载时还会重新查询并比较 manifest，因此本条不声称所有旧结果都会直接导出；已确认的问题是旧备料清单继续以已确认结果显示、下载按钮仍开放，用户到点击后才可能被拒绝。同应用 `CostPanel` 已对 revision 做失效处理，可作为一致性参照。

**验证：** 基于原 `explosion.page.spec.ts` 的独立临时文件，原有 7 项用例通过；新增“完成展开后仅递增 `dataRevision`”的用例失败：期望 `exportable() === false`，实际 true。源码 `/tmp/rxdb-pr129-explosion-audit.spec.ts`，日志 `/tmp/rxdb-pr129-explosion-audit.log`。

**修复：** 缓存保存数据 revision，数据变更后清理或明确标记旧结果；已选行的计算依据与导出资格随同失效。补跨路由返回和在途/已完成结果两类回归。

### B-05 · P2：环约束演示每次失败仍提交空行，反复操作会撞唯一键

**位置：** [`BomDemoService.rawCycleInsert`](../../apps/dev-rxdb-bom/src/app/bom-demo.service.ts) 第 711–725 行；同文件 `formCycleInsert` 第 732 行起。

```ts
const lineNo = 500 + Math.floor(Math.random() * 400);
await this.adapter.rawQuery('INSERT INTO "bom$bom_line" ...', ...);
try { await this.adapter.rawQuery('INSERT INTO "bom$bom_line_occurrence" ...', ...); }
```

**触发与影响：** 每次插入成环发生项被拒绝时，前一个独立事务中的逻辑行已经提交。两个演示按钮共用 400 个随机行号，重复点击会积累空行；随机命中已用行号后，在发生项和 `try` 之前就因 `(headerId, lineNo)` 唯一约束失败，演示不再返回预期环错误。行号随机只推迟碰撞，无法消除它。

**验证方式：** 源码事务边界与实体唯一索引调用链核对，未声称运行浏览器连点。可将随机源固定为同一值后连续调用两次；第二次必然命中已提交的行号，是确定性复验，不需要概率压测。

**修复：** 在同一个适配器事务内创建逻辑行和发生项，让预期的环拒绝回滚整次演示；原始 SQL 和表单路径保持相同原子性。回归断言连续失败后表行数不变、错误仍为环约束。

### B-06 · P2：导入把不存在的日历日期静默改成下一月

**位置：** [`importDate`](../../packages/rxdb-plugin-bom/src/resolve/import-contract.ts) 第 145–157 行，调用方 `naturalKeyFor` 和 `integration.importEntityData`。

```ts
typeof value === 'string' && ISO_DATE_PREFIX.test(value) ? new Date(value) : null;
if (date === null || Number.isNaN(date.getTime())) {
  /* 拒绝 */
}
```

**触发与实测：** `importDate('effectiveFrom', '2026-02-30T00:00:00.000Z')` 不抛错，而是返回 `2026-03-02T00:00:00.000Z`。此函数承诺有效 ISO 8601 日期；2 月 30 日并不存在。JS 日期构造器的宽松滚动被当成校验，后续自然键与真实写入都使用滚动后的 Date，ERP 上传的生效日因此在无诊断时被改写。

**验证：** 临时纯函数回归断言应拒绝，实际 `expected function to throw`；见 `/tmp/rxdb-pr129-bom-audit.log`。同分支 `ext-attr.isIsoDateText` 和演示服务 `#date` 已做日历回读检查，导入路径缺少相同边界。

**修复：** 严格校验原始年月日及时区/时间语法，再转换成时刻；保留合法带偏移的 ISO 时间，不能只将转换后的 UTC 日期与原文本日期直接相等比较。补闰年、月末、2 月溢出、带偏移时间和自然键稳定性的回归。
