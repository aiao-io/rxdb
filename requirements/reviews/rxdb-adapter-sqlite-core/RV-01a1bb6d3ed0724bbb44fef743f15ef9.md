# RV-01a1bb6d3ed0724bbb44fef743f15ef9：批量写回查漏解码 bigint 外键，把实体外键回填成 number

## 问题与影响

父实体主键声明 bigint，子实体通过多对一外键引用它。批量写完成后的回查若从后端得到安全范围 INTEGER 的 number（如 1），会把子实体 parentId 从正确的 1n 回填成 number 1；再次把它作为 FK 写入则被写侧 bigint 校验拒绝。普通仓储查询另有 decodeForeignKeyValues，不能据此说所有查询都错。定 P2：范围限定为批量写回查绕过类型补偿，以及后端返回安全整数 number 的形态，未证明数值精度或存量行丢失。

## 证据与根因

源码快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`packages/rxdb-adapter-sqlite-core/src/sqlite-core.utils.ts:648` 命中 FK 缓存映射后直接赋 `obj[fkPropName] = value` 并 continue，未使用已提供的 resolveEntityMetadata 查目标主键类型；同文件同步转换函数在第 773–777 行也直接透传 FK。普通属性分支则调用 transformValueSqliteToJs，它在 bigint 分支能把安全整数转成 BigInt。

写侧同文件第 393–402 行恰好已经按关系目标主键执行 transformValueJsToSqlite，对 bigint 的 number 输入拒绝。因此当前读出的 FK 不满足本包自己的写契约。现有 bigint-binary.spec 覆盖了 FK 写侧拒绝 number，却没覆盖此读取形态；utils.spec 的 FK 水合用例只用 string。

有界诊断用真实 SQLite 绑定 1n 写入 INTEGER 主键/外键，真实 SELECT 得到 number 1；用冻结的 getEntityObjectFromResult、真实 Entity/SchemaManager/EntityManager 水合：子实体 parentId 仍为 number，父 id 正确成为 bigint；把水合外键再送入冻结写侧函数，稳定拒绝。未 mock SQL 行、元数据解析或实体水合，未启动完整适配器连接。

继续核对真实消费者后收窄归因：`packages/rxdb-adapter-sqlite-core/src/transaction_sqlite_result.ts:54` 的 decodeForeignKeyValues 会在普通仓储水合中补转 FK，故普通 get/find 不属于已证范围；批量路径 `packages/rxdb-adapter-sqlite-core/src/rxdb_adapter_mutations.ts:82` 直接调用通用行工具，第 105 行直接 repository.updateEntity，没有这一步补偿。`packages/rxdb/src/repository/RepositoryBase.ts:97` 的 updateEntity 仅调用 applyExternal，不解码外键。诊断证明的原始行工具/实体水合/写侧不对称，结合该完整静态回填链证明批量路径缺口；未声称运行过整个 saveMany。

## 修复方向

让批量写回查复用普通仓储已有的 FK 解码规则，或抽成共享行解码器，在所有需要业务类型的回填点统一使用。仅按目标主键类型转换，保留 null，不能把所有整数 FK 都改成 BigInt。补 saveMany/mutations 之后安全范围/超安全范围 bigint FK 的实体类型、再次写回，以及 ordinary repository 对照。
