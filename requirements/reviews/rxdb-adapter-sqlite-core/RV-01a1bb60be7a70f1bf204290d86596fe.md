# RV-01a1bb60be7a70f1bf204290d86596fe：批量删除把主键中的 NUL 丢掉，误删另一个实体

## 问题与影响

string 主键允许包含 NUL；例如库里分别有 `id\0tail` 和 `idtail` 两行。批量删除请求前者时，生成器把 NUL 静默移除，实际删除后者，目标行反而保留。属于可证明的误删数据，定 P1；条件是特殊但被接受的字符串主键，不是全部普通 id。若旁观行有级联关系，影响还可能扩散，但本次没有据此虚报级联实测。

## 证据与根因

全部本仓库源码证据来自 `0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`packages/rxdb-adapter-sqlite-core/src/entity/deletes_sql.ts:16` 用 `get_sql_value(e.id)` 把 id 内联进 IN 列表；`packages/rxdb-adapter-sqlite-core/src/sqlite-core.utils.ts:553` 对字符串执行 `replaceAll('\0', '')`，改变了要匹配的值。quote 转义之后生成的 SQL 本身合法，所以没有错误能阻止误删。

实际批量写入口 `packages/rxdb-adapter-sqlite-core/src/rxdb_adapter_mutations.ts:188` 的 apply_removes 调用该生成器并把 SQL 交给 adapter.query，未传绑定参数；后续又按调用方请求的实体集合标记 removed、清缓存。单条删除生成器使用 `WHERE id = ?` + params，不需要丢弃 NUL，这也说明字符串值并非 SQLite 绑定不支持。

有界 Node 诊断加载冻结的批量删除生成器及字面量工具，使用真实 metadata normalization 与真实 SQLite：

1. `normalizeCreateEntity()` 保留主键 `id\0tail`。
2. 用参数化 INSERT 成功创建 `id\0tail` 与 `idtail` 两个不同主键。
3. 为前者生成的 SQL 实际是 `DELETE FROM "probe$nul_delete" WHERE "id" in ('idtail');`。
4. 执行后只剩 `id\0tail`，断言确认旁观行被删。

未 mock SQLite、SQL 生成或字符串处理。该诊断验证真实 SQL 误删，并静态核对批量写消费者；未运行整个 RxDB 删除事务。

## 修复方向

批量删除使用参数绑定，或在现有公开字符串生成器中明确拒绝无法无损内联的 NUL，不能把它映射成另一个主键。若新增参数化生成器，保留/明确处理现有公开返回类型兼容性，并按绑定上限分批。检查同一字面量工具用于初始数据播种、触发器分支身份等位置的无损性；补同时存在原 id 与去 NUL id 的批量删除回归，断言目标删除、旁观行保留及缓存一致。
