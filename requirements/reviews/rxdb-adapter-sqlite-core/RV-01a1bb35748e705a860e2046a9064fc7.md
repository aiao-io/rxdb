# RV-01a1bb35748e705a860e2046a9064fc7：OO1 缓存忽略 locateFile 回调变化，后续客户端加载错误 WASM

## 问题与影响

同一 JS realm 中先后创建两个 OO1 客户端，两者都通过 `locateFile` 指向自己的 WASM 资源，其他选项相同。第二次请求直接复用首个模块，第二个定位函数一次都不调用。第二个客户端明确选择的资源与其模块级扩展/版本因此被忽略；只有调用者恰好另外修改 `wasmPath` 等指纹字段才会重新加载。属于多客户端资源配置边界，定 P2；本次复现没有推断数据损坏。

## 证据与根因

源码快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`packages/rxdb-adapter-sqlite-core/src/sqlite-oo1-load.utils.ts:277` 生成指纹时只存 `hasLocateFile`，`packages/rxdb-adapter-sqlite-core/src/sqlite-oo1-load.utils.ts:299` 比较的也是存在性。两个不同回调都变成 true，实际函数身份被丢掉。该字段的注释承认这条限制，但它不是函数身份不可比较造成的限制：这里完全没有比较两个回调是否为同一个引用。

`packages/rxdb-adapter-sqlite/src/sqlite-official-load.utils.ts:43` 计算此指纹后，命中缓存会提前返回，连 `buildOo1InitOptions(options)` 都不执行。`packages/rxdb-adapter-sqliteai/src/sqliteai-load.utils.ts:47` 使用相同公共指纹、相同提前返回。与官方 loader 的公开 TSDoc（locateFile 改变时重载）及 `packages/rxdb-adapter-sqlite-core/src/sqlite-oo1-load.utils.ts:90` 的定位优先级不一致。

真实上游模块隔离复现，加载原公共工具、原官方 loader 的去类型模块，并保留真实 AsyncQueueExecutor 与 `@sqlite.org/sqlite-wasm` 初始化：

1. 回调 A 指向已安装的 sqlite3.wasm；回调 B 指向本组目录里相同二进制的另一份副本。
2. `await sqliteLoad({ locateFile: A })` 后 `await sqliteLoad({ locateFile: B })`：返回模块引用相同，A 调用 1 次，B 调用 0 次。
3. 保持 B，只额外增加一个 `wasmPath` 指纹值：此时按定位优先级仍应该用 B，实际也调用 B 并得到新模块。对照证明 B 的返回路径有效、初始化支持重新加载，前次跳过完全由指纹碰撞导致。

只为模块在评审组目录内可加载而重写导入路径；没有 mock loader、缓存函数、队列或上游 WASM 初始化。sqliteai 消费者已完整静态核对，未运行其二进制。

## 修复方向

在加载指纹中保留 `locateFile` 引用并按函数身份比较；同一回调复用，不同回调按既有配置变更规则重载。补两种后端对「A → B 不复用」「A → A 继续复用」的回归；不要用 `toString()` 把不同闭包误判相等。若要改变公开资源定位契约，应明确形成兼容性决策，不能把传入配置静默忽略。
