# RV-01a1baee8d39781aa6d3f95a08cd8d36：保存等待期间的新编辑被成功回填覆盖，后续 save 静默无操作

## 问题与影响

编辑已保存的实体并调用 save() 后，底层写入尚未返回时，用户继续修改同一字段。写入成功返回的整行只包含较早提交的值，但结果处理无条件覆盖当前实体并清空 modified 和 patch。较新的输入消失，后续 save() 也不会产生第二次 UPDATE。异步保存与继续输入是正常使用时序，定为 P1；本次验证的是实体编辑丢失，未发现数据库结构损坏。

## 证据与根因

证据快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`packages/rxdb-adapter-sqlite-core/src/repository/SqliteRepository.ts:85` 的 update() 先生成 SQL、等待 writeQuery()，再以 forcedUpdate=true 调用 addQueryCache()。结果处理在 `packages/rxdb-adapter-sqlite-core/src/transaction_sqlite_result.ts:131` 至 133 行直接 state.replace(entityObjectData)，将等待期间的编辑覆盖并纳入旧基线。公共仓库确实建立了状态检查点，但 `packages/rxdb/src/entity/entity-status.ts:372` 在 committed=true 时直接返回，收集的新编辑仅用于回滚，成功时被丢弃。

用实际 EntityManager.save()、Repository 门面、transactionalRepository 包装、SqliteRepository 与 SQL 生成/结果处理链复现；存储使用 Node 内置 SQLite 内存库，诊断适配器只控制 writeQuery 返回与事务调度：

1. 库中 title=original，水合为 local=true 的实体；改为 submitted 后开始 entity.save()。
2. writeQuery 已执行实际 UPDATE，但暂不返回结果；把 entity.title 改成 typed while saving。
3. 放行结果并等待 save 完成。实际 title=submitted、origin.title=submitted、modified=false、patch={}。
4. 再 await entity.save()，总写入仍为 1 次，物理行仍是 submitted；无并发编辑的对照组同样只有一次写入且行为正常。

原样运行诊断入口：`node <git-common-dir>/ai-review/v1/runs/full-main-20261108/save-during-write-probe.mjs`。诊断断言确认缺陷仍在，退出 0 不代表修复通过；未使用生产客户端的任务队列或触发器。

继续核对消费者后，PGlite 单条仓库并不调用 transaction_pglite_result：`packages/rxdb-adapter-pglite/src/repository/PGliteRepositoryBase.ts:54` 经 RepositoryBase.updateEntity() 调用 applyExternal()，会保留后续编辑。本条归因收窄到 SQLite 共享核心；PGlite 独立结果工具与批量写路径另行核实。

## 修复方向

在写入开始时明确本次提交的字段快照；成功后以数据库返回值推进基线，同时恢复或保留提交后产生的新编辑，重新计算 patch。统一核对创建、更新、批量写及两个后端的成功与回滚收尾，避免仅把全部写回改成普通 mergeExternal 而让已提交编辑一直残留。增加延迟写回时继续编辑同字段与其他字段、然后再次保存的回归。
