# RV-01a1bbbbcc987642b37fed8c02d8ae89：PGlite 批量保存空 patch 仍更新时间并追加伪变更

## 问题与影响

已保存实体把业务字段改动后又改回原值，状态可能是 modified=true、patch={}。单条 save 明确不写，SQLite 批量也跳过；PGlite 经 EntityManager.saveMany 的 mutations 路径仍发 UPDATE，仅改变 updatedAt/updatedBy，并追加一条 RxDBChange。没有业务差异的保存因此制造撤销/同步历史与通知，并推进实体新鲜度。不是等待中继续编辑后的 modified 清零问题；当前发现发生在下发 SQL 之前、输入 patch 已为空，定 P2。

## 证据与根因

冻结源码：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`packages/rxdb-adapter-pglite/src/rxdb_adapter_mutations.ts:156` 对所有收集到的实体都调用 generate_entity_update_sql，没有检查 status.patch 的键数。`packages/rxdb-adapter-pglite/src/entity/update_sql.ts:23` 随后即使无业务列仍注入 updatedAt；`packages/rxdb-adapter-pglite/src/table/trigger_sql.ts:233` 的差异集合包含 updatedAt，于是它确实记录 UPDATE。

消费者 `packages/rxdb/src/entity/entity-manager.ts:473` 的 saveMany 按 modified 收集并转 mutations；`packages/rxdb/src/entity/entity-manager.ts:600` 的单条 save 则同时检查 patch 非空。对照 `packages/rxdb-adapter-sqlite-core/src/rxdb_adapter_mutations.ts:165` 在 SQL 生成之前跳过空 patch。

有界实际验证使用真实原 PGlite：已有 title=bulk-updated 的实体先改再改回，确认 modified=true 且 patch={}。单条 await entity.save() 前后变更日志增量=0；重新做同样的改回操作，再调用 EntityManager.saveMany，日志增量=1，新增的是无业务内容的 UPDATE。

入口范围必须区分：`packages/rxdb/src/entity/entity-manager.ts:537` 交给 adapter.mutations，`packages/rxdb-adapter-pglite/src/RxDBAdapterPGlite.ts:471` 再交给事务执行器 mutations。PGlite adapter.saveMany 自身在同文件 562 行另走 UPSERT；诊断先用它发现并未触发 applyUpdates，随后改用真实 EntityManager.saveMany 核实上述缺陷，不把两个 API 混为一谈。

现有 rxdb_adapter_mutations.spec 覆盖正常 CREATE/UPDATE/DELETE，没有当前边界。已有 RV-01a1bb00a9827a22b7895a021202f6ce 的根因在回查后 updateCachedEntity 无条件清 modified，与本问题不同，没有重复新增它。

## 修复方向

在生成批量 UPDATE 前沿用 SQLite 的空 patch 守卫，确保没有可写差异的实体不发 UPDATE、不推进时间戳、不进回查更新集合。补改后改回、只读字段与真修改混合批次，核对 SQL、时间戳和 RxDBChange 增量。
