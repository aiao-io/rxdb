# RV-01a1bbbbcc4571dd8890be7126da6b2c：PGlite 批量更新直接采用整批墙钟，令领先时钟的 updatedAt 回退

## 问题与影响

实体已保存，当前 updatedAt 领先本机墙钟（例如导入或同步了未来时间，或时钟后拨）时，经公开 EntityManager.saveMany 保存业务修改，PGlite 的批量 UPDATE 会把 updatedAt 写回更早的整批 now。单条仓储会使用 getMonotonicUpdatedAt，SQLite 批量也逐行抬高，当前 PGlite 路径破坏相同的新鲜度契约。缓存/增量通知用 updatedAt 排序，合法新写因此可能被较新的缓存基线当成旧事件。触发条件是已有时间领先，按边界定 P2，不扩报普通墙钟递增的每次写入。

## 证据与根因

冻结源码：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`packages/rxdb-adapter-pglite/src/rxdb_adapter_mutations.ts:104` 在批次入口只取一次 now；`packages/rxdb-adapter-pglite/src/rxdb_adapter_mutations.ts:159` 给每一行 UPDATE 显式传 updatedAt:now。`packages/rxdb-adapter-pglite/src/entity/update_sql.ts:23` 原样采用该值。`packages/rxdb-adapter-pglite/src/repository/PGliteRepository.ts:76` 的单条路径反而调用 getMonotonicUpdatedAt；`packages/rxdb-adapter-pglite/src/pglite.utils.ts:64` 在 candidate 不超过 current 时返回 current+1ms。

触发器已经完整核对：`packages/rxdb-adapter-pglite/src/table/trigger_sql.ts:281` 为 AFTER 触发器，只记录 OLD/NEW 的差异并返回 NEW；没有 BEFORE 写入或 GREATEST 保护。真实引擎读回进一步排除了隐藏保护。`packages/rxdb/src/query/stale-event.utils.ts:45` 使用 cachedAt>payloadAt 判旧，说明该水位是实际消费者契约。

有界实际验证：真实内存 PGlite 与原始 adapter/SQL 生成/触发器；普通 SQL 绑定把现有行 updatedAt 设为 2035-01-01，再经真实仓储取回确认缓存时间；修改 title 后调用 EntityManager.saveMany。物理行实际从 2035-01-01T00:00:00.000Z 回退为 2026-11-08T15:16:01.959Z，业务修改成功。

入口范围必须区分：`packages/rxdb/src/entity/entity-manager.ts:537` 交给 adapter.mutations，`packages/rxdb-adapter-pglite/src/RxDBAdapterPGlite.ts:471` 再交给事务执行器 mutations。PGlite adapter.saveMany 自身在同文件 562 行另走 UPSERT；诊断先用它发现并未触发 applyUpdates，随后改用真实 EntityManager.saveMany 核实上述缺陷，不把两个 API 混为一谈。

现有 rxdb_adapter_mutations.spec 覆盖正常 CREATE/UPDATE/DELETE，没有当前边界。已有 RV-01a1bb00a9827a22b7895a021202f6ce 的根因在回查后 updateCachedEntity 无条件清 modified，与本问题不同，没有重复新增它。

## 修复方向

批量逐行使用与单条相同的 getMonotonicUpdatedAt(entity, now)，把整批 now 作为首选值而不是强制值。补已领先缓存时间、时钟后拨与同毫秒连续批量的回归，断言物理行时间严格晚于原值。
