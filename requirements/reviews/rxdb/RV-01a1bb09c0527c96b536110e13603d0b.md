# RV-01a1bb09c0527c96b536110e13603d0b：findAll 增量合并按未保存字段重新筛选，错误移除数据库仍命中的行

## 问题与影响

活查询按 done=false 筛选。用户把已命中实体的 done 编辑为 true 但尚未保存，随后另一来源只更新 title；JS 增量合并却把该行移出结果。数据库中的 done 始终为 false，显式重查时同一行又出现，查询结果取决于走 SQL 还是 JS。需要未保存筛选字段与外部事件并存，按边界条件定为 P2。

## 证据与根因

证据快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`packages/rxdb/src/query/merge-update-basic.ts:35` 至 38 行先安全合并外部 patch、保留本地未保存字段，再直接用当前可见实体判 where。相反，刷新门控在 `packages/rxdb/src/query/need_refresh_update.ts:102` 至 104 行已使用 persistedState()，把脏字段还原到 origin 后判定——SQL 查询也按持久化值筛选。门控与实际合并使用了两份不同的行状态。

真实 PGlite 内存后端、公开 Repository.findAll() 与实际触发器/通知链复现：

1. 保存 done=false、title=original 的行，订阅 findAll({where:done=false})，首次结果含该 id。
2. 在本地把 entity.done 改为 true，不保存。
3. 通过实际 SQL 只把该行 title 更新为 external title，并推进 updatedAt；等待数据库事件送达。活查询第二次发射 []。
4. 直接 SELECT WHERE done=false 仍返回该行；调用 repo.refreshAllQueries() 后活查询再次含该 id。实体 done=true、modified=true、patch={done:true}，草稿本身保留。

完整发射序列为 [[id],[],[id]]。没有替换 QueryTask、匹配器或序列化函数。

## 修复方向

查询成员资格、前后态分类与排序统一使用持久化状态，实体引用仍保留用户草稿；或者在相关筛选字段被本地编辑时回 SQL。核对 classifyUpdates 与 handleFindOneUpdate 是否有同类分歧，补脏筛选字段加无关外部更新、之后显式刷新仍得到同一成员集合的回归。
