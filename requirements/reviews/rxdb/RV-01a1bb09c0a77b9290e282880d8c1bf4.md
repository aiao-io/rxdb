# RV-01a1bb09c0a77b9290e282880d8c1bf4：日期 in 条件按 Date 引用比较，外部更新后活查询丢失仍匹配的行

## 问题与影响

DateRules 公开支持 in/notIn；SQL 按时间值匹配，JS 增量匹配却使用 Array.includes 的引用相等。实体水合出来的 Date 与调用方规则中的 Date 不是同一对象，即使毫秒值完全相同也判不命中。已由 SQL 命中的日期 in 活查询在无关字段更新后变为空数组，显式重查再恢复。日期集合条件是明确支持的少见分支，定为 P2。

## 证据与根因

证据快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`packages/rxdb/src/repository/query.interface.ts:244` 的 DateRules 包含 RuleIn。`packages/rxdb/src/query/query-matching.utils.ts:223` 至 225 行对标量直接 value.includes(entityValue)，没有使用该文件为日期等值和排序提供的 toEpochMs 按值归一。Date 对象经过实体构造、SQL 回读或事件反序列化后拥有独立引用，因此同一时间点不能通过 includes。

真实 PGlite 内存后端复现：

1. 保存 scheduledAt=new Date(2026-01-01T00:00:00.000Z)、title=original 的行。
2. 用另一个 new Date(同一时间点) 构建 scheduledAt in [date]，通过公开 Repository.findAll() 订阅；首次 SQL 结果含该行。
3. 只用 SQL 修改 title 并推进 updatedAt，scheduledAt 不变；实际触发器事件使活查询第二次发射 []。
4. 物理 SELECT 确认该行仍在且时间值未变；显式 refreshAllQueries() 后结果重新含该行，完整发射序列为 [[id],[],[id]]。

本次运行验证 in 的实际查询链；notIn 使用同一 matches 取反，尚未独立运行该分支。

## 修复方向

日期集合成员判断按时间值归一，与日期等值/区间比较保持一致，并保留字符串/数字等普通标量的现有语义。补不同 Date 引用、Date 与 ISO 负载、in/notIn 和外部无关字段更新的 SQL/JS 一致性回归。
