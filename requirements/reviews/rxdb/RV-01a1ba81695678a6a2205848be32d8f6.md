# RV-01a1ba81695678a6a2205848be32d8f6：共享查询错误分发期间的 retry 不会重新执行查询

## 问题与影响

同一查询先有 retry(1) 订阅者，再有一个普通订阅者时，第一次异步查询失败后，retry 仍命中正在分发失败的旧任务，没有执行第二次底层查询，还会立即收到同一次失败。没有第二名订阅者时相同 retry 代码能够成功重试。共享查询是否能恢复取决于其他组件的订阅和注册顺序；影响瞬时失败恢复，定为 P2。

## 证据与根因

证据快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`packages/rxdb/src/repository/QueryTask.ts:369` 直接遍历活的 observers Set 广播错误；某订阅者同步重试会在同一个 Set 里加入新观察者。`packages/rxdb/src/repository/QueryManager.ts:270` 至 275 行仍将失败分发中的任务当成可复用缓存，run() 的首次运行标志又使它不重启底层 runner。

公共 Repository.count() 复现使用返回 Promise 的仓库替身，符合 IRepository 的异步契约：第一次 count() 返回待结算 Promise，第二次本应 Promise.resolve(7)。先订阅 query.pipe(retry(1))，再订阅 query；拒绝第一次 Promise 后：

- 无第二订阅者：calls=2、seen=[7]、errors=[]；
- 有第二订阅者：calls=1、seen=[]，两个订阅者都收到 transient 错误。

不是网络一直失败：复现将第二次结果固定为成功，第二次调用根本没有发生。现有 QueryTask 测试覆盖直接 refresh 后恢复，但没有覆盖共享 RxJS 订阅者的同步重试。

## 修复方向

隔离当前错误分发与下一代订阅：重试应解析到新的可执行任务，错误只交给本轮失败对应的观察者快照。同步调整旧任务清理的身份守卫，防止旧 onClean(key) 删除同 key 新任务；保留直接 QueryTask.refresh 的现有恢复契约。补两名订阅者、两种注册顺序和有限重试回归。
