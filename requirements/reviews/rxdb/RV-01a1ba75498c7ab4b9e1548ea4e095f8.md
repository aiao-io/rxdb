# RV-01a1ba75498c7ab4b9e1548ea4e095f8：生成实体撞名时静默复用不兼容的用户实体

## 问题与影响

用户实体与仓储生成实体或多对多中间表恰好拥有同 namespace/name 时，生成分支只判断 key 是否存在，静默使用已注册实体。初始化可能成功，但生成表缺少所需字段或外键；后续图和多对多操作会访问不兼容结构。对于 entityGenerator，交换用户实体与源实体的注册顺序还会在成功与命名冲突之间切换。触发需要命名碰撞，定为 P2。

## 证据与根因

证据快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`packages/rxdb/src/schema/SchemaManager.ts:117` 发现生成实体 key 已存在就跳过，不校验定义来源或兼容性；普通实体注册在同一方法的前半段却会检查不同 class 争抢同 key。`packages/rxdb/src/schema/SchemaManager.ts:178` 的多对多生成分支同样直接复用任意已有 key，并在 193–194 行将它交给两个关系。

公共入口复现一：定义 UserRecord（name=GeneratedCollision，只有 userValue）及 GeneratedRecord（同名，只有 generatedValue），给 GeneratorSource 的仓储注册 entityGenerator。entities=[UserRecord,GeneratorSource] 时 init 成功，选中 UserRecord，propertyMap 不含 generatedValue；反向排列却抛实体命名冲突。

公共入口复现二：两端 CollisionUser.roles / CollisionRole.users 互为多对多，同时声明只有 payload 字段的用户实体 review_m2m.CollisionRole_CollisionUser。init 成功，roles.junctionEntityType 正是这个用户实体，junctionForeignKeys=[]。SQLite 与 PGlite 的 join_sql 根据 junctionEntityType 生成多对多连接，实际中间实体没有两端外键，不能完成该关系的查询。

既有 SchemaManager.registration.spec.ts 检查普通实体撞名和两条生成关系撞名，未覆盖生成实体与普通用户实体相撞。

## 修复方向

区分用户声明实体、仓储生成实体与中间表的登记来源，生成前校验命名冲突或完整结构兼容性；保留同一生成者在重入时的合法复用，以及 entityGenerator 原样返回已注册同一 class 的现有用法。给两种生成入口补撞名测试，并确保调换注册顺序不改变结论。
