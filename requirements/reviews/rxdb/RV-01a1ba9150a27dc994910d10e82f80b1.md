# RV-01a1ba9150a27dc994910d10e82f80b1：普通本表 CREATE 被误判成关系变更并触发整表重查

## 问题与影响

没有任何关系字段的普通实体，其 findAll 查询收到本表 CREATE 后仍走 SQL 整查，而不是已声明的 JS 增量路径。每条写入会重新读取完整结果，开销随表大小和活查询任务数放大。该错误不改变最终数据，属于可复现的查询性能退化，定为 P2。

## 证据与根因

证据快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`packages/rxdb/src/query/query-relation.utils.ts:119` 收集依赖时包含主查询实体自身；127 行据此把本表也认成关系实体，143–144 行又把普通当前事件加入 relation_entities。`QueryRulesBuilder.buildRelationWhereRulesForCreate()` 因 hasRelationChanges=true 选择刷新，merge_create 因此跳过增量维护。这个逻辑原本用于真正的自引用关系，但没有要求存在该关系。

公共 Repository 复现使用 relationMap 为空的 PlainRow，where 为空 and 组；初次查询空表，模拟持久化一行后发送完整 INSERT：

- findAll：底层 find 调用次数从 1 变 2，结果 [0,1]；
- 同条件 findByCursor：底层 find 只调用 1 次，结果同为 [0,1]，因为 separateEntities 专门排除了该类型的重复分类。

两组返回相同正确结果，证明第二次读取并非数据不足的必要降级。既有自引用测试使用确有自关联的 RelationNode，不能证明无关系实体的分类正确。

## 修复方向

主实体属于依赖集合不等于存在关系依赖。仅在实际自引用或查询关系条件需要时把本表事件同时放入 relation_entities；保留 EXISTS 与其他关系查询的 SQL 刷新，以及 count 为保证正确性而主动整查的策略。补普通无关系实体 CREATE 不额外查询的回归。
