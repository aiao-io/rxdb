# RV-01a1bba6d9b57b0491de54ab9130073b：getRepository 文档误称实体 save/remove 自动归属当前事务

## 问题与影响

TransactionExecutor.getRepository 的公开 TSDoc 声称：该仓库创建/加载的实体会登记到 executor，随后 entity.save()/remove() 自动属于本事务。使用者按此说明在事务内 get 一行、编辑、await entity.save()，会重新排队等待自己，事务无法结束；如果上层用超时/取消使外层回滚，先前排队的 save 仍可随后在独立事务生效。限定在错误文档引导的接入方式，按 P2 记录；事务仓库自身的显式 update/remove 并未因此失效。

## 证据与根因

冻结快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`packages/rxdb/src/transaction/transaction-executor.interface.ts:106` 附近的 getRepository 段落明确作出自动实体绑定承诺，与同文件类级 TSDoc 的“事务回调不能等待 entity.save”相反。实际 `packages/rxdb/src/entity/entity-manager.ts:435` 附近的实体保存始终进入真实数据库的公共仓库；事务仓库读取后创建实体引用也经同一 EntityManager，没有登记 executor 的分支。

`packages/rxdb-adapter-pglite/src/RxDBAdapterPGlite.ts:707` 的 createUncachedRepository 仅把 executor facade 交给仓库；实体引用仍由实际 rxdb.entityManager 维护。后续实体 save 进入 public transactionalRepository，再走真实 adapter.runInTransaction 新开排队事务，不能因最初读取来自 executor 而自动复用。

真实 PGlite 内存库有界复现：先存一行；在 adapter.transaction 回调里用 executor.getRepository(Row).get(id) 取出它，改 title 后发起 loaded.save()。为避免无界挂起，诊断不直接 await 这个 promise，而在35ms观察窗口后使外层受控回滚。实际外层占有事务时 save 未结算；回滚释放队列后它才结算，物理 title 变成 saved after rollback。

输出 settledInside=false、rolledBack=true、settledAfterOuterTransaction=true，说明该实体保存属于独立事务。复现没有替换保存、仓库、队列或事务实现；没有在真实业务库上运行。

## 修复方向

让方法级文档与类级规则、实际实现和 README 一致：经事务仓库的 update/remove 或 executor 的批量方法写入，实体实例方法是外部调用。补一个从事务仓库取实体后显式更新并回滚的文档/运行期对照，保留清晰的事务归属说明。
