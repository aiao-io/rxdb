# RV-01a1ba81690674fbb672a7c5d51ba7b1：命名空间可覆盖 RxDB 生命周期方法并污染共享原型

## 问题与影响

实体 namespace 是公开字符串配置，尚无保留名校验。`namespace: 'destroy'` 时 init 成功却把 db.destroy 改成普通对象，后续无法通过公开销毁入口释放实例；`namespace: '__proto__'` 时，登记实体会写入共享 RxDB.prototype，使没有注册该实体的其他实例也暴露它，且该属性不可配置。需要特定命名空间配置，定为 P2；未证明任何远程不可信输入通道，不将其描述为远程攻击。

## 证据与根因

证据快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`packages/rxdb/src/schema/SchemaManager.ts:219` 使用 Reflect.get 读取继承属性，把任意对象当作本实例的命名空间；读到函数或其他非对象时，222 行又直接用新对象覆盖同名 API。228 行随后把实体类装到所选对象上，没有核对该对象的所有权。

公开入口隔离复现：

- 定义 `Entity({ namespace: 'destroy', name: 'Row' })` 并 init，实际 initialized=true、typeof db.destroy=object、db.destroy.Row===Row；调用 db.destroy() 抛 db.destroy is not a function。该隔离进程通过 RxDB.prototype.destroy.call(db) 完成资源释放。
- 定义 `Entity({ namespace: '__proto__', name: 'PrototypeLeakedRow' })` 并 init，实际 RxDB.prototype.PrototypeLeakedRow===Row，另一份 entities=[] 的实例也读到同一属性；Object.getOwnPropertyDescriptor(...).configurable=false。两个实例均已销毁，污染只存在于该隔离 Node 进程。

两项配置均未被元数据验证拒绝，副作用发生在 SchemaManager 把实体挂到宿主命名空间时。

## 修复方向

命名空间容器必须归本实例持有，拒绝继承来的对象和会覆盖宿主 API 的保留名；对允许复用的用户命名空间记录明确归属，保留 catalog 等现有正常扩展。补不修改共享原型、其他实例不可见、生命周期方法保持可调用的回归。
