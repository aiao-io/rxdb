# RV-01a1baf64f8e79568c7e00e72bce1c09：一对多集合解绑后保存父实体不会提交子实体外键

## 问题与影响

已保存的父子实体存在可空外键关系，调用 parent.children$.remove(child) 后再 await parent.save()。子实体内存中的 parentId 变成 null，但保存父实体时没有任何 UPDATE，数据库仍保留原关联，重新读取后关系恢复。公开集合 API 声明操作后保存所属实体即可持久化；常规一对多解绑路径失效，定为 P1。

## 证据与根因

证据快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`packages/rxdb/src/entity/relation-helper.ts:148` 至 152 行先把子实体从父实体关系缓存移除，再调用子实体的 parent$.remove() 将其标脏。`packages/rxdb/src/entity/relation-cache.ts:278` 至 280 行对普通关系只 cache.delete(entity)，没有保留待保存的解绑对象。

父实体 save() 使用 getNeedSaveEntities() 遍历当前关系缓存；`packages/rxdb/src/entity/entity-status.ts:561` 至 572 行只遍历仍在关系集合里的实体，`packages/rxdb/src/entity/entity.utils.ts:393` 至 407 行据此收集待写对象。解绑后子实体已经不在这张图中，尽管它的 patch 是 {parentId:null}，也不会进入本次保存。文档 `website/docs/model-definition/relations.md:214` 至 230 行将 ONE_TO_MANY 与 MANY_TO_MANY 统一列为集合关系，示例是 remove() 后保存关系所属实体。

受控复现使用实际 RxDB / EntityManager / 关系访问器、公共事务仓库包装及 SqliteRepository，底层为 Node 内置 SQLite 内存库；诊断适配器提供事务调度：

1. 物理库中父 id=parent、子 id=child、parentId=parent；都水合为 local=true 的干净实体。
2. parent.children$.add(child) 登记已有关系，随后 remove(child)。此时 child.parentId=null、modified=true、patch={parentId:null}。
3. await parent.save()，写入次数=0，物理 parentId 仍是 parent。
4. 对照 await child.save()，写入次数变为 1，物理 parentId 才变为 null。

诊断入口：`node <git-common-dir>/ai-review/v1/runs/full-main-20261108/one-to-many-detach-probe.mjs`。现有关系访问器测试只断言 remove 转发和缓存调用，未断言保存父实体后的物理外键；共享关系套件没有覆盖该一对多解绑保存链。

## 修复方向

区分关系的当前成员与本次工作单元里待持久化的解绑对象，集合 remove() 后仍让根实体保存过程收集该子实体；提交成功后清理待写集合，失败时保留以便重试。避免把解绑误作删除子行。补充一对多 add/save、remove/save、失败重试与批量保存的物理库回归，并核对两个本地后端。
