# RV-01a1bb4f17da77b6b0e32e1bc1888a7a：字符串 CHECK 区间按 UTF-16 校验，与数据库字节序相反

## 问题与影响

字符串/枚举区间端点混合 BMP 高位字符与非 BMP 字符时，JS UTF-16 顺序与 SQLite BINARY / 约定的 PG C 字节序不同。合法的数据库区间会在元数据期被误报为反转；反方向本应拒绝的区间反而被编译成恒假的 BETWEEN 或恒真的 NOT BETWEEN。条件唯一索引 where 使用同一编译路径，也受该边界校验影响。需要这种 Unicode 端点组合，按 P2 记录。

## 证据与根因

冻结快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`packages/rxdb/src/entity/check-constraint.ts:264` 附近的 compareCheckLiteralValues 对字符串直接使用 a < b / a > b，却把它声明为按数据库字节序比较；`packages/rxdb/src/entity/check-constraint.ts:370` 附近据该结果判断端点反转。`packages/rxdb/src/entity/conditional-unique-index.ts:74` 同样调用 compileCheckRuleGroup。

有界复现使用实际公开 compileCheckRuleGroup() 与 transitionMetadata()，底层对照为 Node 内置 SQLite：

1. 端点 lower=U+F8FF（）、upper=U+1F600（😀）。SQLite SELECT lower < upper 返回 1，JS lower < upper 返回 false。
2. 合法 between [,😀] 被编译器拒绝，报“下界  大于上界 😀”。
3. 反向 notBetween [😀,] 被接受，生成 `("code" NOT BETWEEN '😀' AND '')`。实际 SQLite 用此 CHECK 建表后能插入任意普通文本，说明“反转边界必须拒绝”的保护在该输入下失效。

现有 check-constraint.spec.ts 的区间边界回归仅使用整数；Unicode 回归验证的是约束名的字节长度和可用字符，未比较字符串端点顺序。本次未运行真实 PGlite，只验证了实际 SQLite 对照及共享编译器行为。

## 修复方向

端点比较与约定的数据库排序规则一致，使用字节序或等价的有效 Unicode 码点顺序，避免依赖 JS 默认 UTF-16 比较或受 locale 影响的比较器。补字符串/枚举正向与反向区间，覆盖 BMP 与非 BMP 混合字符，并核对两个后端的编译/拒绝结果。
