# RV-01a1bb360421727ab98985c2ea7d81ee：含斜杠 ID 的路由测试实际只使用 UUID，遗漏编码边界断言

## 问题与影响

名为“id 里含 / 时经编码后能定位到行”的测试没有创建含斜杠 ID，使用缺省 UUID 再 encodeURIComponent。即使路由完全漏掉 URL 解码，普通 UUID 的 PATCH 仍会成功，该测试无法阻止其声明验证的编码 ID 回归。属于具体测试缺口，定为 P2；未声称当前 decodeSegments 实现已经有路由故障。

## 证据与根因

证据快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`apps/dev-rxdb-http-server/src/__tests__/server.spec.ts:470` 的标题承诺含 / ID；:473 创建请求仅含 title/status，:474 编码服务端生成的 ID，但没有断言这个 ID 含 / 或 %。`modules/recipes-domain/src/recipe-schema.ts:29` 为 ID 提供 uuid() 默认值，UUID 不含斜杠，encodeURIComponent 后与原串相同。该测试 :471 的“写端点不接受客户端指定 id”注释也已与实现冲突：`apps/dev-rxdb-http-server/src/recipes-repository.ts:263` 明确采纳 suppliedId，且同一个 server.spec.ts:155 已验证 client-supplied ID。

当前 `apps/dev-rxdb-http-server/src/server.ts:467` 附近的 decodeSegments 先 split 再逐段 decode，是该用例应该保护的边界：创建如 a/b 或 a%2Fb 的合法字符串 ID，再通过编码路径 PATCH 才会真正经过它。现有 UUID 请求对“解码存在/完全不解码”的两种实现没有区分能力。

## 修复方向

利用已支持的客户端 id 创建含 /、字面 % 或编码文本的 ID；断言实际创建的 ID 等于该值，然后经 encodeURIComponent 路径更新并按同 ID 回读。分别保护段拆分与只解码一次的语义。
