# RV-01a1bb467e017517894b50101207f734：共用 sqlite-wasm 客户端不校验数据库身份，第二个逻辑库仍访问首库

## 问题与影响

两个标签页经同一 SharedWorker 中的单一 SqliteClient 连接时，配置不同 dbName，第二次 init 仍成功，却继续使用首个库的连接。第二个逻辑库因此读取、写入首个库；适配器的跨标签事务锁反而按两个不同 dbName 分开，进一步失去互斥。仓库公开支持 SharedWorker 共用客户端，冲突名字应在连接时拒绝。定 P1，触发条件明确为共用客户端上不同库名，并非所有多标签连接都受影响。

## 证据与根因

源码快照：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`packages/rxdb-adapter-sqlite-wasm/src/SqliteClient.ts:97` 在已初始化时不比较 dbName / vfs / readonly 等配置，直接登记 owner 后返回；同文件 `packages/rxdb-adapter-sqlite-wasm/src/SqliteClient.ts:101` 的在途初始化分支同样只等待首个 promise。初次加载才在 `packages/rxdb-adapter-sqlite-wasm/src/SqliteClient.ts:321` 把名字交给 sqliteLoad。

真实消费者是 `packages/rxdb-adapter-sqlite-wasm/src/create_sqlite_client.ts:87` 的 `init(dbName, loadModuleOptions, owner)`。`packages/rxdb-adapter-sqlite-wasm/src/__tests__/sqlite-wasm-shared-client.worker.ts:16` 为全部连入端口 expose 同一个客户端，故第二个端口的 init 会进入上述提前返回。`packages/rxdb-adapter-sqlite-wasm/src/RxDBAdapterSqlite.ts:92` 又按各自 dbName 算锁名，不会识别它们实际使用首个连接。

Node 隔离诊断加载原 SqliteClient 与 executeHelper（TypeScript 去类型），仅在 sqliteLoad 模块边界注入真实 wa-sqlite WASM / MemoryVFS 连接工厂，保留真实队列、事件调度、SQL 执行与实体外的连接行为：先 init logical-a/owner-a 并写 A-only，再 init logical-b/owner-b，后者成功且 SELECT 得到 A-only；loader 实际只收到 logical-a。这个复现没有跑浏览器 Comlink，跨端口路由由上述真实 Worker 夹具静态核对。

已读的 wa-sqlite 客户端使用 assertSameIdentity 拒绝这类配置冲突，是同一仓库已有的可行语义；不能把不同名字静默路由到首库当作幂等。

## 修复方向

记录已初始化及在途初始化的规范化身份，对 dbName、VFS、readonly、fsRoot 和实际资源/锁配置逐项比对；只让等价调用共享初始化与登记 owner。补顺序/并发冲突初始化、两个 SharedWorker 端口不同库名、同名等价配置继续共享等回归。断开后重新初始化另一库的现有能力需保留。
