# Review：BOM 映射的已解析基线

## 结论

**当前剩余 1 个 P1，无新增 P0 / P2。** 对应 US-516 的映射跟进能力，不阻塞首轮的建图、展开、判环与数量切片；在 US-516 开工前必须补齐。

基线：`12276e04`。核对 epic-009、US-507～US-525 以及 US-030，共 21 个需求文件，内容指纹 `b8e7199a279296a9`。RV-081 的 7 项在需求合同层面可关闭，不在本报告重复列入；这不等于待建 BOM 实现已通过验收。

**✅ 值得做**：保留本轮对数值域、运行投影、ECN 依赖与头链范围的修订。

**⚠️ 需澄清**：跟进基线如何表达一次真实解析，而非只表达末端行的存储版本。

Epic 的真实业务解锁条件不变。本报告不建议扩张为自动 EBOM→MBOM 转换、联合成本分配或历史重放引擎。

## 问题

### P1-01：末端行发生项 ID 不能代表映射所依据的已解析结构

**证据**：

- [US-516「跟进基线」第 40～42 行](../stories/plugin/US-516-ebom-mbom-mapping.md#L40-L42)：只记录 `source_occurrence_id` 与 `target_occurrence_id`；用“源逻辑行当前有效发生项 ≠ 基线”判断跟进缺口。
- [US-516 第 33～39 行](../stories/plugin/US-516-ebom-mbom-mapping.md#L33-L39)：支持跨层映射及共享子装配的路径级映射，但 `source_line_path` 是稳定的**逻辑行** ID 序列，不能表达沿途发生项的更替。
- [US-508 修订选择](../stories/plugin/US-508-bom-view-resolution.md#L24-L28)：imprecise 行会选取评估日已生效的最新已发布修订，行发生项本身无须变化。
- [US-508 resolution manifest](../stories/plugin/US-508-bom-view-resolution.md#L43-L47)：解析结果已经记录命中的头、修订与发生项，可以复用其结构依据。

#### 反例 A：祖先用量变了，末端行没变，扁平化 MBOM 的需求已经不对

无损耗、无换算、各头基准量均为 1：

| 对象      | 确认映射时                                      | 祖先 ECN 生效后                       |
| --------- | ----------------------------------------------- | ------------------------------------- |
| EBOM：A→B | 每个 A 用 2 个 B，发生项 `ab_v1`                | 每个 A 用 3 个 B，发生项 `ab_v2`      |
| EBOM：B→C | 每个 B 用 5 个 C，发生项 `bc_v1`                | 仍是 5，发生项仍为 `bc_v1`            |
| MBOM：A→C | 扁平化为每个 A 用 10 个 C，发生项 `ac_m1`       | 尚未跟进，仍为 10，发生项仍为 `ac_m1` |
| C 的映射  | 源 B→C，目标 A→C；可带路径 `[line_ab, line_bc]` | 源行、目标行、逻辑行路径均未换 ID     |

ECN 使根级 C 的设计需求由 `2 × 5 = 10` 变为 `3 × 5 = 15`，但当前映射基线的两端仍是 `bc_v1` / `ac_m1`；只比较这两个发生项 ID 不会列出应跟进的 MBOM C 行。

即使祖先 B 本身有一条 `removed` 映射并产生另一条提示，也不能替代对扁平化 C 行的跟进判定：B 的制造侧结构删除关系可以继续成立，C 的制造用量仍必须复核。

#### 反例 B：imprecise 解析到新修订，行发生项根本不会变

EBOM 的 C 行发生项为 `c_src1`，`child_revision_id = NULL`。确认映射时解析到 C_D，MBOM 对应行 precise 锁 C_D。随后 C_E 发布并进入评估日的选择范围：

- EBOM 解析结果变为 C_E；MBOM 仍锁 C_D，应标为待人工复核。
- `c_src1` 没有任何改写，目标发生项也没变；存储的 `source_occurrence_id` / `target_occurrence_id` 全部仍相同。
- 基线没有记录确认时实际选中的 C_D，仅凭末端发生项 ID 无法比较解析修订变化。

**证据等级**：两个场景都是依据当前文档的合同反例；独立十进制/身份比较探针复核了 `10 → 15` 与“发生项 ID 不变但已解析修订变化”。没有声称待建插件已出现运行期漏洞。

**问题边界**：这不是要求推翻头链范围或禁止跨期预建映射。新头链已经修复另一根头的行混入范围的问题；本条讨论的是在给定 `ResolutionContext` 下，已确认映射的**解析依据**改变后能否正确告警。稳定业务身份与版本基线是两层合同，前者不能代替后者。

## 根因

1. 行发生项是存储版本，不是解析版本：imprecise 的修订选择可能独立变化。
2. 跨层重构把祖先路径的用量带到目标行，末端行版本不是全部依赖。
3. 路径 ID 刻意使用逻辑行以保持身份稳定，这个选择本身正确，但需要另存解析依据来检测变化，不能把“路径身份没变”当作“工程依据没变”。

## 修复方案

### 最小合同

- 保留 `source_line_id` 和逻辑行路径作为稳定身份。
- 将人工确认时的**源侧已解析结构依据**纳入基线，至少覆盖相关路径上的发生项、实际选中的修订和头；复用 US-508 manifest 的结构字段，不新建历史重放引擎。
- 路径级映射只比较该路径的解析依据；行级映射明确比较其作用范围内的相关源路径集合。不能只检查路径末端。
- 跟进查询先按当前 `ResolutionContext` 解析，再与上述基线比较；祖先发生项或实际选择的修订变化时，列出对应目标行待复核。
- 保留人工“确认跟进”作为裁决点。无需自动推导 MBOM 的正确数量，也不要求源目标行裸数量相等；确认后推进完整基线，而非只改末端发生项 ID。
- `as_of_date` 字符串变化本身不是工程变更；比较实际解析依据，避免每天把未改变的映射重新标红。公式参数和换算率是否纳入跟进口径应写出边界，不能默认为已被发生项 ID 覆盖。

### 补充 AC

| #   | 场景                                                  | 必须得到的结果                                                                           |
| --- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 1   | 反例 A：A→B 从 2 改 3，B→C 仍为 5，C 的末端发生项不变 | 列出扁平化 MBOM 的 C 行待跟进，能指出祖先发生项 `ab_v1 → ab_v2`；不能因 `bc_v1` 不变吞掉 |
| 2   | 反例 B：EBOM imprecise C_D→C_E，MBOM precise 仍为 C_D | 源发生项不变仍标待复核，基线与当前解析修订分别可见                                       |
| 3   | 源行 precise 锁 C_D，之后 C_E 发布                    | 实际解析仍为 C_D，不因此产生跟进缺口                                                     |
| 4   | 反例 A 人工改好目标并确认，再查询；随后祖先再改一次   | 确认后缺口消失，再次祖先变化后重新出现；推进的是完整解析基线                             |
| 5   | 相同解析依据，只改变评估日到另一个没有结构变化的日期  | 不产生假缺口；相同输入与数据快照下结果稳定                                               |

以上随 US-516 交付，不把它变成首轮切片的额外前置。
