# RV-01a1bb58e24373e3aeecc4babbc98555：undo 选取后新增的推送认领不再复核，已上行变更仍被本地撤销

## 问题与影响

同一进程内，undo 先选出未推送的 INSERT，随后 push 才认领并发送它，undo 仍会把该行从本地删掉。远端回执到达后源 change 同时带 remoteId 和 revertChangeId，本地已经回滚，远端仍有该行；后续 push 排除这条变更，既没有补偿 DELETE，也不会重推，形成持续分叉。无需多标签页或损坏输入，只需要自动同步与用户撤销并发。属于同进程隔离契约失败，定为 P1。

## 证据与根因

完整冻结 SHA：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

1. `packages/rxdb-plugin-history/src/undo-redo-apply.ts:103` 只在选取历史时读取一次 `pushInFlight.snapshot()`，构造静态 lastPushedMap。
2. `packages/rxdb-plugin-history/src/history-scope-api.ts:239` 起用该快照过滤可撤销项，再进入 apply。
3. `packages/rxdb-plugin-history/src/undo-redo-apply.ts:162` 等待 change sequence，随后还有适配器解析和写队列等待，push 可以在这些窗口里开始认领。
4. `packages/rxdb-plugin-history/src/undo-redo-apply.ts:213` 的写事务 prepare 复核分支、undo session 和子分支分叉点，**没有**重新核对实时推送认领、已推水位或 change 的已推状态。认领本身不切换 undo session，故它不会被 session 身份守卫挡下。
5. `packages/rxdb-plugin-history/src/push-inflight.ts:39` 的既有契约已解释为何 undo 不能越过在飞认领：撤销只标原 change，不生成可推出的补偿变更。
6. `packages/rxdb-plugin-sync/src/push-repository.ts:1024` 接受远端 applied 回执，后续只落回执/水位。正常 applied 不做被拒对齐，无法把已撤销的本地行自动修回来；下轮待推查询排除 remoteId 非空或 revertChangeId 非空的源行。

有界复现 `repro-history-undo-after-push-claim.cjs` 加载真实源 `createHistoryScopeApi`、fetch/apply、过滤器、认领登记及公共 `pushRepository`，复用现有 push 测试的 I/O 接缝。只在 getRxDBChangeSequence 与远端回执设置门闩，不靠 sleep 猜时序：

- 调 `api.undo()`，等它完成选取并进入 sequence 读取；此时没有认领。
- 调公共 push，等真实规划认领 `public:User → 1` 且远端替身已执行 INSERT，暂不回执。
- 使用此刻真实过滤器重新计算，`currentCandidates=0`，证实当前判据本应拒绝撤销；原 undo 却仍执行删除与 revert 标记。
- 放远端回执，push 返回 pushed=1；再次 push 返回 0。

实际断言全部成立：`localRows=0, remoteRows=1, revertChangeId=101, remoteId=101, pushed=1, retryPushed=0, remoteCalls=1`。适配器 SQL/网络是受控接缝，应用动作、认领、过滤、回执和后续推送选择均走真实源码；未运行真实后端并发集成测试。

现有 `packages/rxdb-plugin-history/src/__tests__/push-inflight.spec.ts` 只覆盖「选取前已经存在认领」时的纯过滤器，没有覆盖选取与落库之间才认领的顺序。

## 修复方向

让 undo 写入与 push 的选取/认领共享同一套不可穿透的仲裁：在真正应用前按当前认领与已推状态复核，并确保复核到写入之间 push 不能再认领同一变更。只在 fetchLatestHistories 多读一次仍有窗口。push 也应避免发送在其选取后已被撤销的旧快照。补双向顺序的确定性回归，分别断言本地/远端终态、源 change 标记和后续推送，不只测快照过滤器。
