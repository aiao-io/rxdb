# RV-01a1bb5d87e87965ba5946993b203713：同毫秒同实体的历史指纹碰撞会让一次 redo 删除多项重做记录

## 问题与影响

同一实体的两次独立 UPDATE 拥有相同的 createdAt 毫秒值时，两条不同 change id 的历史会得到相同 fingerprint。分别撤销两次后，`redo(1)` 只应用一条历史，却把两条都从重做栈移除；另一条仍被 revert 标记，后续 redo 没有候选，用户失去尚未重做的操作。createdAt 从未承诺唯一，这种输入合法；触发需要时间碰撞，按 P2 记录。

## 证据与根因

冻结 SHA：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

- `packages/rxdb-plugin-history/src/history-item-builder.ts:48` 的指纹只含 type、entityId、createdAt.getTime()，没有 changeId / transactionId，两个独立 UPDATE 可以完全相同；namespace 和 entity 也未参与。
- `packages/rxdb-plugin-history/src/redo-stack.ts:65` 用 fingerprint Set 匹配待移除项，`:67` 与 `:69` 一次匹配并删除全部同指纹历史。它把非唯一展示指纹当成唯一身份。
- `packages/rxdb-plugin-history/src/HistoryManager.ts:489` 将移除操作直接委托 RedoStack；`packages/rxdb-plugin-history/src/undo-redo-apply.ts:241` 起的 redo 出口把本次实际应用的 histories 交给该方法。

有界反例 `repro-history-redo-fingerprint-collision.cjs` 使用真实 createHistoryItem/RedoStack/createHistoryScopeApi/applyUndoRedoHistories。构造 changeId=1、2 的两次 UPDATE，同一实体、createdAt 相同，值依次 0→1→2，两个 change 都处于已撤销状态；栈顺序为 [第一次 UPDATE, 第二次 UPDATE]（分别 undo 两次后的形状）。经公共 scope API 调 redo(1)：

- appliedOperations=1、value=1，只有第一项被重做；
- removedHistories=2、remainingRedo=0，第二项却随同移除；
- secondChangeStillReverted=true；再调 redo(1) 也不再执行写入。

所有断言通过，适配器写入为受控接缝；没有依赖数据库时钟碰巧撞上，也没有证明某个后端的碰撞频率。

## 修复方向

用日志中的持久唯一身份区分独立历史项：普通历史可以取 change id，事务历史可以取 transaction id 或有序 change id 集合，并保留跨重读的稳定性。也可在 RedoStack 移除时按真实历史身份比较，但不能继续假定 type/id/time 唯一。补相同时间的同实体两次 UPDATE，以及跨 namespace 同 id 的选择性 redo 回归。
