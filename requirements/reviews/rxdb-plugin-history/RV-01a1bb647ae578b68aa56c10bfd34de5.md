# RV-01a1bb647ae578b68aa56c10bfd34de5：squash 合并把删旧行后重建再删误判为幽灵操作，遗漏最终删除

## 问题与影响

main 上已有 id=X 的 A，从它分出的 feature 依次 DELETE A、INSERT 同 id 的 B、DELETE B。feature 最终不存在 X，合回 main 应删除 A。默认 squash 策略却报告 merged=0、一个写操作也不发，A 继续留在 main；同样输入的 normal 策略会正确删除。合并预览共用 squash 计算，也会隐藏这项实际删除。只有「本批开始前已存在、批内又重建再删」组合触发，按 P2 记录。

## 证据与根因

完整冻结 SHA：`0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

- `packages/rxdb-plugin-history/src/merge-branch.ts:88` 起的 squash_source_changes 先调用本包 get_switch_version_actions；该折叠原本保留最终 DELETE。
- `packages/rxdb-plugin-history/src/merge-branch.ts:90` 把本批出现过的所有 INSERT 键收进 createdInSource，没有区分它是否在本批开始前已存在。
- `packages/rxdb-plugin-history/src/merge-branch.ts:92` 对这些键一律删除 actions.deletes，导致上述真实删除变成零净操作。真正可抵消的幽灵操作，应以本批首个有效操作是 INSERT 为前提。
- `packages/rxdb-plugin-history/src/merge-branch.ts:243` 起按剩余动作数计算 merged；归零时提前返回，目标库不再发生删除。

有界反例 `repro-history-squash-delete-recreate-delete.cjs` 加载真实 merge_branch 和 squash_source_changes，以相同源日志和初始目标 A 分别执行两种策略。存储接缝只应用真实产出的 actions，分支校验与控制流保持真实：

- squash：merged=0、targetRows=1、writes=0；
- normal：merged=3、targetRows=0、writes=3。

这是独立于 core.compactChanges 的根因：history 调用自己的 get_switch_version_actions，最终 DELETE 被本函数后置的幽灵过滤删掉。没有因为 core 压缩删除的 inversePatch=B 而重复建记录，也未登记 core 覆盖。

## 修复方向

按每个实体本批第一个有效操作判断初始存在性，只抵消真正从不存在开始的 INSERT→DELETE；保留 DELETE→INSERT→DELETE 对批次起点的删除贡献。让 preview 与真实 squash 继续共用同一份判定，补与 normal 策略的终态对照，并覆盖 DELETE→INSERT 的替换场景。
