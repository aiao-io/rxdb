# RV-01a1bb29b3e17701944ef043b8c14bf5：再次解锁清除旧密钥时未取消在途解密，锁定后仍返回明文

## 问题与影响

已解锁并开始读取加密单元格后，再次调用 `unlock()`；本次密钥输入无效或 provider 失败，keyring 按设计清除原密钥并保持锁定。在途的旧 `decrypt()` 却仍成功返回完整明文，而 `isLocked === true`，`lockChange$` 也已发出 true。失效的解锁尝试与在途加密读取交错时，锁定态隔离被绕过。属于边界时序，定 P2；本次未证明落盘数据损坏，也未推断远程越权。

## 证据与根因

全部源码证据来自冻结快照 `0ffa3c419fcc59dc3e13d695ca4658116134bfa0`。

`packages/rxdb-adapter-encrypted/src/keyring.ts:391` 的 `performUnlock()` 先调用 `resetKeyState()`。`packages/rxdb-adapter-encrypted/src/keyring.ts:382` 的重置只清 key/kid、计时器与策略，发出锁定事件，不增加 `lockEpoch`。随后无效 keyBytes 在 `packages/rxdb-adapter-encrypted/src/keyring.ts:450` 导入时拒绝，保持锁定。

`packages/rxdb-adapter-encrypted/src/keyring.ts:291` 的 `decrypt()` 在进入时保存旧 key/kid，WebCrypto 完成后仅用 `packages/rxdb-adapter-encrypted/src/keyring.ts:346` 的 epoch 比较判定取消。重新解锁的重置未改变 epoch，故仍返回旧明文。相同根因也使在途 `encrypt()` 的完成屏障失效。显式 `lock()` 在 `packages/rxdb-adapter-encrypted/src/keyring.ts:253` 增加 epoch，因此对照组会拒绝。

消费者并未额外取消这类操作：`packages/rxdb-adapter-sqlite-core/src/RxDBAdapterSqliteBase.ts:581` 和 `packages/rxdb-adapter-pglite/src/RxDBAdapterPGlite.ts:249` 的 facade 直接转发 `unlock()`；`packages/rxdb-adapter-sqlite-core/src/sqlite-core.utils.ts:710` 等待 `keyring.decrypt()` 后将返回明文反序列化到实体。

隔离 Node 复现直接加载冻结实现去类型后的模块，使用真实 WebCrypto、RxJS 与内存单例存储，未改业务源码：

1. 用 32 字节 keyBytes 解锁并产生一份加密信封。
2. 启动 `decrypt()`，同 tick 调用 `unlock({ keyBytes: new Uint8Array(1) })`。
3. 等待第二次解锁拒绝，确认 `invalid_key_bytes` 且 `isLocked === true`。
4. 等待原解密，实际成功得到 `secret-in-flight`。
5. 重新正常解锁，启动同样解密后显式调用 `lock()`，实际按预期拒绝 `locked`。

## 修复方向

统一所有使密钥失效的状态转换与敏感操作取消屏障。重新解锁时也应令旧的 encrypt/decrypt 失效，同时保留当前解锁尝试自身的取消基线；不要仅在 `resetKeyState()` 中递增 epoch 而使每次 unlock 都取消自己。补充无效凭据、provider 拒绝和慢 provider 期间旧 decrypt/encrypt 的交错回归。
