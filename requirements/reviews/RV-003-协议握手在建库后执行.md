# Review：协议握手在建库后执行

## 问题

🔴 High。US-207 AC#9 明确要求 host/renderer 版本不一致时“连接失败且不建库”，但当前版本号只在
`open` 响应里。两套 host 已经创建目录、数据库文件和 session 后，renderer 才能发现不匹配；
失败还拿不到可管理的 `DesktopSqliteClient`，因此不会主动关闭刚创建的 session。

`DesktopSqliteClient.connect()` 发送的 `open` 请求不带版本
（[desktop-sqlite-client.ts](../../packages/rxdb-adapter-desktop/src/desktop-sqlite-client.ts#L183)）：

```ts
const request = { kind: 'open', storage, batchTimeout: options?.batchTimeout } as const;
const response = assertDesktopHostResponse('open', await transport.request(request));
const opened = parseDesktopHostOpenResult(response.result);
```

Electron 的 `createElectronSqliteHost().open()` 先调用 `NodeSqliteEngine.open()`、写入 `sessions`，再把
`protocolVersion` 放进结果
（[desktop-sqlite-host.ts](../../packages/rxdb-adapter-desktop/src/desktop-sqlite-host.ts#L191)）。Tauri 的
`Host::open()` 顺序相同：`resolve_database_path()` → `Engine::open()` → `table.insert()` → 响应版本
（[session.rs](../../apps/dev-rxdb-tauri/src-tauri/src/rxdb/session.rs#L125)）。

现有 `refuses a host that speaks a different protocol version` 用例只篡改已经成功的 `open` 响应，
仅断言客户端抛错
（[desktop-sqlite-client.spec.ts](../../packages/rxdb-adapter-desktop/src/__tests__/desktop-sqlite-client.spec.ts#L63)）；
它没有断言路径解析器未调用、库文件不存在或 `openSessionCount === 0`。因此测试为绿不能证明 AC#9。

## 根因

把协议版本当成响应字段校验，而不是任何有副作用请求之前的握手。对“新 renderer + 旧 host”而言，
只给 `open` 新增 `protocolVersion` 字段也不够：旧 host 会丢弃未知字段，仍然先建库。

## 修复方案

新增无副作用的 `handshake`/`hello` 请求，`DesktopSqliteClient.connect()` 必须先完成版本协商，再发送
`open`。旧 host 不认识新请求时只返回 `protocol_violation`，不会触碰文件系统；新 host 则必须拒绝
未握手或版本不匹配的 `open`，覆盖“旧 renderer + 新 host”。

Electron 与 Tauri 各补双向版本偏差测试，至少断言：路径解析器未调用、应用数据根不存在、会话数为
0。修复落地前，US-207 AC#9 不能标 ✅；US-210 AC#10 也应继续保持 ⚠️。

## 解决记录

会话泄漏那一半已在 `local-db` 分支落地（`open` 解析失败先关会话再抛错），此处不再展开；「握手先于建库」仍未落地，待开 PR。

**未修（真正的「不建库」）**：新增无副作用的 `handshake` / `hello` 请求，把版本协商挪到 `open` 之前。

- 这需要两端各加一个请求类型（TS host + Rust host + 协议解析 + 双向偏差用例），
  换来的是「版本不匹配时磁盘上不留一个空库文件」——库文件本身无害，下次连上的正确版本会照常用它
- 触发条件是 renderer 与 host 来自不同版本。Electron 路径上两者同一次打包，结构上不可能漂；
  真正会漂的是 Tauri（Rust host 手抄第二份），而那条路径现在由
  `conformance/protocol-handshake.spec.ts` 在 CI 里钉着
- 按 US-207 AC#9 的字面要求，这条 AC 仍不能标 ✅；US-210 AC#10 的版本绑定已由一致性握手用例关闭，
  但「握手先于建库」不在其中
- 若要做，形态按本文档「修复方案」节原样：旧 host 不认识新请求只会回 `protocol_violation`，
  碰不到文件系统；新 host 拒绝未握手的 `open` 以覆盖「旧 renderer + 新 host」
