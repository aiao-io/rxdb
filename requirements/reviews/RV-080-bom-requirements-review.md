# Review：BOM 需求深度评审

## 结论

**🟡 领域拆分方向合理；🔴 当前跨故事合同不够一致，不能按现文直接进入完整 Epic 的开发。**

- **10 个 P1 + 5 个 P2，无 P0。** 此处 P1 表示对应能力开工前必须修正的需求矛盾或关键合同缺口，不表示已有生产事故。
- **✅ 值得做**：在真实驱动出现后，按首轮切片验证结构、展开、判环和数量。
- **❌ 不值得做**：在没有真实业务驱动时启动完整的 19 条故事；不应以这次评审代替 Epic 的解锁条件。
- **⚠️ 需澄清**：数值边界、ECN 的候选态与运行态、跨层映射身份、联产输出与成本归属。

评审基线：`abb34952`；覆盖 [epic-009](../epics/epic-009-bom-domain-model.md)、US-507～US-525 全部 19 条故事，交叉核对 US-030、roadmap、status-overview，以及现有实体属性与 PGlite 数字映射。当前没有 `packages/rxdb-plugin-bom`，因此以下不是 BOM 实现缺陷报告。

### 证据等级

- **源码实证**：实际读取了现有实现；仅涉及通用基础设施，不推称待建 BOM 已有缺陷。
- **合同探针**：用独立的内存 SQLite、实际 PGlite、十进制算术或排序反例复核需求的后果；不是待建插件的回归测试。
- **文档推断**：由两条需求或一个未定义的合同推导出风险；没有冒充运行期实测。

## 问题

### P1-01：34 位精度只规定了计算，没有规定无损输入、存储与导出

**证据**：US-511「精度与舍入」和「舍入只在需求行上发生」要求 34 位有效数字、位级一致；[US-511 第 47～50 行](../stories/plugin/US-511-bom-quantity-semantics.md#L47-L50)。现有 [PropertyType](../../packages/rxdb/src/entity/property-types.interface.ts) 没有 decimal；[rxDBColumnTypeToPGliteType](../../packages/rxdb-adapter-pglite/src/pglite.utils.ts) 把 `PropertyType.number` 映射到 `double precision`，`assertFiniteNumber` 的说明明确要求任意精度改用字符串承载。

**问题与反例（源码实证 + 合同探针）**：输入 `1.000000000000000000000000000000001`，经过 JS number 或 PGlite double precision 回读为 `1`。显式以文本进入 PGlite numeric 则保留原值。把已损失精度的 number 再交给 34 位计算库，不能恢复原输入。当前需求没有选定数量、换算率、概率、费率、价格等字段的无损表示。

**建议**：在 US-507 / US-511 / US-514 / US-521 共同定义 decimal 值合同。优先采用插件局部的规范十进制字符串和值对象，不为 BOM 自动扩张核心类型系统；明确数据库表示、JSON 表示、校验、排序及范围比较如何保持数值语义。范围字段若暂用整数或有限精度，也必须显式声明，不把词法字符串比较当数值比较。

**补 AC**：34 位输入经 UI/导入 → 存储 → 回读 → 计算 → 导出，全程无 number 中转，SQLite 与 PGlite 输出一致；包含最小差异值、负值、指数表示与非法值。**阻塞首轮步骤 1～3。**

### P1-02：只检查边端点更新，遗漏改变图作用域与归属的写入口

**证据**：[US-509 第 24～28 行](../stories/plugin/US-509-bom-dag-cycle-detection.md#L24-L28) 按 `(bom_type, org_id)` 判环，只列发生项插入、`child_item_id` / `flow_direction` 更新；只宣布 `bom_header.parent_revision_id` 与修订 `item_id` 不可改。[US-510 第 41～43 行](../stories/plugin/US-510-bom-multilevel-explosion.md#L41-L43) 的可达性维护同样只列发生项写入口。

**问题与反例（文档推断）**：组织 X 有 A→B，组织 Y 有 B→A。把 Y 的头改到 X，不需要修改任何发生项，即在 X 内产生环。改头的 `bom_type`、把 `bom_line.bom_header_id` 换到另一头、改发生项的 `bom_line_id`，也会改变所属图或父端点。现文没有禁止这些更新，也没有要求它们重检环及维护可达性。

**建议**：把结构身份/归属列创建后不可修改作为存储合同，包括头的类型/组织/父修订、逻辑行所属头、发生项所属逻辑行。需要移动就删除/重建草稿对象，走已有校验；不要增加多套隐式迁移路径。若必须支持移动，另行穷举旧作用域删除、新作用域插入的原子协议。

**补 AC**：直连 SQL 逐一更新上述归属列；要么统一拒绝，要么重检后拒绝成环且保持 `bom_reach` 一致。**阻塞首轮步骤 1～2。**

### P1-03：ECN 草稿允许临时重叠，与 US-030 的即时排他不是同一合同

**证据**：[US-515「发布是校验点」](../stories/plugin/US-515-bom-change-management.md#L81-L84) 允许草稿中间态暂不合法，发布时校验发生项重叠；[US-030「区间排他的声明与语义」](../stories/core/US-030-declarative-storage-constraints.md#L218-L228) 明确两端逐行即时检查、不提供延迟检查；[US-507 AC#9](../stories/plugin/US-507-bom-graph-skeleton.md#L69-L71) 要求草稿发生项保存时也拒绝区间重叠。

**问题与反例（合同探针）**：旧发生项 `[2026-01-01, +∞)`；先插入挂 draft ECN 的后继 `[2026-11-01, +∞)`，即时排他在插入期就拒绝，根本到不了 ECN 发布。先截旧再插新则可构造简单替换。因而问题不是「ECN 全部无法实现」，而是文档同时承诺“草稿允许这类非法中间态”和“每行即时合法”。US-515 AC#9 所需的重叠草稿如何保存也未定义。

**建议**：明确选择一种：首轮延续即时排他，ECN 编辑遵循收窄旧区间 → 插入新区间的受限协议，并收窄“草稿可不合法”的范围；或者把 ECN 候选时间线与已发布运行时间线分开。不要只把校验移动到发布而留下同表即时排他，亦不要取消直连 SQL 保障。

**补 AC**：正常替换的允许写入顺序、错误顺序、两张未来 ECN 改期、撤回与恢复；明确哪些错误发生在保存、哪些在发布，且两端一致。**阻塞 US-515。**

### P1-04：ECN 对 DAG 的“可见性”定义直接反转了并集政策

**证据**：[US-509 第 24～26 行](../stories/plugin/US-509-bom-dag-cycle-detection.md#L24-L26) 明确所有已存发生项都参与判环，包含 draft 头和 draft ECN；[US-515 第 106～107 行](../stories/plugin/US-515-bom-change-management.md#L106-L107) 及 References 又写“并集只算可见发生项”。US-508 明确 draft ECN 的发生项对解析不可见。

**问题与反例（文档矛盾）**：已存 A→B，draft ECN 引入 B→A。按 US-509，写入时必须拒绝；按 US-515 的可见集合，草稿可写入、发布才拒绝。两种实现的触发器、错误时机与 `bom_reach` 内容都不同，不能共享同一套 AC。

**建议**：遵守 Epic 已确认的并集政策，删除 US-515 的“只算可见发生项”；明确成环草稿本来就不能保存。把发布期重检定位为原子一致性检查，而非首次允许触发环校验的位置。若决定放宽，则同步修改 US-509 / US-510 / Epic，而不是只改单句。

**补 AC**：draft 头、draft ECN、未来 released ECN、取消 ECN 四态对并集的贡献；解析不可见不等于判环不可见。**阻塞 US-515；应在首轮定 schema 时先统一政策。**

### P1-05：已发布头的 ECN 写入白名单缺少逻辑行与其他成员表

**证据**：[US-507 两层行身份](../stories/plugin/US-507-bom-graph-skeleton.md#L37-L48) 区分 `bom_line` 与 `bom_line_occurrence`；[US-515 写入白名单](../stories/plugin/US-515-bom-change-management.md#L93-L105) 只穷举发生项和位号，其余一律拒绝；US-515 AC#2 要支持“新增”。US-512 的替代成员、US-520 的工序分摊也属于发布后不可直连改写的成员。

**问题与反例（文档推断）**：在已发布 H 下通过 ECN 新增 line_no=40，先要创建新的 `bom_line`；该逻辑行本身没有 `ecn_in_id`，白名单没有对应形态。给新发生项补替代组成员、工序分摊也没有放行协议。若一律拒绝，合法变更建不出来；若这些表无保护，又能直接修改已发布聚合而绕过校验。

**建议**：补一张完整的“表 × 操作 × draft/released × ECN 状态”矩阵。至少闭合逻辑行创建、替代组/成员、工序分摊、位号的准备与取消；说明无发生项的逻辑行是否不可见、何时可清理。头上不能经 ECN 修改的字段显式列为需新修订，不留默认放行。

**补 AC**：一张 ECN 同时新增逻辑行、创建其发生项与子表、发布、取消；协议外的直接子表修改全部拒绝。**阻塞 US-515 与替代/工序组合交付。**

### P1-06：替代组与阶梯组的聚合没有时间切片，正常行变更会制造非法聚合

**证据**：[US-512 第 24～33 行](../stories/plugin/US-512-bom-substitute-group.md#L24-L33) 的成员引用发生项，要求原始集合恰好一个 primary；[US-512 第 87～93 行](../stories/plugin/US-512-bom-substitute-group.md#L87-L93) 明确发布校验原始录入集合，运行才过滤有效成员。[US-511 第 134～139 行](../stories/plugin/US-511-bom-quantity-semantics.md#L134-L139) 对同头阶梯组禁批量区间重叠，但未说明如何与发生项日期求交。

**问题与反例（文档推断）**：primary 的 o1 在 11 月 1 日截止，o2 当日接续，且两者都属于同一个替代组。任一时点都只有一个 primary，但原始集合有两个，无法通过整组校验；删除旧成员会丢失过去日期的替代关系。同理，阶梯行 `[0,100)` 改量产生新发生项后，旧新发生项的批量区间相同、日期不交，现文只按批量维度检查会误拒。

**建议**：聚合校验作用于明确的有效集合：按发生项生效域的断点验证各可运行切片，或者对整个替代方案做不可变版本。至少定义“原始概率合计”的原始是哪一版，而非所有历史发生项。禁止无条件把旧新成员一起相加，也禁止删除旧成员补救。

**补 AC**：primary 换发生项、替代概率跨期变更、阶梯行跨期改量、ECN 改期与取消；过去和未来各自合法且可查询。**阻塞 US-512 / US-515 组合；阶梯部分影响 US-511。**

### P1-07：映射要求两侧即时父件相同，反而禁止 EBOM→MBOM 重新分层

**证据**：[US-516 第 24～32 行](../stories/plugin/US-516-ebom-mbom-mapping.md#L24-L32) 要求 source/target 行所在头的父件是同一物料；AC#5 和技术笔记同时承诺不同分层、自由拆合与整体重新分层。

**问题与反例（文档推断）**：EBOM 为 `整机 A → 功能模块 B → 螺钉 C`，MBOM 扁平化为 `整机 A → 螺钉 C`。C 的源行父件为 B、目标行父件为 A，合法的重新分层会被同父件约束拒绝。问题不在 graph 算法，而在映射关系的业务作用域。

**建议**：同一变换范围应由根级 EBOM/MBOM 配对定义，不要求每对映射行的即时父件相同；组织约束可以保留。针对共享子装配，还应明确映射的是行定义还是某一条展开路径，不能用行 ID 模糊替代路径身份。

**补 AC**：跨父件提升、下沉、合并；共享子装配两条路径仅一处重构，映射及覆盖率仍可区分。**阻塞 US-516。**

### P1-08：成本的子件单价与父件需求不在同一单位，公式可错一个包装倍数

**证据**：[US-514 成本公式](../stories/plugin/US-514-bom-cost-rollup.md#L64-L72) 定义 `unit_cost = batch_cost / cost_lot_qty`，而 `req(l,L)` 明确以子件库存单位计；[US-511 第 39～41 行](../stories/plugin/US-511-bom-quantity-semantics.md#L39-L41) 与 AC#9 明确允许子头 `base_uom` 和库存单位不同。US-514 没有把两种单位统一。

**问题与反例（合同探针）**：子件库存单位为“件”，子头基准单位为“盒”，1 盒=10 件，`cost_lot_qty=1 盒`、整批成本 20 元。现式求出的 unit_cost 是 20 元/盒。父件需求 2 件，直接相乘得到 40，正确是 4 元。现有 AC#7 全部单位相同，发现不了这个错误。

**建议**：明确 `cost_lot_qty` 的单位；让子件单位成本统一成“元/库存单位”，或在每次乘法前把需求换到成本基准单位。价格、费用与明细也都带单位；不要只给成本总数贴币种。

**补 AC**：库存件/头盒、库存 g/头 kg、行级换算覆盖三种成本 golden；输入和材料明细量纲逐项相消。**阻塞 US-514。**

### P1-09：数量明确要求装配损耗传到工序，加工费公式却仍乘无损耗的 L

**证据**：[US-511 第 121～127 行](../stories/plugin/US-511-bom-quantity-semantics.md#L121-L127) 明确“装配损耗级联到所有组件和工序”；[US-514 第 65～72 行](../stories/plugin/US-514-bom-cost-rollup.md#L65-L72) 的材料调用损耗公式，而工时仍是“每件 → run × L”。

**问题与反例（合同探针）**：生产合格品 L=100 件，装配损耗为加成制 10%，run=1 小时/件、费率 1 元/小时、无其他损耗。按 US-511 的工序口径，应加工 110 件、110 小时；US-514 公式只得 100 元。两条故事不能同时为真。

**建议**：定义每道工序的工作量基数，至少明确装配损耗后 `P'` 如何进入变动工时；setup/fixed 仍按批不缩放。工序自身损耗是否进一步放大前段加工量另给规则，不能只靠投料公式代替工时公式。

**补 AC**：装配损耗 + run + setup 的具体金额；加成制与良率制各一组，再加一条中间工序损耗用例。**阻塞 US-514 / US-524 的加工费用交付。**

### P1-10：多输出只有方向枚举，没有定义输出批量与成本归属

**证据**：[US-513 第 24～35 行](../stories/plugin/US-513-bom-coproduct-byproduct.md#L24-L35) 支持多输出，却把“工艺配方的批次放大规则”排除；第 64～71 行仅写 `produce` 的主产品成本即卷算结果。[US-514 第 65～72 行](../stories/plugin/US-514-bom-cost-rollup.md#L65-L72) 使用未定义的 `out(b,L)`，成本节点仍是头。

**问题（文档推断）**：一批消耗原料 110 kg，产主品 M=100 kg、副品 S=10 kg。给出 `by_product.qty=10` 后，L 是 1 个工艺批、100 kg M，还是父件基准量？当 L 翻倍或含装配损耗时 S 怎么变？如果同一头有两个 `produce`，成本归谁？如果头父件是工艺 P、产物是 M，下游 consume M 如何取得 P 卷算的成本？现文缺少唯一答案，`credit_price` 只能回答单位抵减价格，回答不了产出量及主产物归属。

**建议**：先收窄到可闭合的最小模型：一个明确的主产物，与头父件/基准批量的对应关系固定；其他输出明确相对该基准的产出系数、单位和缩放规则。真正的多主产物联合成本分配可以继续价值待证，但不能在没有分配合同的情况下宣称已支持联产品成本。

**补 AC**：一组具体“投入量 → 主产量/副产量 → 抵减 → 每库存单位主品成本” golden；无主产物、多主产物、产物与头父件不一致要有明确结果或明确拒绝。**阻塞 US-513 / US-514 组合。**

### P2-01：导入自然键排序有同键平局，尚未证明诊断与输入行序无关

**证据**：[US-521 第 69～74 行](../stories/plugin/US-521-bom-erp-mrp-integration.md#L69-L74) 仅按自然键排序、逐行 SAVEPOINT，并声称消除了行序依赖；AC#6 要求失败行集合与诊断相同。

**问题与反例（合同探针）**：两条输入自然键完全相同、qty 分别为 1 和 2。稳定排序会保留原输入顺序，打乱输入就改变先写入者以及被唯一/排他约束拒绝的对象。声明的自然键还没有完整表达修订、序列与批次等后续身份维度。保存点能收集“尝试过的语句错误”，不自动定义同批冲突该归责哪些源记录。

**建议 / AC**：定义稳定源记录 ID、同键冲突的归责集合和顺序；重复键双方都报错优于任取赢家。补同键不同载荷、相同记录重复、同批环与依赖缺失四类打乱顺序测试；明确“全部失败行”是确定性尝试序列中的失败集，还是输入集合的全部冲突参与者。

### P2-02：“同上下文永远同结果”缺少数据快照前提，历史装载又是明确例外

**证据**：[US-508 用户目标与历史装载](../stories/plugin/US-508-bom-view-resolution.md#L16-L34)、AC#8；[US-521 AC#9](../stories/plugin/US-521-bom-erp-mrp-integration.md#L48-L52) 要求同上下文导出逐字节一致；US-508 技术笔记承认换算、参数、费率可变，且 `loadHistory` 可补入过去生效的数据。

**问题（文档推断）**：同一 `as_of_date` 的结果会因合法的历史补装而改变；对未来日期的结果会因新发布/ECN 改期而改变。显式日期只能消除隐式读时钟，不能冻结数据库。一次解析若分多次读取，还需避免发布/改期夹在读取之间，生成混合时点的结构与 manifest。

**建议 / AC**：改为“同一输入与同一已提交数据快照下确定”；过去稳定保证显式排除历史装载，或定义其知识版本。一次解析/卷算/导出共享一致快照，manifest 绑定该次实际输入。补两次读取之间发生发布、补装历史、改费率的用例；不要因此扩张为历史重放引擎。

### P2-03：PG advisory lock 不是隔离级别合同，旧快照风险未覆盖

**证据**：[US-509 第 133～139 行](../stories/plugin/US-509-bom-dag-cycle-detection.md#L133-L139) 在触发器中取 `pg_advisory_xact_lock`，AC#13 仅描述双连接并发反向边，没有限定事务隔离级别。PostgreSQL 18 官方手册 13.2.2 指出 Repeatable Read 在首条非事务控制语句固定快照；13.3.5 说明 advisory lock 是应用定义的锁。

**问题（官方语义 + 文档推断，未在真实 PostgreSQL 运行）**：两个 Repeatable Read 事务提前建立空图快照；第一个拿锁写 A→B 并提交，第二个随后拿到同一把锁，普通可达性 SELECT 仍可能使用旧事务快照，看不到 A→B。写入被排队，不等于快照被刷新。不能将这一推断说成已复现的远端缺陷，也不能拿 PGlite 单连接测试替代它。

**建议 / AC**：明确支持的隔离级别，并在 DDL 内执行检查/拒绝，而非只写使用说明；或者建立能在旧快照场景强制冲突/重试的协议。真实 PG 测试涵盖 Read Committed、提前建立快照的 Repeatable Read、Serializable 重试，以及多作用域锁顺序。远端 DDL 发布前必须处理。

### P2-04：“换头保留逻辑行身份”没有跨头身份规则

**证据**：[US-507 第 37～40 行](../stories/plugin/US-507-bom-graph-skeleton.md#L37-L40) 的逻辑行属于一个头，身份 `(bom_header_id, line_no)`；[US-516 第 29～32 行](../stories/plugin/US-516-ebom-mbom-mapping.md#L29-L32) 又写换头不自动迁移、按逻辑行身份不变者保留。

**问题（文档推断）**：新修订有新头，复制同一个 line_no 并不会保留原逻辑行身份。新头若全部创建新逻辑行，则所有旧映射都留在旧头，不存在自然“身份不变”的行。现文的保留条件在换头场景可能为空，不能让接入者误以为同号行自动继承映射。

**建议 / AC**：最简方案是明确“换头全部待人工重新映射”；只有业务确实要求继承时才定义显式 lineage 或迁移操作。补新修订换头、同号行换子件、旧映射留存与当前覆盖率的用例，不把 `line_no` 当全局业务身份。

### P2-05：配置 UI 被两边同时排除，没有接收方

**证据**：[US-517 Out of Scope](../stories/plugin/US-517-configurable-sales-bom.md#L34-L38) 把配置界面交给 US-522；[US-522 Out of Scope](../stories/plugin/US-522-bom-tri-framework-ui.md#L32-L36) 又明确排除配置界面；US-525 也排除配置器。

**问题（文档矛盾）**：没有故事拥有该 UI。“本期不做”可以接受，“→ US-522”但接收方不做则是断裂的交付合同。

**建议 / AC**：若不做，就删除 US-517 的转交并写清只提供模型/API；若做，则在 US-522 明确对应阶段、前置、三端范围与选择/冲突/缺参验收。不要为了消除死引用再凭空排一套完整配置器。

## 根因

1. 单条故事写得细，但缺少跨故事共同使用的**对象身份、时间切片、数值单位、状态写入矩阵**。
2. 把“解析不可见”和“存储并集不参与”混用了；把“发布时聚合校验”和“逐行排他”混用了。
3. 正向 oracle 偏向同单位、单时间切片、单层成员集合；真实风险集中在“同一对象跨版本/跨单位/跨父层”的组合。
4. 部分目标比实际保证强：显式日期不等于冻结数据，拿锁不等于刷新快照，十进制计算不等于无损传输。

## 修复方案

### 顺序

1. **不解锁 Epic，不改业务代码。** 先由 owner 确认真实驱动、首期行业语义和输入规模。
2. **首轮 schema 前**：先处理 P1-01 / P1-02；同时统一 P1-04 的并集政策，避免后续 ECN 反向改 schema。
3. **ECN/替代阶段前**：合并处理 P1-03～P1-06，交付一套状态写入矩阵与时间切片规则。
4. **映射阶段前**：处理 P1-07 与 P2-04，不把即时父件相同当变换范围。
5. **成本阶段前**：处理 P1-08～P1-10，用带单位、带损耗、带产出基准的独立 golden 闭合公式。
6. **集成与远端 DDL 前**：处理导入平局、快照确定性、真实 PG 隔离级别；配置 UI 则明确不做或明确归属。

### 尚需产品回答，不计入缺陷数量

- 非虚拟件没有可用子 BOM 时，如何区分合法外购叶子与缺失制造结构？若首期不区分，应明确完整性保证的边界。

- 首轮不支持同步、HTTP/Supabase 初始化 fail-fast、无路线明确为 NULL、部分故事只关闭阶段 AC，均已显式定义，不能假装是遗漏。
