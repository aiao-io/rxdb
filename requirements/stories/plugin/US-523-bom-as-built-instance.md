# 用户故事：as-built / as-maintained 实例 BOM

## 作为/我想要/以便

**作为** 售后与追溯工程师
**我想要** 已交付个体的实际装机结构独立于主数据 BOM 存在
**以便** 回答「这台设备装的是哪个批次的哪个件」，且主数据变更不改写历史

## 范围边界

### In Scope

- `bom_instance_node`：实例节点，带序列号 / 批次 / 装机时间
- 实例节点引用其来源 `bom_line`，但**不共享闭包表**
- 实例树的展开与反查（这个件装在哪台设备上）
- 主数据 BOM 变更**不影响**既有实例

### Out of Scope

- 维修工单与换件事务（属事务域）
- 实例与主数据的自动差异告警
- 质量追溯的召回范围计算

## 验收标准

| #   | 前置条件                   | 操作       | 预期结果                                               | 状态 |
| --- | -------------------------- | ---------- | ------------------------------------------------------ | ---- |
| 1   | 已按某版 BOM 生产一台设备  | 建实例     | 实例节点带序列号 / 批次，可整树展开                    | ⬜   |
| 2   | 主数据 BOM 改版            | 查既有实例 | 实例结构**不变**                                       | ⬜   |
| 3   | 某批次的件                 | 反查       | 列出装了它的所有实例                                   | ⬜   |

| 5   | 实例数据量                 | 规模检查   | 实例闭包与主数据闭包**分离**，实例增长不拖慢主数据查询 | ⬜   |

## 技术笔记

**本故事的关闭条件是「实例图与主数据图分离」。**

实例 BOM 与主数据 BOM 的基数差异是几个数量级：一张主数据 BOM 对应成千上万台实例，
每台实例一棵完整的树。塞进同一套 `bom_header` / `bom_line` 会让主数据查询被实例数据淹没，
而 AC#5 正是为此设的规模验收。

另一个不能合并的理由是**生命周期相反**：主数据 BOM 会改版、会失效、会被 ECN 重写；
实例 BOM 一旦记录就是历史事实，永不随主数据变化（AC#2）。同一张表上放两种可变性不同的数据，
迟早要靠「这行是不是实例」的分支判断来保护历史，而那种分支会被漏掉。

实例节点引用来源 `bom_line`（回答「本该装什么」），但实例的父子关系是自己的边，
不进 [US-510](US-510-bom-multilevel-explosion.md) 的 `bom_closure`。

AC#4 的「装机区间可查」意味着实例节点需要 `installed_at` / `removed_at`，
这是有效性的第四种形态——与 [US-508](US-508-bom-view-resolution.md) 的日期生效期形似但语义不同：
前者是既成事实的记录，后者是计划的适用范围。不共用实现。
