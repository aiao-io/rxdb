# 用户故事：三框架 BOM 编辑与展开视图

## 作为/我想要/以便

**作为** 三框架的应用开发者
**我想要** BOM 的编辑与多级展开在 Angular / React / Vue 上同功能同 API
**以便** 不需要为某一端另写一套 BOM 交互

## 范围边界

### In Scope

- 多级展开树视图：懒加载、层级、展开量显示、`truncated` 提示
- 行编辑：用量、损耗、工序、生效期
- 环路插入的错误在三端一致（同一错误对象与消息）
- 活查询增量刷新

### Out of Scope

- 配置界面（US-517 的配置模型的 UI）
- 成本卷算结果的报表呈现
- 拖放重排（依赖 US-028 的可排序实体）

## 验收标准

| #   | 前置条件                | 操作         | 预期结果                                     | 状态 |
| --- | ----------------------- | ------------ | -------------------------------------------- | ---- |
| 1   | 同一份 BOM 数据         | 三端分别渲染 | 行为与 API 一致，**单端缺失 = 未完成**       | ⬜   |
| 2   | 展开树已渲染            | 改一行用量   | 活查询增量刷新，不整表重渲染                 | ⬜   |
| 3   | 试插入成环的行          | 保存         | 三端得到同一个错误对象与同一条消息           | ⬜   |
| 4   | 深度超限的 BOM          | 展开         | 显示 `truncated` 提示而非静默截断            | ⬜   |
| 5   | 同一物料在同一父下 3 行 | 渲染         | 三行独立可见可编辑（多重边在 UI 上不被合并） | ⬜   |

状态符号：⬜ 未开始 / ⚠️ 进行中或有保留 / ✅ 通过

## 技术笔记

AC#1 是本仓铁律的直接落地：三框架 API 必须对称，单端缺失即未完成。
因此本故事**不拆成三条按端的故事**——那会让「两端已交付」看起来像进度，而实际上能力不可用。

AC#2 落在既有活查询能力上，BOM 侧的额外要求是：展开结果是**派生视图**，
它的失效依赖必须精确到「哪些 `bom_line` 参与了这次展开」，否则任何一行改动都会全量重算。
这与 [US-510](US-510-bom-multilevel-explosion.md) 的闭包/数量分离是同一件事的 UI 面。

AC#5 是多重边在 UI 层的验收：后端允许同一 `(parent, child)` 多行，前端若按物料聚合就把它抹平了。
这条与 [US-507](US-507-bom-graph-skeleton.md) AC#1 成对——存储层允许而展示层合并，等于能力不存在。
