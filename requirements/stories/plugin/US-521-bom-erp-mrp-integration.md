# 用户故事：ERP/MRP 集成契约

## 作为/我想要/以便

**作为** 集成开发者
**我想要** 一份稳定的 BOM 导出契约与可诊断的批量导入
**以便** 对接 ERP/MRP 时不靠读源码猜字段，且导入失败能定位到行

## 范围边界

### In Scope

- 导出契约：展开结果与主数据的稳定形状，纳入 api-baseline 与兼容承诺；导出附带 [US-508](US-508-bom-view-resolution.md) 的 resolution manifest
- **导出只接受完整结构**：展开结果标 `truncated`（[US-510](US-510-bom-multilevel-explosion.md)）或 `unresolved`（US-508 / US-512 / US-518）即拒绝导出
- **批量导入 = 整批原子提交到草稿**：导入数据整批写入 `draft` 头；任一行失败整批回滚，返回**全部**失败行的逐行诊断（不止第一条）；
  通过后由调用方显式发布，发布走 [US-507](US-507-bom-graph-skeleton.md) 的发布转移校验
- 诊断的确定性：同一输入、任意行序，失败行集合与诊断相同——不出现「先到的行赢、后到的行背锅」
- `supply_to_vendor`（委外供料）语义：影响采购而非生产结构
- 组织/工厂维度（`org_id`）在契约里显式

### Out of Scope

- MRP 运算本身（净需求、提前期、批量规则）
- 具体 ERP 厂商的字段映射表
- 实时双向同步
- 平台同步（pull / merge / replay）写入 BOM 实体——首轮不支持，见 [US-509](US-509-bom-dag-cycle-detection.md) AC#12
- 部分成功导入（成功行落地 + 失败清单）

## 技术笔记

AC#1 按本仓约定：新导出必须进 api-baseline（首跑失败属正常，基线 diff 随提交）。

AC#2 的「按行报错」是集成场景的关键质量项：ERP 导入动辄数万行，整批失败且只给一条错误
等于让对方从头人工排查。环路检测（[US-509](US-509-bom-dag-cycle-detection.md)）在批量路径上
必须能报出**是哪条路径成环**，而不只是「存在环」。

**为什么导入选整批原子。** 部分成功要回答一串难题：成功行落地后聚合是否合法（位号、替代组合计、环）？
A→B 与 B→A 同批出现时拒绝哪一条取决于行序，同一份文件两次导入结果不同；失败行修好后重导，又要与已落地的行合并。
整批原子把这些都消掉：草稿里要么全有要么全无，聚合合法性留给发布转移一次判定，诊断与行序无关（AC#6）。
代价是一行错整批重来，但逐行诊断列全了失败行（AC#5），重来只需改这些行。

**同步与导入走同一道门。** 离线客户端各自新增 A→B、B→A，本地都合法，合并后成环；它们是不同记录，普通行冲突检测发现不了。
首轮不解决同步合并，而是不让 BOM 实体进同步（US-509 AC#12）；导入则只写草稿、经发布转移校验，
与人工编辑共用同一个领域提交边界。解锁同步时，pull / merge / replay 也必须经过这道门，届时另立故事。

AC#8 与 US-510 AC#11、US-514 AC#11 同一裁决：截断或未解析的结构交给 MRP，就是一份看起来正常的错误需求。

`supply_to_vendor`（AC#3）是少数「不改结构只改视图」的真实例子——它确实可以用视图过滤实现，
与 [US-516](US-516-ebom-mbom-mapping.md) 的 EBOM→MBOM 重构形成对照。
