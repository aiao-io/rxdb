# 用户故事：BOM 视图解析：类型/组织/修订/生效期过滤

## 作为/我想要/以便

**作为** BOM 工程师
**我想要** 按一个显式的解析上下文 `ResolutionContext` 解析出唯一一份有效行集
**以便** 同一物料在不同工厂、不同时点看到正确的结构，且同一上下文在同一份已提交数据上永远得到同一结果

## 范围边界

### In Scope

- **`ResolutionContext`**：`bom_type`、`org_id`、`as_of_date`、父修订选择、`alternative_no` 选择策略；
  [US-517](US-517-configurable-sales-bom.md) 的配置与 [US-518](US-518-bom-unit-lot-effectivity.md) 的序列/批次在各自阶段扩入同一上下文，
  不另开第二套入参。`as_of_date` **必填**，缺失即拒绝，不读系统时钟、不默认今天
- 修订选择：precise 行锁版；imprecise 行取 `state = 'released'` 且 `effective_from ≤ as_of_date` 的修订中 `effective_from` 最大者。
  同一物料两个已发布修订的 `effective_from` 相同属非法态，在发布时拒绝，所以「最新」唯一
- **禁止追溯生效**：修订发布、头发布与 ECN 发布时，`effective_from` 不得早于发布当日。「发布当日」是发布事务内由存储层取的
  **UTC 日期**（SQLite `date('now')`、PG `(now() AT TIME ZONE 'UTC')::date`），不由调用方传入。由此「对过去日期的结构解析」
  不会被之后的发布改写——这是本故事提供的历史保证，见技术笔记「历史查询的边界」
- **历史装载通道**（默认决定，第 0 步复核）：种子与历史数据经 `loadHistory(batch)` 一次事务写入，事务内建一行**开启态**的
  `bom_history_batch` 并给本批发布的修订 / 头 / ECN 盖批次号；只有指向开启态批次的发布跳过禁止追溯检查，其余校验照常；
  提交前批次关闭，批次表只追加。见技术笔记「历史装载」
- 日期区间有效性：行发生项（[US-507](US-507-bom-graph-skeleton.md)）的 `[effective_from, effective_to)` 半开区间
- **发生项可见性**：头为 `released`，且 `ecn_in_id` 为空或其 ECN 已发布（`released`，含已到生效日的派生态 `effective`）；
  挂在 `draft` / `cancelled` ECN 上的发生项不入结果；`ecn_out_id` 指向未发布 ECN 时不截止——存储里的区间是候选时间线，
  截止标记写入时 `effective_to` 已收窄为该 ECN 的生效日，解析按 `+∞` 处理。写入协议见
  [US-515](US-515-bom-change-management.md#已发布头的写入协议)；首轮没有 `ecn` 实体，两列恒空，本条退化为只看头状态。
  可见性只管解析；判环看全部已存发生项，见 [US-509](US-509-bom-dag-cycle-detection.md)
- **一致快照**：一次解析的全部读取在同一个读事务里完成，看到的是同一份已提交数据；manifest 记录的就是这一份数据上的实际依据。
  确定性的承诺是「同一输入 + 同一份已提交数据 → 同一结果」，不是「同一 `as_of_date` 永远同一结果」，见技术笔记「确定性的前提」
- 区间排他作用域是**同一逻辑行的发生项**（`bom_line_id`），声明式约束而非应用层校验
- 多个 `alternative_no` 并存不被重叠约束误拒——备选 BOM 本该同时有效
- `alternative_no` 的选择规则放**策略层**（按批量区间 / 按工厂优先 / 手动指定），不写进 SQL；策略选不出唯一备选时，
  结果标 `unresolved` 并列出候选，交给调用方，不擅自挑一个
- 解析结果附带 **resolution manifest**：命中的头、修订、行发生项 ID 与上下文，供下游审计与比对

### Out of Scope

- 序列与批次有效性（→ US-518）
- 跨 `bom_type` 的解析——EBOM→MBOM **不是视图**，是重构（→ US-516）
- ECN 派生生效日（→ US-515）
- 换算率、公式参数、费率的时间版本化与「精确重放当年计算」——manifest 只记录结构依据，见技术笔记

## 技术笔记

**首轮切片验收 AC#1～#11 / #13～#15**：AC#12 / #16 要造并发布 ECN，等 [US-515](US-515-bom-change-management.md) 落地，
本故事在此之前不置 Done，见 [epic-009 首轮可开工切片](../../epics/epic-009-bom-domain-model.md#首轮可开工切片)。

区间排他的作用域**必须精确到同一逻辑行 `bom_line_id`**，不能对整表施加：
多个 `alternative_no` 与多个替代行（US-512）本来就该并存，全局禁重叠会把正常数据拒掉。
也不能是 `(bom_header_id, line_no, child_item_id)`：那样同一逻辑行同一时段换成另一子件就能两条都生效，
等于一行同时是两种东西。PGlite 侧可用 `daterange` + GiST `EXCLUDE`；SQLite 侧无此能力，退回触发器等价物，
两侧的**错误语义必须一致**（见 US-521 AC#2 的逐行报错要求）。这两项声明能力本仓当前都没有，
落点是 [US-030](../core/US-030-declarative-storage-constraints.md) 阶段 B 与 C。

**「版本」在本故事里只有一个意思：修订。** `bom_header` 挂 `parent_revision_id`
（[US-507](US-507-bom-graph-skeleton.md)），所以视图的四个轴是类型、组织、修订与时点；
`alternative_no` 是并行备选（AC#3），不是版本轴，这正是 AC#2 的重叠约束不能覆盖它的原因。

**历史查询的边界。** 「按当前知识查询过去适用的结构」与「重放当年那次计算」是两种能力，本故事只承诺前者，
并用一条规则让前者足够稳定：**任何发布都不得追溯生效**（AC#9）。修订、头与行发生项一经发布不可改写
（[US-507](US-507-bom-graph-skeleton.md) AC#10 / #14），ECN 已生效后不可取消或提前（[US-515](US-515-bom-change-management.md)），
于是对过去日期的结构解析只依赖当时已发布的数据，之后的**发布**改不了它；历史装载是有意的例外，见下文「确定性的前提」。

这条保证相对的是**写入端宿主时钟**：「当日」由存储层在发布事务里取，设备时钟被拨回，追溯判定也随之失真。
首轮不开同步（[US-509](US-509-bom-dag-cycle-detection.md) AC#12），写入端就是一台设备，这是可接受的边界；
开同步须另立故事，届时多端时钟的可信度要一并解决。取 UTC 而不是组织时区，是为了两个后端与所有宿主得到同一个日期，
代价是本地午夜前后可能差一天——禁止追溯只需要一个单调的「今天」，不需要它与墙上日历对齐。

**历史装载。** 禁止追溯生效一刀切会把两件正当的事也拦下：demo 的确定性种子（[US-525](US-525-bom-end-to-end-demo.md)
AC#1，日期固定，宿主日期一过就成了「追溯」）与从 ERP 迁入的历史结构。二者写入的都是**已经发生过的**发布，
不是今天的新发布。所以开一条专用通道：`loadHistory` 在一次事务里建开启态批次、写数据、关闭批次，
触发器只对指向**开启态**批次的发布跳过追溯检查（AC#13），关闭的批次号不再放行（AC#14）。

**确定性的前提。** 显式 `as_of_date` 消除的是隐式读时钟（AC#7 / #8），冻结不了数据库：对未来日期的结果会因新发布、ECN 改期而变，
对过去日期的结果会因合法的历史装载而变。所以承诺写成「同一输入、同一份已提交数据 → 同一结果」：
「过去不被改写」的历史保证**显式排除**历史装载——补装的就是过去生效的数据，它本来就该改变过去日期的结果，批次号让这种改变可查；
一次解析分多次读取时，必须在同一个读事务里完成，否则夹在两次读取之间的发布、补装或改率会拼出一份混合时点的结构与 manifest（AC#15）。
[US-511](US-511-bom-quantity-semantics.md) 的数量、[US-514](US-514-bom-cost-rollup.md) 的卷算与 [US-521](US-521-bom-erp-mrp-integration.md) 的导出
把各自的读取放进同一个快照，不另起读取。这不是历史重放引擎，也不为此引入数据版本号。

这条通道**可审计而非不可绕过**：直连 SQL 也能先插一行开启态批次再追溯发布。触发器拦不住它，但留得下痕迹——
每一行历史数据都带批次号，批次表只追加，事后查得出哪些数据不是经正常发布进来的。按
[US-509](US-509-bom-dag-cycle-detection.md) 引的那条原则，这里写明它拦不住，而不是假装拦得住。
[US-521](US-521-bom-erp-mrp-integration.md) 的日常导入仍只写草稿、不走这条通道；ERP 历史迁移要用它时在 US-521 另加 AC。

结构之外的输入——单位换算率、`qty_formula` 参数、费率——本 Epic 不做时间版本化，它们变了，旧日期的数量与成本会跟着变。
manifest 记录结构依据（头、修订、发生项 ID），[US-511](US-511-bom-quantity-semantics.md) 与 [US-514](US-514-bom-cost-rollup.md)
再把各自用到的换算率、参数与费率值追加进去，下游可以比对两次 manifest 判断差异来自哪一层；但 manifest 不是重放引擎，
「拿旧 manifest 重新算出当年数字」需要真实驱动场景再立项。

**`unresolved` 不是错误，也不是结果。** 探索性浏览（[US-522](US-522-bom-tri-framework-ui.md)）可以展示候选集；
需要完整结构的消费方——[US-514](US-514-bom-cost-rollup.md) 卷算、[US-521](US-521-bom-erp-mrp-integration.md) 导出——遇到 `unresolved` 一律拒绝，
不能把候选集当作已选结构。
