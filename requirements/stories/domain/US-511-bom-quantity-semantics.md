## 范围边界

### In Scope

- 用量四态：标量、定量（不随父件缩放）、公式（参数化 BOM）、批量阶梯
- **阶梯组**：阶梯行以 `(bom_header_id, tier_group_no)` 成组，组内按 P 恰好命中一行；非阶梯行三列皆空，不参与阶梯校验。
  同一子件可以既有普通行又有阶梯组（[US-507](US-507-bom-graph-skeleton.md) AC#1 的多重图），组号才是阶梯的身份，子件不是
- **数量带单位**：父计划量、行需求量、递归输入都是「值 + 单位」；进入子 BOM 前先转到其 `bom_header.base_uom`，
  缺换算率或量纲不兼容即拒绝，**不默认 1**。同量纲（g → kg）用单位制的标准系数；跨量纲（米 → 千克、g → 件）**只**经显式的
  物料级或行级换算率，「量纲不兼容」指跨量纲且两级都没有声明换算率——判据是有没有声明，不是单位名本身
- **十进制值合同**（见技术笔记「十进制值合同」）：数量、换算率、损耗率、固定损耗、阶梯边界、概率、`equiv_qty`、分摊比例、
  `cost_lot_qty`、价格、费率与工时一律以**规范十进制串**承载，从输入、存储、回读、计算到导出全程不经 JS `number` 或
  `double precision`；插件局部的值对象负责解析与运算，不为 BOM 扩张核心 `PropertyType`
- 单位换算：行 UoM → 子件库存 UoM → 子 BOM 头基准 UoM，物料级换算率 + 行级覆盖
- 三类损耗各就其位：装配损耗在**头**、组件损耗在**行发生项**、工序损耗在**工序**；三处各自声明 `scrap_convention`
- 损耗记法两制并存：加成制 `x × (1+s)` 与良率制 `x ÷ (1−s)`；合法域加成制 `s ≥ 0`、良率制 `0 ≤ s < 1`，`s = 1` 拒绝
- 虚拟件穿透，且**行级标记覆盖修订级标记**
- 只有 `flow_direction = 'consume'` 的行进入需求展开（`flow_direction` 由 [US-513](US-513-bom-coproduct-byproduct.md) 引入；
  它落地前所有行都是 `consume`，本故事不因此阻塞）
- **精度与舍入**：内部按 34 位有效数字的十进制（decimal128 语义）计算，中间量 half-even；只在需求行上按子件库存单位声明的小数位
  **向上取整**一次；虚拟件穿透的中间量不舍入。**默认决定（第 0 步复核）**：非虚拟子装配的需求行取整后的值就是其子 BOM 的 P（AC#17）
- 虚拟件在当前 `ResolutionContext` 下没有可用的 BOM 头即拒绝（AC#18），不当作叶子产出需求行
- 结果在 [US-508](US-508-bom-view-resolution.md) 的 manifest 上追加本次用到的换算率、公式参数、公式语法版本与算法版本
- 遇到 [US-510](US-510-bom-multilevel-explosion.md) 的 `truncated` 或 US-508 的 `unresolved` 结构，拒绝计算

### Out of Scope

- 工序损耗的工序序列本身（→ US-520 提供 `operation_seq` 与分摊）
- 替代组的需求分摊（→ US-512）
- 成本（→ US-514）
- 非 `consume` 行的数量语义（→ US-513）：`by_product` 的产出量与 `scrap_out` 的废料量
  都不是「需求」，不进本故事的七步公式
- 通用表达式求值（任意 JS / SQL 表达式）——公式只接受本故事定义的受限语法

## 技术笔记

**顺序不可颠倒**，这是 MRP 与成本算错最常见的根因。下式里 `conv(·)` 表示按单位换算，`scrap(x, s, convention)`
加成制为 `x × (1+s)`、良率制为 `x ÷ (1−s)`：

```
1. 父件计划量                P            单位 = h.base_uom（已由上一层归一）
2. 装配损耗（头级）          P' = scrap(P, h.assembly_scrap, h.assembly_scrap_convention)
3. 组件毛需求                q  = 本发生项的 qty，或按语法版本求值 qty_formula；阶梯按 P 选行
                             G  = is_fixed ? q : q × P' / h.base_qty                 单位 = l.uom
4. 组件损耗（行级）          G' = scrap(G, l.component_scrap, l.component_scrap_convention)
                                  + l.component_scrap_fixed                         单位 = l.uom
5. 工序损耗（工序级）        G'' = G' 依次过 scrap(·, op.scrap, op.convention)，
                             op 从 l.operation_seq（含）起至末工序                  -- 阶段 B2
6. 单位换算                  D  = conv(G'', l.uom → child.stock_uom)
7. 虚拟件穿透 / 产出需求行   phantom = COALESCE(l.phantom_override, r.default_phantom)
                             phantom 为真：conv(D, child.stock_uom → child_header.base_uom)
                                           作为子 BOM 的 P 回到第 1 步，不产生需求行、不舍入
                             phantom 为假：按 child.stock_uom 小数位向上取整，产出需求行
```

**单位换算在穿透之前，不在之后。** 若让 `G''` 先作为子件的 P 下钻、再做单位换算：
A 需要 1000 g 的 phantom B，B 的头以 1 kg 为基准、每 kg 用 2 件 C，正确是 `1000 × 0.001 × 2 = 2` 件 C，
直接把 1000 当 B 的 `P` 得 2000 件，**错 1000 倍**（Decimal 探针复现）。数量只有数值没有单位才会犯这种错，
所以第 1、3、6、7 步都显式写出单位。非 phantom 的下层展开同样从第 1 步进入子 BOM，同样先归一。

**工序损耗的方向：从投料工序（含）到末工序。** 物料在工序 10 投入，就要经过 20、30；20 的报废会吃掉 10 投入的料，
所以 10 投料的需求要被 20 的损耗放大；30 投入的料不经过 20，不受影响。10→20→30、只有 20 损耗 3% 时，
加成制下投料基数 100 的需求是 10:103、20:103、30:100（AC#13）。
[US-520](US-520-bom-routing-operation.md) AC#3 与 [US-525](US-525-bom-end-to-end-demo.md) AC#9 的断言用同一方向。

**三类损耗不能合成一个字段**——它们在公式里的位置不同：装配损耗级联到所有组件**和工序**，
组件损耗只放大本行，工序损耗从投料工序起逐工序累乘。

「装配损耗级联到工序」的口径是**工序加工量**：工序 j 要加工的件数 `W_j = P'` 依次过 `scrap(·, op.scrap, op.convention)`，
op 从 j（含）至末工序——与第 5 步投料同一方向，工序 20 报废 3% 时工序 10、20 都要多做、30 不必。
[US-514](US-514-bom-cost-rollup.md) 的变动工时按 `W_j` 计，不按无损耗的父计划量；`setup` 与固定工时按批，不随 `W_j` 缩放。

**两种损耗记法必须显式记录，且每一处各记各的。** s = 5% 时加成制与良率制相差 0.25%，s = 20% 时是 120 对 125；
不记 `scrap_convention`，与 ERP 对接会出现无人能解释的差。内部可统一存良率因子，但**入口必须能声明来源制**，
头、行发生项、工序（[US-524](US-524-routing-master-model.md) 阶段 D）三处各有自己的 convention 字段。
固定损耗 `component_scrap_fixed` 以**行 UoM** 计，粒度与定量用量相同（每条路径的每个父批次一次），不随父件缩放、不再被良率放大。

**用量四态的边界：**

- `qty` 与 `qty_formula` 恰好一项非空（单行 CHECK，落点 [US-030](../core/US-030-declarative-storage-constraints.md) 阶段 A）；
- 公式只接受受限语法：十进制字面量、`+ − × ÷`、括号、命名参数；持久化时同时记 `formula_grammar_version`，
  语法升级不改旧公式的含义；缺参、语法错、除零、非有限值、负值都拒绝整次展开（AC#14），不以 0 或跳过兜底；
- 定量用量与固定损耗的粒度是「每条路径的每个父批次」：同一子装配经两条路径出现，就是两个装配批次，各计一次（AC#15）；
- 阶梯按**损耗前**父计划量 P 选：阶梯是对订单批量的约定，用损耗后的量会让同一订单因损耗率变化而跳档；
  阶梯行以 `(bom_header_id, tier_group_no)` 成组，组内区间为半开 `[lotsize_from, lotsize_to)`；同组两个发生项只有**生效域**
  （日期；[US-518](US-518-bom-unit-lot-effectivity.md) 落地后含序列 / 批次）与批量区间**同时相交**才算重叠，在头发布或 ECN 发布时
  按切片拒绝（[US-507](US-507-bom-graph-skeleton.md) 发布边界、AC#24）——只按批量维比，会把「同一档跨期改量」的旧新发生项误拒；
  P 落在评估日切片内组内所有区间之外则拒绝展开（AC#19）。
  组键不能用「同一头同一子件」：US-507 AC#1 允许同一子件挂多条逻辑行（不同工位、不同位号组），按子件分组会把它们误判为重叠阶梯。
  `tier_group_no`、`lotsize_from`、`lotsize_to` 三者同空或 `tier_group_no` 与 `lotsize_from` 同非空（单行 CHECK，US-030 阶段 A）。

**十进制值合同。** 34 位有效数字只约束计算不够：输入 `1.000000000000000000000000000000001` 经 JS `number` 或 PGlite 的
`double precision` 回读即为 `1`，已经丢掉的位后面的计算库补不回来（RV-080 用实际 PGlite 走 text → double precision → text 与
text → numeric → text 复核过，前者丢末位、后者保留）。现有 [`PropertyType`](../../../packages/rxdb/src/entity/property-types.interface.ts)
没有 decimal，PGlite 把 `number` 映射到 `double precision`，[`assertFiniteNumber`](../../../packages/rxdb-adapter-pglite/src/pglite.utils.ts)
的说明本就要求任意精度改用字符串承载。所以：

- **规范十进制串**：可选负号、整数部分无前导零（单个 `0` 除外）、无指数、小数部分无尾随零、`-0` 写作 `0`，至多 34 位有效数字。
  输入接受指数写法并在入口规范化；超过 34 位、非有限值、空串、语法错一律拒绝（AC#23），不截断、不舍入后接受；
- **存储**：实体属性声明为字符串，两后端都存规范串。格式校验由插件**自己发的触发器**承担（同 [US-509](US-509-bom-dag-cycle-detection.md) 的做法），
  不走 [US-030](../core/US-030-declarative-storage-constraints.md) 的 CHECK——它的操作符白名单没有 `LIKE` / 正则，而文本的 `<` 在 PG 下随库排序规则变，
  不能拿来判数值。存储层对十进制文本只做格式、符号，以及能写成逐字节谓词的范围判断：非负 ⇔ `substr(s, 1, 1) <> '-'`，
  良率制 `0 ≤ s < 1` ⇔ `s = '0' OR substr(s, 1, 2) = '0.'`。直连 SQL 写入非规范串（`1.5E-3`、`01`、`1.50`、`-0`）一律拒绝，规范化只发生在插件入口；
  本合同首期没有允许负值的字段，负号语法留给日后字段；
- **存储层的数值运算只有两处，各自收窄字段域**（默认决定，第 0 步复核）。字符串传输无损不等于存储层运算无损：
  SQLite 没有十进制类型，对文本做 `SUM` / `CAST AS REAL` 就回到 double。所以凡是存储触发器要算的十进制字段，都把域收窄到
  「两后端用各自原生能力算出同一结果」的范围，越界在保存时两端一致拒绝；不引入 SQLite 十进制扩展（宿主可用性无法保证），
  不用浮点 epsilon、不先归一化、不只在 API 层校验：
  - **阶梯边界比较**（AC#24 的发布校验）：`lotsize_from` / `lotsize_to` 限 **15 位有效数字、整数部分至多 15 位、小数部分至多 15 位**
    （后两条都是逐字节长度谓词）。值域因此落在 `{0} ∪ [1e-15, 1e15)`，全是 double 的正规数，15 位以内的十进制与 double 往返无损、
    序关系不变：PG 侧 `::numeric` 比较、SQLite 侧 `CAST(… AS REAL)` 比较，结论一致。只限有效位数不够——`1e-400` 只有 1 位有效数字，
    在 SQLite 里转 REAL 为 0，`[1e-400, 3e-400)` 与 `[2e-400, 4e-400)` 的重叠会被漏判（AC#26）；
  - **发布聚合求和**（[US-512](US-512-bom-substitute-group.md) 的 `usage_probability` 合计、[US-520](US-520-bom-routing-operation.md) 的分摊比例合计）：
    这两个字段取值 `[0, 1]`，**小数部分至多 9 位**，即只接受 `0`、`1` 与 `0.` 后跟 1～9 位数字（`length(s) <= 11`）。
    触发器把每个值按逐字节规则换成 10⁹ 倍的整数——`'1'` → 10⁹、`'0'` → 0，其余取 `substr(s || '000000000', 3, 9)` 转整数——
    两后端都做**整数**求和后与 10⁹ 比较，不碰 `REAL` / `double precision`；合计在报错里按同一规则还原成规范十进制串，两端逐字一致。
    9 位对业务概率与工序分摊绰绰有余；反例 `0.5 + 0.5000000000000001` 在 SQLite 原生 `SUM` 下得 `1.0`、PGlite numeric 下得
    `1.0000000000000001`，收窄后第二个值保存即拒，发布期不再存在两端分歧（US-512 AC#15 / US-520 AC#10）。
    日后若真要更多位，改为同样的定点整数规则扩位数（10¹⁵ 倍仍在 int64 内），不退回浮点；
  - 不拿词法字符串比较冒充数值比较；
- **计算与导出**：kernel 只经插件的十进制值对象运算；导出 JSON 里十进制字段是字符串（[US-521](US-521-bom-erp-mrp-integration.md)），
  不出现 JSON number。两后端回读同一规范串，输出逐字一致（AC#22）。

这份合同由本故事定义，[US-507](US-507-bom-graph-skeleton.md) 的 `qty`、[US-512](US-512-bom-substitute-group.md) 的概率与 `equiv_qty`、
[US-514](US-514-bom-cost-rollup.md) 的价格与成本批量、[US-520](US-520-bom-routing-operation.md) 的分摊比例、[US-524](US-524-routing-master-model.md)
的工时与费率共用它，不各自另立表示。

**舍入只在需求行上发生。** 每一步都舍入会让多层结构的误差逐层累积，而且依赖舍入位置的结果无法与手算对账。
只在产出需求行时按库存单位小数位向上取整（AC#16）——向上是因为毛需求取整向下会造成缺料。

「十进制精确」做不到：良率制 `x ÷ (1−s)` 与公式里的除法会产生无限小数。所以精度是**约定**而不是精确：
34 位有效数字、中间量 half-even，七步顺序固定，结果因此**可复现**——golden 按同一精度、同一顺序手算，
对账比的是位级一致，不是数学真值。工作精度与舍入模式写进 manifest 的算法版本，改动即升版本。

**非虚拟子装配的取整值向下传递（默认决定，第 0 步复核）。** S 的需求行取整为 3 件，S 自己的 BOM 就按 3 件展开（AC#17），
因为车间实际投产的是 3 件 S；按 2.5 件展开子件会让 S 的子件需求与 S 的生产订单对不上。虚拟件不落成需求行，所以不取整。
若驱动方的 MRP 采用「下层按未取整量展开」，翻转这一条只改第 7 步非虚拟分支，不动其余六步。

**虚拟件无头即拒绝（AC#18）。** 虚拟件的定义就是「穿透到它的子件」，没有子件可穿透时，把它降级为叶子需求行
是在替计划员做决定——那张需求行对应一件不会被生产、也不会被采购的物料。

**非虚拟件无头不拒绝，这是首期完整性保证的边界。** 非虚拟件在当前上下文下没有可用头时按叶子产出需求行（外购件就是这样），
首期**不区分**「合法外购叶子」与「本该有制造结构却缺了头」，完整性保证只覆盖虚拟件（AC#18）。
要区分时需要物料上的自制 / 外购属性，由驱动场景决定后另加 AC，不在这里用启发式猜。

**AC#4 是最易漏的一条**：同一物料在不同装配下 phantom 与否不同，
所以标记要能同时挂节点与边，且**边覆盖节点**。只在物料主数据上放一个布尔值是不够的。

节点侧的那个布尔值挂 `item_revision` 而不是 `item`（[US-507](US-507-bom-graph-skeleton.md) 阶段 A）：
虚拟与否是**设计决定**，同一物料的 D 版可以是虚拟件、E 版改成实体件。挂在 `item` 上则改一次
会追溯性地改掉所有历史修订的展开结果，而历史结构解析本该稳定（[US-508](US-508-bom-view-resolution.md)「历史查询的边界」）。

**七步公式只认 `qty`。** 位号数不是第二个数量来源——一致性由
[US-507](US-507-bom-graph-skeleton.md) AC#5 在发布转移上保证，展开期不做推导也不做校正。

**阶段 B 拆成 B1 / B2 是因为前置不同。** 装配与组件损耗只需要本故事自己的字段；工序损耗要 US-520 的
`operation_seq` 与 US-524 阶段 D 的 `operation_scrap`。B2 之前，模型里根本没有工序损耗字段，不存在「接受后静默忽略」。
