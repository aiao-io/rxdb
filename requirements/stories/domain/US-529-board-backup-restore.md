# 用户故事：重开恢复与备份导出

## 作为/我想要/以便

**作为** 单人看板用户
**我想要** 导出我的看板数据，关掉浏览器、甚至清掉站点数据后，还能导回来继续用
**以便** 攒了半年的任务清单不会因为清一次浏览器缓存就没了

## 范围边界

### In Scope

- **重开恢复**：刷新 / 重开浏览器后板、列、任务、标签与排序全部原样（持久化验收，与
  [US-526](US-526-board-column-task-skeleton.md) AC#3、[US-528](US-528-task-detail-editing.md) AC#1
  的重开断言同源，本故事把「重开」做成产品入口与验收闭环）
- **备份导出**：以 [US-217](../adapter/US-217-local-database-backup-restore.md) 已交付的备份 API
  生成归档文件，浏览器侧触发下载（归档可带走，与站点数据隔离）
- **备份恢复**：从归档恢复（同 adapter 边界、归档完整性校验、损坏归档拒绝——全部是 US-217 已
  交付行为，本故事只做看板侧接线与产品入口）
- **UI 入口**：导出 / 恢复按钮与结果反馈（成功 / 失败原因）；三端交互由
  [US-531](US-531-board-tri-framework-ui.md) 接线，本故事定语义与验收
- **连接形态约束**：demo 与三端接线只承诺 US-217 支持的主线程连接备份；OPFS 专用 Worker 与
  IDB SharedWorker 连接返回 `unsupported_combination` 的组合**必须如实提示「当前连接形态不支持
  备份」**，不静默、不假装成功（US-909 阶段 B 实测记录的事实，见技术笔记）

### Out of Scope

- 跨端同步备份（→ [US-533](US-533-board-team-sync.md)）
- 云备份 / 自动定时备份
- 备份加密与 keyring 语义——US-217 已覆盖（加密字段保持密文、密钥不进入归档），本故事不扩展
- 损坏数据库的自动修复（US-217 边界：只允许拒绝，不得猜测性恢复）

## 技术笔记

**这是 domain-research 产品形态结论的直接落地：浏览器清数据即丢库，备份 / 导出必须一等公民。**
零后端单机版（静态托管、无服务端）的命门就是「清一次站点数据 = 丢库」，因此备份不是可选
功能而是首轮切片的一部分（epic 默认决策 4）。引擎侧已被 US-217 完整覆盖（✅ Done 2026-09-29：
快照 / 恢复、归档元数据与兼容性检查、加密字段保持密文、损坏归档拒绝、备份失败后源库可继续
读写），本故事**不新增任何引擎能力**，只有三处接线：

- **主线程连接约束**：US-909 阶段 B 实测过三个 demo 的 OPFS 专用 Worker 与 IDB SharedWorker
  两条分支都返回 `unsupported_combination`（US-217 只交付主线程连接备份）。看板的备份入口
  必须显式处理这条边界（AC#5）——把「不支持」如实告诉用户，而不是让按钮报一个看不懂的错误。
- **恢复即数据替换**：恢复写目标库前的兼容性检查、全量摘要校验都在 US-217 内（「恢复库对
  普通连接可见前验证完成」）。看板侧只要不绕过它直连写库。
- **产品入口的状态反馈**：导出中 / 已下载 / 恢复中 / 失败原因，四种状态在三端一致（US-531）。

**为什么不承诺跨端同步备份。** 归档文件是「同 adapter 恢复」的单机快照（US-217 边界）。把它
放到云端、多设备拉取是团队版（US-533）的同步问题，单人版不做第二次。

**关闭条件**：重开不丢；导出 → 清库 → 恢复闭环数据一致；损坏归档拒绝且库不受损；不支持
备份的连接形态如实提示；恢复后功能照常。
