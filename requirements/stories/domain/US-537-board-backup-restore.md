# 用户故事：重开恢复与备份导出

## 作为/我想要/以便

**作为** 单人看板用户
**我想要** 导出我的看板数据，关掉浏览器、甚至清掉站点数据后，还能导回来继续用
**以便** 攒了半年的任务清单不会因为清一次浏览器缓存就没了

## 范围边界

### In Scope

- **重开恢复**：刷新 / 重开浏览器后板、列、任务、标签与排序全部原样（持久化验收，与
  [US-534](US-534-board-column-task-skeleton.md) AC#3、[US-536](US-536-task-detail-editing.md) AC#1
  的重开断言同源，本故事把「重开」做成产品入口与验收闭环）
- **备份导出**：以 [US-217](../adapter/US-217-local-database-backup-restore.md) 已交付的备份 API
  生成完整归档并交给浏览器下载（归档可带走，与站点数据隔离）。页面只能确认「归档已完整生成」，
  浏览器是否保存完成、用户是否取消保存对页面不可观测，所以成功状态写「备份已生成」，不写「已下载」
- **备份恢复**：在 `rxdb.connect()` 之前，把同 adapter、实体结构指纹一致的归档恢复到一个**新的库名**；
  恢复完成后整页重载，启动时连接新库并读回成功才把它记为活动位置。失败或取消保留原库与原活动位置，
  不覆盖或合并非空库
- **启动入口**：没有活动位置记录时先显示「新建空看板 / 装载演示数据 / 从备份恢复」，选择前不连接数据库、
  不建表、不装载种子；已有看板从工具菜单进入恢复，先确认「恢复成功后将打开备份中的看板」
- **演示数据只进新库**：启动页「装载演示数据」与工具菜单「重置为演示数据」都在新库名上建库并装载种子，
  后者与恢复走同一套两阶段切换；不向已有库追加，避免种子的固定 ID 撞主键
- **UI 状态**：生成备份中 / 备份已生成 / 选择备份 / 恢复中 / 切换中 / 已恢复 / 失败或取消；三端交互由
  [US-539](US-539-board-tri-framework-ui.md) 接线，本故事冻结状态转换与失败后去向
- **首轮支持组合**：三端宿主与 demo 使用 US-217 阶段 B 已支持的 **sqlite-wasm 主线程 `vfs: 'idb'`**，
  导出和恢复保持同 adapter、同兼容配置；必须实跑导出 → 清站点数据 → 启动恢复 → 重开闭环
- **额外连接形态**：OPFS 专用 Worker / IDB SharedWorker 等不在备份矩阵内的组合必须如实拒绝；
  此类拒绝仅验证能力边界，不能替代首轮支持组合的成功验收
- **归档兼容边界**：归档只恢复到实体结构指纹、系统表版本与变更编码版本都一致的应用版本，恢复时不迁移；
  不一致按 `incompatible_archive` 拒绝，提示「备份来自不兼容的版本」
- **旧库保留**：切换成功后旧库原样保留、不再被打开；首轮不提供清理入口

### Out of Scope

- 跨端同步备份（→ [US-541](US-541-board-team-sync.md)）
- 云备份 / 自动定时备份
- 备份加密与 keyring 语义——US-217 已覆盖（加密字段保持密文、密钥不进入归档），本故事不扩展；看板实体不加密
- 损坏数据库的自动修复（US-217 边界：只允许拒绝，不得猜测性恢复）
- 覆盖或合并非空库、跨 adapter 迁移、跨 schema 版本的迁移式恢复、自动把 Worker 连接降级成内存库
- 旧库清理、活动位置记录丢失后找回已有库
- 外置附件备份；首轮看板数据不包含附件，归档仅覆盖数据库

## 技术笔记

**这是 domain-research 产品形态结论的直接落地：浏览器清数据即丢库，备份 / 导出必须一等公民。**
零后端单机版（静态托管、无服务端）的命门是「清站点数据 = 丢库」，备份属于首轮切片。
US-217 已交付一致快照、连接前恢复到空目标、完整性检查与失败原子性；看板仍须补齐**应用启动、
存储位置选择、跨页面状态与切换**，不能把引擎能力完成等同于产品闭环完成。本故事不修改引擎 API。

**支持配置先固定。** sqlite-wasm 主线程 `vfs: 'idb'` 在 US-217 阶段 B 的支持范围内：
`RxDBAdapterSqlite.backupStorage()` 只拒绝 Worker 与 SharedWorker 传输，`idb` 走持久化存储，
`storageKey` 为 `<adapter>:<label>:<dbName>`（[`persistentBackupStorage`](../../../packages/rxdb-adapter-sqlite-core/src/RxDBAdapterSqliteBase.ts)）。
恢复入口 `RxDBAdapterSqliteBase.restore()` 的 TSDoc 写明「必须在 `rxdb.connect()` 之前调用
（经 `rxdb.getAdapter(name)` 拿到尚未连接的实例）」，只写入空目标，兼容性在写入第一条语句之前判定。
能力表 [`VFS_CONFIGS`](../../../packages/rxdb-adapter-sqlite-wasm/src/sqlite-load.utils.ts) 声明 `idb`
可在主线程运行且支持多连接；多页并发写不丢更新、另一标签页打开时导出，由 epic 第 0 步实测确认。
US-909 实测的 OPFS 专用 Worker / IDB SharedWorker 仍明确拒绝；不可用内存目标冒充「重开恢复」。

**每个存储位置一个库名。** 看板实体不加密，[`getRxDBBackupAuthDomain`](../../../packages/rxdb/src/backup/backup-target.ts)
对非加密库返回 `null`，归档不绑定库名，可以恢复到新的 `dbName`。活动位置就是当前使用的 `dbName`，由应用记在
`localStorage`；新旧库名不同，[`RxDBTabsGateway`](../../../packages/rxdb/src/gateway/RxDBTabsGateway.ts)
的广播与选主按 `dbName` 区分，旧页面与新库不会共用网关。

**切换用整页重载，不做页内热切换。** 页内换库三端做不到对称：Angular 的 `provideRxDB` 启动时解析一次，
React / Vue 虽能换实例，三端数据 hooks 在库关闭后都不重新订阅；实体类全局绑定一个 RxDB 实例，连接中恢复
还得克隆实体类。仓库已有同型先例 [`imported-db.ts`](../../../apps/dev-rxdb-angular/src/app/rxdb/imported-db.ts)：
「写覆盖键后整页重载」。恢复编排因此是两阶段，状态机放在核心包、三端共用：

| 状态              | 允许操作与转换                                                                                                       | 失败 / 取消后去向                                              |
| ----------------- | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 启动选择          | 无活动位置记录时选择新建、装载演示数据或恢复；只有新建与装载演示数据才连接                                           | 留在启动选择，不自动建库                                       |
| 选择备份          | 文件选择本身不写库；已有库恢复先确认，取消不启动恢复                                                                 | 回到原看板或启动选择                                           |
| 恢复中            | 写「恢复中」标记，所有页面暂停写入；断开本页连接，生成新库名，在未连接的 adapter 上调用 `restore()`                  | 清理本次目标、清除标记，原活动位置不变，原看板重新打开         |
| 切换中            | 恢复完成后写「待切换位置」并整页重载；启动时连接新库并读回，成功才把它写成活动位置并清除标记                         | 断开新库、清理本次目标、删除待切换记录，按旧活动位置重连       |
| 已恢复            | 打开备份中的看板；其他页面监听到活动位置变更后重载                                                                   | 后续操作沿正常看板流程                                         |
| 恢复失败 / 未完成 | 按错误类别展示重试、释放空间或清理入口；重开时遇到待切换记录或 `restore_incomplete`，先 `cleanupIncompleteRestore()` | 未完成目标不作为活动位置；清理失败保留可判别状态，不伪装成空库 |

新目标必须没有任何引擎内容、系统表或元数据（否则 `target_not_empty`）。活动位置是启动选择的唯一依据：
切换提交前中断仍回到旧位置，提交后中断只能打开完整的恢复库；检测到未完成恢复不得走普通空库初始化。
连接一个不存在的库名会静默建出空库，公开 API 也不能在不连接的前提下判空，所以不靠探测库是否存在做判断。
种子仅由「装载演示数据 / 重置为演示数据」触发，不能挂在页面加载或恢复目标连接钩子中。

导出沿用 US-217 的写出语义：`backup()` 只在归档完整写出、输出端 `close()` 完成后返回，生成期间禁止重复导出。
首轮输出端是内存 Blob，看板数据量下可接受；`showSaveFilePicker` 只在 Chromium 可用，不作为首轮依赖。
恢复错误按稳定错误码映射为用户可执行的提示，技术详情放诊断信息，不要求用户理解 adapter、Worker 或物理存储位置。
与原看板断开、目标连接及活动位置切换失败都必须覆盖，不能只测试归档损坏。

**归档跨版本不可恢复。** 兼容判定逐项比对实体结构指纹、系统表版本与变更编码版本，恢复时不迁移。应用任何一次
加字段之后，旧归档都会被 `incompatible_archive` 拒绝。所以首个持久化版本的 schema 一次到位（标签、截止日、描述与
可搜索字段，见 epic 首轮切片）；之后的 schema 变更必须连同「旧版本建的库在新版本重开」与本条边界一起评审。

**关闭条件**：首轮支持组合在三端完成持久化导出 → 清站点数据 → 连接前恢复 → 重开闭环；
已有库恢复到新库名、整页重载读回成功才切换，失败保留原库；多页面「恢复中」暂停写入、取消、中断与失败路径
符合上述状态流；不支持组合与不兼容归档如实拒绝；恢复后继续编辑和导出正常。US-540 AC#6 复用连接前启动恢复路径。
