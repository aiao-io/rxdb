# 用户故事：三框架 BOM 编辑与展开视图

## 作为/我想要/以便

**作为** 三框架的应用开发者
**我想要** BOM 的编辑与多级展开在 Angular / React / Vue 上同功能同 API
**以便** 不需要为某一端另写一套 BOM 交互

## 范围边界

### In Scope

- 多级展开树视图：懒加载、层级、展开量显示、`truncated` 提示
- 行编辑：用量、损耗、工序、生效期。写入路径服从 [US-507](US-507-bom-graph-skeleton.md) 的发布边界与
  [US-515 写入协议](US-515-bom-change-management.md#已发布头的写入协议)：`draft` 头逐行直接编辑，已发布头只经挂在 `draft` ECN 上的写入（见技术笔记「写入路径」）
- 错误在三端一致：同一错误**契约**——`code`、`payload` 结构与 `message` 相同；不是跨运行时的同一对象引用
- 三端共享同一业务 kernel 与同一份 fixture，框架层只做绑定
- 活查询刷新：依赖 = **查询谓词作用域**（`ResolutionContext` 覆盖的头、类型、组织、日期）+ 结果引用的实体
  （含作用域内发生项所挂 ECN 的状态，[US-508](US-508-bom-view-resolution.md) 的可见性由它裁决）；
  重算范围先取这个保守依赖集保证正确性（AC#6～#9）、再缩小，渲染范围始终受路径身份 key 约束（AC#2）
- 树节点 key 用**路径身份**（行发生项 ID 序列，[US-510](US-510-bom-multilevel-explosion.md)），不用裸 `item_id`

### Out of Scope

- 配置界面（US-517 的配置模型的 UI）——本 Epic 不做，US-517 只提供模型与 API
- 成本卷算结果的报表呈现
- 拖放重排（依赖 US-028 的可排序实体）

## 技术笔记

AC#1 是本仓铁律的直接落地：三框架 API 必须对称，单端缺失即未完成。
因此本故事**不拆成三条按端的故事**——那会让「两端已交付」看起来像进度，而实际上能力不可用。

AC#2 / #6～#9 落在既有活查询能力上，BOM 侧的额外要求是：展开结果是**派生视图**，它的失效依赖不能只是「哪些 `bom_line` 参与了这次展开」。
ECN 发布使新行可见（AC#6）、失效行变有效（AC#7）、imprecise 子件发布新修订（AC#8）、发布 phantom 默认值不同的新修订或换算率变化（AC#9）都会改变结果，
却都没有命中旧的参与行集合——按参与集过滤事件就会漏刷新。AC#6 尤其：新行写入时挂在 `draft` ECN 上、对解析不可见，
使它进入结果的是 ECN 的状态转移，不是任何 `bom_line` 的写入。所以依赖是两部分：查询谓词覆盖的作用域（任何落进作用域的写入都相关）
与结果引用的实体（物料、修订、换算率，以及作用域内发生项所挂 ECN 的状态）。先用这个保守依赖集把四类用例做绿，再谈缩小重算范围；
这与 [US-510](US-510-bom-multilevel-explosion.md) 的可达性 / 数量分离是同一件事的 UI 面。

**AC#2 约束渲染范围，不约束重算范围。** 保守依赖集下，作用域内任何写入都可能让整棵展开重算一遍，这不允许表现为整表重渲染：
节点 key 是路径身份，重算后路径没变的节点必须在三端都复用原来的 DOM 元素。判据是元素引用，不是渲染函数的调用次数——
三个框架的组件更新机制不同，次数没有可比性：用例在改动前按 key 记下各已渲染节点的 DOM 元素，改动后路径不含 o1 / o2 的节点必须仍是同一个引用。
缩小重算范围是正确性做绿之后的优化，AC#2 不依赖它。

**写入路径（AC#2 / #6）。** 展开树只含 `released` 头（[US-508](US-508-bom-view-resolution.md) AC#5），而已发布头的成员不接受原地改写
（[US-507](US-507-bom-graph-skeleton.md) AC#10）。所以展开树里「改一行用量」「新增一条行」都走
[US-515 写入协议](US-515-bom-change-management.md#已发布头的写入协议)：旧发生项打截止标记，新行与新发生项挂在 `draft` ECN 上，
写入时对解析不可见，ECN 发布后评估日到达其生效日才进入结果（US-508 AC#12）。这两条因此以 US-515 为前置；
ECN 生效日不早于宿主 UTC 当日（禁止追溯生效），评估日取同一天。`draft` 头可以逐行直接编辑，但它不入解析结果，展开树里看不到
（AC#3 的成环行写在 `draft` 头下，原因同此）。ECN 的新建 / 发布 / 取消界面不在本故事内，两条 AC 里的 ECN 操作由测试经 kernel 完成；
已发布头上行编辑的交互形态开工时随 US-515 一并裁决。

**「同一错误」指同一契约（AC#3）。** 三个运行时各有自己的错误对象，对象引用相等无从谈起；三端断言比的是 `code`、`payload` 与 `message`，
它们来自同一个共享 kernel，框架层不重新拼装。

AC#5 是多重边在 UI 层的验收：后端允许同一 `(parent, child)` 多行，前端若按物料聚合就把它抹平了。
这条与 [US-507](US-507-bom-graph-skeleton.md) AC#1 成对——存储层允许而展示层合并，等于能力不存在。
AC#10 是它在路径维度上的同一要求：同一子装配经两条路径出现是两个结果节点，用 `item_id` 做 key 会把它们的展开状态串在一起。
