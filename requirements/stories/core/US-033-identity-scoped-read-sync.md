# 用户故事：按身份同步可见数据（只读）

## 作为/我想要/以便

**作为** 用 RxDB + Supabase 做本地优先应用的开发者
**我想要** 没登录的访客能浏览全部公开数据，登录用户只同步自己有权限的行，换账号时本机缓存互不可见
**以便** 不靠匿名账号、不靠共享日志，就能让同一个后端服务权限不同的用户

## 现状（`b8e0e6601`）

- **共享日志做不到「各看各的」。** `rxdb_change` 对全部登录者可读，日志同步只适用于所有登录者可见范围一致的数据（[US-225](../adapter/US-225-supabase-sync-protocol-access-baseline.md) 的适用边界）。
- **QueryCache 的读取已经以调用方身份走业务表。** [`RxDBAdapterSupabase.fetchMetadata()`](../../../packages/rxdb-adapter-supabase/src/RxDBAdapterSupabase.ts) 与 `findByIds()` 用调用方的客户端查业务表，RLS 直接生效：

  ```ts
  const query = this.#client.from(scope.tableName);
  ```

  [`QueryCacheEngine`](../../../packages/rxdb-plugin-querycache/src/QueryCacheEngine.ts) 按查询比对元数据，本地有、远端以当前身份查不到的行作为孤儿删除（[US-020](US-020-querycache-repository.md)）。但没有任何用例在 RLS 下证明「各身份只拿到自己能看的行、失权后本地跟着删」。

- **换账号不隔离。** 同一个本地库换了身份，缓存优先（`localCacheFirst`）或离线时，会先露出上一个账号缓存的行，要等对账完成才消失。

## 范围边界

### In Scope

- **测试夹具**：一张带「公开 / 租户私有」标记的业务表与一张租户成员表，RLS 让 anon 只读公开行，登录用户读公开行与自己所在租户的行（测试环境 SQL）。
- **契约测试**：anon、两个用户、两个租户，经 QueryCache 只读同步；覆盖首次同步、成员关系变化而业务行不变、可见性变化、远端删除，以远端按该身份的查询结果作对照。
- **本地库绑定身份**：第一次与远端交换数据时记下身份（未登录记为 anon，登录记为用户 id 的不可逆摘要）；之后身份对不上就停止同步并报错——查询缓存的远端读取、日志拉取与推送都停，本地数据不动。同一用户刷新令牌不算身份变化。
- **按身份算本地库名的工具**：同一身份得到同一个名字，不同身份互不相同，名字里不含邮箱或用户 id 原文。应用按当前身份打开各自的库。
- **文档**：公开数据给 anon、受限数据靠 RLS、按身份分库与身份不匹配的处理。

### Out of Scope

以下是同一 epic 的后续故事：

- **写入**：离线写、Supabase 适配器在 QueryCache 模式下写远端。
- **实时刷新**：公开数据走公开频道、受限数据按租户划分私有频道。本故事靠查询时对账。
- **全量离线同步公开数据**：已定按查询缓存。
- **跨标签页广播锁定、「从此设备移除此账户数据」**。

## 技术笔记

- **身份从哪来**：Supabase 客户端发请求时带的令牌——有会话时是会话令牌（`sub` 即用户 id），没有会话时 supabase-js 交出 apikey 本身（anon）。令牌刷新时 `sub` 不变，身份也就不变。
- **守卫放在哪**：与远端身份（`remote-backend.ts`）同一处比对——日志拉取与推送的入口、查询缓存读取远端之前。不匹配时同样「停下 + 报错」，不自动改绑：自动改绑会把上一个账号缓存的行露给新账号。
- **绑定存在哪**：优先复用 `rxdb_migration` 的水位行（与能力认领同一类「这个库上发生过什么」的事实），这样不必升系统 schema；行不够用再给系统表加列（schema 9 → 10）。
- **核心公开面**：核心新增导出受命名门禁约束，守卫、错误类型与库名工具放在同步插件或适配器包，核心只在必要时扩展远端适配器契约。
- **为什么不用匿名账号**：公开数据本来就不需要身份；每个浏览器一个匿名用户要多一次注册、多一行 `auth.users`，量大了要定期清理，还要加验证码防滥用。
