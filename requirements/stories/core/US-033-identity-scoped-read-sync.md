# 用户故事：按授权分区同步（只读）

## 作为/我想要/以便

**作为** 用 RxDB + Supabase 做本地优先应用的开发者
**我想要** 数据按授权边界分区（公开区、每个租户一个区），每个身份只能拉到自己能读的区，在能读的区里再按实体同步规则挑选要同步的行
**以便** 没登录的访客能离线浏览选中的公开数据，登录用户离线拥有自己有权限的数据，同一个后端服务权限不同的用户

## 现状（`26521c24`）

- **共享日志不分授权。** `rxdb_change` 对全部登录者可读（[US-225](../adapter/US-225-supabase-sync-protocol-access-baseline.md) 的适用边界），日志同步只适用于所有登录者可见范围一致的数据。
- **实体同步规则只是筛选，且条件变化时不可靠。** `SyncType.Filter` 的 `remote.filter` 是函数，每次拉取重新求值，`syncManager.pull()` 也接受调用方传入的 `filter`。但：
  - 拉取进度每个实体只有一个，不记录当时的条件（[`getOrCreateSyncRecord`](../../../packages/rxdb/src/sync-contract/sync-record-utils.ts)）：

    ```ts
    const syncId = `${namespace}:${entity}:${branchId}`;
    ```

    条件放宽后，进度之前、刚变得匹配的行永远拉不到。

  - 离开条件的行不会自动从本地删除，要手动调 [`syncManager.cleanupExpired()`](../../../packages/rxdb-plugin-sync/src/cleanup-expired.ts)，遇到不能取反的操作符会报错（`Cannot invert operator`）。

- **同一条规则有两套语义不同的求值器。** 日志上的 [`rxdb_jsonb_matches_rule`](../../../docker/sql/02-rxdb-sync-functions.sql) 把 `!=` 实现为 `IS DISTINCT FROM`，字段为 NULL 时命中；仓储查询经 [`normalize_field_filter`](../../../packages/rxdb-adapter-supabase/src/rule_group_builder.ts) 翻译成 PostgREST 的 `neq`，按 SQL 三值逻辑不命中。今天筛选只用来少拉数据，多拉无害；按规则决定本地该有哪些行之后，两处口径不同就是数据不一致。

## 范围边界

### In Scope

- **分区规则**：业务表的生成列 `rxdb_bucket`，表达式由应用写（例如 `CASE WHEN visibility = 'public' THEN 'public' ELSE 'tenant:' || tenant_id END`），服务端计算，客户端改不了。生成列只能引用本行：子表要自己带租户键与可见性字段，一行只属于一个区。
- **不带正文的分区日志**：新表 `rxdb_bucket_change`，只记日志 id、区、实体、行 id 与操作（写入或移除），不存行内容。一行换区时，旧区记一条「移除」，新区记一条「写入」。日志 id 顺序等于提交顺序，做法与 `rxdb_change` 相同。`rxdb_change` 与它的授权保持 US-225 的状态。
- **读授权**：SQL 函数 `rxdb_caller_buckets()` 返回调用者能读的区。平台默认给 `public` 与 `user:<auth.uid()>`；应用把自己的成员判断登记给平台，由平台函数调用，重跑参考 SQL 不会覆盖应用的登记。分区日志表开 RLS，日志行只对能读该区的身份可见，anon 能读公开区。
- **按区快照与按区拉取**：两个 `SECURITY INVOKER` 函数，正文都从业务表读，调用者的 RLS 与列权限照常生效。增量取该区游标之后的日志行，按行去重，逐行取当前行：取得到并且匹配实体同步规则就返回这一行，否则返回「移除」。快照是同一套列与规则去掉游标条件，按主键分页。每一行带版本号，即它在这个区里最大的日志 id。一次请求可以带多组（区、实体、游标）。
- **区内可读的行须一致**：同一个区里的成员能读相同的行；列可以不同，由业务表的列权限裁决。区的划分要与业务表的 RLS 一致：两者不一致时不会泄露正文，但没划进区的行同步不到。
- **分区实体登记与旧协议**：分区实体在服务端显式登记，登记时校验 `rxdb_bucket` 生成列。登记后它的变更只进分区日志：旧推送 `rxdb_mutations` 带这些实体的日志时一律拒绝，旧拉取读不到它们的任何日志，全局频道 `rxdb:changes` 里没有它们的通知，首版不发分区通知。客户端在同步开始时向服务端取已登记的分区实体，按分区协议同步它们。没有分区列的旧表维持 US-225 的行为。
- **按区进度**：每个「区 × 实体」一条进度，记游标与上一次的规则原文。同步开始时取一次能读的区，与本地记下的比较，得出加入与退出。加入一个区时先记下快照点，再拉快照，之后从快照点增量拉；退出一个区时，本地整块删掉该区的行。
- **落库规则**：本地记下每行的来源区与版本号。一条变更只有在版本号大于本地版本时才应用，写入与移除都一样；「移除」另外只删来源区对得上的行。行与该区的进度在同一个本地事务里提交。每轮同步有一个本地轮次，落库前核对本轮没有被更新的轮次取代。
- **实体同步规则筛选**：在能读的区里按 `remote.filter()` 挑行。规则在服务端编译成 SQL 条件，在业务表上求值，快照与增量是同一套，口径与仓储查询一致。规则变化分两种。形状不变、只有比较边界朝收窄方向移动时（滚动时间窗口属于这一种），不重拉快照，只在本地清掉不再匹配的行。其余变化按新规则重新对账受影响的「区 × 实体」：补拉新规则下的快照，删掉本地不在快照里的行。两种情况都跳过带未推送修改的行。
- **测试**：公开行、两个租户、两个用户与 anon 的 SQL 回归和真栈契约测试。两者共用一个专门的测试夹具实体：带「公开 / 租户私有」标记与租户键，一个可为空的分类字段，一个只授给登录用户的成本列，以及更新时间。全部 AC 通过之前不接入第二个实体。
- **文档**。

### Out of Scope

以下是同一 epic 的其他故事：

- **每个身份一个本地库**（[US-035](US-035-identity-bound-local-database.md)）：库名、打开时与同步前的身份核对、换身份时在途响应的丢弃。
- **写入**（US-034，无故事文件）：推送时服务端按写后的行算区并记进对应区的日志、离线写、冲突，以及被移出某个区时本机未推送修改的处理。本故事里分区实体不参与推送，本地修改留在本机；测试数据经业务表直写（同步触发器路径）产生。
- **实时刷新**：按区的通知频道。
- **同一个区里可读的行不同**：这时分区日志会让区内成员看到自己读不到的行的 id 与变更时间，要先评估这层元数据再做。
- **撤权的即时性**：离线设备在下一次与远端交换数据之前感知不到撤权，本故事不承诺撤权即时生效。
- **规则之外的公开行**：同一个实体的同步类型互斥，分区同步的实体不能同时走 QueryCache 在线浏览规则没选中的公开行。
- **非 main 分支的分区化**。
- **QueryCache**：保持现状，只用于「不落地、只在线浏览」。

## 验收标准

对照基准：同步完成后，本地该实体的行与字段，等于以该身份、同一条实体同步规则，对每个能读的区重新做按区快照的结果。下表的预期结果都按这个基准比对。

## 技术笔记

- **为什么分区日志不带正文**：日志带正文时，正文由日志的分区 RLS 裁决，业务表的列权限与删除都管不到它。[试验](US-033-bucket-log-spike.md)里，anon 从公开区的日志读到了业务表没授给它的成本列，后加入的成员读到了已删除的行与被覆盖的旧值；行换区还要在业务事务里把旧区的历史正文置空。不带正文之后这三件事都不存在，快照与增量也成了同一条读路径。代价是每页多一次按主键取行，并且客户端拿不到逐条 patch，US-034 做冲突裁决时要另定基线。
- **为什么单独成表**：给 `rxdb_change` 加分区列，就要在它上面开 RLS、把 anon 的读权限放回去，旧日志靠「分区列为空」区分；而 [01-rxdb-system-tables.sql](../../../docker/sql/01-rxdb-system-tables.sql) 里还有一行 `ALTER TABLE IF EXISTS public.rxdb_change DISABLE ROW LEVEL SECURITY`。单独成表之后旧表原样不动，anon 仍然碰不到它，旧客户端直读 `rxdb_change` 也读不到分区实体的任何日志。
- **为什么是分区日志，而不是以身份直读业务表再对账**：直读对账（QueryCache）只覆盖查过的范围，加入、退出租户要对全部可见行做对账，大列表每次同步都要拉回全部元数据，Supabase 下也不能写远端。按区记日志后，加入与退出租户是整个区的下载与丢弃，换租户、公开改私有是两条增量。本方案的正文虽然读业务表，增量仍只取变更过的行。
- **授权与筛选分开**：分区由服务端算、由 RLS 裁决能读哪些区；实体同步规则只在能读的区里挑行，客户端改规则扩大不了授权。
- **快照与增量的一致性**：先读快照点（已提交的最大日志 id；日志 id 顺序等于提交顺序，在途事务的 id 一定更大），再拉快照，再从快照点增量。快照可能已包含快照点之后的修改，增量重放后最终收敛。两个函数都声明为 `STABLE`，返回的行内容与版本号取自同一个语句快照。
- **迟到的条目**：各区的进度各自推进，同一行在两个区的日志之间没有到达顺序的保证。本地按版本号与来源区裁决：版本号不大于本地版本的写入与移除都丢弃，「移除」只删来源区相同的行。
- **规则变化的判定**：只存指纹分不出放宽还是收窄，所以进度里存上一次的规则原文。两份规则形状相同，且不同之处只是 `>=` / `>` 的值变大或 `<=` / `<` 的值变小，判为纯收窄。[同步文档](../../../website/docs/collaboration/sync.md)里的滚动时间窗口每次同步求出的边界都不同，属于这一种；它若按「规则变了就重新对账」处理，每次同步都要重拉全量快照。
- **筛选口径**：仓库里同一条规则已有两套求值器，NULL 的结论不同（见现状）。本故事把规则编译成 SQL 条件，在业务表上求值，口径以仓储查询为准：`!=`、`notIn` 遇到 NULL 不命中。这样快照、增量与仓储查询三处一致，条件还能走索引；[试验](US-033-bucket-log-spike.md)里在当前行上逐行调用日志求值器，比 SQL 比较慢两个数量级。只接受现有筛选同步支持的操作符与实体自身的字段（[`assertSnapshotFilterSupported`](../../../packages/rxdb-adapter-supabase/src/supabase.helpers.ts)），字段名按标识符转义，值不拼进 SQL 文本。旧的 `rxdb_pull_changes` 不动，它在日志上的求值口径维持原样。
- **增量的计划形状**：从变更的行 id 出发，逐行按主键取当前行。写成半连接时规划器会对业务表做全表扫描，并且先对区里每一行求筛选，代价随区的大小增长。试验里 2 万行的区改 1000 行，前一种写法 10 ms，后一种 192 ms。
- **列清单**：按调用者的列权限生成。对整行取 `to_jsonb` 的话，只授了部分列的角色会得到权限错误。
- **进度与来源区存在哪**：同步插件自己的表，不新增核心导出（核心命名门禁）。远端适配器契约在核心包，阶段 B 的契约变更要过 API 基线。
- **RLS 性能**：分区日志的策略写成 `bucket IN (SELECT public.rxdb_caller_buckets())`，函数 `STABLE`、语句内只算一次；日志按（区、实体、日志 id）与（区、实体、行 id、日志 id）各建一个索引。应用的成员判断放进 `SECURITY DEFINER` 函数，成员表建 `(user_id, tenant_id)` 索引，策略里用 `(SELECT auth.uid())`。
- **只读阶段的推送**：分区实体的日志不进 `rxdb_change`，旧推送入口会拒绝它。客户端因此在推送资格判定里把分区实体标为不可推，不发远端请求。
- **日志 id 的位宽**：分区日志的 id 用 `bigint`。`rxdb_change.id` 是 32 位的 `serial`，新表不必沿用；这个 id 还要当每行的版本号，换区一次就写两条。
