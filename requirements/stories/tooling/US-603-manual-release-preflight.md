# 用户故事：手工发布入口的提交与校验结果一致性

## 作为/我想要/以便

**作为** 手工执行发布的维护者
**我想要** 仓库支持的发布入口确认校验结果属于当前待发布提交和产物
**以便** 不把未经校验的改动或与清单不符的系统迁移发布出去

## 症状

`0.0.28` 的产物将系统 schema 从 3 抬到 7，发布清单仍声明 `normal` 且升级位为 false；
当前清单门禁已阻止新候选重复这一错误，但手工发布入口尚未绑定 `pnpm test-all` 的通过结果。
依据与下一次发布基线见 [release-plan](../../release-plan.md)。

## 范围边界

### In Scope

- 仓库支持的发布入口：根 `package.json` 的 `publish` 与 `publish:sequential`
- 发布前检查当前提交、工作区状态、版本和清单，以及 `pnpm test-all` 的通过结果
- 约束已构建/打包产物与通过校验的提交一致；选择运行校验还是读取证据由实现计划决定
- 保留手工发布和 owner 决定发布时间的流程，不引入自动发布 workflow

### Out of Scope

- 阻止维护者绕过仓库入口直接调用 npm registry API 或 `npm publish`
- 重新实现现有迁移清单、API 基线、包组合门禁或改变它们的规则
- 自动选择发布版本、推 tag、发布 npm 包或修改分支保护

## 验收标准

| #   | 前置条件                                    | 操作                                   | 预期结果                                               | 状态 |
| --- | ------------------------------------------- | -------------------------------------- | ------------------------------------------------------ | ---- |
| 1   | 当前提交没有通过全量校验                    | 使用任一受支持发布入口                 | 发出任何 registry 写入之前拒绝发布，指出缺失/失败校验  | ⬜   |
| 2   | 提交 A 通过校验，之后改动工作区或切到提交 B | 使用受支持发布入口                     | 不复用 A 的证据，要求验证当前待发布内容                | ⬜   |
| 3   | 当前提交通过校验，但版本/迁移清单不符       | 使用受支持发布入口                     | 现有对应门禁失败即停止，不能继续发包                   | ⬜   |
| 4   | 产物构建或打包之后又修改源码                | 使用受支持发布入口                     | 拒绝过期产物，或从已验证内容重新构建打包               | ⬜   |
| 5   | 当前提交、校验、版本清单与产物全部一致      | 使用受支持发布入口的可控 registry 替身 | 允许执行发布步骤，两条入口遵守同一前置规则             | ⬜   |
| 6   | 阅读发布文档                                | 对照支持范围                           | 明确手工入口及绕过路径边界，不宣称能约束仓库外发布命令 | ⬜   |

## 实现文件

- `package.json` — 两条手工发布入口
- `scripts/publish-sequential.mjs` — 顺序发布路径
- `scripts/` — 前置校验与回归用例，具体落点由计划确定
