# 候选领域：人生快进中（微信小游戏）

> 本文评审用户提供的《人生快进中》V0.1 MVP 策划案（2026-10-18），记录契合度与验证范围。
> 候选状态只在[本目录 README](README.md)维护；本文不是用户故事或实现排期。

**结论：✅ 值得做小规模验证。** 「职业操作 → 人生选择 → 可解释的人格与人生总结」适合做
轻量小游戏闭环。当前 V0.1 的时间预算、广告推进与数值规则需要先收敛；作为本仓库的产品实验成立，
但现有小程序适配器尚无 Cocos 微信小游戏兼容证据，不能直接承诺已支持。

## 与仓库是否匹配

| 真实需求                   | 可复用能力                 | 边界                                                            |
| -------------------------- | -------------------------- | --------------------------------------------------------------- |
| 多次进入继续同一人生       | 本地存储、类型化实体、迁移 | 小游戏宿主需单独验证；本地存档不自动跨设备                      |
| 选择后属性与履历一起更新   | 事务、响应式查询、日志实体 | 普通重复操作的幂等需要业务规则；崩溃安全不能由事务 API 名称推导 |
| 按年龄、职业、事件生成总结 | 结构化日志查询、模板生成   | 娱乐画像来自游戏内选择；无需引入 LLM 或向量检索                 |
| 职业小游戏                 | 内存中的实时状态与操作结果 | 渲染、碰撞、音效和手感由 Cocos / 游戏逻辑负责                   |
| 分享与激励广告             | 微信小游戏平台 API         | 广告、分享卡绘制与平台运营属于应用层                            |

离线续玩、状态订阅、结构化模型与结算约束覆盖了领域研究的三个评估维度，但轻量存档方案也能满足
首版需求。RxDB 的价值要靠存档恢复、日志一致性和开发成本验证，不凭「需要存档」就认定必须上数据库。
策划没有提出多人协作或跨设备同步，首版不额外添加这些需求，也不需要把每个选择变成数据库 commit。

## 策划必须先闭合的规则

本节指出原稿中的缺口；涉及范围删减或玩法变更的内容均为评审建议，尚未替换原策划。

### 时间预算与内容量

策划 2.2 / 3.3 / 11 节的数字不能同时作为保证：

- 7 天 × 每天 30～60 分钟，总预算为 **210～420 分钟**。
- 240～400 个事件 × 每个 1～2 分钟，单事件层就需要 **240～800 分钟**。
- 职业小游戏、测评、过场、总结还没有计入；「每年 3～5 个事件」也没有留下明确的平淡年份。

先确定总决策数与每次事件时长，再决定章节数。「7 天」需要明确是预计总游玩周期、七次章节，还是
日历解锁；原稿只写不强制连续登录，没有定义这三者。退休后应直接展示总结，不能只为凑 Day7 延迟反馈。

第 12 节首版只有司机职业，换职业、投资、家庭后置；第 11 节 Day2～Day5 却依赖这些内容。
建议首个验证版采用独立的一局节奏，暂缓完整七天表与 24～64 种剧本卡。

### 时间推进与广告奖励

「推进五年并补日志」不能代替五年里的玩家选择。推进需遵循同一套规则，遇到未决关键事件停下；
未发生的选择不能写进人格变化和总结。平淡年份如果本就自动结算，快进券的额外价值仍需说明。

双倍收入会改变财富指数、培训机会与后续选项，因此广告的准确承诺应是「不直接增加人格分」，
不能宣称不改变人生结果。建议第一局验证暂不接广告，先证明原有循环值得重复玩。

接广告时，官方 `onClose` 的 `isEnded` 表示是否完整观看；`show()` 成功不代表已经看完。
奖励需要一次性结算凭据，覆盖重复回调、提前关闭、错误与切后台。原稿「加载失败给游戏币」是另一套
奖励规则，不能混同已看完广告；首版移除广告后也不需要这条补偿路径。

### 测评、数值与因果

- 情境选择题可以提供偏好或人格基线，不能据此测得反应、记忆与体力。建议首版能力使用共同基线，
  操作表现独立记录；职业推荐不作为准入限制。
- 明确人格初值、范围、每事件效果与重复规则。若按 0～100、初始 50，七次 `+8` 就封顶；
  大量事件下仅有上下限并不能保证画像有区分度。建议首版用固定数量的一次性关键事件。
- 「天真随年龄自然下降」会让年龄覆盖玩家选择，建议首版暂不做自动人格衰减。总结至少引用实际选择，
  让玩家知道标签从何而来。
- 工作是否消耗人生时间、能否无限刷钱、健康归零如何继续都需要规则。建议每局工作消耗固定人生时间；
  首版健康归零触发提前退休，后续再设计复健和转折路径。
- 第 5 节定义心情，第 5.5 节却用幸福计分；第 9 节称五项状态但只列四项，遗漏财富。
  先统一财富、健康、心情、关系、成就。财富与其他分数的单位不同，未经归一化不能直接加权。
  第一局可以先展示各项与选择依据，把综合人生指数后置。

## 建议的第一局

以下是缩减建议，尚未替换原策划：

| 项目     | 验证范围                                         |
| -------- | ------------------------------------------------ |
| 总时长   | 约 15～20 分钟，完整走到退休与总结               |
| 职业     | 司机一个职业，先验收一套操作机制                 |
| 人生阶段 | 青年、中年、老年三个阶段；其他年份概述           |
| 测评     | 约 60～90 秒，只形成初始偏好，不锁职业           |
| 关键选择 | 约 10 个，每个约 30～60 秒，优先一次性事件       |
| 职业操作 | 约 3～4 局，每局约 45 秒                         |
| 结尾     | 一张履历 / 人格总结卡，引用本局选择              |
| 后续项   | 七天内容、换职业、婚姻投资、广告、排行和云端账号 |

至少打通一条有后果的链：工作选择改变健康与财富 → 后续危机选项与代价改变 →
总结明确引用这些经历。同一事件不能只是换一段文案或给任意分数。

第一轮要看到玩家能完成一生、不同选择形成至少两条可解释轨迹，以及任意决策节点退出重进都能继续。
埋点先看第一局完成率、事件退出点、总结到达率与自愿再开率；七天留存和广告观看率等完整循环成立后再测。
不先编造没有试玩数据支持的达标阈值。

## 数据与游戏循环的分层

数据结构先保持小：

- `LifeRun`：当前年龄 / 阶段、属性状态、待决事件、内容版本、随机种子与结算位置。
- `LifeLog`：已结算事件实例、玩家选项、实际效果与发生年龄；同一人生中的事件实例唯一。
- `LifeSummary`：退休时的结果与日志依据，也可按固定模板重建。

静态事件先用带版本的 JSON，选择效果与触发规则由纯 TS 逻辑计算。记录实际效果与内容版本，
避免更新事件文案或数值后旧人生被重新解释；随机事件须持久化已选结果，重进不能重抽。

一次选择的状态更新、日志与结算标记在同一事务内完成，处理双击和重复命令。职业操作的逐帧状态放内存，
只在节点或单局结束时保存。Cocos 组件订阅领域状态，不让数据库写入进入逐帧循环。

游戏宿主使用框架无关数据层；如果新增公共 Angular / React / Vue 绑定，继续遵守三端对称。
Cocos 游戏本身无需复制成三个 Web 框架项目。

## 小游戏宿主：当前缺口

Cocos Creator 的微信小游戏发布目标是 `wechatgame`，生成 `game.json` / `project.config.json` 等配置。
官方小游戏示例通过 `wx.createCanvas()` 创建画布；不能把浏览器 DOM 或现有 Taro 页面直接搬入。

本仓库 [`rxdb-adapter-miniprogram`](../../packages/rxdb-adapter-miniprogram/README.md) 当前明确限定为
小程序逻辑层、同步 wa-sqlite、单 realm / 单连接，不支持 Worker、WAL 或并发连接。它整库缓冲到内存，
只适合约 10 MB 内的兼容性验证，且不承诺崩溃恢复安全。
[`rxdb-taro`](../../packages/rxdb-taro/README.md) 是 Taro 4.3.x + Vite 构建接线，无法直接作为 Cocos 插件。
不要用「放进 Worker」解决帧时间问题，现有适配器没有该支持。

先做 Cocos 小游戏最小存档探针，验收：

1. Cocos 发布产物中的 WASM 路径与分包、glue 加载、可信随机源、`BigInt` 和运行时能力预检。
2. 建库 → 保存一项状态与日志 → 退出重开 → 内容一致；Android / iOS 真机分别验证，模拟器通过不算完成。
3. 切后台、重复提交、配额失败及保存期间被终止，区分正常重开、逻辑事务与尚未证明的崩溃恢复能力。
4. 职业小游戏期间的同步 SQL / 文件写入开销、冷启动、包体与内存，按实测决定可否用于该产品。

探针未通过前，只记录为小游戏数据层候选，不扩大现有适配器的支持声明。

## 立项前置

- 明确一局时间预算与工作 / 事件 / 退休状态转换，先写领域逻辑红测。
- 先完成小游戏存档探针，再承诺持久化能力与发布平台。
- 明确首批事件、司机操作机制及一条因果链的至少两个选择结果；美术、内容、分享与广告是应用成本。
- 微信云开发不作为首局必需依赖；账号、排行榜或可信奖励确有需求时再设计服务端边界。

## 入场条件（什么信号才值得继续）

用户已明确提出加入此游戏，本轮先纳入研究。正式立项前应能找到具名试玩者愿意完成第一局，
并对「选择带来的后果与总结」有明确反馈；若只是想分享一张测评卡，应重新评估职业小游戏与长人生的成本。
RxDB 接入价值则以真实的退出续玩、状态 / 日志一致性和维护成本验证。
