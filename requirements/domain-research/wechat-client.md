# 候选领域：微信客户端部分功能复刻（独立客户端，非小程序）

> 本文是候选领域分析，不是用户故事，不参与状态统计。状态与维护规则见
> [本目录 README](README.md)。

**一句话结论**：引擎契合度与 BOM 并列第一，且**零引擎缺口**——会话列表、聊天记录、搜索、
离线、加密全部现成；但微信体验的约六成在引擎外（消息通道、附件、音视频），产品生死取决于
是否自建 IM 服务端。定位：做「本地层 + UI 层」的演示项目是顶级候选；做真实产品要先回答
「IM 服务端谁来建」。

## 范围

独立客户端（Web / 桌面 / 移动），复刻微信客户端的**数据与交互层**部分功能：
会话列表 + 未读角标、聊天记录分页浏览、通讯录、聊天记录全文搜索、离线读旧消息与草稿、
本地库加密。**不含**实时音视频通话、朋友圈分发（可作为后续扩展另行评估）。

微信客户端本身的架构就是「本地 SQLite 全量留存 + 服务端同步」，rxdb 正是这条技术路线的
现成实现。

## 契合点：现有能力逐项映射（全部零成本）

| 微信客户端功能       | 引擎现有能力                                                                  | 出处                                                          |
| -------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------- |
| 会话列表 + 未读角标  | 活查询：新消息落库 → 列表自动重排刷新，响应式查询的主场                       | [capability-matrix](../capability-matrix.md) 跨框架 hook 矩阵 |
| 聊天记录分页         | 按会话收窄的有界查询 + `useFindByCursor` + InfiniteScroll（三端已交付）        | [capability-matrix](../capability-matrix.md)                  |
| 搜索聊天记录         | FTS5 + CJK bigram 已交付（web / 桌面端）                                       | [US-702](../stories/future/US-702-full-text-search.md)        |
| 离线读旧消息 / 草稿  | Local-first 全量本地留存                                                       | [epic-001](../epics/epic-001-core-mvp.md)                     |
| 发送队列（断网暂存） | 同步队列持久化、断点续传、重试与积压监控是 vision 阶段 2 的方向                | [vision](../vision.md) 阶段 2                                 |
| 本地库加密           | 加密 keyring 内建                                                              | [US-803](../stories/future/US-803-local-encryption.md)        |
| 手机 / 桌面 / Web 三端 | 三框架对称 + Electron / Tauri 适配器                                           | [capability-matrix](../capability-matrix.md)                  |

**零引擎缺口**是它和 BOM 最大的差别：BOM 要先补声明式约束与多重边（US-030 / US-507）才能开工，
复刻微信一个引擎缺口都不用补。

## 关键设计修正：加密与搜索不互斥

早期分析按「端到端加密（E2EE）」假设得出「加密与搜索互斥」的结论，**该假设作废**：
微信不是 E2EE——服务端可见消息，本地加密只为设备安全。照微信模式做，
「本地加密 + 服务端明文索引」不冲突，FTS 照用。E2EE 场景（如 Signal 式产品）才触发
「加密字段不进索引」的冲突（见 [vision](../vision.md) 阶段 6 与 rejected-domains 相关条目）。

## 引擎外成本：三座大山，约占微信体验六成

| 大山       | 内容                                                                                          | 仓库现状                                                                                      |
| ---------- | --------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 消息通道   | WebSocket 长连接、消息路由、群组广播、在线状态、离线推送（APNs / 厂商通道）、送达 / 已读语义  | 必须自建。[dev-rxdb-http-server](../../apps/dev-rxdb-http-server) 只是 REST + SSE 参考后端，不是 IM 服务器；SSE 只做失效通知，不得变成长连接流（[US-212](../stories/adapter/US-212-http-adapter.md)） |
| 附件消息   | 图片 / 语音 / 视频 / 文件的分片上传、缩略图、对象存储同步                                      | vision 阶段 5 的方向，今天未交付；微信消息一半以上是附件                                       |
| 实时音视频 | WebRTC 通话                                                                                    | 彻底在引擎外，仓库无任何相关能力                                                              |

引擎内的部分做得再好，也只是复刻了微信客户端的「SQLite 层 + UI 响应层」。实时性是 IM 的灵魂，
引擎的同步是异步合并模型——rxdb 不解决消息通道，只解决「消息到了之后」的一切。

## 入场条件（什么信号才值得立项）

- **产品路线**：已决定自建 IM 服务端（或已有具名「多设备消息不同步 / 离线收不到消息」的
  具体症状），本候选作为客户端底座立项
- **演示路线**：owner 决定做引擎能力演示——展示活查询 / 搜索 / 离线的教科书场景，
  演示价值入场（先例：BOM 由完整功能演示应用驱动）

**状态**：研究中
