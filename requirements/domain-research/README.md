# 候选领域研究区

> 这里是领域想法在成为用户故事之前的家：自由研究、记录契合度分析、写明入场条件。
> 本目录文件**不是用户故事**：无 story frontmatter，不计入故事数，不进
> [status-overview](../status-overview.md)，也不是承诺清单。故事五态、价值待证判据与写作规范见
> [CONVENTIONS](../CONVENTIONS.md)，本目录只定义自己的候选状态与维护规则。

## 底线判据

一个领域要同时用得上「离线 + 响应式 + 多端同步 + 模型驱动」中至少三项，才值得付
「三框架对称 + 适配器矩阵」的税；只吃单一能力的领域（如纯游戏存档同步）养不起这套引擎。
引擎能做什么、不能做什么以 [capability-matrix](../capability-matrix.md) 为准，长期方向看
[vision](../vision.md)（那是方向不是承诺）。

## 产品形态：零后端单机版

浏览器内 SQLite 让「数据库即前端」成立：候选可以先交付**纯静态托管的单机版**——零服务端代码、
零运维，数据层测试在 Node 里跑同一份 wasm SQLite（仓库 conformance 套件已这么干）。
多设备 / 多用户才需要同步端，且可复用 Supabase / HTTP 适配器而不必自建。
评估维度见横向对比「零后端可交付」列。

三个坑：① 浏览器清数据即丢库，备份 / 导出必须一等公民（[US-217](../stories/adapter/US-217-local-database-backup-restore.md) 已交付）；
② 秘密 / 支付 / 合规仍需最小 serverless 后端；③ 单机产品变现倾向「买断 + 同步增值」（Anki 模式），
SaaS 订阅可行性未经采用验证。

注意：零后端可交付指服务端成本趋零，不等于产品开发成本为零；「市场空白」「订阅走不通」等
商业判断目前没有采用与付费证据支持（见[复核纠偏](#复核纠偏2026-10-18)）。

## 优先级结论（2026-10-18 复核）

按用户确认的目标「尽快交付可用产品，同时验证并推广 RxDB」复核全部候选：

**✅ 第一顺位：[模型驱动后台](admin-framework.md) 的严格切片——给定实体 schema 的单人 Web 本地
数据工作台**，首版交付录入、编辑、筛选、持久化与备份恢复闭环。它已有最多可以直接复用的产品
交互，也最容易让外部开发者验证「定义实体之后少写了多少 CRUD」。

第二顺位为单人任务看板。个人消费产品优先考虑文本 SRS 或健身记录，具体顺序由真实使用者与内容决定。
AI 构建器和小游戏适合继续做有边界的技术 / 玩法验证，当前不作为最快交付主线。

评估口径：现有实现距用户闭环有多远、能否自然验证 RxDB、是否依赖另一项大型工程、能否找到持续
使用入口、失败后的投入是否可控。不用市场规模、虚构用户数量或精确工期评分。各候选的顺位与判断
见[候选清单](#候选清单)「顺位」列与[优先级评审](#优先级评审2026-10-18)详情。

以下情况会推翻第一名：

- 最小独立消费应用存在必须先改底层的安装、样式、持久化或备份问题。
- 首个用户必需多人权限、按人限制同步行，或要求浏览器运行时改 schema。
- 找不到愿意使用固定 schema 工作台的人，而看板、SRS 或健身已经有持续用户与明确验收任务。

## 优先级评审（2026-10-18）

按「尽快交付可用产品并验证 RxDB」做的一次跨候选评审。复核对象：14 个独立候选 + 草稿区 +
未深入候选 + 五类否决方向；BOM 已解锁 Epic，单独处理（见下）。同一梯队内部的细小名次没有
足够用户证据支持，明确第一与第二顺位，其余按入场条件推进。

### 核对后的事实

- `rxdb-model` 核心及三框架绑定已包含列表、详情、表单、表格和查询构建器；现有实体页面确实直接消费组件。
- 现有 `Task` 是带排序的 Todo 数据，不包含完整 Board / Column / 跨列移动产品。
- 当前实体写权限为 `both / system`，不是角色、owner、租户与行级读隔离；US-029 仍为 Backlog。
- GeneratorPage 导出实体 JS / 类型声明，完整应用壳、路由、依赖与发布模板还需要另做。
- Git 基准完成了特定浏览器和 fixture 的实验，代码编辑、编译、依赖与隔离预览尚未组成应用构建器。
- 本分支的 BOM 19 条故事 YAML 都为 Backlog，未发现 `apps/dev-rxdb-bom`；已解锁代表已有授权与范围，
  不能直接读成已经完成。其他分支的进度以对应验收记录为准。

### 为什么工作台比看板更值得先做

工作台的列表、表单、详情与查询交互已有组件和消费页面。看板复用的主要是实体、排序与 Todo 页面，
新增列之间的移动、批量改序和并发冲突语义仍需要实现。文本 SRS 与健身记录也需要各自的调度 /
训练状态机与面向手机的产品流程。

工作台直接服务已有的目标人群——试用 RxDB 的开发者，可以回答具体问题：增加一个关联实体需要
多少应用代码？校验失败如何展示？关闭重开能否恢复？备份能否在新环境继续使用？这些验证结果
可以回写组件、示例和接入文档，收益能复用到其他候选。

最大的反方是「空工作台只是更好看的 DevTools」。因此首版必须带一份实际会持续维护的数据，
例如用户自己的轻量事项或样例资产，验证从接入到恢复的完整任务。纯粹播放预置数据不能证明
重复 CRUD 劳动已经减少。

## 维护规则

1. **每个候选必须写「入场条件」与「立项前置」**——入场条件回答「什么信号出现才算
   「今天用户踩得到的具体症状」」（CONVENTIONS 价值待证判据），立项前置回答「立项前引擎侧
   必须先交付什么」；缺一项不进候选清单
2. **否决的也记理由**——对抗兴趣跳跃（AGENTS.md ENFP 陷阱第一条），防反复重访旧想法
3. **孵化即冻结**——候选建成 story 后，本目录文件不再独立演进，挂进 story 的 References
   作为设计依据（先例：[data-i18n-research](../data-i18n-research.md)）
4. **随节奏清理**——每次 roadmap 批次评审或 release 时过一遍候选清单：已孵化的移成指针、
   已否决的保留一句话结论，防止本目录变成第二个想法回收站
5. **立项时复核事实**——能力事实会随 story 关闭过期（如 FTS 放行、adapter 转正），
   立项时必须对照 [capability-matrix](../capability-matrix.md) 复核研究文件里的事实声明
6. **领域代码的合并受分支治理约束**——领域功能不经评审不进 main；领域分支对 `packages/*` 的
   改动先单独提取、评审并单独合并进 main，再从 main 合并回领域分支
   （见 [CONTRIBUTING](../../CONTRIBUTING.md) 与 [AGENTS.md](../../AGENTS.md)）

## 毕业路径

研究收敛 → 按 CONVENTIONS 建 story 文件（`Backlog`，写不出具体症状则标价值待证）→
进 [roadmap 立项池](../roadmap.md) 记入场条件 → owner 决策解锁成 Epic（先例：epic-009）。
研究文件自始至终不代替 story，YAML `status` 才是唯一真相源。
