## 底线判据

一个领域要同时用得上「离线 + 响应式 + 多端同步 + 模型驱动」中至少三项，才值得付
「三框架对称 + 适配器矩阵」的税；只吃单一能力的领域（如纯游戏存档同步）养不起这套引擎。
引擎能做什么、不能做什么以 [capability-matrix](../capability-matrix.md) 为准，长期方向看
[vision](../vision.md)（那是方向不是承诺）。

## 产品形态：零后端单机版

浏览器内 SQLite 让「数据库即前端」成立：候选可以先交付**纯静态托管的单机版**——零服务端代码、
零运维，数据层测试在 Node 里跑同一份 wasm SQLite（仓库 conformance 套件已这么干），
成本约等于零。多设备 / 多用户才需要同步端，且可复用 Supabase / HTTP 适配器而不必自建。
评估维度见横向对比「零后端可交付」列。

三个坑：① 浏览器清数据即丢库，备份 / 导出必须一等公民（[US-217](../stories/adapter/US-217-local-database-backup-restore.md) 已交付）；
② 秘密 / 支付 / 合规仍需最小 serverless 后端；③ 单机产品变现走「买断 + 同步增值」
（Anki 模式），SaaS 订阅走不通。

## 维护规则

1. **每个候选必须写「入场条件」与「立项前置」**——入场条件回答「什么信号出现才算
   「今天用户踩得到的具体症状」」（CONVENTIONS 价值待证判据），立项前置回答「立项前引擎侧
   必须先交付什么」；缺一项不进候选清单
2. **否决的也记理由**——对抗兴趣跳跃（AGENTS.md ENFP 陷阱第一条），防反复重访旧想法
3. **孵化即冻结**——候选建成 story 后，本目录文件不再独立演进，挂进 story 的 References
   作为设计依据（先例：[data-i18n-research](../data-i18n-research.md)）
4. **随节奏清理**——每次 roadmap 批次评审或 release 时过一遍候选清单：已孵化的移成指针、
   已否决的保留一句话结论，防止本目录变成第二个想法回收站
5. **立项时复核事实**——能力事实会随 story 关闭过期（如 FTS 放行、adapter 转正），
   立项时必须对照 [capability-matrix](../capability-matrix.md) 复核研究文件里的事实声明

## 毕业路径

研究收敛 → 按 CONVENTIONS 建 story 文件（`Backlog`，写不出具体症状则标价值待证）→
进 [roadmap 立项池](../roadmap.md) 记入场条件 → owner 决策解锁成 Epic（先例：epic-009）。
研究文件自始至终不代替 story，YAML `status` 才是唯一真相源。
