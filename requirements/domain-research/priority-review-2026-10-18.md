# 候选计划优先级评估：先交付本地数据工作台

> 评估日期：2026-10-18。目标由用户确认：**尽快交付可用产品，同时验证并推广 RxDB**。
> 本文是跨候选评审与范围建议；候选状态仍以 [README](README.md) 为准。

**结论：✅ 最值得先做的是 `admin-framework` 的严格切片——开发者给定实体 schema 的
单人 Web 本地数据工作台。** 首版交付录入、编辑、筛选、持久化与备份恢复闭环。
它已有最多可以直接复用的产品交互，也最容易让外部开发者验证「定义实体之后少写了多少 CRUD」。

下一顺位是单人任务看板。个人消费产品优先考虑文本 SRS 或健身记录，具体顺序由真实使用者与内容决定。
AI 构建器和小游戏适合继续做有边界的技术 / 玩法验证，当前不作为最快交付主线。

## 评估口径与证据

本目录当前有 14 个独立候选，以及浏览器 Git 的两份技术补充、索引与否决记录；BOM 另有已解锁 Epic。
本次同时复核了草稿区、未深入候选和五类否决方向。新加的本评审不另算产品候选。

排序主要看五件事：现有实现距用户闭环有多远、能否自然验证 RxDB、是否依赖另一项大型工程、
能否找到持续使用入口、失败后的投入是否可控。没有采用假定市场规模、虚构用户数量或精确工期评分。
现有研究尚未给出可核验的采用、留存、付费与获客证据，以下属于工程与验证优先级。

核对后的重要事实：

- `rxdb-model` 核心及三框架绑定已包含列表、详情、表单、表格和查询构建器；现有实体页面确实直接消费组件。
- 现有 `Task` 是带排序的 Todo 数据，不包含完整 Board / Column / 跨列移动产品。
- 当前实体写权限为 `both / system`，不是角色、owner、租户与行级读隔离；US-029 仍为 Backlog。
- GeneratorPage 导出实体 JS / 类型声明，完整应用壳、路由、依赖与发布模板还需要另做。
- Git 基准完成了特定浏览器和 fixture 的实验，代码编辑、编译、依赖与隔离预览尚未组成应用构建器。
- 本分支的 BOM 19 条故事 YAML 都为 Backlog，未发现 `apps/dev-rxdb-bom`；已解锁代表已有授权与范围，
  不能直接读成已经完成。其他分支的进度以对应验收记录为准。

## 为什么工作台比看板更值得先做

工作台的列表、表单、详情与查询交互已有组件和消费页面。
看板复用的主要是实体、排序与 Todo 页面，新增列之间的移动、批量改序和并发冲突语义仍需要实现。
文本 SRS 与健身记录也需要各自的调度 / 训练状态机与面向手机的产品流程。

工作台直接服务已有的目标人群——试用 RxDB 的开发者，可以回答具体问题：
增加一个关联实体需要多少应用代码？校验失败如何展示？关闭重开能否恢复？备份能否在新环境继续使用？
这些验证结果可以回写组件、示例和接入文档，收益能复用到其他候选。

最大的反方是「空工作台只是更好看的 DevTools」。因此首版必须带一份实际会持续维护的数据，
例如用户自己的轻量事项或样例资产，验证从接入到恢复的完整任务。
纯粹播放预置数据不能证明重复 CRUD 劳动已经减少。

## 首版边界与验收

建议首版只交付：

1. 开发者预置两三个有关联的实体 schema，明确哪些实体可见；用现有列表与详情组件构成导航。
2. 创建、编辑、删除、校验反馈与查询筛选；覆盖加载、失败和空态。
3. 本地持久化，刷新 / 关闭重开后可继续编辑。
4. 备份，在独立环境恢复，再查询和继续编辑；明确失败结果与数据保留状态。
5. 一份独立消费接入示例，记录新增代码、依赖与样式要求，验证它确实能降低接入成本。

首版先固定 Web 宿主与已验证的本地适配器，复用现有三框架组件；新增公共框架 API 时仍需三端对称。
任意运行时建表 / schema 编辑、完整应用源码生成、多用户 RBAC、协作、附件同步与 AI 不进入这轮闭环。
任务看板也不在同一轮额外开发。

成功信号是：具名试用者带入自己的实体与数据，独立完成录入 / 编辑 / 筛选 / 重开 / 备份 / 恢复，
并能指出减少了哪些重复接线。不预设没有基线支持的工期、采用率或代码量阈值。

以下情况会推翻第一名：

- 最小独立消费应用存在必须先改底层的安装、样式、持久化或备份问题。
- 首个用户必需多人权限、按人限制同步行，或要求浏览器运行时改 schema。
- 找不到愿意使用固定 schema 工作台的人，而看板、SRS 或健身已经有持续用户与明确验收任务。

## BOM：已有承诺，单独处理

[epic-009](../epics/epic-009-bom-domain-model.md) 已由 owner 解锁，范围包含 19 条故事与多个阶段。
当前分支的故事状态和产品入口表明，它不属于低成本即将交付的候选；全域 BOM 也不适合用来证明
「最快交付」这一目标。

已开展的 BOM 工作应按现有切片收敛到可演示和可验收状态，再确定新产品的启动位置。
本次新候选评审推荐工作台，不将 BOM 的领域抽象、ERP 集成和全域功能搬进工作台首版。

## 草稿与未深入方向

| 方向           | 当前建议                           | 继续研究的信号                                                     |
| -------------- | ---------------------------------- | ------------------------------------------------------------------ |
| 客服工单       | 保留草稿；工作台之后的业务模板候选 | 有具名坐席流程、离线症状与真实工单样本                             |
| 开发者配置同步 | 保留小实验，不作为主产品           | 有具体工具、配置格式、合并与密钥边界；不能只说同步 JSON            |
| 个人健康仪表盘 | 暂不扩展                           | 有明确数据源、导入授权、展示任务与目标用户                         |
| 家庭相册元数据 | 后置                               | 文件可恢复、权限与跨设备访问闭环明确；照片字节不能由元数据同步替代 |
| 医疗诊所 EHR   | 暂缓                               | 有明确诊所、业务协作方、数据治理与行业验证资源                     |
| 个人财务记账   | 保留轻量数据模型候选               | 有明确记账习惯、导入来源与持续使用者，能解释相对普通本地存储的收益 |

这几项都没有足够材料超过当前首选；缺材料不等于永久否决。

## 五类已否决方向的复核

| 方向                       | 判断             | 限定理由                                                                 |
| -------------------------- | ---------------- | ------------------------------------------------------------------------ |
| 大规模 BI / 数仓           | 继续不选作主方向 | 大规模扫描、分析管线与有界响应式缓存目标不同；有界业务统计可以做         |
| Google Docs 级实时协同     | 首发后置         | 需要逐字编辑协议与协作服务，通用冲突中心不能直接替代                     |
| 银行账务 / 服务端 ERP 核心 | 继续不选作主方向 | 账务强一致与可审计业务边界不能由本地实体复制兑现                         |
| 海量多重图网络             | 继续不选作主方向 | 当前图插件语义与规模目标不覆盖，BOM 独立 schema 也不代表通用多重图已完成 |
| 纯游戏存档同步             | 不作为旗舰展示   | 只验证存储 / 同步一个能力；人生模拟的玩法价值应独立验证                  |

## 原研究中需要纠正的完成度判断

| 原判断                                      | 复核结果                                                                                |
| ------------------------------------------- | --------------------------------------------------------------------------------------- |
| 后台已经有行级权限                          | `both / system` 是实体操作入口约束；角色 / owner / 多租户安全边界仍需设计               |
| GeneratorPage 已能生成应用                  | 当前是实体 JS 和声明文件；可运行应用的依赖、路由、构建与发布未生成                      |
| commit graph 就是可信审计 / 多成员协作      | 当前是本地实体版本历史，显式提交且作者由调用方提供；身份、授权、远程提交协议另做        |
| 三框架对称等于所有宿主产品都可直接运行      | DOM、VTable、平台 UI 与小程序逻辑层适配不是同一件事；小游戏也未继承小程序验证           |
| 加密、全文搜索、AI 可直接叠加               | 同字段 `encrypted + searchable` 会拒绝，向量 SQL 原语也不是完整记忆与检索产品           |
| replay 已经是 agent trace                   | 当前是 rrweb DOM 录制，模型请求、工具调用与任务恢复需独立事件模型                       |
| HTTP 能直接做完整双向同步，或完全不能离线写 | 现有 QueryCache outbox 可排队重放 REST 写入；不是 Full / Filter changelog 同步          |
| Web / 桌面全部后端都支持同等搜索            | 搜索有后端放行表，原生 Electron / Tauri 与小程序需分别核对；UI 框架对称不能代替后端验证 |
| 引擎外成本≈0 / 市场空白 / SaaS 订阅走不通   | 没有采用与商业验证支持；离线可用、静态托管和无必需云服务不等于产品开发成本为零          |
