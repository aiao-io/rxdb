Local-first keeps coming up these days, but the conversation is no longer the same one we had a decade ago.

The first time I came across [PouchDB](https://pouchdb.com/) and [CouchDB](https://couchdb.apache.org/), I realized that what this approach really wanted to change was not the caching strategy, but the default premise that a web app's availability and responsiveness depend on the network.

## PouchDB actually pointed in the right direction back then

**PouchDB** gave frontend developers, for the first time, a systematic way to store structured data on the user's device, read and write offline, and then sync with a remote server. What made it so compelling was not how elegantly any particular API was designed, but what it made you realize: a web app can keep working when the network is down, instead of erroring out on the spot.

**CouchDB**'s design was equally instructive. It turned sync, versioning, and the document model into built-in database capabilities, instead of leaving all of that for each business system to assemble on its own. The distance between the frontend and the database shrank noticeably, and many things that once had to go through an intermediate layer had, for the first time, a much more direct path.

But the approach never truly went mainstream back then. The PouchDB ecosystem gradually cooled off, and the community slowly went quiet. The problem was not that the direction was wrong — it was that browsers, toolchains, and the teams' own understanding were not ready for it yet.

## The idea wasn't wrong — the conditions just weren't there

Looking back, I can name at least three very real kinds of resistance:

1. **The engineering bar was high**: you not only had to write frontend code, but you also had to understand modeling, sync, indexes, and conflicts — problems that traditionally belonged to database engineering.
2. **The inertia of the default architecture was too strong**: most teams were long used to "frontend calls APIs, backend owns the data." Switching to "works locally first" was never just a matter of swapping in a library.
3. **Browser capabilities weren't mature enough**: early storage capabilities, execution performance, and the relevant APIs were nowhere near as stable as they are today, and complex data apps would hit a wall quickly.

## Looking at it now, the timing really is different

What has actually changed the landscape over the past few years is not an "offline-first" slogan, but the fact that the browser's underlying capabilities have finally caught up. With WebAssembly and the browser's accompanying storage capabilities now mature, the frontend can, for the first time, seriously discuss running a database inside the browser.

A few changes matter most:

- [wa-sqlite](https://github.com/rhashimoto/wa-sqlite) brings SQLite into the browser, so local relational queries, indexes, and transactions are no longer the exclusive territory of native apps.
- [PGlite](https://github.com/electric-sql/pglite) pushes PostgreSQL-style capabilities even further into the frontend runtime, so complex queries no longer have to fall back to the server from day one.
- Browser-side persistence, Workers, and the WASM tooling ecosystem are far more mature than before, giving the local data layer a sustainable engineering foundation at last.

This means Local-first is no longer limited to lightweight uses like "caching list-page data." It now has a real chance to support genuinely complex business data scenarios.

## The frontend is no longer just "call an API and render"

Products like [Figma](https://www.figma.com) have already proven that the browser is not just a shell for presentation. It can fully host complex state, real-time collaboration, and heavy client-side computation. The impact of this shift on frontend development is direct:

- The frontend is no longer just a UI layer that consumes APIs.
- Complex business rules and part of the data processing can live directly on the client.
- User experience no longer has to be constrained by network round-trips and server response times at every step.

So these days I prefer to think of Local-first as an architectural choice: take "available first, responsive first, data lands on the user's device first" as the default premise, and only then design sync, collaboration, and remote consistency — rather than the other way around.

## This is also why we're building @aiao/rxdb

Based on these thoughts, our team is building **@aiao/rxdb**. What it sets out to solve is not "repackaging the Local-first concept one more time," but turning the in-browser data layer into real engineering infrastructure: reusable, maintainable, and able to land in actual business systems.

Right now we're focused on a few things:

### 1. Get the model right first

- Define entities, fields, relationships, and constraints with a declarative model.
- Let types, query capabilities, and generated code revolve around the model, instead of being scattered across pages and service layers.
- Reduce the "the more complex the business, the more fragmented the data code" problem.

### 2. Bring database capabilities into the frontend stacks people already know

- Reuse the same model, query, and entity semantics across Angular, React, and Vue.
- Keep the differences confined to each framework's own binding layer, instead of turning the data-layer API into three completely different things.
- Let teams discuss data structures and query semantics first, and only then figure out how a specific UI framework plugs in.

### 3. Separate the data layer from the UI layer

- Draw clear boundaries between local persistence, reactive queries, entity operations, and the UI layer.
- Write less glue code around caching, sync state, and API translation.
- Leave stable extension points for future sync, collaboration, and versioning capabilities.

### 4. Make frontend data structures a real asset

- Once data truly lives in the frontend, local data structures stop being merely throwaway state and gradually become reusable assets.
- Complex queries, tree structures, relationship traversal, and derived views should be reused the way components are, instead of being rewritten from scratch in every project.

## When you should seriously try Local-first

If your app is already showing these signs, it's worth taking a serious look at this path now:

- Pages increasingly feel like a local workbench rather than a simple data-display layer.
- Users are starting to demand offline availability, instant startup, and low-latency feedback on operations.
- The frontend has accumulated a pile of caching logic, state patches, and re-wrapped API clients.
- You want the same data abstraction to be reusable across different frameworks instead of rewritten over and over.

To me, Local-first is no longer a "future trend" prediction — it's the natural outcome of the shifting boundaries of frontend engineering. The browser can finally take on heavier data responsibilities, and the question that actually matters now is not whether to keep repeating the slogan, but how to make this capability more solid, more clear, and better suited to real business.

If these are the problems you're facing right now, you're welcome to check out our [GitHub repository](https://github.com/aiao-io/rxdb), and to bring your real business scenarios to the discussion. More than re-telling the vision, I care about whether it holds up in real projects.
