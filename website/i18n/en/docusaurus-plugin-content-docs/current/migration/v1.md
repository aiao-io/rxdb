# v0 → 1.0 upgrade

Aiao is currently in the **0.x stage** (latest published version `0.0.28`). Under [semver](https://semver.org/lang/zh-CN/), breaking changes are allowed in minor versions during 0.x. This page explains what 1.0 will stabilize and how breaking changes are tracked and announced.

> For the versioning policy, the public API surface, and deprecation cycles, see [Versioning and API stability](/versioning.md).

## What 1.0 will stabilize

After 1.0 ships, the following external surfaces enter semver maintenance; breaking changes may only ship with a major release:

- **Core**: the entity decorators, Repository/query interfaces, and `RxDB` lifecycle APIs of `@aiao/rxdb`
- **Adapter contracts**: the public constructors and option types of `@aiao/rxdb-adapter-*`
- **Framework bindings**: the public hook / provider APIs of `@aiao/rxdb-{angular,react,vue}` (symmetric across the three frameworks)
- **Plugin contracts**: the registration entries and option types of `@aiao/rxdb-plugin-*`

What is not in the stable scope (internal implementations, symbols marked `@internal`, undocumented exports) is covered in the [stability policy](/versioning.md).

## How breaking changes are tracked

- Every public package maintains an **API baseline snapshot** (`requirements/api-baseline/<pkg>.json`) recording the exported symbol surface.
- CI compares the baseline on every change: **undeclared breaking changes fail the check**.
- A change that is genuinely breaking must: update the baseline, mark it breaking in the PR, and add upgrade notes to this page.

## Upgrade advice during 0.x

Before 1.0:

1. **Pin the minor version**: check the [CHANGELOG](https://github.com/aiao-io/rxdb/blob/main/CHANGELOG.md) before upgrading.
2. **Upgrade `@aiao/*` together**: all packages share one published version number; avoid mixing different versions.
3. **Check the compatibility matrix**: confirm Node / framework / adapter versions, see [compatibility matrix](/compatibility.md).
4. **Run the type checks through**: this project runs compile-time contract tests on the public types; run `tsc` on the consumer side after upgrading.

## Upgrade steps (generic)

```bash
# 1. Upgrade all @aiao/* to the target version together
pnpm up "@aiao/*@latest"

# 2. Reinstall and build
pnpm install
pnpm build

# 3. Run type checks and tests to confirm nothing broke
pnpm tsc --noEmit
```

If the upgrade involves data structure changes, write a one-time migration script following [Schema migrations](/migration/schema.md).

## Version-specific breaking changes

> When 1.0 formally ships, this section will list breaking changes per version with their migration steps. For changes during the current 0.x stage, see the [CHANGELOG](https://github.com/aiao-io/rxdb/blob/main/CHANGELOG.md).

> **`0.0.28` bumped the system schema from 3 to 7.** A database opened with 0.0.28 is refused by clients at 0.0.26 and earlier (`UnsupportedRxDBSystemVersionError`); all clients must upgrade together, there is no downgrade path. The source has moved to 8; the next release is likewise a migration release (7 → 8).

### `0.0.28` (relative to `0.0.26`)

Items 1–3 and 6–8 change interface **members** or function **parameters**. `requirements/api-baseline/*.json` only compares each exported symbol's name and kind (value / type / both) and cannot see this class of change, so they are registered here by hand. Items 4 and 5 are ordinary export removals; the baselines were updated with the commit (`rxdb-plugin-querycache.json` / `rxdb.json`), and they are listed here for easy reference. Item 9 changes the install-surface dependency declarations (dependencies / peerDependencies in `package.json`), which the API baseline cannot see either.

Item 1 and items 4–9 affect applications upgrading from `0.0.26`. Items 2 and 3 touch APIs that did not exist in `0.0.26` (the working tree capability was never published): applications that only upgrade from `0.0.26` never reach them; code that develops against `main` and used these APIs must change as described below.

#### 1. `SwitchBranchOptions` gains the required member `prepare`

`prepare` is a pre-hook inside the switch transaction: the adapter `await`s it after resolving the target branch and before touching the first row; a throw rolls back the whole switch.

Code that calls `adapter.switchBranch()` directly must pass `prepare`, otherwise it fails at compile time. Call sites that need no pre-check pass the sentinel implementation explicitly:

```ts
import { SKIP_BRANCH_SWITCH_PREPARE } from '@aiao/rxdb';

// before
adapter.switchBranch({ branchId, actions });

// after
adapter.switchBranch({ branchId, actions, prepare: SKIP_BRANCH_SWITCH_PREPARE });
```

Adapters that implement `switchBranch()` themselves must call `options.prepare({ executor, targetBranchId })` exactly once, inside the switch transaction, after resolving the target branch and before changing `activated` / rebuilding triggers / applying actions; rethrow whatever it throws, do not catch.

#### 2. `uninstallWorkingTreeCapture` drops the `raw` parameter

```ts
// before
function uninstallWorkingTreeCapture(target: WorkingTreeCaptureMountTarget, raw: RawWritePrimitives): void;

// after
function uninstallWorkingTreeCapture(target: WorkingTreeCaptureMountTarget): void;
```

Callers delete the second argument; uninstalling no longer needs the caller to hand the raw write methods back.

#### 3. `RxDBSystemContribution`: `assertBranchSwitchable` renamed to `prepareBranchSwitch`, plus two new required methods

- `assertBranchSwitchable` → `prepareBranchSwitch`. The signature is unchanged (`(context: RxDBBranchSwitchContext) => Promise<void>`), the semantics changed: it used to run before the switch, inside a separate **read-only** transaction opened by the caller; now the adapter calls it back through `SwitchBranchOptions.prepare` **inside the switch transaction**, `context.executor` is writable, rows written there live and die with this switch, and a throw rolls back the whole switch. Only rows the switch itself necessarily brings should land there (for example, activation generation +1); business data does not belong here.
- Two new required methods:
  - `takeOverBranchSwitch(context: RxDBBranchSwitchTakeoverContext): Promise<RxDBBranchSwitchTakeover>`: contributing parties that do not take over return `'not_applicable'`, and the main flow proceeds with the ordinary switch
  - `settleBranchSwitchFailure(context: RxDBBranchSwitchFailureContext): Promise<void>`: contributing parties with no diagnostics to record return a settled promise

The contribution points (not counting the three identity fields `capability` / `version` / `packageSpecifier`) go from 7 to 9, all required. Plugins that implement `RxDBSystemContribution` themselves must perform the rename and add the two new methods; structural type checking points out the missing members at compile time.

#### 4. `@aiao/rxdb-plugin-querycache` narrows its public exports (10 root exports removed)

The following symbols are no longer exported from the package root: `assertQueryCacheCapabilities`, `createQueryCachePrimary`, `DEFAULT_QUERY_CACHE_SYNC_STALE_TIME`, `queryCacheFingerprint`, `QueryCacheFingerprintInput`, `QueryCachePrimaryLocalAdapter`, `QueryCachePrimaryRepository`, `QueryCacheSyncMemo`, `QueryCacheSyncResult`, `RxDBQueryCacheEngineFactory`. They are internal assembly pieces of the read path; after `rxdb.use(rxDBPluginQueryCache)` the plugin assembles them itself, and nothing outside the package referenced them in the repository.

The package root keeps only `rxDBPluginQueryCache`, `RxDBPluginQueryCache`, `RxDBPluginQueryCacheOptions`, and `QueryCacheEngine` (experimental tier). Code that imported a removed symbol should register the plugin and use the read path through `rxdb` instead. The read path spans three packages — `@aiao/rxdb-plugin-history`, `@aiao/rxdb-plugin-sync`, `@aiao/rxdb-plugin-querycache` — registering querycache alone throws `RxDBMissingPluginError` from `connect()`:

```ts
rxdb.use(rxDBPluginHistory);
rxdb.use(rxDBPluginSync);
rxdb.use(rxDBPluginQueryCache);
```

See [Query-cache read engine split](/migration/querycache-plugin.md).

#### 5. `@aiao/rxdb` root entry no longer exports nine entity internal functions

`entity.utils` changed from `export *` to named exports; the following nine functions are no longer exported from the package root:

- `setSafeObjectKey`, `setRuntimeObjectKey`, `setRuntimeObjectGetter`, `setSafeObjectWritableKey`, `setSafeObjectKeyLazyInitOnce`: `Object.defineProperty` wrappers that hang non-enumerable metadata on entity classes and instances
- `fillDefaultValue`, `fillInitValue`: the fill steps during entity construction
- `getNeedSaveEntities`, `getNeedRemoveEntities`: the steps that recursively collect related entities on the save/delete paths

None of them has a public replacement. `getEntityStatus(entity)` still has same-named `getNeedSaveEntities()` / `getNeedRemoveEntities()` methods, but they only look at this one entity's direct relations, without the recursive collection and filtering of the removed functions, so they cannot be dropped in as-is.

#### 6. Trigger / create-table SQL generation functions no longer default to `main`; `branchId` becomes required

Triggers bake `branchId` into the SQL as a literal, deciding which branch every subsequent write to that table is recorded under. Previously the generation functions substituted `'main'` when the caller gave none; with the database parked on another branch, the writes went to the wrong place with no error, only visible later in history audits. Now every call site supplies its own branch id; new databases pass `MAIN_BRANCH_ID` explicitly when creating tables:

- `generate_table_trigger_sql(metadata, options)` of `@aiao/rxdb-adapter-sqlite-core`: `options.branchId` goes from optional to required; missing at runtime throws `RxDBAdapterSqliteError`.
- `generate_trigger_sql(metadata, options)` of `@aiao/rxdb-adapter-pglite`: same, missing throws `RxdbAdapterPGliteError`.
- `create_tables_sql` of `@aiao/rxdb-adapter-sqlite-core`: gains a required third positional parameter `branchId`; the old third parameter `entities` shifts to fourth.

```ts
import { MAIN_BRANCH_ID } from '@aiao/rxdb';

// before
generate_table_trigger_sql(metadata, { resolveEntityMetadata });
create_tables_sql(adapter, EntityTypes, entities);

// after
generate_table_trigger_sql(metadata, { branchId: MAIN_BRANCH_ID, resolveEntityMetadata });
create_tables_sql(adapter, EntityTypes, MAIN_BRANCH_ID, entities);
```

When the database may already be parked on a non-main branch (for example, adding entity tables to an existing database), read the currently active branch in the same transaction and pass it in; `RxDBAdapterSqliteBase.createTables` does exactly that. The pglite `create_tables_sql` / `create_tables_statements` signatures are unchanged: at table-creation time they still generate for `main`, and `RxDBAdapterPGlite.createTables` remounts them under the current branch in the same transaction.

#### 7. `getEntityMutations` input fields become camelCase

The two input fields of `getEntityMutations(options)` in `@aiao/rxdb` were renamed; semantics unchanged:

```ts
// before
getEntityMutations({ need_save_entities, need_remove_entities });

// after
getEntityMutations({ needSaveEntities, needRemoveEntities });
```

TS callers get a compile-time error. JS callers (and call sites that bypass type checks) get no warning: the old keys destructure to `undefined`, and the run reaches the iteration step and throws `TypeError`. The input type is now exported as `EntityMutationsOptions`; code that needs to declare the input separately should reference it directly.

#### 8. The `RxDB` interface no longer declares the `RxDBSync` / `RxDBMigration` / `RxDBChange` / `RxDBBranch` members

`@aiao/rxdb` used to augment the `RxDB` interface with these four members through `declare module '@aiao/rxdb'` (the types being the same-named system entity classes), but the runtime never assigned them: `rxdb.RxDBChange` compiled, but read as `undefined`. The augmentation was deleted; code written that way now fails at compile time. The four entity classes were always exported from the package root; import them directly:

```ts
// before
rxdb.RxDBChange; // undefined at runtime

// after
import { RxDBChange } from '@aiao/rxdb';
```

#### 9. `@aiao/rxdb` goes into `peerDependencies` everywhere (US-602 A2)

Previously the packages declared core in split ways: some put `@aiao/rxdb` in `dependencies` (an exact version after publish), others put it in peers but mixed `*` / `workspace:*` / `^0.0.26`. For libraries built on the decorator metadata registry, each package giving a different version constraint on core means a version mismatch installs two copies of core, and which copy a plugin registers into depends on load order — a known failure mode. From A2 on it is unified: **`@aiao/rxdb` always goes into `peerDependencies`**, the peers among other `@aiao/*` and the sibling edges left in `dependencies` are uniformly `workspace:^` (rewritten to `^<version>` at publish), and the `peerDependenciesMeta.optional` semantics are kept.

What this means for you:

1. **The core package must be installed explicitly by your project** (npm 7+ auto-installs peers, and pnpm does by default; explicitly declaring `@aiao/rxdb` as a direct dependency is recommended, at the same version as the rest of `@aiao/*`).
2. **Version incompatibilities now fail explicitly** instead of silently installing two cores: on `ERESOLVE` / `ERR_PEER_INVALID` at install or resolve time, upgrade all `@aiao/*` to the same version.
3. One copy of core is shared by all packages (single instance); plugins and adapters register into the same registry.

```jsonc
// After upgrading (package.json)
{
  "dependencies": {
    "@aiao/rxdb": "^0.0.26", // install core explicitly
    "@aiao/rxdb-adapter-pglite": "^0.0.26",
    "@aiao/rxdb-plugin-history": "^0.0.26"
  }
}
```

### After `0.0.28` (unreleased)

- System schema goes from 7 to 8: `RxDBChange` gains `tableSetSuffix`. Databases already upgraded are refused by clients at 0.0.28 and earlier; upgrade together.
- The public functions that derive physical table names and generate create-table / read-write / trigger SQL gained a required table set parameter, see [table-set-parameter](/migration/table-set-parameter.md); the rest is in the [CHANGELOG](https://github.com/aiao-io/rxdb/blob/main/CHANGELOG.md) "Unreleased" section.
